The terms used along that construction are:

- **Algorithm, interface, and implementation:** an algorithm is a sequence of actions for obtaining a result. Its interface states the inputs and output; its implementation performs those actions.
- **List, array, element, and contiguous storage:** a list is an ordered sequence. An array is a concrete representation with consecutive element storage; an element is one stored value. Contiguous means adjacent, with no gaps between element slots.
- **Memory cell, address, index, and indexing:** a cell is one value's storage in the lesson's drawing. An address identifies a location. An index counts element offsets from the beginning; indexing selects the element at that offset.
- **Type and integer:** a type describes what values are allowed. `int` stores integers, or whole numbers; `int[]` describes an array of integers.
- **Object, reference, dereference, and heap:** an object is the allocated array with its elements and length. A reference identifies that object; dereferencing follows it to the object. The heap is the dynamic-memory area used for these objects in the lesson's model.
- **Length, buffer, property, and slice view:** length counts array cells. A buffer is the storage reserved for those cells. A property is a named value accessed through an object, as in `a.Length`. A slice view describes a portion of existing storage; changing a view's extent does not resize the underlying array.
- **Declaration, initialization, assignment, and expression:** declaration introduces a variable; initialization supplies its first value. Assignment evaluates an expression on the right and writes its result on the left. An expression is code that produces a value.
- **Allocation and `new`:** allocation creates storage for an object. `new` is the object-creation keyword used here to allocate an array.
- **Array initializer, inferred type, implicitly typed array creation, and collection expression:** an initializer lists starting element values in braces. Inference means the compiler determines a type or count from context or values. Implicitly typed array creation uses `new[]` to infer the element type from the values. A collection expression uses brackets such as `[6, 8, 5]` and needs a suitable target type.
- **Function, local function, header, body, and call:** a function is named executable code; a local function is declared within another function's code. Its header describes the result and inputs; its body contains the instructions. A call invokes it.
- **Return type, returned value, and `return`:** the return type specifies the kind of result. The returned value is the result of a call. `return` ends that invocation and supplies its result.
- **Parameter, argument, caller, callee, and pass by value:** a parameter is an input variable in a function declaration. An argument is the expression supplied at a call. The caller invokes the callee. Ordinary passing copies the argument's value into the parameter.
- **Local variable, temporary, scope, and lifetime:** a local belongs to a function or block; a temporary holds working data. Scope determines where its name is usable, while lifetime concerns its existence during execution.
- **Block and braces:** a block groups statements inside `{ }` and bounds the scope of variables declared there.
- **Modifier and `static`:** a modifier is a keyword attached to a declaration. `static` is retained on the local function; its detailed meaning is explicitly deferred in this lesson.
- **Control flow, label, and `goto`:** control flow is the order of execution. A label names a statement; `goto` transfers execution to it.
- **Loop, iteration, body, and state:** a loop repeats a body of instructions. One repetition is an iteration. State is the changing data that determines the next step, here an index and a running sum.
- **Accumulator and compound assignment:** an accumulator keeps a running result. `s += value` adds to the old sum and writes the result back; `i += 1` increments the index by one.
- **Boolean, condition, guard, and negation:** a Boolean is `true` or `false`; a condition computes such a value. A guard tests whether work may proceed. Negation reverses true and false.
- **Bounds and off-by-one error:** bounds identify valid indices. An off-by-one error chooses a boundary one position too early or too late.
- **`if`, `break`, and unreachable code:** `if` executes its attached block only when its condition holds. `break` exits the enclosing loop. Unreachable code has no execution path leading to it.
- **`while`, infinite loop, `for`, and `foreach`:** `while` repeats while a condition is true; `while (true)` keeps repeating unless control exits explicitly. `for` packages initialization, a condition, and an update in its header. `foreach` visits element values directly, using `in` to identify the collection.
- **`var`:** this asks the compiler to infer a local variable's type from its initializer; it does not mean “a variable restricted to numbers.”
- **Scope boundaries only — null and integer overflow:** null means no object reference; integer overflow means an arithmetic result exceeds the range of its integer type. Handling either is outside the implementation developed here.
- **Compiler, IDE, and debugger:** the compiler checks and translates source. The IDE is the editing environment that offers syntax suggestions and diagnostics. The debugger lets the recording trace calls and values.

## Move the algorithm into a goto body

[00:09:23](https://www.youtube.com/watch?v=VhA2OupAYRc&t=563s) The existing basic code already expresses the summing steps. The lesson first ports that logic using C#'s basic **`goto`**, a transfer of control to a named **label**, before replacing it with loops. The stated aim is to move away from goto promptly.

The starting algorithm, reconstructed from the preceding procedure and the transfer described here, is:

1. Initialize an accumulator to zero and an index to zero.
2. Check whether the index has reached the end.
3. If it has, finish with the accumulator as the answer.
4. Otherwise, add the indexed element, advance the index, and repeat the check.

[00:09:23](https://www.youtube.com/watch?v=VhA2OupAYRc&t=563s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
// Existing algorithm shape, before wrapping it in a function:
int[] r = [6, 8, 5];
int s = 0;
int i = 0;

CheckIndex:
if (i >= r.Length)
    goto Finished;
s += r[i];
i += 1;
goto CheckIndex;

Finished:
Console.WriteLine(s);
```

[00:09:29](https://www.youtube.com/watch?v=VhA2OupAYRc&t=569s) **Control flow** determines which statement runs next. A label ends with a colon; a goto names the destination. It can jump forward to a check or backward to repeated work. Labels do not store values.

Move the working instructions into the function, read the length from its parameter, and replace “finish and print” with a **`return`**, which ends the call and delivers its result. The following deliberately keeps both forward and backward jumps visible:

[00:09:29](https://www.youtube.com/watch?v=VhA2OupAYRc&t=569s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
static int SumNumbers(int[] r)
{
    int s;
    s = 0;
    int i = 0;
    goto CheckIndex; // forward jump: check before any element read

AddElement:
    s += r[i];
    i += 1;

CheckIndex:
    if (i >= r.Length)
        return s;
    goto AddElement; // backward jump: repeat the work
}
```

A **compound assignment** such as `s += r[i]` computes the old sum plus this element and stores the result back. Similarly, `i += 1` increments the index by one. A semicolon terminates each ordinary statement.

## Replace backward goto with while

[00:12:49](https://www.youtube.com/watch?v=VhA2OupAYRc&t=769s) A **loop** repeats a body of instructions; an **iteration** is one repetition. The backward goto pattern can be rewritten as **`while (true)`**, a loop whose condition is always true.

To perform the rewrite:

1. Put `while (true)` before the repeated instructions.
2. Place the destination label's repeated code inside its braces.
3. Remove the label and the goto that jumped back to it.
4. Keep the termination check before any array access.

[00:12:49](https://www.youtube.com/watch?v=VhA2OupAYRc&t=769s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
static int SumNumbers(int[] r)
{
    int s = 0;
    int i = 0;
    while (true)
    {
        if (i >= r.Length)
            return s;
        s += r[i];
        i += 1;
    }
}
```

[00:13:11](https://www.youtube.com/watch?v=VhA2OupAYRc&t=791s) The **body** is the block inside the loop. If control reaches its closing brace, it returns to the loop head rather than falling through to the next statement after the loop.

[00:13:34](https://www.youtube.com/watch?v=VhA2OupAYRc&t=814s) An **infinite loop** has no automatic stopping point when its condition is always true. Without an exit, the body repeats forever and statements after the loop are never reached. This summing version has an explicit return, so it is finite for the demonstrated array.

[00:13:52](https://www.youtube.com/watch?v=VhA2OupAYRc&t=832s) The recording recommends this structured loop in place of the goto-and-label repetition. It makes the repeated region visible in one block.

[00:14:01](https://www.youtube.com/watch?v=VhA2OupAYRc&t=841s) **Unreachable code** has no execution path. The IDE greys out a goto after a return because returning has already ended the function.

[00:14:01](https://www.youtube.com/watch?v=VhA2OupAYRc&t=841s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
if (i >= r.Length)
{
    return s;
    // goto AddElement; // unreachable if written after this return
}
```

[00:14:18](https://www.youtube.com/watch?v=VhA2OupAYRc&t=858s) **`return`** ends the whole function invocation and transfers control back to the call site. It is different from finishing an ordinary block.

## Choose the correct loop boundary

[00:14:24](https://www.youtube.com/watch?v=VhA2OupAYRc&t=864s) A **condition** evaluates to a **Boolean**, true or false. **Negation** reverses that value. Changing a loop's condition alone does not preserve behavior; the stop test and continue test must be logical opposites with the corresponding control flow.

[00:14:27](https://www.youtube.com/watch?v=VhA2OupAYRc&t=867s) The correct continue test is `i < length`; its inverse stop test is `i >= length`. Equivalently for an integer index, stopping at `i > length - 1` means the same thing. It is not equivalent to `i >= length - 1`, which would stop before processing the last cell.

[00:14:54](https://www.youtube.com/watch?v=VhA2OupAYRc&t=894s) **Bounds** identify the legal positions. An array of length three has indices 0, 1, and 2. Index 3 is already beyond its final element. The final valid index is `length - 1`.

[00:15:10](https://www.youtube.com/watch?v=VhA2OupAYRc&t=910s) The strict comparison `i > length - 1` is equivalent to `i >= length` for integer indices because there is no fractional index between those bounds.

[00:15:10](https://www.youtube.com/watch?v=VhA2OupAYRc&t=910s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```text
// For an integer index and length = 3:
last valid index: 2
continue: i < 3       // includes i == 2
stop:     i >= 3      // excludes i == 3
same stop: i > 3 - 1  // i > 2
wrong stop: i >= 3 - 1 // would wrongly stop at i == 2
```

[00:15:25](https://www.youtube.com/watch?v=VhA2OupAYRc&t=925s) “Less than length” excludes the one-past-the-end position, `length`; it includes the last element at `length - 1`. Reading it as excluding the final element would introduce an **off-by-one error**, a boundary shifted by one position.

[00:15:51](https://www.youtube.com/watch?v=VhA2OupAYRc&t=951s) Separate loop termination from returning the result. **`break`** exits the loop; the return can then follow it. Moving the positive continuation test into the while header removes the separate if-and-break pair.

[00:15:51](https://www.youtube.com/watch?v=VhA2OupAYRc&t=951s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
// Intermediate shape:
int s = 0;
int i = 0;
while (true)
{
    if (i >= r.Length)
        break;
    s += r[i];
    i += 1;
}
// s now holds the answer; return it from the enclosing SumNumbers body.

// Clearer shape, replacing that loop:
s = 0;
i = 0;
while (i < r.Length)
{
    s += r[i];
    i += 1;
}
return s;
```

[00:16:00](https://www.youtube.com/watch?v=VhA2OupAYRc&t=960s) In the infinite-loop form, the stop check must run before the indexed work. In the conditional-while form, that same decision is made at the loop head. A stop condition merely written as an expression cannot exit a loop; it needs the exit action or the inverse continuation guard.

[00:16:22](https://www.youtube.com/watch?v=VhA2OupAYRc&t=982s) A **guard** is the test permitting the body to run. It is evaluated before the very first iteration and again every time control returns to the head. An empty array therefore performs no element reads and leaves the sum zero. This follows from the reconstructed code; the recording's demonstrated numeric test uses three elements.

<details>
<summary>What would happen with i &lt;= r.Length instead of i &lt; r.Length?</summary>

The guard would permit index Length, which is one past the end. The body would then try to read a nonexistent cell. With Length = 3, the valid indices are only 0, 1, and 2.

</details>

## Collect loop state in a for header

[00:16:59](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1019s) The index is **temporary working state**, data that changes solely to walk through this array. It supplies the guard and the next element position. [00:17:00](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1020s) Its declaration, test, and update currently sit in different places in the while version.

[00:17:00](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1020s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
int i = 0;                 // initial state
while (i < r.Length)        // continuation guard
{
    s += r[i];             // useful body work
    i += 1;                // next-state update
}
```

[00:17:13](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1033s) The recording identifies four structural pieces: starting state, an ending or continuation condition, the useful work that changes accumulated data, and the transition to the next iteration's state. Here they are index zero, the bounds test, addition to the sum, and incrementing the index.

[00:17:24](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1044s) **State** need not mean one index. It may include several values, such as two indices whose updates depend on their current values. The summing example stays with one.

[00:17:35](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1055s) A **`for` loop** collects the traversal controls into its header: initial state A, continuation guard B, and next-state update C. The braces contain the useful work, the body. B decides whether another iteration may start; C runs after each completed body, not just once at the end of the whole loop.

[00:17:57](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1077s) The recording prefers this form for this pattern because the initialization, guard, and update are next to one another, making the traversal easier to read.

[00:18:21](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1101s) Converting it is mechanical:

1. Move `int i = 0` into the first header slot.
2. Put `i < r.Length` in the second slot.
3. Move `i += 1` into the third slot.
4. Remove the old separate declaration and increment.
5. Keep `s += r[i]` inside the body.

[00:18:21](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1101s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
int s = 0;
for (int i = 0; i < r.Length; i += 1)
{
    s += r[i];
}
return s;
```

The two semicolons in the header separate its three parts. Execution is initialization once, guard, body, update, then guard again. The conversion retains the three-element sum, 19.

## Match variable scope as well as behavior

[00:18:46](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1126s) The loop conversion preserves the arithmetic, but there is a **scope** difference: scope is where a declared name may be used. An index declared in the for header belongs to that for.

[00:19:05](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1145s) It is available in the header's condition and update, and in the body. It is not available after the loop. Two separate for loops can each declare their own `i` without those declarations sharing one surrounding scope.

[00:19:05](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1145s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
for (int i = 0; i < r.Length; i += 1)
{
    Console.WriteLine(i); // valid: inside this loop's scope
}
// Console.WriteLine(i); // compile error if uncommented: i is not in scope

for (int i = 0; i < r.Length; i += 1)
{
    // a different loop-local i
}
```

[00:19:16](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1156s) Attempting the after-loop print produces the recording's compiler error: that name is unavailable. The **compiler** checks where names are declared, not just whether a loop has finished at runtime.

[00:19:17](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1157s) The correction to “100% equivalent” matters. In the plain while form, declaring `i` before the loop leaves it in the surrounding scope, where it can still be read afterward. It therefore has the same traversal behavior but a different visible-name boundary.

[00:19:17](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1157s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
int i = 0;
while (i < r.Length)
{
    s += r[i];
    i += 1;
}
Console.WriteLine(i); // valid here; equals r.Length after this traversal
```

[00:19:35](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1175s) A **block**, statements enclosed by braces, can restrict that declaration. Wrap both the initialization and the while loop in their own block to match the for index's visibility.

[00:19:35](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1175s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
{
    int i = 0;
    while (i < r.Length)
    {
        s += r[i];
        i += 1;
    }
}
// Console.WriteLine(i); // invalid here: outside i's block
```

[00:19:42](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1182s) Variables declared in a block cannot be named from outside it. For this example, the wrapped while now matches both the traversal order and the relevant index scope of the for form. The sum can still be returned afterward because `s` is declared outside that inner block. Equivalence here describes the code's control flow and visibility, not a claim that the compiler must emit a particular machine-code sequence.

<details>
<summary>Why does the after-loop print compile for the unwrapped while but fail for the for?</summary>

The unwrapped while's index was declared in the surrounding block. The for's index was declared in its own header and remains local to that loop. Wrapping the while declaration and loop in a new block gives its index a comparable boundary.

</details>

## Visit values directly with foreach

[00:20:00](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1200s) The next step is a higher-level traversal: use each element's value without spelling out an index, initial index, final boundary, or increment. **`foreach`** repeats work for successive elements.

[00:20:23](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1223s) For an array, the compiler can generate the mechanics needed to visit its elements, including index-based traversal. This explanation concerns the array example; other kinds of collections may be traversed differently.

[00:20:34](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1234s) Declare a variable for the **current element**, the value being visited on this iteration, instead of an index. Then write **`in`**, the keyword connecting that variable to the source array.

[00:20:34](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1234s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
int s = 0;
foreach (int element in r)
{
    s += element;
}
return s;
```

[00:20:55](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1255s) Inside the body, `element` already contains the integer value. There is no need to read `r[i]` manually. The sum still receives 6, then 8, then 5.

[00:21:01](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1261s) A **local variable** names data available in this part of the function. Conceptually, the indexed form first creates a local holding the current value, then uses it. The foreach declaration supplies that local directly.

[00:21:01](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1261s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
// Indexed body:
for (int i = 0; i < r.Length; i += 1)
{
    int element = r[i];
    s += element;
}
// Foreach supplies the current element variable in its header instead.
```

[00:21:13](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1273s) **`var`** asks the compiler to infer the variable type from the values being visited. For this `int[]`, the inferred element type is `int`. Remove the separate element declaration and use the header variable directly:

[00:21:13](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1273s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp

{
    int s = 0;
    foreach (var element in r)
    {
        s += element;
    }
    return s;
}

int[] r = [6, 8, 5];

Console.WriteLine(sum); // 19
```

[00:21:21](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1281s) The recording runs the shortened form after making this change. It has the same summing behavior as the earlier versions; the transcript does not narrate a separate new numeric output at this moment. The result 19 follows from the same three input values and additions.

Use foreach when the body needs values, and the indexed forms when the lesson's explicit positions are useful. The recording's progression removes bookkeeping without changing the function's interface.

## Read an if and recognize unreachable code

[00:21:27](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1287s) The recording returns to explain the earlier **`if` statement**, a conditional instruction. It evaluates the **Boolean condition** inside its round brackets. In the array guard, that question is whether the current index is greater than or equal to the length.

[00:21:27](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1287s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
if (i >= r.Length)
{
    return s; // finish before attempting an out-of-bounds read
}
s += r[i];    // reached only when the above test is false
```

[00:21:39](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1299s) The attached **block** runs only when the condition is true. When it is false, the entire block is skipped. Placing the stopping action before indexed access protects against stepping beyond the array's end.

[00:21:51](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1311s) An ordinary completed if block is followed by the next statement in order. An if itself does not automatically end a function:

[00:21:51](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1311s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
if (i >= r.Length)
{
    Console.WriteLine("End reached");
}
Console.WriteLine("Next statement"); // follows either branch if execution continues
```

[00:22:00](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1320s) **`return`** is the action that ends the function. In the earlier guarded body, if its condition holds, returning prevents later statements from executing on that path. Any statement placed immediately after a return in the same block is **unreachable**, meaning no control-flow path can execute it.

[00:22:00](https://www.youtube.com/watch?v=VhA2OupAYRc&t=1320s) Simplified video reconstruction, supported by the [immutable transcript][recorded-transcript], rather than an exact committed program:

```csharp
if (i >= r.Length)
{
    return s;
    // Console.WriteLine("After return"); // unreachable inside this block
}
// Reaching here means the if condition was false.
```

This distinction explains both the array guard and the greyed-out instruction demonstrated earlier: conditional branching decides which block to enter, and return decides when the invocation ends.
