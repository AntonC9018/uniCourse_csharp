# From source files to function calls

[00:00:02](https://www.youtube.com/watch?v=jLWY_id6nXU&t=2s) Follow a small C# console program from its source files to its compiled output, then follow execution through individual statements and named groups of statements. The aim is to explain both where the runnable program comes from and why its actions happen in a particular order.

The [Basic project lab](../../../labs/1_basic/02_project.md) provides related practice. The [Git lab](../../../labs/1_basic/03_git.md) covers repository setup separately; this recording only explains why generated folders should be ignored.

The vocabulary needed for the walkthrough is:

- **Source file and project configuration:** a source file contains C# text, normally in a `.cs` file; the `.csproj` file describes how to build the project. The **.NET SDK** supplies development tools, including the **compiler**, which translates that source into compiled program code.
- **Compilation and build:** compilation translates the code; a build performs the work needed to produce the output, including preparation and compilation. **Launch** means starting that output.
- **Top-level statement, class, and entry method:** a top-level statement is executable code written directly in the main source file. The compiler puts it into a generated class, a container for program members, and a generated entry method, the routine through which the program starts. Their implementation is deferred.
- **Statement or instruction:** one executable action in the source program. The course uses “instruction”; the English programming term is “statement.” The examples put one statement on each line, but a statement and a physical text line are not always the same thing.
- **Console and `Console.WriteLine`:** the console is the terminal input/output interface; `Console.WriteLine` prints a value followed by a new line.
- **DLL, library, executable, and runtime:** a DLL is a compiled .NET assembly; a library supplies reusable code to other programs; an executable is an output file you can launch. The **.NET runtime** provides the execution environment for compiled .NET code. Being launchable separately does not establish that an application was deployed with its own runtime.
- **`bin`, `obj`, and build artifacts:** artifacts are generated files. `bin` holds build output; `obj` holds intermediate build data. A **cache** stores reusable work. A **package** supplies reusable software; a **dependency** is software the project needs.
- **`Debug` and target framework:** `Debug` is the build configuration used here; the target framework identifies the .NET version the project targets, shown as `net9.0` in the recording.
- **Full path and call operator:** a full path starts from the drive or filesystem root, so the terminal can find a file independently of its current folder. The PowerShell example uses its call operator, `&`, to start the executable named by a quoted path.
- **Git repository and `.gitignore`:** a repository records source history. `.gitignore` lists paths Git should leave out when considering untracked files.
- **Sequential execution and processor:** the processor executes the program's work. Sequential execution means the actions in the sequence finish one at a time before the next begins.
- **`Thread.Sleep(1000)`:** a call that pauses the current thread, the execution sequence being followed, for 1,000 milliseconds, or one second.
- **Function or method, definition, and body:** a function is a named sequence of instructions. Its definition gives it a name and a body, the instructions between `{` and `}`. The recording also uses the word “method.”
- **`void`, parentheses, braces, and semicolon:** `void` is the keyword before the function names shown here, not a name for the function itself. Parentheses `()` appear in definitions and calls; braces `{}` enclose a body; a semicolon `;` ends the statements shown here. Detailed declaration syntax and the meaning of `void` as a return type are postponed.
- **Call, caller, return, and nested call:** a call starts a function's body; the caller is the code making that call. Returning resumes the caller after the call. A nested call occurs when one function's body calls another.

## Calls inside function bodies

[00:09:39](https://www.youtube.com/watch?v=jLWY_id6nXU&t=579s) A **nested call** is a call made inside another function's body. There is no special rule for it: the called body still runs to completion before the caller can continue.

[00:09:52](https://www.youtube.com/watch?v=jLWY_id6nXU&t=592s) The trace enters `Hello`, runs its three actions, then reaches a call to another list. A reduced reconstruction shows that direction of nesting; the second list's name and printed values here are illustrative:

```csharp
Hello();

void Hello()
{
    Console.WriteLine(1);
    Console.WriteLine(2);
    Console.WriteLine(3);
    Other();
}

void Other()
{
    Console.WriteLine("A");
    Console.WriteLine("B");
}
```

Follow each transfer rather than just reading down the entire file:

1. The startup call enters `Hello`.
2. [00:09:58](https://www.youtube.com/watch?v=jLWY_id6nXU&t=598s) Its three printing statements finish in order.
3. [00:10:07](https://www.youtube.com/watch?v=jLWY_id6nXU&t=607s) Its last call enters `Other`, starting at that body's first instruction.
4. [00:10:10](https://www.youtube.com/watch?v=jLWY_id6nXU&t=610s) The two statements in the inner body finish.
5. [00:10:18](https://www.youtube.com/watch?v=jLWY_id6nXU&t=618s) Execution returns to the call site inside `Hello`.
6. [00:10:25](https://www.youtube.com/watch?v=jLWY_id6nXU&t=625s) Because that was `Hello`'s final instruction, `Hello` also finishes.
7. [00:10:33](https://www.youtube.com/watch?v=jLWY_id6nXU&t=633s) Execution returns again, this time to the startup call. With nothing after it, the program ends.

The shorter description “a function calls Hello” works the same way: reverse which body contains the call, and the call enters `Hello` first, prints its three actions in order, and returns to that caller. What matters is the call site and its continuation, not which name is the outer one.

Returning still takes place when there is no next instruction. It is how completion of the inner body lets the enclosing body, and then the startup sequence, finish. A final nested call is not a reason to skip the caller.

## Following the whole execution path

[00:10:41](https://www.youtube.com/watch?v=jLWY_id6nXU&t=641s) The final walkthrough follows another statement and another call after returning. To make both the intermediate return and the eventual end visible, this reduced variation adds a continuation in the startup code:

```csharp
Hello();
Console.WriteLine("After the first call");
Hello();

void Hello()
{
    Console.WriteLine(1);
    Console.WriteLine(2);
    Console.WriteLine(3);
    Other();
}

void Other()
{
    Console.WriteLine("A");
    Console.WriteLine("B");
}
```

Use the same procedure at every level:

1. [00:10:41](https://www.youtube.com/watch?v=jLWY_id6nXU&t=641s) After a call finishes, continue with the next statement in its caller. Here the message between the two calls prints.
2. [00:11:01](https://www.youtube.com/watch?v=jLWY_id6nXU&t=661s) At a function call, enter the first instruction of the named body. The second startup call starts `Hello` afresh.
3. [00:11:08](https://www.youtube.com/watch?v=jLWY_id6nXU&t=668s) Execute that body's statements in order, completing each before starting the next; a nested call follows the same rule.
4. [00:11:16](https://www.youtube.com/watch?v=jLWY_id6nXU&t=676s) When the last body statement finishes, return to its call site. If the last statement was another call, its completion allows the enclosing body to finish too.
5. [00:11:25](https://www.youtube.com/watch?v=jLWY_id6nXU&t=685s) A body that only exists as a definition contributes no actions unless it is called somewhere on the executed path.

<details>
<summary>Predict how often A prints, and explain why the definitions do not add extra runs.</summary>

A prints twice. Each startup call enters Hello; each execution of Hello calls Other once. Other prints A and B and returns to Hello, which returns to the startup sequence. The two definitions only make their bodies available.
</details>

[00:11:16](https://www.youtube.com/watch?v=jLWY_id6nXU&t=676s) “Return to the line with the call” and “continue after the call” describe two parts of the same event: control returns to that caller, the call is now finished, and the next statement can begin. At the final startup call there is no next statement, so termination follows.
