# What an algorithm is made of

[00:00:00](https://www.youtube.com/watch?v=C6plSGSYuyc&t=0s) The goal of the lesson is to learn how to solve problems, especially non-trivial ones — problems that cannot be solved in a single step and must be split into several solution steps — and how that connects to how programs as a whole are built. The scope stops at describing algorithms; nothing here is written into a project yet, and the only program code appears on screen near the end as a demonstration of the translation from steps to code.

Terms used throughout the lesson:

- **Algorithm:** a program that performs a task; it consists of input data, output data, and a concrete realization of the steps.
- **Input data** (**input**): what the task consumes.
- **Output data** (**output**): what the task produces.
- **Interface:** the constantly used name for the input and output data of a program; more generally, the system of interaction with some system.
- **Implementation** (realization): the box inside the program that takes the input and performs the task.
- **Decomposition:** splitting a task into simpler sub-steps, repeatedly, until elementary primitive steps are reached.
- **Primitive operation:** an elementary step already available in a programming language.
- **Array:** a stretch of memory where values are written one after another.
- **Index:** a position relative to the start of that memory stretch, that is, how many elements you must jump over to reach the element.
- **Abstraction:** referring to an existing algorithm by name without knowing how it works internally.
- **High level / low level:** high level means using a ready-made algorithm; low level means splitting the algorithm into primitive steps.

## Arrays and indices

[00:13:14](https://www.youtube.com/watch?v=C6plSGSYuyc&t=794s) To explain walking over every value, one thing has to be cleared up first: what an array is.

[00:13:23](https://www.youtube.com/watch?v=C6plSGSYuyc&t=803s) An array is a stretch of memory where values — here, numbers — are written one after another, with as many memory cells as there are values. ```

[00:13:50](https://www.youtube.com/watch?v=C6plSGSYuyc&t=830s) Walking over the values of an array is done by **index**: a position relative to the start of the memory stretch, that is, how many elements you have to jump over to reach the element. [00:14:11](https://www.youtube.com/watch?v=C6plSGSYuyc&t=851s) The index is usually denoted by a letter, and [00:14:14](https://www.youtube.com/watch?v=C6plSGSYuyc&t=854s) index zero means the first element, because the count starts at the beginning of the array: to reach the first element you jump zero elements and stay in place. [00:14:32](https://www.youtube.com/watch?v=C6plSGSYuyc&t=872s) The element at the third index is reached by jumping three positions from the start of the array — past the elements with indices 0, 1 and 2.

[00:15:02](https://www.youtube.com/watch?v=C6plSGSYuyc&t=902s) With the index you can denote which element you are on at the current moment. [00:15:11](https://www.youtube.com/watch?v=C6plSGSYuyc&t=911s) To move to the next element, the index is increased by one, that is, shifted one element further: index 1 corresponds to jumping one element, index 2 to jumping two.

[00:15:33](https://www.youtube.com/watch?v=C6plSGSYuyc&t=933s) Edge case: the maximum available index equals the number of elements minus one, because the offset of the last element is one less than that of all the previous ones. [00:15:47](https://www.youtube.com/watch?v=C6plSGSYuyc&t=947s) In the listing, an extra indent before the first cell and before the last cell makes the padding from the last cell to the end of the list visually distinguishable, which makes the snippet easier to read:

[00:15:57](https://www.youtube.com/watch?v=C6plSGSYuyc&t=957s) The first cell has offset zero and the last has count minus one, so to reach the last cell you count exactly that many elements. [00:16:10](https://www.youtube.com/watch?v=C6plSGSYuyc&t=970s) The distance from the last cell to the end of the list is the last index, and that is the last element. ## Naming the traversal as a sub-algorithm

[00:16:23](https://www.youtube.com/watch?v=C6plSGSYuyc&t=983s) The idea of walking over every value is decomposed into a named sub-algorithm whose steps can be written down and reasoned about separately.

[00:16:38](https://www.youtube.com/watch?v=C6plSGSYuyc&t=998s) Traversing the values means iterating over every index in turn and reading the value stored at that index, while keeping a current index that moves forward on each step. [00:17:00](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1020s) The behaviour of the current index is described by four rules, which together specify how the index must be initialized, updated, and when the traversal must stop:

1. The first index is zero, so the current index is initially zero.
2. At every stage the index is increased by one, which is what makes the traversal visit the elements in order.
3. The last index is the termination rule.
4. The amount of jumps from the beginning is what tells the algorithm whether to pull a value out of the list.

[00:17:18](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1038s) The last index is the termination rule of the algorithm: because the current index grows by one per step, its passing the last index means every available value has been visited. [00:17:32](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1052s) Passing beyond the last index is the signal that all indices have been traversed, so this comparison replaces any explicit count of iterations. [00:17:40](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1060s) The count of jumps from the beginning is also what tells the algorithm whether to pull a value out of the list or not, so the index encodes both position and loop progress.

## Writing the traversal as steps

[00:17:58](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1078s) Program instructions are a list of concrete steps that the program must perform in order to produce the sum, and those steps are now written down using the rules just derived. [00:18:12](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1092s) The first step creates a memory cell for the current index, because that index changes during execution and a variable is the only way to remember its value between steps. A variable is a memory cell into which values can be written, so the current index is stored there and initialized with zero, making the traversal start at the beginning of the list. This simplified pseudocode accompanies the [steps written at 18:12](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1092s); the recording shows the same list on screen but the repository holds no snapshot of it:

```text
1. create a cell for the current index; write 0 into it
2. go to step 3
3. if the index is past the end of the list, finish          ← empty list ends here
4. take the element at the current index; add it to the current sum
5. increase the index by one; go to step 3
6. the answer is in the current-sum cell
```

[00:18:43](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1123s) The third step checks whether the end of the list has already been reached, because an empty list has no available indices at all and therefore counts as already finished. [00:19:12](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1152s) Edge case: when the end of the list is detected the algorithm terminates, which prevents reading past the end of the array.

[00:19:12](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1152s) Fetching a value means stepping from the start of the array as many times as the stored index says, with the stored number counting 0, then 1, then 2 until the whole list has been covered. [00:19:32](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1172s) After the fetched element is added to the running sum, the algorithm must advance to the next index and continue with the next element. [00:19:46](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1186s) The fourth step increments the current index by one, which is the operation that moves the traversal to the next element of the list. [00:19:53](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1193s) Edge case: right after incrementing, the algorithm checks the bounds again and exits if the index has left the list, so the out-of-range step never executes. [00:20:09](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1209s) The fetch, add and increment steps form a loop that must repeat until the index goes beyond the bounds of the array, which is what turns the three steps into a full traversal.

## Adding each element to the current sum

[00:20:22](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1222s) The deferred sixth step adds each element to the current sum, referring back to the running sum that was postponed while the traversal steps were written.

[00:20:44](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1244s) Edge case: what if the list is empty, with no elements at all? The sum of the elements of a list is then defined as zero, so the algorithm must still produce zero rather than fail to initialize the sum. [00:20:52](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1252s) Why zero is the right answer follows from the associativity of addition. [00:20:57](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1257s) Summing a list is presented as a left-to-right fold: add the first element to the second, add the result to the third, and so on until the last operation yields the total, which is valid because addition is associative.

[00:21:23](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1283s) The total can be decomposed into a base sum plus each element added one after another, which turns a single long expression into a sequence of simple additions. [00:21:32](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1292s) Because the base sum is zero, starting from it and adding the first, second, third, fourth and fifth element in order produces exactly the full sum:

```text
0 + 7 + 5 + 4 + 3 + 8
start from the base sum 0
add the first element 7   → 7
add the second element 5  → 12
add the third element 4   → 16
add the fourth element 3  → 19
add the fifth element 8   → 27
```

[00:21:53](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1313s) Summing therefore reduces to walking every element of the collection and adding each of them in turn, and the algorithm for iterating over elements has already been built earlier. [00:22:06](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1326s) The running total is kept in a dedicated cell that starts out holding the base value, so every element is added onto the accumulated value rather than being combined pairwise. [00:22:08](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1328s) To perform the addition against the current value, a new cell is introduced that stores the current sum.

[00:22:16](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1336s) On the first pass through the loop the current sum holds the base value and is combined with the first element, producing a temporary sum that is then extended with each following element. [00:22:34](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1354s) Each subsequent element is added to the temporary sum and the result is written back into the current-sum cell, so 5 plus 5 gives 10, and then 10 plus 4 gives 19 for the following step. [00:23:20](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1400s) At every step the current sum equals one node and moves to the next node by adding that node's value: 19 plus 3 gives 22, and 22 plus 8 gives 30. [00:23:31](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1411s) The last node holds the final sum, and because the current-sum cell passes through all nodes and stops at the last one, the answer is left in that cell.

[00:23:44](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1424s) Implementing the summing algorithm requires adding each element's value to the current sum, which combines the previously explained iteration over elements with the idea of accumulating. [00:24:04](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1444s) The pseudocode therefore gains one extra step before the loop that creates a cell for the current sum and writes the base sum into it, after which the existing element-by-element loop runs and the result is read from that cell:

```text
0. create a cell for the current sum; write the base sum 0 into it
1. create a cell for the current index; write 0 into it
2. go to step 3
3. if the index is past the end of the list, finish
4. take the element at the current index; add it to the current sum
5. increase the index by one; go to step 3
6. the answer is in the current-sum cell
```

[00:24:39](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1479s) After the loop has passed over every element the current sum equals the value stored in the final node, which is why that cell can be returned as the list sum.

## From written steps to code

[00:24:58](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1498s) The written algorithm translates directly into code: a cell for the current sum is created and the base sum is written into it before the loop starts. [00:25:15](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1515s) The code allocates memory for the current index, writes into that cell, and checks whether the index has reached the list length, in which case the answer is in the current-sum cell. [00:25:36](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1536s) Inside the loop the code adds the array element at the current index to the current sum, then increments the index by one and jumps back to the third step. This simplified sample sits beside the [code written at 25:15](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1515s); no repository commit holds this on-screen state:

```csharp
int currentSum = 0;
int currentIndex = 0;

while (currentIndex != values.Length)
{
    currentSum += values[currentIndex];
    currentIndex += 1;
}

// currentSum is the sum of the list
```

[00:25:58](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1558s) The manual increment and jump-back is usually replaced by a `for` loop, a small modification of the same code. [00:26:03](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1563s) A step-by-step algorithm description maps almost one-to-one onto program code, so wrapping it in a function with a name, parameters and a return type yields a complete summing function. [00:26:14](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1574s) Giving the average-value sub-algorithm a name plus its input data and return type turns the prose description into a complete callable interface:

```csharp
int Sum(int[] values)
{
    int currentSum = 0;
    for (int i = 0; i < values.Length; i += 1)
    {
        currentSum += values[i];
    }
    return currentSum;
}
```

[00:26:24](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1584s) The average is computed by summing the values and dividing the sum by the list length, which is a trivial primitive-level operation. [00:26:32](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1592s) The list length is already available as a stored primitive value, so the division needs only reading the sum, reading the length, and dividing them. [00:26:53](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1613s) Dividing the obtained sum by the length yields the answer, which completes this sub-algorithm.

## High level, low level and abstraction

[00:28:15](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1695s) **High level** means using an existing ready-made algorithm, while **low level** means splitting the algorithm into primitive steps. [00:28:31](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1711s) An algorithm written in a more primitive, detailed way is the low-level description of the same behaviour. [00:28:40](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1720s) High level means knowing that an algorithm exists and what it does, such as summing a list of numbers, without thinking about how it internally allocates variables and walks the list. [00:29:01](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1741s) Referring to an existing algorithm by name without knowing how it works internally is called **abstraction**. [00:29:18](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1758s) Abstraction means using a name that simply describes what will happen at a high level.

High level: it names an already available value (the stored length) instead of decomposing the counting of elements into primitive steps.
</details>

## Drawing an algorithm as memory cells

[00:29:31](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1771s) Algorithms should be decomposed not only into steps but also into an interface. [00:29:40](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1780s) The interface of an algorithm consists of its input and its output. [00:29:47](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1787s) The implementation is the concrete steps plus the working memory, which is the temporary memory created as cells for variables. [00:30:03](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1803s) An algorithm is drawn as memory cells for the input, separate memory cells for the output, and a separate memory space for the temporary memory used while running:

```text
input cells        output cells       temporary memory (workspace)
[ a ]  [ b ]       [ result ]         [ sum ]
```

[00:30:19](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1819s) Input memory cells hold data the algorithm cannot control, since they are supplied from outside. [00:30:23](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1823s) For an algorithm that adds two numbers, the input cells hold `a` and `b`, and a temporary cell stores the sum so the answer 11 can be produced.

## Passing a list in practice

[00:30:42](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1842s) Scope boundary: this cell representation only describes what an algorithm is, so in practice the question becomes how to pass a list of elements into it. [00:30:50](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1850s) Writing every list element one after another and additionally passing the length separately is not how this is normally done. [00:31:02](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1862s) Normally an object representing the list lives at some address whose value is passed in a memory cell, and inside it are the elements, the length, and the returned values, all of which can be thought of as separate memory:

```text
cell passed in: address ──► [ elements ... | length ]
```
