# Поиск унаследованных членов и композиция

[00:00:00](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=0s) Этот урок задаёт два связанных вопроса: как C# находит член класса, когда классы наследуют друг друга, и является ли наследование удачным способом смоделировать способности животного. Начнём с небольшого примера «базовый/производный» класс, построим рабочую иерархию животных, а затем заменим иерархию способностей композицией.

Вам понадобится следующий словарь:

- **Класс, объект и ссылка:** класс определяет тип; объект — это экземпляр этого типа; ссылка позволяет переменной указывать на этот объект.
- **Член, поле и метод:** член принадлежит классу; поле хранит состояние; метод выполняет операцию.
- **Наследование, базовый класс и производный класс (подкласс):** производный класс расширяет базовый и наследует его члены. В примерах используются общедоступные члены.
- **Компилятор, область видимости и поиск членов:** компилятор проверяет и транслирует исходный код; область видимости и поиск определяют, к какому члену относится имя.
- **Модификатор доступа:** ключевое слово, управляющее доступностью; в примерах используется `public`, разрешающее доступ с места вызова.
- **Методы экземпляра и статические методы:** метод экземпляра работает с объектом как с получателем; статический метод принадлежит типу и не имеет получателя-экземпляра.
- **Статический тип и тип времени выполнения:** статический тип — тип, известный компилятору для выражения; тип времени выполнения — фактический класс указанного объекта.
- **Сокрытие имени и `new`:** объявление в производном классе вводит собственный одноимённый член; модификатор `new` явно признаёт, что он скрывает унаследованный член.
- **Виртуальный метод, переопределение и динамическая диспетчеризация:** `virtual` разрешает реализацию в производном классе; `override` её предоставляет; динамическая диспетчеризация выбирает эту реализацию по объекту времени выполнения.
- **Полиморфизм:** работа с объектами через общий тип, когда реализации могут различаться; подробное рассмотрение отложено.
- **Приведение к базовому типу, сужение и явное приведение:** ссылка на производный объект может использоваться как ссылка на базовый; сужение получает более конкретный тип; явное приведение запрашивает преобразование.
- **Массив и цикл:** массив хранит последовательность элементов одного объявленного типа элемента; цикл обрабатывает эти элементы.
- **Проверка типа и шаблон объявления:** `is Sparrow s` проверяет совместимость и при успехе привязывает ссылку указанного типа к `s`.
- **Композиция, способность и модуль:** композиция собирает объект из взаимодействующих объектов; способность — это умение, например плавание; модуль реализует одно такое умение.
- **Фабричная функция и конструктор:** фабрика собирает и возвращает объект; конструктор инициализирует экземпляр при его создании через `new`.
- **Инициализатор объекта:** фигурные скобки после создания объекта присваивают поля или свойства.
- **Интерполяция строк:** `$"...{expression}..."` вставляет значение выражения в текст.
- **Null, ссылка, допускающая null, и шаблон «не null»:** `null` означает отсутствие указанного объекта; `?` допускает такое отсутствие в объявлении ссылочного типа; `is not null` или `is { }` проверяет наличие значения. Пустой шаблон свойства `{ }` — это синтаксис последнего шаблона.
- **Интерфейс:** контракт, который могут реализовать разные типы; он упоминается в конце как частичная альтернатива и здесь не раскрывается.

О более ранней практике с методами экземпляра см. [лабораторную по методам экземпляра](../../../labs/1_basic/16_method.md). Полиморфизм и интерфейсы разбираются отдельно; [лабораторная по полиморфизму и интерфейсам](../../../labs/1_basic/18_interface.md) — необязательное дополнительное чтение, **не материал этого видео**.

Примеры ниже — короткие реконструкции **состояний видео** с поясняющими именами и выводом. ## Унаследованные поля и методы

[00:00:14](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=14s) **Базовый класс** предоставляет состояние и операции, которые наследует **производный класс**. В `class Derived : Base` двоеточие объявляет наследование. **Поле** хранит данные на объекте, поэтому производный объект может читать унаследованное публичное поле под тем же именем. Модификатор доступа `public` разрешает доступ с этих мест вызова.

Начальное состояние видео, упрощённо:

```csharp
class Base
{
    public int Value;
    public void BaseMethod() => Console.WriteLine(Value);
}

class Derived : Base
{
    public int Extra;
    public void Method() => Console.WriteLine(Extra);
}

// На месте вызова:
Derived d = new Derived();
d.Value = 10;  // унаследованное поле
d.Extra = 20;  // поле, добавленное Derived
```

[00:00:28](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=28s) **Метод экземпляра** вызывается через ссылку на объект. Его объявление может находиться в производном классе или в доступном базовом классе. Получателем остаётся `d`: вызывайте `d.Method()` для добавленного метода и `d.BaseMethod()` для унаследованного. Ссылка базового типа тоже может вызвать член базового класса. Упрощённое состояние на месте вызова:

```csharp
d.Method();
d.BaseMethod();

Base b = d;
b.BaseMethod();
```

[00:00:48](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=48s) Унаследованная **область видимости** означает, что член базового класса остаётся достижимым через производный объект. Перенос операции в базовый класс не заставляет вызывающий код отказываться от своей ссылки на производный объект. Будьте точны в синтаксисе: `Base.Method()`, где `Base` — имя класса, не может вызвать обычный метод экземпляра без получателя.

[00:00:57](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=57s) Далее изменим методы на **статические**, у которых нет получателя-экземпляра. Состояние видео реконструировано здесь:

```csharp
class Base
{
    public static void BaseMethod() { }
}

class Derived : Base
{
    public static void Method() { }
}

Derived.Method();
Derived.BaseMethod();
Base.BaseMethod();
// d.BaseMethod(); // недопустимо для статического метода
```

[00:01:04](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=64s) К статическим методам обращаются по имени типа, даже если объект существует. Здесь «нет экземпляра» означает отсутствие получателя-экземпляра у метода, а не то, что программа не может содержать объекты. [00:01:11](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=71s) И `Derived.BaseMethod()`, и `Base.BaseMethod()` приводят к унаследованному статическому члену.

[00:01:19](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=79s) **Поиск членов** — это разрешение имени члена компилятором. В этом простом примере, не найдя `BaseMethod` в `Derived`, он продолжает обход базовых классов и находит объявление в `Base`. [00:01:33](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=93s) Такой поиск происходит при компиляции. Работающая программа не ищет объявления в классах многократно, чтобы разрешить этот невиртуальный вызов.

## Сокрытие и статический тип

[00:01:51](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=111s) Теперь дадим обоим классам метод с одинаковым именем и сигнатурой. Побуждающая проблема в том, что объявление в производном классе скрывает унаследованное объявление. Добавьте модификатор **`new`**, чтобы подтвердить намеренное **сокрытие имени**; это применимо и к статическим, и к экземплярным объявлениям.

[00:02:15](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=135s) В этом контексте `new` означает «я знаю, что унаследованный член уже существует, и объявляю отдельный член, который его скрывает». Это не то же самое, что `new Derived()`, где `new` создаёт объект. Запись описывает эту диагностику как ошибку; обычно отсутствие модификатора сокрытия даёт **предупреждение компилятора**, хотя проект может трактовать предупреждения как ошибки. См. [справку C# по модификатору new](https://learn.microsoft.com/dotnet/csharp/language-reference/keywords/new-modifier).

[00:02:26](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=146s) Вернёмся к методам экземпляра и сравним две переменные, ссылающиеся на один и тот же объект. Упрощённое состояние видео:

```csharp
class Base
{
    public void Method() => Console.WriteLine("Base");
}

class Derived : Base
{
    public new void Method() => Console.WriteLine("Derived");
}

Derived d = new Derived();
Base b = d;
d.Method();
b.Method();
```

Проследите вызовы по порядку:

1. [00:02:35](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=155s) **Статический тип** `d` — `Derived`, поэтому поиск начинается там и находит `Derived.Method`.
2. Если бы метода там не было, поиск продолжился бы в базовых классах.
3. [00:02:49](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=169s) Статический тип `b` — `Base`, поэтому поиск находит `Base.Method`, хотя **тип времени выполнения** объекта — `Derived`.
4. [00:03:03](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=183s) При запуске демонстрации сначала печатается `Derived`, затем `Base`.

[00:03:14](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=194s) Для таких скрытых невиртуальных методов выбранный член определяется типом переменной на этапе компиляции. Изменение статического типа ссылки не меняет объект, на который она указывает. [00:03:25](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=205s) Выбор поведения по типу времени выполнения — отдельный механизм; здесь он лишь кратко продемонстрирован.

Почему после присваивания `d` в `b` второй вызов печатает `Base`?

<details>
<summary>Ответ</summary>
Обе ссылки указывают на один и тот же объект типа Derived. Методы — это два отдельных невиртуальных объявления, и поиск для b.Method начинается со статического типа Base. Присваивание не делает b переменной типа Derived.
</details>

## Краткая демонстрация виртуальной диспетчеризации

[00:03:33](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=213s) Заменим сокрытие на **виртуальный метод** и **переопределение**. Виртуальный метод разрешает реализацию в производном классе; переопределение предоставляет эту реализацию. **Динамическая диспетчеризация** затем выбирает реализацию по объекту времени выполнения.

Упрощённое изменённое состояние видео:

```csharp
class Base
{
    public virtual void Method() => Console.WriteLine("Base");
}

class Derived : Base
{
    public override void Method() => Console.WriteLine("Derived");
}

Derived d = new Derived();
Base b = d;
d.Method();  // Derived
b.Method();  // Derived
```

[00:03:56](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=236s) Теперь показанный запуск выполняет производную реализацию при обоих вызовах. Компилятор по-прежнему разрешает виртуальный член по статическому типу выражения, а вот диспетчеризация этого члена использует тип объекта времени выполнения. Это краткое противопоставление показывает, чем `new` отличается от `override`. Подробный полиморфизм выходит за основные рамки этого видео.

## Построим иерархию животных

[00:04:01](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=241s) Перейдём от правил поиска к работающей модели. Теперь **базовый класс** — `Animal`. Его **поле** хранит возраст в днях, а общий **метод экземпляра** печатает возраст и имя конкретного класса. `GetType()` возвращает тип времени выполнения; его `Name` даёт имя класса. Интерполяция строк, синтаксис `$"...{expression}..."`, подставляет значения выражений в печатаемый текст.

Упрощённое начальное состояние видео с животными:

```csharp
class Animal
{
    public int AgeInDays;

    public void Print() =>
        Console.WriteLine($"{GetType().Name}: {AgeInDays} days");
}

class Penguin : Animal
{
    public void Swim() => Console.WriteLine("Swimming");
}

class Sparrow : Animal
{
    public void Fly() => Console.WriteLine("Flying");
}
```

[00:04:15](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=255s) **Подклассы** добавляют только свои собственные умения: `Penguin` добавляет `Swim`, а `Sparrow` — `Fly`. Оба наследуют возраст и печать. Базовый метод печати может сообщить `Penguin` или `Sparrow` через `GetType()`, и его не нужно переопределять.

[00:04:35](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=275s) **Приведение к базовому типу** позволяет использовать ссылку на производный объект там, где ожидается базовый тип. С его помощью помещаем разных конкретных животных в один **массив** — последовательность, объявленный тип элемента которой равен `Animal`. Упрощённое состояние видео с построением массива:

```csharp
Penguin p = new Penguin();
Sparrow s = new Sparrow();

Animal[] animals =
{
    p,
    s,
    new Penguin()
};
```

[00:04:52](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=292s) Компилятор знает, что `Penguin : Animal`, поэтому разрешает `p` в ячейке типа `Animal`. [00:05:11](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=311s) Для `s` рассуждение то же: `Sparrow : Animal` делает его ссылку пригодной как ссылка на `Animal`. Это не создаёт новый объект и не стирает его конкретный тип времени выполнения.

## Обработаем общее состояние

[00:05:24](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=324s) **Статический помощник** — это операция, вызываемая без получателя-экземпляра. Дадим ему параметр `Animal` и применим его к каждому элементу массива с помощью **цикла**. Общее поле возраста доступно потому, что оно объявлено на общем базовом типе.

Упрощённое состояние видео с общей обработкой:

```csharp
static void PassDay(Animal animal)
{
    animal.AgeInDays++;
}

foreach (Animal animal in animals)
{
    PassDay(animal);
    animal.Print();
}
```

`foreach` обходит каждый элемент; `++` увеличивает поле на единицу. Это поле «общее» в смысле общего объявления, **а не** в смысле одного глобального значения: у каждого объекта животного свой возраст.

[00:05:37](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=337s) Тот же цикл вызывает общий метод печати. Разные классы времени выполнения не мешают использовать унаследованные состояние и операции через `Animal`.

[00:05:42](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=342s) Вне цикла переменная со статическим типом `Penguin` позволяет напрямую вызвать плавание. [00:05:52](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=352s) Чтение элемента из `Animal[]` даёт выражение со статическим типом `Animal`; сам по себе этот тип не может гарантировать умение плавать. Упрощённое промежуточное состояние, не компилирующееся:

```csharp
p.Swim();           // разрешено: p имеет тип Penguin
// animals[0].Swim(); // не компилируется: тип элемента Animal
```

Даже если первый элемент случайно окажется пингвином, компилятор не может вывести такую гарантию из объявленного типа массива.

## Сузите ссылку перед вызовом конкретного умения

[00:06:14](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=374s) Решение — **сужение**: получить ссылку конкретного подкласса перед вызовом его умения. **Проверка типа** подтверждает совместимость времени выполнения. **Шаблон объявления** одновременно проверяет совместимость и привязывает типизированную переменную.

[00:06:24](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=384s) Упрощённое изменённое состояние видео:

```csharp
Animal animal = animals[0];

if (animal is Penguin penguin)
{
    penguin.Swim();
}
```

[00:06:33](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=393s) В `is Penguin penguin` имя `Penguin` называет требуемый тип, а `penguin` — переменную, привязываемую при успехе. Переменная ссылается на тот же объект; шаблон не создаёт пингвина. [00:06:38](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=398s) Если объект времени выполнения несовместим, тело пропускается. [00:06:45](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=405s) Поэтому вызов умения выполняется только после установления совместимости.

[00:06:58](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=418s) Проверка без указания переменной, например `animal is Sparrow`, проверяет объект, но оставляет `animal` статически типизированным как `Animal`. Вызов, доступный только воробью, через исходную переменную всё равно не сработает. [00:07:09](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=429s) Сначала преобразуйте, потом вызывайте. **Явное приведение**, записанное как `(Sparrow)animal`, запрашивает конкретный тип ссылки; предшествующая проверка делает это приведение безопасным в примере.

Упрощённые промежуточная и исправленная формы из этого состояния видео:

```csharp
if (animal is Sparrow)
{
    // animal.Fly(); // недопустимо: animal по-прежнему Animal
    ((Sparrow)animal).Fly();
}

// Шаблон объявления объединяет проверку и преобразование:
if (animal is Sparrow sparrow)
{
    sparrow.Fly();
}
```

[00:07:18](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=438s) Применим этот шаблон в цикле по объектам базового типа. Упрощённое состояние видео с фильтрацией:

```csharp
foreach (Animal animal in animals)
{
    if (animal is Penguin penguin)
    {
        penguin.Swim();
    }
}
```

[00:07:32](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=452s) Каждый текущий элемент проверяется независимо. [00:07:52](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=472s) Совпавший элемент получает вызов метода конкретного типа; несовместимые элементы не делают ничего. [00:07:57](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=477s) Это позволяет действовать только на пингвинов, сохраняя один смешанный массив.

<summary>Ответ</summary>

</details>

[00:08:07](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=487s) **Граница рассмотрения:** **полиморфизм**, то есть работа через общий тип при различающихся реализациях, намеренно оставлен другому видео для полного разбора. Этот пример использует явные проверки и ссылки на подклассы; он не строит общую виртуальную или интерфейсную схему способностей.

## Проверим пример с наследованием

[00:08:12](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=492s) Запуск в записи подтверждает, что помощник «пропустить день» выполняется отдельно для каждого животного и увеличивает возраст каждого на один день. После этого общая операция печати может показать обновлённое состояние каждого животного.

[00:08:26](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=506s) Далее метод, специфичный для воробья, вызывается напрямую через переменную воробья, а цикл фильтрации вызывает `Swim` для каждого пингвина. Упрощённая проверенная последовательность вызовов:

```csharp
foreach (Animal animal in animals)
{
    PassDay(animal);
    animal.Print();
}

s.Fly();

foreach (Animal animal in animals)
{
    if (animal is Penguin penguin)
        penguin.Swim();
}
```

[00:08:36](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=516s) Добавим ещё одного `Penguin` в массив. При трёх пингвинах плавание выполняется трижды — по одному разу на каждый подходящий элемент массива. Добавленный элемент меняет работу цикла, не требуя ещё одного оператора вызова умения.

Это результаты, продемонстрированные в записи, а не утверждение, что реконструированные примеры исполнялись в этой сессии написания.

## Заменим иерархию композицией

[00:08:44](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=524s) Рабочая иерархия показывает, что умеет наследование; это не рекомендация моделировать способности животных таким способом. [00:08:54](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=534s) Совет по проектированию: используйте наследование сдержанно и для этого сценария предпочитайте **композицию**.

[00:08:59](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=539s) **Композиция** означает построение животного из взаимодействующих объектов. **Способность** — это умение, например плавать или летать, а **модуль** — отдельный объект, который это умение реализует. Дайте общему `Animal` общие данные и имя, а модулям способностей — доступ к этому животному.

[00:09:06](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=546s) Упрощённое состояние видео с композицией:

```csharp
class Animal
{
    public string Name = "";
    public int AgeInDays;
    public SwimModule? Swimming;
    public FlyModule? Flying;

    public void Print() =>
        Console.WriteLine($"{Name}: {AgeInDays} days");
}

class SwimModule
{
    Animal animal;

    public SwimModule(Animal animal)
    {
        this.animal = animal;
    }

    public void Swim() =>
        Console.WriteLine($"{animal.Name} swims");
}

class FlyModule
{
    Animal animal;

    public FlyModule(Animal animal)
    {
        this.animal = animal;
    }

    public void Fly() =>
        Console.WriteLine($"{animal.Name} flies");
}
```

**Конструктор**, например `SwimModule(Animal animal)`, инициализирует только что созданный модуль. `this.animal` обозначает его поле, а неквалифицированное `animal` справа — параметр. Модуль хранит **ссылку** на общее животное, поэтому его операция может использовать те же имя и данные. Никакое объявление наследования не связывает эти три класса.

Аннотации **ссылок, допускающих null**, `SwimModule?` и `FlyModule?` допускают **null**, то есть отсутствие модуля. У животного может быть плавание, полёт, и то и другое, или ни то ни другое. Работа с именем относится к общим данным животного, а не к отдельным реализациям подклассов.

## Собираем животных фабриками

[00:09:23](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=563s) Конкретные классы `Penguin` и `Sparrow` исчезают из композиционной версии. Создание переносится в **фабричные функции**: функции, которые собирают и возвращают настроенных животных.

[00:09:35](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=575s) Соберём пингвина по шагам:

1. Создайте `Animal` с именем и начальным возрастом.
2. Создайте модуль плавания, используя ссылку на это животное.
3. Присвойте модуль полю плавания и оставьте полёт отсутствующим.
4. Верните собранное животное.

**Инициализатор объекта** — это присваивание полей в фигурных скобках после `new Animal()`. Упрощённое состояние видео с фабрикой пингвина:

```csharp
static Animal CreatePenguin(int age)
{
    Animal animal = new Animal()
    {
        Name = "Penguin",
        AgeInDays = age
    };
    animal.Swimming = new SwimModule(animal);
    return animal;
}
```

Сам проект модуля может зависеть от данных, передаваемых фабрике, либо использовать достаточно общий тип модуля; композиция не требует одной зашитой реализации навсегда.

[00:09:50](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=590s) Повторим схему построения для воробья, дав ему полёт вместо плавания. Упрощённое состояние видео со второй фабрикой:

```csharp
static Animal CreateSparrow(int age)
{
    Animal animal = new Animal()
    {
        Name = "Sparrow",
        AgeInDays = age
    };
    animal.Flying = new FlyModule(animal);
    return animal;
}
```

Обе функции возвращают один и тот же общий тип. Их имена описывают выбранную сборку, а не разные подклассы времени выполнения.

## Читаем способности из полей

[00:10:18](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=618s) В этой упрощённой модели воробей летает, но не плавает, пингвин плавает, но не летает, а утка умеет и то и другое. Само по себе понятие «птица» не определяет набор способностей. Поэтому проверка класса вида — неправильный источник сведений о способностях в новой схеме.

[00:10:39](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=639s) Вместо этого читайте **поля** модулей у общего `Animal`. Поле хранит ссылку на объект способности; само его наличие сообщает программе, какая операция доступна.

[00:10:59](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=659s) Животные по-прежнему могут пользоваться одним **массивом**, а общие операции работы с возрастом и печати продолжают работать — теперь уже без иерархии подклассов животных. Упрощённое состояние видео с композиционным массивом:

```csharp
Animal[] animals =
{
    CreatePenguin(10),
    CreateSparrow(20)
};

foreach (Animal animal in animals)
{
    PassDay(animal);
    animal.Print();
}
```

Эти значения возраста иллюстративны. Здесь массив хранит собранных животных, а не модули умений. Плавание и полёт остаются в полях модулей каждого животного. Нет нужды извлекать ссылку на `Penguin` или `Sparrow`, чтобы использовать общие данные.

## Проверьте модуль перед вызовом

[00:11:19](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=679s) Поле модуля может быть **null**, то есть объект способности отсутствует. Вызов метода через отсутствующую ссылку завершился бы ошибкой, поэтому перед вызовом операции сделайте проверку. Упрощённая первая форма из состояния видео:

```csharp
foreach (Animal animal in animals)
{
    SwimModule? swimming = animal.Swimming;
    if (swimming != null)
    {
        swimming.Swim();
    }
}
```

В записи также показана проверка самого поля напрямую. Обе формы спрашивают, существует ли способность, а не имеет ли животное определённый тип вида.

[00:11:39](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=699s) Сократите проверку с помощью **шаблона объявления**, который при успехе привязывает пригодную ссылку на модуль. Упрощённое переработанное состояние видео:

```csharp
if (animal.Swimming is SwimModule swimming)
{
    swimming.Swim();
}
```

[00:11:46](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=706s) Это похоже на более раннюю проверку подтипа, но входное поле уже имеет объявленный тип `SwimModule?`. Более узкого типа времени выполнения здесь искать нечего: для этого выражения успех означает лишь, что поле не равно null. Общий синтаксис позволяет проверять совместимость времени выполнения, когда входной тип менее конкретен.

[00:11:54](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=714s) Уберите повторяющийся тип модуля с помощью **пустого шаблона свойства** `{ }`. Этот **шаблон «не null»** соответствует имеющемуся значению и может привязать его к переменной. Упрощённая финальная проверка в записи:

```csharp
if (animal.Swimming is { } swimming)
{
    swimming.Swim();
}

// Проверка «не null» без захвата новой переменной:
if (animal.Swimming is not null)
{
    animal.Swimming.Swim();
}
```

Обе формы выражают проверку на отсутствие null, но только первая показанная форма привязывает `swimming`. Не объединяйте эти написания в `is not null swimming`. Пустой шаблон не запрашивает другой тип и не копирует объект модуля: его переменная хранит вычисленную ссылку на поле. См. объяснение [шаблонов свойств и позиций](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/patterns/property-positional-patterns) от Microsoft.

[00:12:11](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=731s) Преимущество в том, что клиент больше не называет вид и не повторяет конкретный тип модуля в своей проверке. Если объявленный тип поля изменится, но по-прежнему будет предоставлять нужную операцию, эта форма проверки на наличие может остаться прежней.

[00:12:32](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=752s) Плавание и полёт принадлежат отдельным **модулям**, а не типу птицы. Общий клиентский код может читать эти поля и использовать способности везде, где нужно. Это и есть выгода от повторного использования, которую следующий набросок с наследованием с трудом воспроизводит без повторяющихся реализаций или более сложной иерархии.

Как изменится цикл плавания, если добавить утку с обоими модулями?

<details>
<summary>Ответ</summary>
Цикл может остаться прежним. Он проверяет поле плавания у каждого Animal, поэтому модуль плавания утки вызывается так же, как у пингвина. Воробей с пустым полем плавания пропускается. Проверку типа Duck добавлять не нужно.
</details>

## Почему альтернатива с наследованием становится неудобной

[00:12:49](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=769s) Вернёмся к наследованию, чтобы показать давление проектирования. Пингвин плавает, воробей летает, а утке нужно и то и другое. Упрощённый набросок с наследованием из этого состояния видео:

```csharp
class Animal { }

class Penguin : Animal
{
    public void Swim() { }
}

class Sparrow : Animal
{
    public void Fly() { }
}

class Duck : Animal
{
    public void Swim() { } // повторяет операцию плавания
    public void Fly() { }  // повторяет операцию полёта
}
```

[00:13:01](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=781s) Обсуждение также рассматривает переопределение поведения. **Переопределение** заменяет соответствующую виртуальную реализацию базового класса, как в более ранней демонстрации диспетчеризации; приведённый выше набросок показывает только дублирование способностей и не утверждает, что его методы что-либо переопределяют. Пустые тела — это заглушки: реальное поведение может печатать сведения или вычислять данные, что делает дублирование дороже.

[00:13:20](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=800s) Один из возможных выходов — общая **статическая функция**, вызываемая методом каждого класса. Это позволяет централизовать реализацию, но тогда повторное использование идёт из обычного вызова помощника, а не из наследования этого поведения. Классы всё равно добавляют методы-переадресаторы; наследование даёт для такого повторного использования немного. Видео лишь набрасывает этот вариант, не доводя его до законченной схемы.

[00:13:34](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=814s) Ещё одна проблема — место вызова. Ссылка типа `Animal` не может вызвать `Swim` только потому, что `Penguin` и `Duck` объявляют его независимо: `Animal` должен предоставить подходящий общий член. Упрощённое не компилирующееся состояние места вызова:

```csharp
Animal animal = new Penguin();
// animal.Swim(); // недопустимо: Animal не объявляет член Swim
```

[00:14:05](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=845s) Чтобы унаследовать одну реализацию плавания, введите общий базовый класс плавания. Но утке также нужна общая реализация полёта. [00:14:29](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=869s) C# разрешает классу наследоваться только от **одного базового класса**, поэтому он не может просто унаследовать и класс плавания, и класс полёта. Попытки втиснуть каждую комбинацию способностей в иерархию классов приводят к накоплению похожих классов и дублирующегося кода. Это ограничение здесь иллюстрируется, а не утверждается, будто наследование никогда не позволяет повторно использовать код.

[00:14:44](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=884s) **Интерфейсы** — контракты, которые реализуют типы — отчасти позволяют выразить несколько способностей. В обсуждаемом подходе с контрактами интерфейсов каждому классу по-прежнему нужно предоставить реализацию или делегировать её общему коду; одно лишь объявление контракта не даёт двух нужных реализаций классов. Современный C# также поддерживает реализации интерфейсов по умолчанию, поэтому утверждение «интерфейсы никогда не могут содержать повторно используемые реализации» было бы слишком широким. Эта возможность **здесь не рассматривается**; её описывает [документация по наследованию](https://learn.microsoft.com/en-us/dotnet/csharp/tutorials/inheritance) от Microsoft.

Урок завершается компромиссом проектирования: держите общие данные животного в одном месте и собирайте независимые способности в композицию, когда их комбинации меняются. Подробный полиморфизм, полное проектирование интерфейсов и реализации интерфейсов по умолчанию остаются за рамками урока.

- [00:00:14](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=14s) Base/Derived начинается с унаследованного состояния и методов экземпляра.
- [00:00:57](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=57s) Методы становятся статическими; вызовы используют имена классов.
- [00:01:51](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=111s) Одноимённые методы вводят намеренное сокрытие с помощью `new`.
- [00:02:26](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=146s) Ссылки базового и производного типов показывают разный выбор невиртуальных членов.
- [00:03:33](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=213s) `virtual` и `override` заставляют оба вызова выбирать производную реализацию.
- [00:04:01](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=241s) Animal/Penguin/Sparrow вводит общий возраст и печать с отдельными умениями.
