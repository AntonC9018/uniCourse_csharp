# Encapsulation constructors and properties

[00:00:00](https://www.youtube.com/watch?v=IESVXL16OBA&t=0s) This lesson turns a combat character's freely writable health into state that can be changed through deliberate operations. Follow the changes from extracted methods, through private fields and constructors, to properties whose accessors control reading and writing. The final walkthrough explains how a new object receives its initial values.

The ideas and terms used below are:

- **Class, object, field, and method:** a class defines a type; an object is an instance of it; a field stores state; a method performs an operation. An instance method works on a particular object.
- **Parameter, argument, and `this`:** a parameter is a variable in a callable's declaration; an argument supplies its value at a call. `this` identifies the current object, acting as an implicit receiver for instance operations.
- **Refactoring and abstraction:** refactoring reorganizes code while preserving intended behavior; abstraction gives an operation a name so callers can work without repeating its implementation. A change made to illustrate an idea is not automatically a design improvement.
- **Contract or precondition:** an assumption that must hold when an operation starts, such as “the player is alive.” **Validation** checks whether a value satisfies a rule.
- **Assertion, Debug, and Release:** `Debug.Assert` checks an assumption during development. Debug builds normally include these calls; Release builds normally omit them.
- **Access modifier, `public`, `private`, and encapsulation:** access modifiers control where members are accessible. Public members are available to callers; private members are restricted to their declaring type. Encapsulation hides stored data behind controlled operations.
- **Object initializer and `required`:** an initializer assigns accessible members after creation; `required` demands caller initialization of a member. It does not grant access to a private member.
- **Factory function and constructor:** a factory is an ordinary function that returns an object; a constructor initializes a newly created object and uses the class name in its declaration. `new` creates and initializes an object.
- **Named argument:** an argument labeled with its parameter name, such as `health: 20`, so its meaning is visible without remembering its position.
- **Default value, `readonly`, and target-typed construction:** default values are the initial values of storage, here zero for integers. A readonly field can be initialized at its declaration or in the relevant constructor. Target-typed `new(...)` gets its type from the surrounding declaration.
- **Overload and overload resolution:** overloads offer different parameter lists for the same callable name; resolution selects an applicable overload from the supplied arguments.
- **Copy constructor, copy factory, and copy method:** three ways to make a new object from an existing object's values.
- **Getter, setter, and clamping:** a getter returns a stored value; a setter changes it and can validate it. Clamping replaces an out-of-range value with a boundary, such as replacing negative health with zero.
- **Property and accessor:** a property is a named member whose `get` and `set` accessors perform reading and writing with field-like call syntax.
- **Auto property and backing field:** an auto property has bodyless accessors; the compiler provides its hidden storage, called a backing field. Explicit accessors can use a field you declare.
- **`value`, PascalCase, and underscore naming:** `value` is the implicit parameter of a property setter. PascalCase starts words with capitals, as in `Health`; private fields conventionally use a leading underscore, as in `_health`.
- **Reference, dynamic memory, and temporary stack storage:** a reference identifies an object; the lesson draws the object in dynamic memory and parameters in temporary memory to distinguish their lifetimes. The drawn numeric addresses are explanatory labels, not addresses a normal C# reference exposes.

```csharp
}
```

Clamping changes the incoming parameter before storing it. Validation rejects or diagnoses bad values; clamping accepts a corrected boundary value. They express different policies. Assertions alone do not enforce rejection in a normal Release build.

## Bind reading and writing into a property

[00:18:29](https://www.youtube.com/watch?v=IESVXL16OBA&t=1109s) A **property** binds related read and write operations under one member name. Its **accessors**, `get` and `set`, are method-like operations, while callers use field-like syntax. At [00:18:43](https://www.youtube.com/watch?v=IESVXL16OBA&t=1123s), the recording introduces this common C# syntax: braces after a member's type and name contain its permitted operations. It resembles a field declaration, but it declares a property.

At [00:18:53](https://www.youtube.com/watch?v=IESVXL16OBA&t=1133s), choose an externally readable property with writing restricted to the class. At [00:19:04](https://www.youtube.com/watch?v=IESVXL16OBA&t=1144s), make the property's read access public. At [00:19:12](https://www.youtube.com/watch?v=IESVXL16OBA&t=1152s), the resulting permission split is:

```csharp
public int Health { get; private set; }

// Outside Stat:
Console.WriteLine(player.Health);
// player.Health = 0; // Not allowed: the setter is private.
```

The `public` modifier belongs on the property here; `get` inherits it, while `private set` is more restrictive. At [00:19:21](https://www.youtube.com/watch?v=IESVXL16OBA&t=1161s), accessors are full method-like operations and may have explicit bodies.

At [00:19:29](https://www.youtube.com/watch?v=IESVXL16OBA&t=1169s), distinguish names as the code grows: methods use **PascalCase**, such as `GetHealth`, and private storage conventionally uses a lowercase name with a leading underscore, such as `_health`. Properties commonly use PascalCase too. These conventions help readers recognize roles; they do not determine access permissions.

## Understand what an auto property generates

[00:19:41](https://www.youtube.com/watch?v=IESVXL16OBA&t=1181s) With an **auto property**, the bodyless `get;` and `set;` ask the compiler to supply the implementation and a hidden **backing field**, storage for the property's value. Update the damage operation to use the property:

```csharp
public int Health { get; private set; }

public void TakeDamage(int damage)
{
    Health = Health - damage;
}
```

At [00:19:58](https://www.youtube.com/watch?v=IESVXL16OBA&t=1198s) and [00:20:04](https://www.youtube.com/watch?v=IESVXL16OBA&t=1204s), the generated setter simply stores the supplied value. Replacing the earlier checked or clamping setter with this bodyless setter removes its custom logic. Auto properties do not automatically reproduce validation from a method that was deleted.

At [00:20:13](https://www.youtube.com/watch?v=IESVXL16OBA&t=1213s), the generated setter is private because `set` was declared private. At [00:20:17](https://www.youtube.com/watch?v=IESVXL16OBA&t=1217s), outside reading now uses `player.Health` rather than `player.GetHealth()`. The generated getter is an accessor, not a source method named `GetHealth`.

At [00:20:42](https://www.youtube.com/watch?v=IESVXL16OBA&t=1242s), the property's accessibility governs its accessor methods unless an accessor is made more restrictive. At [00:20:53](https://www.youtube.com/watch?v=IESVXL16OBA&t=1253s), the compiler-created backing field has a hidden name that this example cannot reference in normal source code. The visible member is the property.

<details>
<summary>Does a private auto-property setter guarantee nonnegative health?</summary>
No. It limits who may write, but an allowed internal assignment can still store a negative number. Keeping the earlier rule requires an explicit setter body or another checked operation.
</details>

## Expand accessors to restore validation

[00:21:04](https://www.youtube.com/watch?v=IESVXL16OBA&t=1264s) Instead of hidden auto-property storage, declare your own **backing field** and write explicit **accessor** bodies. At [00:21:18](https://www.youtube.com/watch?v=IESVXL16OBA&t=1278s) and [00:21:20](https://www.youtube.com/watch?v=IESVXL16OBA&t=1280s), expand `get` to return that field and `set` to assign it. At [00:21:25](https://www.youtube.com/watch?v=IESVXL16OBA&t=1285s), the setter's implicit parameter is named `value`: it is the incoming value, not the property's name. Simplified intermediate health reconstruction:

```csharp
private int _health;

public int Health
{
    get
    {
        return _health;
    }
    private set
    {
        _health = value;
    }
}

public void TakeDamage(int damage)
{
    Health = Health - damage;
}
```

At [00:21:33](https://www.youtube.com/watch?v=IESVXL16OBA&t=1293s), unpack the final assignment: its right side reads `Health` through `get`, subtracts damage, and its left side sends the result through `set` as `value`. Thus the accessors execute even though the call site looks like a field operation.

At [00:21:42](https://www.youtube.com/watch?v=IESVXL16OBA&t=1302s), restore validation in the setter and check `value`, which is the incoming parameter visible there. The change to that accessor is:

```csharp
private set
{
    Debug.Assert(value >= 0);
    _health = value;
}
```

Constructor assignment through `Health` can use the same setter; direct assignment to `_health` would bypass it.

A [related committed lab example](https://github.com/AntonC9018/uniCourse_csharp/blob/19d6c57ba17ef64ef9c65d22808e2c3f682768c2/labs/1_basic/17_encapsulation.md) likewise puts an assertion in a setter. This is supporting property syntax, not the exact combat source. Its simplified core is:

```csharp
set
{
    Debug.Assert(value != "");
    _nameInclude = value;
}
```

The committed lab snippet exposes its backing field publicly; that detail should not be copied when the aim is preventing bypass of the property.

At [00:21:50](https://www.youtube.com/watch?v=IESVXL16OBA&t=1310s), properties encapsulate field access and are preferred here to separate getter/setter methods because both operations share one property name. Whether you assert or clamp remains an explicit policy in the accessor.

## Distinguish fields parameters and properties

[00:22:02](https://www.youtube.com/watch?v=IESVXL16OBA&t=1322s) A leading underscore conventionally marks a private field. It distinguishes permanent storage from a similarly named parameter when the code is read in isolation. **PascalCase** capitalizes each word's start; a property such as `Health` and a method such as `GetHealth` use that style. A lowercase **parameter** such as `health` or the setter's special `value` represents incoming data.

Simplified naming version of the video's constructor and backing-field idea:

```csharp
private int _health;

public Stat(int attack, int health)
{
    Attack = attack;
    _health = health;
}
```

At [00:22:46](https://www.youtube.com/watch?v=IESVXL16OBA&t=1366s), naming is a cue to meaning. A PascalCase member may be a public field or a property; capitalization alone cannot establish which it is. The assignment above makes the roles explicit: `health` is the temporary input and `_health` is the object's storage. It illustrates naming, not validation; using `Health = health` would route initialization through the property setter.

## Keep usage syntax while adding abstraction

[00:22:53](https://www.youtube.com/watch?v=IESVXL16OBA&t=1373s) The lesson discourages public fields in classes whose state is encapsulated, while acknowledging that replacing an unrestricted public field with a trivial unrestricted property may add no immediate validation or behavior. Both choices can work at this introductory stage.

At [00:23:07](https://www.youtube.com/watch?v=IESVXL16OBA&t=1387s), a field can later become a property with added logic while preserving ordinary read/assignment syntax. Simplified successive declarations and unchanged caller:

```csharp
// Earlier member:
public int Attack;

// Alternative later member:
public int Attack { get; set; }

// Ordinary usage in either version:
enemy.Attack = 7;
Console.WriteLine(enemy.Attack);
```

These are alternative declarations, not two members to declare together. Keeping the same name lets the ordinary source usage shown here stay the same; this is not a claim that every use of fields and properties is interchangeable.

At [00:23:27](https://www.youtube.com/watch?v=IESVXL16OBA&t=1407s) and [00:23:48](https://www.youtube.com/watch?v=IESVXL16OBA&t=1428s), the concrete advantages of fields versus properties are explicitly deferred because it is too early for that comparison. At [00:24:06](https://www.youtube.com/watch?v=IESVXL16OBA&t=1446s), using a property adds an abstraction boundary: reading invokes a getter instead of exposing storage directly. At [00:24:22](https://www.youtube.com/watch?v=IESVXL16OBA&t=1462s), the simple call-site syntax does not show whether the member is a field or a property. This is the scope of the equivalence demonstrated here.

## Trace allocation and constructor arguments

[00:24:35](https://www.youtube.com/watch?v=IESVXL16OBA&t=1475s) Finish with a small constructor walkthrough. A **reference** identifies an object; the recording depicts objects in **dynamic memory** and parameters in **temporary stack storage** to explain which values survive the call. Treat this as a conceptual storage model, not a guarantee of the runtime's exact physical layout.

Simplified video-state reconstruction:

```csharp
class Test
{
    private int data1;
    private int data2;

    public Test(int data1, int data2)
    {
        this.data1 = data1;
        this.data2 = data2;
    }
}

Test t = new Test(data1: 1, data2: 3);
```

Follow the construction in order:

1. At [00:24:35](https://www.youtube.com/watch?v=IESVXL16OBA&t=1475s), the declaration introduces local variable `t`. Before its initializer completes, it is not yet assigned a usable reference.
2. At [00:24:59](https://www.youtube.com/watch?v=IESVXL16OBA&t=1499s), allocate the new object. Its declared integer fields initially contain their default values, zero.
3. At [00:25:08](https://www.youtube.com/watch?v=IESVXL16OBA&t=1508s), the next operation is constructor initialization.
4. At [00:25:09](https://www.youtube.com/watch?v=IESVXL16OBA&t=1509s), account for three conceptual inputs: the hidden `this` receiver plus the two explicit data arguments. There are **two declared parameters**, not three explicit parameters.
5. At [00:25:18](https://www.youtube.com/watch?v=IESVXL16OBA&t=1518s), represent the receiver and each parameter as temporary storage cells. A parameter is a temporary input variable; a field is storage belonging to the object.
6. At [00:25:29](https://www.youtube.com/watch?v=IESVXL16OBA&t=1529s), distinguish names that look identical. In `this.data1 = data1;`, `this.data1` selects the object's field and unqualified `data1` selects the parameter because it shadows the field.
7. At [00:25:48](https://www.youtube.com/watch?v=IESVXL16OBA&t=1548s), give `this` the new object's reference. The receiver is implicit; callers do not write an extra explicit argument for it.
8. At [00:26:24](https://www.youtube.com/watch?v=IESVXL16OBA&t=1584s), the `new` expression's supplied values become the constructor's explicit parameters, ready for the first assignment.

The name-resolution correction matters: an unqualified `data1` does **not** select the field when a same-named parameter is in scope. Writing `data1 = data1;` would assign the parameter to itself and leave the field unchanged.

## Finish construction and retain the object reference

[00:26:33](https://www.youtube.com/watch?v=IESVXL16OBA&t=1593s) In the recording's address illustration, `this` contains an object reference labeled 8000. Follow that same object through the assignments:

1. At [00:26:33](https://www.youtube.com/watch?v=IESVXL16OBA&t=1593s), read the receiver held in `this`.
2. At [00:26:34](https://www.youtube.com/watch?v=IESVXL16OBA&t=1594s), use it to locate the object's `data1` field and copy the first parameter's value into that field.
3. At [00:26:34](https://www.youtube.com/watch?v=IESVXL16OBA&t=1594s), use the same receiver to locate `data2` and copy the second parameter's value there.
4. At [00:26:37](https://www.youtube.com/watch?v=IESVXL16OBA&t=1597s), after initialization completes, the `new` expression yields the new object's reference.
5. At [00:26:42](https://www.youtube.com/watch?v=IESVXL16OBA&t=1602s), store that reference in `t`.
6. At [00:26:45](https://www.youtube.com/watch?v=IESVXL16OBA&t=1605s), the temporary parameter storage is no longer needed; the initialized field values remain in the object.

Simplified result of the preceding constructor state:

```csharp
// Constructor body:
this.data1 = data1; // Field gets 1.
this.data2 = data2; // Field gets 3.

// When new Test(1, 3) finishes:
// t holds the reference to the initialized Test object.
```

At [00:26:38](https://www.youtube.com/watch?v=IESVXL16OBA&t=1598s), clarify the recording's remark about trying to return something: a C# constructor has no return type and cannot use `return expression;` to choose the result. The result of successful `new` is the created object reference, not a constructor return value.

The later spoken address label “88000” does not establish another allocation. The important relationship is that `this` during initialization and `t` afterwards identify the same newly created object. Numeric labels such as 8000 and 88000 are diagram shorthand, not literal values accessible through an ordinary managed reference.

“Temporary data is erased” describes the end of its role in the call. It is not a promise that bytes are securely wiped or that every parameter occupies a physical stack cell. The object keeps the copied integer fields independently of those temporary inputs.

<details>
<summary>Why do the fields survive after the constructor's parameters are gone?</summary>
The constructor copied the input values into the object's own storage. The local variable keeps a reference to that initialized object; the fields do not depend on the parameter variables continuing to exist.
</details>
