# Git: from a local folder to a merged GitHub change

This lesson builds a complete path from checking Git on Windows to recording local changes, recovering files, working on a separate branch, publishing to GitHub, merging a pull request, and bringing the result back to the computer. Follow the steps in order: each later operation depends on the state created earlier.

The vocabulary used along the way is:

- **Console / command / argument / option:** a console accepts text commands; a command requests an operation, an argument supplies a value such as a filename, and an option such as `--help` selects behavior. **HTML** is the web-document format used by the help page shown here.
- **Git / GitHub:** Git records project versions; GitHub hosts Git repositories online and provides collaboration features. A **repository** contains recorded project history. **Local** means on this computer; **remote** means another repository reached through a connection.
- **Working directory / .git:** the working directory holds the files you edit; the hidden `.git` directory holds the local repository's records and settings.
- **Commit / message / identifier:** a commit records a project state as a unit of changes, its message describes the work, and its identifier (hash) distinguishes that history entry. **History / log / pager:** history is the sequence of commits; `git log` displays it, sometimes through a pager that waits for navigation or exit.
- **Untracked / tracked / modified:** an untracked file is on disk but not tracked by Git; a tracked file has been added to Git's management; a modified file differs from its recorded or staged state.
- **Staging area / add:** the staging area holds the file versions prepared for the next commit; `git add` puts changes there. Staging and committing are separate actions.
- **Author identity / configuration scope:** a commit records an author name and email. Repository-local configuration applies to one project; `--global` configures defaults for the current user across repositories.
- **Source / compiler / executable:** source is readable program text; a compiler such as `g++` translates C++ source into an executable program. **Build output** is the generated result. **Architecture** describes the target computer's machine design; **binary machine code** is the executable representation. **Library functions** supply reusable functionality. Bytes and kilobytes (KB) measure file size.
- **.gitignore / rule / wildcard / extension:** `.gitignore` contains rules for ignoring untracked files. A wildcard such as `*` matches variable text; an extension is a filename ending such as `.exe`.
- **Diff / restore / checkout:** a diff shows differences between file states; restore puts working files back to a chosen recorded state; checkout selects a commit or branch state.
- **Branch / master / branch pointer / common commit:** a branch names a line of work, and its pointer identifies its current commit. `master` is the main branch name used in this recording. A common commit belongs to both branches' histories before they diverge.
- **Rebase / merge / squash:** rebase replays a branch's changes on an updated base; merge joins branch histories and can record a merge commit; squash combines several commits' changes into one resulting commit.
- **Pull request / source / target:** a pull request is a GitHub proposal to incorporate one branch into another. The source branch supplies the work; the target (base) branch receives it.
- **Remote name / origin / URL / HTTPS / SSH:** a remote name abbreviates a repository address, conventionally `origin` for the primary connection. A URL specifies that address. HTTPS and SSH are connection methods; the example starts with HTTPS.
- **Upstream / push / pull / authentication:** an upstream associates a local branch with its remote counterpart; push sends commits to a remote; pull retrieves and incorporates remote changes. Authentication authorizes access to a service and is separate from a commit's recorded author.

## Choose a branch-integration workflow

[00:25:01](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1501s) The instructor recommends keeping `master` as the main branch and making new changes on a separate working branch based on it.

[00:25:13](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1513s) A **pull request** is GitHub's proposal to incorporate a working branch into the main branch. It is a service feature, not a Git command. The **source** supplies changes; the **target**, also called the base branch, receives them.

[00:25:45](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1545s) A **merge** joins histories. The variant described here creates a separate **merge commit**, a history entry recording the join. [00:25:51](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1551s) Before that integration, the instructor recommends rebasing the working branch onto master. [00:26:06](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1566s) The stated reason is to simplify integration by first making the working base include master's changes. This describes the demonstrated workflow, not a guarantee that all future merges are conflict-free.

Simplified preparation sequence corresponding to that recommendation:

```cmd
git checkout experiment
git rebase master
```

[00:26:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1581s) **Squash** combines several commits' changes into one resulting commit. [00:26:34](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1594s) For example, adding a file in one commit and editing it in another can become a single history entry containing their combined result.
