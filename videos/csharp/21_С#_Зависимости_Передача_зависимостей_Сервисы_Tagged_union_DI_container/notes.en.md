# Purpose and terms

[00:00:26](https://www.youtube.com/watch?v=z5CUTiubzwU&t=26s) The purpose of this lesson is to make a program's **dependencies** visible: identify what a small item transformation needs, decide how to deliver it, and change the structure without losing the tested result. The route is deliberately incremental: inline rules, an extracted function, a configuration bundle, services, alternative behaviours, a closed union, and finally automatic dependency assembly. This is the simplest possible example; a later video addresses a harder, more realistic situation.

These terms will be used along the way:

- **Item, field, property, initializer, required, and float:** an item is a name-and-price input; a field stores data; a property exposes member access through accessors; an initializer assigns members during creation; required demands that a member be initialized; float is the single-precision number type used for prices.
- **Parameter, argument, signature, prototype, and context:** a parameter declares an input, an argument supplies its value, a signature describes a callable's input/output shape, a prototype declares that shape without a body, and context is the surrounding information needed to perform the operation.
- **Dependency, direct input, and configuration:** a dependency is something an operation needs; the direct input is the value processed in this particular call; configuration sets the rules governing processing. The lesson also distinguishes service dependencies.
- **List, dictionary, set, and fallback:** a list holds an ordered collection; a dictionary maps keys to values; a set supports membership checks; a fallback is the value used when a lookup has no entry.
- **Single responsibility, abstraction, encapsulation, and refactoring:** single responsibility assigns one coherent job to a component; abstraction exposes the useful contract; encapsulation hides representation or dependencies behind it; refactoring changes structure while preserving intended observable behaviour.
- **Nullable result and null:** a nullable item may be an item or null; null means that this transformation produced no item.
- **xUnit, Verify, snapshot, regression, async, and await:** xUnit runs tests; Verify compares serialized actual output with an approved snapshot, the saved expected result; a regression is an unintended behaviour change; async permits asynchronous waiting, and await waits for completion.
- **Service, constructor, private, readonly, and static:** a service joins an operation to its context at class level; a constructor initializes an instance; private hides a member from outside access; readonly restricts field reassignment; static belongs to a type rather than an instance.
- **Record struct:** a value type with compiler-generated data-oriented members; it is used as a concise configuration bundle here.
- **Delegate, method group, lambda, capture, slice, and pure function:** a delegate is a callable value with a declared signature; a method group names a compatible method; a lambda is an anonymous function; capture gives it access to surrounding variables; a slice selects part of a string or sequence; a pure function determines its answer from its inputs without external side effects.
- **Interface, implementation, polymorphism, and Strategy:** an interface specifies operations; an implementation supplies bodies; polymorphism lets the same call reach different implementations; Strategy chooses an operation by supplying an implementation.
- **Open hierarchy and closed hierarchy:** consumers can add implementations to an open hierarchy; a closed hierarchy enumerates the supported alternatives.
- **Tagged union, variant, dispatch, cast, type pattern, and dynamic:** a tagged union represents one selected alternative; each alternative is a variant; dispatch selects its operation; a cast recovers a known type; a type pattern tests and names a typed value; dynamic postpones member selection until runtime.
- **Class, struct, reference type, value type, stack, heap, and boxing:** a class is a reference type; a struct is a value type; references identify objects while values carry their contents; stack and heap describe storage; boxing copies a value into an object representation on the managed heap.
- **Dependency injection, inversion of control, and dependency inversion:** injection supplies dependencies from outside; inversion of control gives outside code responsibility for their selection and creation; dependency inversion expresses a dependency against an abstraction.
- **DI container, IoC container, service provider, and dependency graph:** DI and IoC container name the dependency-assembly mechanism; a provider is its built service-resolution object; a graph describes which objects require which other objects.
- **Service collection, registration, descriptor, factory, extension method, generic type argument, and builder:** the collection stores mutable registrations; a descriptor defines how a service type is supplied; a factory creates an instance; an extension method adds callable syntax to an existing type; a generic type argument selects a type in angle brackets; a builder turns configuration into a finished usable model.
- **Singleton, scope, and scoped lifetime:** a singleton registration reuses an instance within a provider; a scope groups one execution context; scoped services are reused within that scope.
- **Options, IOptions, IOptionsSnapshot, and pipeline:** Options groups related settings into a named type; IOptions is a typed wrapper for accessing options; IOptionsSnapshot supplies options cached for a scope; a pipeline is a sequence of processing steps.

## Build and dispatch a tagged union

[00:31:03](https://www.youtube.com/watch?v=z5CUTiubzwU&t=1863s) Create the union, called RemapNameStringUnion in the reconciled description and RemapNameService_TaggedUnion in the saved code. A **tagged union** represents exactly one of a fixed set of **variants**, the supported alternatives.

1. [00:31:11](https://www.youtube.com/watch?v=z5CUTiubzwU&t=1871s) Give it a constructor for each variant and storage for the selected implementation. A primitive design could have separate fields; the saved version uses one object field.
2. [00:31:21](https://www.youtube.com/watch?v=z5CUTiubzwU&t=1881s) Add **dispatch**, routing the call to the variant actually stored.
3. [00:31:38](https://www.youtube.com/watch?v=z5CUTiubzwU&t=1898s) Handle the first remapping variant.
4. [00:31:57](https://www.youtube.com/watch?v=z5CUTiubzwU&t=1917s) Handle the second.
5. [00:32:05](https://www.youtube.com/watch?v=z5CUTiubzwU&t=1925s) Treat the remaining branch as an impossible state, assuming construction supplied one of the supported non-null variants.
6. [00:32:22](https://www.youtube.com/watch?v=z5CUTiubzwU&t=1942s) Consider replacing typed dispatch with **dynamic**, member selection deferred until runtime. This transient alternative leaves the surrounding consumer unchanged.
7. [00:32:33](https://www.youtube.com/watch?v=z5CUTiubzwU&t=1953s) The union carries and forwards the alternatives; it does not define an additional remapping policy.

The [saved tagged-union implementation](https://github.com/AntonC9018/uniCourse_csharp/blob/9cabfb706383195f1b3b3dade007d2272c62f899/examples/dependencies_simplified/code/Code.cs) uses a struct and type patterns. The earlier class wrapper and dynamic edit are video states, not exact saved declarations. Simplified saved dispatch:

```csharp
public readonly struct RemapNameService_TaggedUnion
{
    private readonly object _impl;
    public RemapNameService_TaggedUnion(RemapNameService mapper)
        => _impl = mapper;
    public RemapNameService_TaggedUnion(RemapNameService_RemovePrefix prefix)
        => _impl = prefix;

    public string RemapName(string name)
    {
        if (_impl is RemapNameService a) return a.RemapName(name);
        if (_impl is RemapNameService_RemovePrefix b) return b.RemapName(name);
        throw new InvalidOperationException("Invalid union state");
    }
}

// Transient alternative from the recording, not the saved implementation:
// return ((dynamic)_impl).RemapName(name);
```

A **type pattern**, such as is RemapNameService a, checks the type and introduces a variable with that type. The runtime type acts as the tag here; there is no explicit integer tag. The sample throws in the fallback; the saved code calls Debug.Fail and returns null. Neither fallback creates a valid new variant.

The impossible-state argument only holds for valid populated construction. Null arguments and, once this is a struct, its default value can leave no usable variant. The lesson does not add complete validation for those cases.

Simplified raw forms beside that reference:

```csharp
// Separate optional arguments: the order also defines priority if both exist.
static string Remap(string name, Dictionary<string, string>? map, string? prefix)
{
    if (map != null) return map.GetValueOrDefault(name, name);
    if (prefix != null && name.StartsWith(prefix)) return name[prefix.Length..];
    return name;
}

// Schematic stored-dependency dispatch:
if (storedDependency is string)
{
    var prefix = (string)storedDependency;
    return name.StartsWith(prefix) ? name[prefix.Length..] : name;
}
if (storedDependency is Dictionary<string, string>)
{
    var map = (Dictionary<string, string>)storedDependency;
    return map.GetValueOrDefault(name, name);
}
```

These are alternative fragments, not one combined function. With separate optional arguments, “both present” and “neither present” need defined semantics. A union intends to express a one-of choice rather than those additional combinations. Casting a raw dependency also makes the consumer know its representation again.

## Reason about value types and allocations

[00:34:47](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2087s) The wrapper can become a **struct**, a value type, rather than a **class**, a reference type. A reference points to an object; a value occupies its containing storage.

1. [00:34:59](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2099s) The motivation is to avoid a separate wrapper allocation on the **heap**, managed object storage, and potentially keep a local value on the **stack**, execution-local storage.
2. [00:35:12](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2112s) Reference-type dependency objects still exist on the heap.
3. [00:35:18](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2118s) Converting an existing service reference to object does not box or duplicate the service; it already is a reference-type object.
4. [00:35:33](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2133s) A value-type dependency stored as object would be **boxed**, copied into a managed object representation.
5. [00:35:45](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2145s) Consider a separate typed union for the input dependencies instead of placing a value dependency into object.
6. [00:35:51](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2151s) Construct that dependency context together, passing the number/count value and an explicit null for an unused dependency. This avoids gathering its fields in separate steps.
7. [00:36:09](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2169s) Keeping a typed value context can avoid an additional context-wrapper object.
8. [00:36:26](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2186s) The principal design cost remains: the union must know every possible implementation.
9. [00:36:39](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2199s) With fixed closed alternatives and construction-time context, this can reduce allocation and improve speed. These are motivations, not measured benchmark results.

The [saved value-type union](https://github.com/AntonC9018/uniCourse_csharp/blob/9cabfb706383195f1b3b3dade007d2272c62f899/examples/dependencies_simplified/code/Code.cs) has an object field holding an already allocated service reference. ## Separate injection control and inversion

[00:38:26](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2306s) Move to automatic dependency injection, beginning with what injection itself means.

1. [00:38:44](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2324s) Simplify the item processor: remove its combined config layer and give each dependency its own field and constructor argument.
2. [00:39:03](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2343s) **Dependency injection** supplies an object's dependencies when it is created, most often through the constructor; other delivery methods are possible.
3. [00:39:19](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2359s) **Inversion of control** means the service does not construct its own dependencies internally.
4. [00:39:27](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2367s) The service's remapper, or hypothetical repository/client, arrives from outside.
5. [00:39:39](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2379s) The code using the service decides which configuration and dependencies to supply.
6. [00:39:51](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2391s) Injection is the act of passing them, together with that outside control over their creation.
7. [00:40:04](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2404s) **Dependency inversion** instead concerns the declared dependency type: use an abstraction, here an interface, rather than one concrete implementation.
8. [00:40:15](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2415s) A high-level service tied to a lower-level concrete class depends on that implementation choice.
9. [00:40:33](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2433s) Declare the dependency against the high-level contract; the consumer need not know how the lower-level implementation works.
10. [00:40:45](https://www.youtube.com/watch?v=z5CUTiubzwU&t=2445s) Lower-level implementations declare that they implement the contract and provide its operations.

The [saved constructor-injection state](https://github.com/AntonC9018/uniCourse_csharp/blob/53502e1527899ae9acf128bbbf3b0388948ec39a/examples/dependencies_simplified/code/Code.cs) has this simplified shape:

<details>
<summary>Which principle changes when you replace a concrete constructor parameter with an interface?</summary>

Dependency inversion changes the dependency contract. Supplying its value from outside is dependency injection; leaving construction and selection to outside code is inversion of control. These are related but distinct decisions.

</details>

The provider-resolved target is now registered, unlike the earlier CreateInstance-only demonstration. The factory still supplies the unregistered ignore set explicitly. Central assembly removes repeated wiring, while the consumer continues to declare what it actually needs.

```csharp
public class PriceCutoffConfig
{
    public required float MinPrice { get; set; }
    public required float MaxPrice { get; set; }
}

public class PriceCutoffService
{
    private readonly PriceCutoffConfig _config;
    public PriceCutoffService(PriceCutoffConfig config) => _config = config;
    public bool AllowsPrice(float price)
        => price > _config.MinPrice && price < _config.MaxPrice;
}

var config = new PriceCutoffConfig { MinPrice = 5, MaxPrice = 50 };
services.AddSingleton(config);
services.AddSingleton<PriceCutoffService>();
```

A **property** exposes access through get and set; these are the accessors in the config class. Its required properties must be initialized when it is created. The **initializer** supplies values in braces. The private readonly field keeps the same config reference, but the config's settable properties can still be changed.

**IOptions<T>** is a typed wrapper through which a consumer accesses options. The config object is not automatically such a wrapper. This step demonstrates that configuration can participate in constructor-based injection as a normal typed dependency.

## Override options within a pipeline scope

[00:53:43](https://www.youtube.com/watch?v=z5CUTiubzwU&t=3223s) Look at the accompanying application example. The saved application is in the lab5 example folder. A **pipeline** is a sequence of processing steps; here it reads items, transforms them, and writes the result.

1. [00:53:51](https://www.youtube.com/watch?v=z5CUTiubzwU&t=3231s) Create the pipeline and choose per-context configuration.
2. [00:54:04](https://www.youtube.com/watch?v=z5CUTiubzwU&t=3244s) Motivate **scoped** settings: different executions can use different chosen values instead of one fixed configuration for the entire program.
3. [00:54:12](https://www.youtube.com/watch?v=z5CUTiubzwU&t=3252s) Use **IOptionsSnapshot<T>**, an options accessor whose values are associated with and cached within a scope, rather than holding one global config value directly.
4. [00:54:27](https://www.youtube.com/watch?v=z5CUTiubzwU&t=3267s) Establish configuration again for a new invocation context.
5. [00:54:40](https://www.youtube.com/watch?v=z5CUTiubzwU&t=3280s) Outside code can obtain the configurable object and set its values before use.
6. [00:55:04](https://www.youtube.com/watch?v=z5CUTiubzwU&t=3304s) The operation then sees the new value instead of the original default, allowing a programmatic override on the fly.

The [saved pipeline application](https://github.com/AntonC9018/uniCourse_csharp/blob/d80428c0f252c626af6927783c16b777dc7f1425/examples/lab5_example/Program.cs) creates a new asynchronous scope for each Run. The [saved builder](https://github.com/AntonC9018/uniCourse_csharp/blob/7f31c6acd0e759a957c51c40ddb9031b1399d17d/examples/lab5_example/Orchestration/OrchestrationBuilder.cs) resolves the options snapshot, invokes the configuration callback on its value, and subsequently creates the reader through its factory. Simplified version of that shared context:

```csharp
services.AddOptions<RandomReaderFactoryOptions>()
    .Configure(options => options.GeneratedCount = 3);

await using var serviceProvider = services.BuildServiceProvider();
await using var scope = serviceProvider.CreateAsyncScope();

var snapshot = scope.ServiceProvider
    .GetRequiredService<IOptionsSnapshot<RandomReaderFactoryOptions>>();
snapshot.Value.GeneratedCount = 10;

// A reader factory using this scope's options sees the updated value.
```

**async** and **await** support asynchronous completion; await using disposes the provider and scope through their asynchronous disposal support. A **scope** is one execution context, and **scoped lifetime** means reuse within it. The builder's caller chooses options before the reader is created, while the consumer receives options through the container.

Scoped lifetime alone does not reload or mutate configuration. IOptionsSnapshot caches an options value within a scope; it does not recompute a fresh object on every read in that same scope. The demonstration chooses a new value for a context, rather than implementing configuration-file reload infrastructure. The [related saved reader/writer factories](https://github.com/AntonC9018/uniCourse_csharp/blob/306f4dda13a4582f96ba2d76c3c130728a064df4/examples/lab5_example/ReaderWriter/Factories.cs) separate settings for different operations. The random-reader factory reads its scope's options when it creates the reader; simplified excerpt:

```csharp
var count = _count.Value.GeneratedCount;
return new RandomReader(count, _generators);
```

Independent pipeline executions therefore need not share one mutable global choice.
