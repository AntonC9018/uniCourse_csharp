The vocabulary needed for that journey is:

- **Coordinate, axis, and coordinate pair:** a coordinate measures position along an axis; X and Y describe the horizontal and vertical directions. A pair is written `(X, Y)`.
- **Grid cell and grid distance:** a cell is one square of the board. Here distance counts horizontal steps plus vertical steps, without diagonal movement.
- **Absolute value:** a number's nonnegative magnitude. C# writes this operation as `Math.Abs`; both `-1` and `1` have magnitude `1`.
- **Variable, type, and memory cell:** a variable names storage for a value of a specified type. `int` is the integer type used here. A cell is the recording's simplified drawing of that storage.
- **Declaration, initialization, and assignment:** a declaration introduces a variable; initialization gives it its initial value; assignment evaluates the right-hand expression and copies its result into the storage on the left. A local declared without an initializer must receive a value before it is read.
- **Expression and value:** an expression is code that computes a result; its value is that result, such as the number produced by a subtraction or a function call.
- **Local and temporary variables:** a local belongs to the executing function or block. A temporary holds an intermediate result.
- **Block, braces, scope, and lifetime:** braces `{ }` enclose a block. Scope determines where a name can be used; lifetime describes how long its variable exists. The lesson connects these through block-local variables.
- **Function or method, definition, body, and call:** a function is reusable named code; its definition describes its inputs and instructions, its body contains those instructions, and a call runs them. The caller invokes it; the callee is the function being invoked.
- **Parameter and argument:** a parameter is an input variable in the function definition. An argument is the expression supplied at a call, whose value is used for that parameter.
- **Return value, return type, `return`, and `void`:** the return value is a result delivered by a call; the return type states its type. `return` ends the current function and can supply that result. `void` declares that no result value is returned.
- **Function header and signature:** the header states the function's modifiers, return type, name, and parameters. The lesson reads this interface as a signature; in precise C# terminology, the return type is not part of the method signature.
- **`static`:** for the local function used here, this modifier prevents capturing surrounding local variables. It keeps the calculation dependent on explicit inputs.
- **Stack and call frame:** the stack is the temporary-memory model used in the recording. A call frame contains the working storage associated with one function invocation, including parameters and locals.
- **Refactoring:** changing code organization while preserving its intended behavior. A correction to a wrong coordinate choice is a separate change to what is calculated.
- **User-defined type, `struct`, and value type:** a user-defined type gives a name and structure to data. A `struct` is a value type: its variable contains the value itself, including its fields.
- **Field, `public`, and dot operator:** a field is a named part of a type's data. `public` makes the fields accessible to the surrounding example code; the dot in `player.X` selects a field of a particular value or object.
- **`new` and object initializer:** `new Position { X = 2, Y = 3 }` creates a position and sets its named fields. These initializer braces serve a different purpose from braces around a statement block.
- **Pass by value and side effect:** ordinary arguments are copied into parameters. A side effect is an observable change outside the function, such as changing the caller's coordinates.
- **`ref`, alias, and address:** `ref` makes a parameter an alias for the caller's storage rather than an independent copy. An address identifies a storage location; the recording uses addresses to explain aliases.
- **`out`:** a related parameter mode through which a function initializes caller-provided storage. It is useful for distinguishing a result written through a parameter from a result returned by a call; the distance trace here follows `return`.
- **`class`, instance, reference type, reference, and heap:** a class is a reference type. Its instance is an object; a variable holds a reference to that object rather than the fields directly. The heap is the dynamic-memory area used for these objects in the lesson's model.
- **Related example only — Euclidean distance, square root, `float`, and `record struct`:** Euclidean distance measures straight-line separation. `Math.Sqrt` computes a square root; `float` stores floating-point numbers; the related file's `record struct` is shorthand for declaring a value type with named coordinate components. ## Returning a value to the caller

[00:19:06](https://www.youtube.com/watch?v=z51K0UhriOk&t=1146s) **`return`** ends the callee's current execution and resumes the caller at the invocation. It does not continue into another unrelated statement in the callee.

[00:19:33](https://www.youtube.com/watch?v=z51K0UhriOk&t=1173s) The control flow is the same as a parameterless call: the caller resumes after the invoked operation. A result-bearing call also supplies a value.

The returned-value transfer in the video can be summarized with this small sample:

```csharp
int distanceToEnemy = Distance(2, 3, 1, 1);
Console.WriteLine(distanceToEnemy); // 3

// At the end of Distance:
// return dist;  // dist holds 3
```

[00:19:47](https://www.youtube.com/watch?v=z51K0UhriOk&t=1187s) **Assignment** copies the right-hand value into the left-hand variable. Here the entire call is the right-hand expression.

Trace the transfer:

1. [00:19:59](https://www.youtube.com/watch?v=z51K0UhriOk&t=1199s) Read the callee's `dist`, which contains `3`.
2. [00:20:08](https://www.youtube.com/watch?v=z51K0UhriOk&t=1208s) Make `3` the value of the call expression.
3. [00:20:25](https://www.youtube.com/watch?v=z51K0UhriOk&t=1225s) Complete the caller's assignment by storing that value in `distanceToEnemy`.

No caller variable becomes another name for the callee's `dist`. The caller receives the value, not access to that temporary.

[00:20:44](https://www.youtube.com/watch?v=z51K0UhriOk&t=1244s) Continue with the caller's next statement, following the call. “After the function” here means after its invocation, not executing source lines merely because they happen to be written below its definition.

[00:20:52](https://www.youtube.com/watch?v=z51K0UhriOk&t=1252s) The completed callee no longer has a live call frame. Its parameters and locals cease to be available.

[00:21:03](https://www.youtube.com/watch?v=z51K0UhriOk&t=1263s) Code outside the callee cannot read those ended parameter or temporary variables. This does not require their old bytes to be erased.

[00:21:07](https://www.youtube.com/watch?v=z51K0UhriOk&t=1267s) The caller's original coordinates remain accessible: they belonged to the caller before the call began and were not consumed by it.

[00:21:14](https://www.youtube.com/watch?v=z51K0UhriOk&t=1274s) The next print reads the returned result from the caller's result variable.

<details>
<summary>Why does the answer survive when the callee's locals disappear?</summary>

The result was copied into a caller-owned variable before the callee's working storage ended. That caller variable has its own lifetime. It does not depend on being able to read the old callee frame.

</details>

## Why four integers invite mistakes

[00:22:49](https://www.youtube.com/watch?v=z51K0UhriOk&t=1369s) The shared function removes repetition but exposes a new problem. All four parameters have type `int`, so many wrong argument permutations remain valid C#.

[00:23:00](https://www.youtube.com/watch?v=z51K0UhriOk&t=1380s) The intended order is X and Y of the first object, then X and Y of the second. Accidentally listing both X coordinates before both Y coordinates can compile yet measure invented positions.

A simplified example of the video problem is:

```csharp
int correct = Distance(2, 3, 1, 1); // (2, 3) against (1, 1): 3
int mixed = Distance(2, 1, 3, 1);   // invented (2, 1) against (3, 1): 1
```

[00:23:22](https://www.youtube.com/watch?v=z51K0UhriOk&t=1402s) The parameter order is not self-evident from a list of plain integers. Group the X and Y belonging to one object into one value, so the call supplies two positions rather than four interchangeable numbers.

[00:23:24](https://www.youtube.com/watch?v=z51K0UhriOk&t=1404s) That requires a small **user-defined type**, a named data shape created for this program. Its role is to represent a complete position.

<details>
<summary>Why can the compiler accept the mixed call?</summary>

Every argument is an integer, which matches every parameter's declared type. The compiler checks those types; it does not know that the second integer was meant to be another object's X. A position type records the pairing in the interface.

</details>

## Creating a Position value with fields

[00:23:45](https://www.youtube.com/watch?v=z51K0UhriOk&t=1425s) Declare a **struct**, a user-defined value type. A **value type** contains its data directly in its variable's storage. Here that data is two integers describing one position.

[00:24:08](https://www.youtube.com/watch?v=z51K0UhriOk&t=1448s) Use `Position` where a variable declaration previously used `int`. The type now describes a pair, so one variable can carry both coordinates.

[00:24:25](https://www.youtube.com/watch?v=z51K0UhriOk&t=1465s) Keep the type declaration at the end of the file in this single-file, top-level program. The reason is the ordering rule for top-level statements: the executable statements precede type declarations. C# can also define the type in another source file; the restriction is not that only this file can contain a type.

[00:24:40](https://www.youtube.com/watch?v=z51K0UhriOk&t=1480s) Initialize a position with `new Position { X = 2, Y = 3 }`. The **object initializer** assigns values to named fields, so the pairing is explicit. The recording adjusts example values while introducing the notation; keep the enemy's `(2, 3)` and player's `(1, 1)` distinct.

Reconstructed video syntax:

```csharp

// Type declarations follow the top-level statements:

{

```

**`public`** allows the surrounding example to access these fields. **`new`** here creates a struct value; the spelling alone does not mean it must allocate a separate heap object.

[00:25:02](https://www.youtube.com/watch?v=z51K0UhriOk&t=1502s) The memory picture changes from unrelated coordinate cells to one larger block for a position. Inside that block are two smaller integer cells, one for X and one for Y.

[00:25:27](https://www.youtube.com/watch?v=z51K0UhriOk&t=1527s) Those named parts are **fields**. The variable's name identifies the complete value, while field names identify its components.

[00:25:55](https://www.youtube.com/watch?v=z51K0UhriOk&t=1555s) The **dot operator** selects a component of a particular variable. `player.X` reads the X field of `player`; `enemy.X` reads the X field of the other position. Bare `X` does not select which position is intended.

The struct is inline storage for this pair. In these local examples the drawing places it in temporary memory; value types are not universally restricted to the stack. Their essential property here is that a normal copy copies their value rather than sharing a separate position object.

## Reading changing and separating position fields

[00:26:15](https://www.youtube.com/watch?v=z51K0UhriOk&t=1575s) **Assignment** reads the right-hand value and copies it into the left-hand storage. Read a field into a separate integer local and the new local receives that field's current value.

[00:26:43](https://www.youtube.com/watch?v=z51K0UhriOk&t=1603s) A field can also be the assignment target. Writing `player.Y = 7` replaces that particular stored coordinate.

A simplified video field demonstration is:

```csharp
Position player = new Position { X = 1, Y = 2 };
int savedY = player.Y; // copy 2 into a separate local
player.Y = 7;         // change the field, not savedY
Console.WriteLine(savedY);  // 2
Console.WriteLine(player.Y); // 7
```

These temporary demonstration coordinates explain field copying; later distance traces return to player `(1, 1)`.

[00:27:01](https://www.youtube.com/watch?v=z51K0UhriOk&t=1621s) Reuse the `Position` type to declare an enemy, with its own `X = 2` and `Y = 3`. Reusing a type does not reuse the first variable's storage.

[00:27:15](https://www.youtube.com/watch?v=z51K0UhriOk&t=1635s) Two positions contain four integer fields in total. Each variable has its own pair.

[00:27:32](https://www.youtube.com/watch?v=z51K0UhriOk&t=1652s) Their independence matters: changing `player.Y` does not change `enemy.Y`. They live in separate position values.

[00:27:45](https://www.youtube.com/watch?v=z51K0UhriOk&t=1665s) Grouping makes each X/Y pair one block. At [00:27:50](https://www.youtube.com/watch?v=z51K0UhriOk&t=1670s), the diagram names its components using the whole variable's name followed by a dot and field name, such as `player.X` and `player.Y`.

[00:28:10](https://www.youtube.com/watch?v=z51K0UhriOk&t=1690s) This is an intermediate state, not the finished interface improvement. The coordinates have been grouped in the variables, but the old function can still be called by extracting all four fields.

The data is now grouped, but the call still permits misordering four integers. The next change must group the parameters as well.

## Grouping the parameters too

[00:28:14](https://www.youtube.com/watch?v=z51K0UhriOk&t=1694s) The next intended change is to replace separate integer coordinate parameters with position parameters. The saved transcript reaches the actual header edit around [00:28:41](https://www.youtube.com/watch?v=z51K0UhriOk&t=1721s).

[00:28:18](https://www.youtube.com/watch?v=z51K0UhriOk&t=1698s) A **parameter** is a variable declared by the function to receive an input. With type `Position`, that one parameter contains X and Y together rather than a single integer.

[00:28:24](https://www.youtube.com/watch?v=z51K0UhriOk&t=1704s) The caller will pass the whole position value. The completed call-site change is described around [00:29:07](https://www.youtube.com/watch?v=z51K0UhriOk&t=1747s): pass `enemy` and `player`, not each field separately.

Reconstructed grouped video state:

```csharp
int distanceToEnemy = Distance(enemy, player);

static int Distance(Position a, Position b)
{
    int x_dist = Math.Abs(a.X - b.X);
    int y_dist = Math.Abs(a.Y - b.Y);
    int dist = x_dist + y_dist;
    return dist;
}
```

The **dot operator** now selects fields from parameter `a` or parameter `b`. The arithmetic still compares like axes, but the function header expresses two positions rather than four unrelated numbers.

For comparison, the inspected repository has a [related two-position distance function](https://github.com/AntonC9018/uniCourse_csharp/blob/d5af1fb372be56a453e3b139990013c28e50198c/examples/property_dict/Subclassing.cs). This immutable file is not an exact video state: it uses floating-point coordinates and Euclidean distance, while the recording counts grid steps. Simplified sample of that related implementation:

```csharp
record struct Position(float X, float Y);

static float Distance(Position a, Position b)
{
    float dx = a.X - b.X;
    float dy = a.Y - b.Y;
    return (float)Math.Sqrt(dx * dx + dy * dy);
}
```

The shared idea is passing two complete positions to one function. Do not replace the video's absolute-value sum with this different formula. The related file's `record struct` shorthand and `float` arithmetic are not taught in this video: they are shown only to identify the repository example accurately.

[00:29:34](https://www.youtube.com/watch?v=z51K0UhriOk&t=1774s) A `Position` parameter has two integer components. The diagram draws a larger cell for the complete parameter and sub-cells for its fields.

[00:29:52](https://www.youtube.com/watch?v=z51K0UhriOk&t=1792s) An `int` needs one integer cell in this teaching model. At [00:29:59](https://www.youtube.com/watch?v=z51K0UhriOk&t=1799s), a position needs two because its type contains two integer fields. [00:30:06](https://www.youtube.com/watch?v=z51K0UhriOk&t=1806s) The enemy value is initialized with X = `2` and Y = `3`.

## Computing and returning the grouped distance

[00:31:37](https://www.youtube.com/watch?v=z51K0UhriOk&t=1897s) With the grouped inputs established, the function reads `a.X` and `b.X` and computes their absolute difference.

## Changing a struct parameter changes its copy

[00:32:29](https://www.youtube.com/watch?v=z51K0UhriOk&t=1949s) Now predict what happens if the body assigns `a.X = 5`. Does the original enemy change?

The video modification can be isolated in a simplified helper:

```csharp
Position enemy = new Position { X = 2, Y = 3 };
ChangeCopy(enemy);
Console.WriteLine(enemy.X); // still 2

static void ChangeCopy(Position a)
{
    a.X = 5;
}
```

**`void`** means this illustrative helper produces no return value. The point of the sample is the same parameter mutation explored inside the recorded function.

Walk through the memory again:

1. [00:32:33](https://www.youtube.com/watch?v=z51K0UhriOk&t=1953s) Create fresh storage for parameter `a` and copy the caller's X and Y into it.
2. [00:32:39](https://www.youtube.com/watch?v=z51K0UhriOk&t=1959s) In the two-position function, create `b` and copy its fields too.
3. [00:32:42](https://www.youtube.com/watch?v=z51K0UhriOk&t=1962s) Resolve `a.X = 5` to the field in the callee's parameter value.
4. [00:32:52](https://www.youtube.com/watch?v=z51K0UhriOk&t=1972s) Replace that copied field without changing where the caller's position is stored.
5. [00:33:03](https://www.youtube.com/watch?v=z51K0UhriOk&t=1983s) Finish the call; the original position was never overwritten.

[00:33:16](https://www.youtube.com/watch?v=z51K0UhriOk&t=1996s) This field write has no **side effect** on the caller's original position. A side effect would be an observable change outside the function; here only the local copy changed. This does not say that every function accepting a struct is incapable of other side effects.

[00:33:21](https://www.youtube.com/watch?v=z51K0UhriOk&t=2001s) The rule is **pass by value**: ordinary arguments initialize independent parameter variables by copying what their argument variables hold. For this struct, that is the X/Y pair itself.

<summary>Would naming the parameter enemy instead of a make the caller change?</summary>

No. The parameter would still be a separate variable initialized from the argument's value. Names do not turn a copy into shared storage.

</details>

## Using ref as an alias

[00:33:27](https://www.youtube.com/watch?v=z51K0UhriOk&t=2007s) The lesson introduces a related feature as an idea, with an explicit boundary: it is probably unnecessary for the lab work at this stage.

[00:33:33](https://www.youtube.com/watch?v=z51K0UhriOk&t=2013s) A value-type argument can instead be passed by reference using **`ref`**. Add the keyword to the parameter declaration and to the argument at the call.

[00:33:37](https://www.youtube.com/watch?v=z51K0UhriOk&t=2017s) A **ref parameter** is an **alias**, another way to access the caller's existing storage. Its field writes can therefore change the original position instead of a copied pair.

Simplified illustration of the video mechanism:

```csharp
Position enemy = new Position { X = 2, Y = 3 };
ChangeOriginal(ref enemy);
Console.WriteLine(enemy.X); // 5

static void ChangeOriginal(ref Position a)
{
    a.X = 5;
}
```

[00:33:57](https://www.youtube.com/watch?v=z51K0UhriOk&t=2037s) This time the write reaches the caller's variable. That change is the purpose of using `ref`; it is not a failure of the ordinary copying rule.

[00:34:08](https://www.youtube.com/watch?v=z51K0UhriOk&t=2048s) An **address** identifies a storage location. The recording explains `ref` as carrying the address of the existing variable instead of copying its X/Y contents. It is a pointer-like mental picture of an alias, not a lesson in raw pointer syntax.

[00:34:15](https://www.youtube.com/watch?v=z51K0UhriOk&t=2055s) Both names access one location. The callee's `a.X` selects the caller's original X field through that alias.

[00:34:29](https://www.youtube.com/watch?v=z51K0UhriOk&t=2069s) At the call, `ref enemy` requests this connection to the variable's storage rather than passing an ordinary value copy. The parameter and call-site keywords must agree.

[00:34:34](https://www.youtube.com/watch?v=z51K0UhriOk&t=2074s) The feature is advanced for the current course stage and is not expected in the lab yet. Around [00:34:48](https://www.youtube.com/watch?v=z51K0UhriOk&t=2088s), the recording reiterates that boundary before moving to classes.

<details>
<summary>What changed between ChangeCopy(enemy) and ChangeOriginal(ref enemy)?</summary>

The first initializes a separate position parameter from a copied value. The second aliases the caller's position variable. The assignment looks similar, but its target storage is different.

</details>

## Changing Position from a struct to a class

[00:34:40](https://www.youtube.com/watch?v=z51K0UhriOk&t=2080s) The next comparison changes the position type from a struct to a **class**. The usage can look almost identical while the memory representation changes.

[00:35:06](https://www.youtube.com/watch?v=z51K0UhriOk&t=2106s) A **class instance** is an object represented through a reference. Its fields occupy dynamic memory in the lesson's **heap** model.

[00:35:15](https://www.youtube.com/watch?v=z51K0UhriOk&t=2115s) A class is a **reference type**: a variable holds a reference to its object, rather than the coordinate fields inline. This contrasts with the earlier **value type**, whose variable held the X/Y pair.

[00:35:21](https://www.youtube.com/watch?v=z51K0UhriOk&t=2121s) Draw one temporary cell for the variable's reference and a separate object containing the fields. The line connecting them means the reference identifies that object.

[00:35:30](https://www.youtube.com/watch?v=z51K0UhriOk&t=2130s) The variable thus contains a link, not the two coordinates themselves.

[00:35:41](https://www.youtube.com/watch?v=z51K0UhriOk&t=2141s) The class demonstration gives both fields initial values of `1`. These are the defaults chosen in the example, not the built-in default value of every integer field; an integer field with no initializer defaults to `0`.

Simplified class version of the video illustration:

```csharp
Position enemy = new Position();
Position player = new Position();
Position tree = new Position();

class Position
{
    public int X = 1;
    public int Y = 1;
}
```

[00:35:59](https://www.youtube.com/watch?v=z51K0UhriOk&t=2159s) Store the reference to the enemy object in its local variable. The drawn address identifies where that object's fields are reached.

[00:36:04](https://www.youtube.com/watch?v=z51K0UhriOk&t=2164s) The player receives a separately created object with its own X/Y fields. Its address differs even though its initial field values also happen to be `1`.

[00:36:21](https://www.youtube.com/watch?v=z51K0UhriOk&t=2181s) The player's temporary cell contains its own object's reference.

[00:36:28](https://www.youtube.com/watch?v=z51K0UhriOk&t=2188s) Creating the tree follows the same pattern: another variable holding a reference to another object.

The reconstructed memory model is:

```text
temporary variables              dynamic objects
enemy  : reference E  -------->   E: X=1, Y=1
player : reference P  -------->   P: X=1, Y=1
tree   : reference T  -------->   T: X=1, Y=1
```

The class change replaces inline coordinate values with links to separate objects. It does not make all three objects one shared position.

## Copying a reference and reaching the same object

[00:36:45](https://www.youtube.com/watch?v=z51K0UhriOk&t=2205s) Calling the function still establishes a frame for its parameters and locals. A class parameter does not remove that temporary working storage.

[00:36:52](https://www.youtube.com/watch?v=z51K0UhriOk&t=2212s) The difference is what the parameter contains: a **reference** identifies an object. Copying the class argument copies that reference, not every coordinate field.

[00:37:11](https://www.youtube.com/watch?v=z51K0UhriOk&t=2231s) The callee can follow the copied reference to the existing heap object and update its fields.

The recorded class mutation, simplified with consistent names, is:

```csharp
Position enemy = new Position(); // fields start at 1
ChangeObject(enemy);
Console.WriteLine(enemy.X); // now 7

static void ChangeObject(Position a)
{
    a.X = 7;
}

// Position is the class declared in the preceding example.
```

[00:37:32](https://www.youtube.com/watch?v=z51K0UhriOk&t=2252s) Here `a.X` means the X field in the referenced object. It is not the field of an independently copied struct. This behavior does not require adding the `ref` keyword: a normal class parameter receives a copy of an object reference. Do not conflate it with the earlier ref alias to a value-type variable.

[00:37:41](https://www.youtube.com/watch?v=z51K0UhriOk&t=2261s) The diagram illustrates the object at address `64`. Following the reference reaches the X field there, and the write changes that field to `7`. The address is an explanatory example, not an address that C# guarantees for this object.

[00:37:58](https://www.youtube.com/watch?v=z51K0UhriOk&t=2278s) The caller's reference and the parameter's copied reference identify the same object. Only the reference was copied, so both see that changed X.

[00:38:11](https://www.youtube.com/watch?v=z51K0UhriOk&t=2291s) Reading the caller's field after the write observes the updated object. The parameter's local storage can end without undoing a write into that shared object.

[00:38:22](https://www.youtube.com/watch?v=z51K0UhriOk&t=2302s) Replacing this class with the earlier struct would change the outcome: ordinary parameter passing would copy the fields, and the mutation would affect only the callee's copy. The written field-access syntax alone does not tell you whether storage is shared; the type and parameter mode do.

[00:38:51](https://www.youtube.com/watch?v=z51K0UhriOk&t=2331s) This distinction makes later language abstractions easier to reason about. First ask what the variable contains, then what is copied, then where a write goes.

[00:39:06](https://www.youtube.com/watch?v=z51K0UhriOk&t=2346s) The closing rule should be read as **ordinary C# parameters pass by value**:

- For a value-type position, the copied value contains the coordinate fields.
- For a reference-type position, the copied value is a reference to an object.

[00:39:16](https://www.youtube.com/watch?v=z51K0UhriOk&t=2356s) Both ordinary calls copy what their argument variables hold. The class call's shared-object mutation does not mean that its parameter was implicitly passed using `ref`. Explicit `ref` and `out` are different parameter modes, so “always by value” without that qualification would be misleading.

<details>
<summary>Why can a normal class parameter change the caller's X, while a normal struct parameter cannot?</summary>

The struct parameter contains its own copied X/Y fields. The class parameter contains a copied reference to the same object the caller references. Writing the latter's X reaches shared object storage, while writing the former's X reaches only copied parameter storage.

</details>
