# Build a city in stages and keep its finished meaning stable

[00:00:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=0s) The lesson develops the **builder pattern** through a small city containing residents and their homes. Start with ordinary objects, expose a mutation bug, then separate editable configuration from the finished city. Later changes add shared defaults, typed identifiers, shared configuration methods, and alternative builder interfaces.

The terms used along that path are:

- **Domain model, entity, and aggregate:** data representing the problem; a citizen or home is an entity, and the city groups the related entities.
- **Reference and object graph:** a reference points to an object; references between objects form a graph. The first model has citizen-to-home links but deliberately omits a stored network of co-residents.
- **Array, list, index, dictionary, and cache:** an array has a fixed number of slots; a list can grow; an index identifies a slot; a dictionary maps keys to values; a cache keeps a result or lookup prepared earlier.
- **Mutable and immutable model:** editable state versus state that stays fixed after construction. **Shallow protection** fixes a member's value or reference; **deep immutability** also protects everything reachable through it.
- **Constructor, accessor, and backing field:** initialization code, property-reading or property-writing code, and the storage underlying a property. A **get-only property** exposes reading without a setter; **readonly** restricts field reassignment; **init** permits property assignment during initialization. **required** asks the caller to initialize a member, without validating its meaning.
- **Nullable value and null-forgiving operator:** a value that may be absent, and the postfix `!` that suppresses a compiler nullability warning without checking the value.
- **Builder and terminal Build:** an object that manages incomplete configuration, and the operation that validates it and creates the final result.
- **Fluent API and immutable copy:** configuration calls chained through returned values; a mutable fluent builder returns itself, while an immutable variation produces a replacement value.
- **Delegate, lambda, and factory:** a callable value, an inline function such as `x => ...`, and code that creates objects. A configuration delegate lets a factory control when configuration runs.
- **Block scope and configuration scope:** a block limits a local variable's visibility; a configuration scope carries defaults copied into objects created through it.
- **Single responsibility and encapsulation:** separating jobs such as data storage and construction, and hiding implementation details behind operations. This example deliberately leaves mutable data open while putting checks and conversion in builders.
- **Validation, exception, and contract:** checking whether input is acceptable, reporting a failure by throwing, and specifying preconditions (requirements before a call) and postconditions (guarantees after it). **Presence validation** checks whether a value was supplied; **range validation** checks which supplied values are allowed.
- **Sentinel:** a reserved value meaning “not supplied,” distinct from an ordinary valid value.
- **Conversion, serialization, and deserialization:** changing one representation into another, writing data into a transferable representation, and reading it back. The lesson's Build mainly converts models in memory; it does not implement a database or file serializer.
- **Struct, record struct, and strongly typed ID:** a value type, a value type with generated value equality and hashing, and a dedicated wrapper identifying one kind of entity rather than an untyped number.
- **Overload, type safety, and optional ID:** methods sharing a name but accepting different parameter types, compiler checks against mixing incompatible categories, and an identifier representation that explicitly permits absence.
- **Lifetime, garbage collection, and weak reference:** how long an object remains part of the program, automatic memory reclamation, and a reference that does not by itself keep its target alive.
- **Interface, abstract builder, and override:** a contract implemented by different types, a builder abstraction that can hide different models or results, and a replacement implementation of a virtual or abstract member.
- **Target-typed new, delegation, and handle:** construction syntax whose type comes from context, forwarding an operation to another object, and a value pairing identity with the context needed to resolve it.
- **Extension method and this:** a static method callable with instance syntax, and the current instance; `this` on an extension method's first parameter identifies its receiver.
- **Interface dispatch:** selecting the implementation of an interface member for the actual receiver; extension methods themselves remain static calls.
- **Explicit interface implementation:** a member provided specifically through an interface, alongside a concrete API that can preserve more specific types.
- **Wrapper and final builder:** an object around another object, and a separate object exposing final creation from the same configured state.
- **ImmutableArray and sparse set:** a C# immutable collection option and an alternative keyed storage structure; both are mentioned, not implemented in depth.

## What immutability protects

[00:02:42](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=162s) An **init accessor** lets a property be assigned during object initialization and prevents an ordinary later assignment. The aim is to prevent accidental changes to a created city ([00:02:53](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=173s)). **Immutable** means state remains fixed after construction; **mutable** means it can change ([00:03:04](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=184s), [00:04:08](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=248s)).

[Related source state](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) shows the lesson's `init` city properties and the constructor-held city reference. The two protections are different:

```csharp
sealed class City
{
    public required Citizen[] Citizens { get; init; }
    public required Home[] Homes { get; init; }
}
sealed class CityLogic
{
    private readonly City _city;
    public CityLogic(City city) { _city = city; }
}
// city.Citizens = anotherArray; // ordinary later reassignment forbidden
// city.Citizens[0] = anotherCitizen; // array contents remain writable
```

[00:03:14](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=194s) A component that receives the city wants other code not to silently change data it depends on. Receiving an ordinary object reference does not confer exclusive ownership: someone else may hold the same reference and change the object during a call or between calls ([00:03:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=204s), [00:03:44](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=224s)). True immutability allows the component to depend on stable data now and later ([00:03:53](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=233s)).

[00:04:12](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=252s) A mutable city can instead be copied into private storage owned by the component. A stable independent copy may require copying nested mutable data too, which costs time and memory. Copying only the outer reference is no protection.

[00:04:35](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=275s) A **constructor** is the initialization code run when an instance is created. Passing the city through its constructor fixes which city the logic uses. A **get-only property** exposes reading without a setter; it is not inherently private. Its access modifier determines who may read it. At [00:04:57](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=297s), the important restriction is that callers cannot assign it. A **readonly field** likewise cannot be reassigned by an ordinary method; it can be initialized at declaration or in its declaring type's constructor ([00:05:01](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=301s), [00:05:11](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=311s)). Neither freezes the referenced object. Constructor assignment, get-only properties, and readonly fields are useful language-level restrictions, not sufficient proofs of deep immutability.

## Break a cached search with mutation

[00:05:18](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=318s) A fresh scan can reflect the current residents on every call. ## Separate shallow protection from immutability

[00:09:13](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=553s) Protecting a property from reassignment is **shallow protection**. **Deep immutability** would also prevent mutation of array cells and fields of the resident and home objects. C# has immutable collection types such as ImmutableArray, whose elements cannot be overwritten through an index assignment; an immutable collection still does not freeze mutable objects stored inside it.

[Related source state](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) preserves the explicit “must not be changed” comment alongside writable arrays and public entity fields. A simplified illustration:

```csharp
// This is an immutable model and must not be changed.
sealed class City
{
    public required Citizen[] Citizens { get; init; }
    public required Home[] Homes { get; init; }
}
// The convention can still be violated:
city.Citizens[0] = new Citizen { Name = "Joe", Age = 18 };
city.Citizens[0].Name = "Changed";
```

[00:09:45](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=585s) The correction is to the logic's assumption: it was written for an unchanging city but was given a mutable one. Safety requires an actual stability guarantee ([00:10:01](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=601s)). Either make an independent copy with a dedicated copying function, or require the whole program to treat the shared city as immutable. When consumers only read it or replace it with a new instance, the dependent logic becomes simpler ([00:10:17](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=617s)).

[00:10:42](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=642s) At this stage array cells and element objects remain writable. The chosen approach is **conceptual immutability**, a convention expressed in a comment and upheld by every consumer ([00:10:56](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=656s), [00:11:11](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=671s)). At [00:11:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=684s), a get-only property is again considered: it prevents replacing the array reference but still permits entering the array and changing cells. This is a limitation of this model, not a claim that deeply immutable C# models are impossible.

[00:11:44](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=704s) The lesson deliberately does not explore ImmutableArray in depth because it wants the design idea to transfer across languages. Get-only or readonly members can restrict individual assignments; a struct stores values rather than separately allocated reference objects, but a struct alone does not prohibit mutation ([00:11:56](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=716s)). Every programmer working with the convention must avoid changing the finished model ([00:12:11](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=731s)).

## Choose fluent configuration or immutable copies

[00:17:44](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1064s) A **fluent API** joins configuration calls into one expression. Each call returns a value on which the next call can operate. ## Consider a configuration delegate

[00:18:50](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1130s) Another configuration style accepts a **delegate**, a callable value, and executes configuration inside it. A **lambda** is an inline function such as `john => ...`. [Related source state](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) uses separate calls instead; it is related builder machinery, not a committed implementation of the delegate alternative. Illustrative call shape:

```csharp

{
    john.Name("John");
    john.Age(18);
    john.Home(home);
});
```

[00:18:58](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1138s) The creation method receives the callback and controls its invocation. Inside it, set the name and, if appropriate, the home ([00:19:04](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1144s)). The intended advantage is that the local citizen variable is not available to later code as a half-configured object ([00:19:13](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1153s), [00:19:16](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1156s)).

[00:19:37](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1177s) John is a local parameter whose visibility ends with the callback block. Parameter types can be inferred from the delegate expected by the API ([00:19:47](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1187s)). A **factory**, code responsible for creating the object, can also choose to run the callback later ([00:19:50](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1190s)). These are API design choices: C# does not prohibit capturing the builder into an outer variable, so a callback by itself is not a runtime non-escape guarantee.

A variation can return the created configuration object so setup can continue outside ([00:20:19](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1219s)).

[00:20:30](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1230s) The implementation proceeds with the simplest scheme: configure a mutable model, then convert it into the intended immutable result. It does not implement every callback or immutable-copy variation.

## Keep data open and put contracts on configuration

[00:23:25](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1405s) The mutable model is useful outside the builder too. Higher-level configuration code can access the fields and implement its own operations ([00:23:35](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1415s)). **Encapsulation** means controlling access through an abstraction; here the data model is deliberately open, and encapsulation of checks and construction lives on the builder.

[Related source state](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) shows the public model reference and configuration methods. Shortened example:

[00:23:46](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1426s) Add a **wrapper**, an object providing operations around the supplied model, expose its reference publicly ([00:23:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1435s)), and retain that reference during construction ([00:24:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1440s)). At [00:24:10](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1450s), the address configuration member writes into the home model. Initially these operations are nearly direct field assignments ([00:24:15](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1455s)). Methods can communicate intent more clearly than raw assignments, but that choice is partly style ([00:24:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1464s)).

[00:24:29](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1469s) Age could be a property or a method. A method can return a value useful for chaining or final construction ([00:24:54](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1494s)); a property getter also returns a value, while a setter does not return the receiver for a fluent chain. For simple reads and writes the forms can express similar behaviour ([00:25:10](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1510s)). Both methods and property setters can perform validation; the method form is not uniquely able to reject negative ages ([00:25:22](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1522s)).

[00:25:40](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1540s) A **contract** describes preconditions and postconditions: which inputs are permitted and what the operation guarantees. The negative-age guard expresses a precondition, not a proof that all required fields have been supplied. ## Convert homes first and preserve shared references

[00:29:45](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1785s) A citizen's staged home is a reference to a MutableHome, not an index and not the final Home. Shortened sequence:

```csharp
var homes = new Home[Model.Homes.Count];
for (int i = 0; i < homes.Length; i++)
    homes[i] = ConvertHome(Model.Homes[i]); // validate, then copy

// While converting each citizen:
```

2. [00:29:48](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1788s) Keep the mutable home reference as the lookup key. The final object does not exist during earlier configuration ([00:31:04](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1864s), [00:31:17](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1877s)).
3. [00:31:18](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1878s) Allocate the mutable-to-immutable dictionary with capacity matching the home count ([00:31:20](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1880s)).
4. [00:31:21](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1881s) Convert each home and store it in the response array. At [00:32:27](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1947s), retain each produced home; at [00:32:28](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1948s), a second loop populates the map using those same array elements.
5. [00:33:43](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=2023s) For a citizen with a home, retrieve its already-converted home; for an absent home, leave null.
6. [00:33:46](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=2026s) Put both arrays into the City and return it.

[00:31:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1884s) MutableHome and Home appear almost duplicated: each has an address, with nullable versus required input playing different roles. ## Replace home references with a typed identifier

[00:48:06](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=2886s) A citizen currently holds a direct home reference. [Related unfinished ID state](https://github.com/AntonC9018/uniCourse_csharp/blob/dcfd6225dc8e41c7cbdc4e86a79a7bf0b5c1f869/examples/builder/Program.cs) contains the later int-valued wrapper and ID-based lookup, but the overall refactor is incomplete. Simplified committed shape:

## Use overloads to preserve entity type

[00:53:10](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3190s) A bare int does not say whether its value identifies a home or a citizen. Two Get(int) methods cannot be distinguished solely by return type, so an untyped design commonly needs names such as GetHome and GetCitizen ([00:53:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3204s)).

[Related unfinished ID state](https://github.com/AntonC9018/uniCourse_csharp/blob/dcfd6225dc8e41c7cbdc4e86a79a7bf0b5c1f869/examples/builder/Program.cs) introduces distinct HomeId and CitizenId wrappers and overloads. Shortened API:

```csharp
readonly record struct CitizenId(int Value);
readonly record struct HomeId(int Value);

public Citizen Get(CitizenId id) => Citizens[id.Value];
public Home Get(HomeId id) => Homes[id.Value];

// Get(new CitizenId(0)) selects Citizen.
// Get(new HomeId(0)) selects Home.
```

[00:53:39](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3219s) Another identifier wrapper makes the same method name possible for another entity. For the citizen lookup the inspected type is **CitizenId**, not CityId. A CityId would identify a city and would be a separate concept.

[00:54:03](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3243s) An **overload** shares a method name but has a different parameter type. At [00:54:10](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3250s), that parameter type selects the entity operation. With CitizenId, the city resolves a citizen through Get ([00:54:29](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3269s)); without distinct wrapper types, the caller must select a separately named operation ([00:54:45](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3285s)).

[00:54:59](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3299s) With bare numbers, accidentally calling GetHome with a citizen index may compile. It can silently retrieve a home instead of the intended citizen ([00:55:17](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3317s)). Distinct ID types prevent that mix-up: HomeId is not a CitizenId, and the correct Get overload follows the argument's type ([00:55:34](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3334s)). The two gains are less entity-name repetition at call sites and compile-time protection against mixing key categories ([00:55:37](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3337s)).

This **type safety** does not prove that the key exists, is in range, or belongs to this particular city. Those are separate runtime or ownership checks.

<details>
<summary>Does Get(new HomeId(0)) know that slot zero is a valid home?</summary>

Its type tells the compiler to choose the home operation. Validity and ownership of the numeric key still need the city's lookup contract and any runtime checks.

</details>

## Understand flat storage and lifetime control

[00:55:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3355s) IDs add implementation work, but direct references also impose construction and conversion work ([00:56:03](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3363s)). The reference-based builder needed a mutable-to-immutable map. An ID can remain the same key across representations, making that relation map unnecessary.

[Related unfinished ID state](https://github.com/AntonC9018/uniCourse_csharp/blob/dcfd6225dc8e41c7cbdc4e86a79a7bf0b5c1f869/examples/builder/Program.cs) captures this intention, including the removal of the build-time home map. Simplified final assignment:

```csharp
// Once the whole ID migration is completed:
var citizen = new Citizen
{
    Name = name,
    Age = mut.Age,
    Home = mut.Home // same optional ID, not a converted Home reference
};
```

[00:56:13](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3373s) An ID is a **key**, not necessarily an array index forever. In dictionary-backed storage the city can ask whether the entity with that key still exists. This separates logical **lifetime**, the period when the entity belongs to the system, from the lifetime of a particular object in memory.

[00:56:22](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3382s) A strong object reference keeps its target reachable. A **weak reference** avoids keeping the target alive by itself, but target disappearance then follows **garbage collection**, automatic memory reclamation, rather than the program's entity-removal rules.

The advantages described are:

- [00:56:51](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3411s) Simpler **deserialization**, reconstructing data from a stored representation: read keys rather than reconstructing and reconnecting a graph of object references.
- [00:57:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3420s) Explicit lifetime control: a key can be tested against the current storage even after an entity has been removed.
- [00:57:14](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3434s) Flat relationship storage: citizens and homes refer to entities by IDs rather than by direct cross-entity object references.
- [00:57:27](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3447s) Simpler building: relation dictionaries can disappear when IDs are preserved across conversion.

“Flat” refers to cross-entity links; the city still owns collections of objects. The lesson does not implement full persistence, deletion, or a production lifetime system.

[00:57:35](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3455s) Working with an ID lets code assert identity or existence without inspecting every home property. An identifier therefore narrows the operations available until the caller resolves it ([00:58:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3480s)). That can reduce coupling between entities.

## Represent an absent home explicitly

[00:58:06](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3486s) A resident may have no home, so the ID representation must express absence. A **sentinel**, a reserved value such as -1, can encode “none” ([00:58:12](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3492s)). An **optional ID** packages that possibility into a distinct type instead of leaving it as a hidden numeric convention ([00:58:25](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3505s)).

[Related unfinished ID state](https://github.com/AntonC9018/uniCourse_csharp/blob/dcfd6225dc8e41c7cbdc4e86a79a7bf0b5c1f869/examples/builder/Program.cs) contains OptionalHomeId and the optional Get overload. Shortened source shape:

```csharp
readonly record struct OptionalHomeId
{
    public static readonly HomeId NoHomeId = new(-1);
    public readonly HomeId Id;
    public bool IsNull => Id == NoHomeId;
    public OptionalHomeId(HomeId id) { Id = id; }
    public OptionalHomeId() : this(NoHomeId) { }
}
public Home? Get(OptionalHomeId id)
{
    if (id.IsNull) return null;
    return Get(id.Id);
}
```

Implement it in steps:

1. [00:58:39](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3519s) Add a parameterless constructor that installs the absence value.
2. [00:58:47](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3527s) Adopt -1 as the no-home convention.
3. [00:58:56](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3536s) Name that value with a static readonly field instead of repeating the literal. It is not a compile-time `const` of this record-struct type.
4. [00:59:07](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3547s) Use constructor syntax to initialize the marker or optional value. In the inspected code the static marker calls the numeric HomeId constructor; the parameterless OptionalHomeId constructor delegates to it.
5. [00:59:15](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3555s) Add an absence predicate, called IsNull in the source.
6. [00:59:26](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3566s) Change the citizen member to OptionalHomeId.
7. [00:59:32](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3572s) Add Get(OptionalHomeId). At [00:59:40](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3580s), return null for absence and otherwise delegate to Get(HomeId).

[00:59:46](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3586s) Absence is now visible in the type and the result `Home?`. Nullable reference annotations can express whether a reference is intended to be nullable, but they do not add runtime enforcement that an arbitrary reference can never be null ([01:00:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3600s)). OptionalHomeId is a custom struct, not `Nullable<HomeId>`.

There is also a value-type edge case: `new OptionalHomeId()` invokes the declared parameterless constructor, whereas `default(OptionalHomeId)` and zero-initialized array elements do not. Default has an ID value of zero rather than -1 in this design. Therefore this sentinel representation does not automatically make every default optional value mean “none.”

[01:00:10](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3610s) The cost is extra wrapper types and overloads. ID-based access also adds a trip through the shared city context instead of immediate access through a stored Home reference ([01:00:20](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3620s), [01:00:40](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3640s)). The optional lookup can produce no Home, so callers must handle a nullable result ([01:00:56](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3656s)).

## Hide different models behind builder contracts

[01:09:21](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4161s) An **abstract builder** can hide its own model or produce a different final representation ([01:09:35](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4175s)). “Abstract” here describes the API role; it need not literally be a C# abstract class. [01:11:22](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4282s) A shared interface creates an awkward boundary for Home. The concrete method expects its own HomeBuilder, but the interface accepts IHomeBuilder. An adapter must verify the supplied builder before forwarding it.

## Pay for abstraction only when it is needed

[01:14:16](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4456s) Interface-based construction can let an implementation keep one model, separate fields, data elsewhere, or an entirely different representation. That is useful when callers must support genuinely different builders.

[Related unfinished abstraction state](https://github.com/AntonC9018/uniCourse_csharp/blob/ff2cc72527a8a97cf7b756d006ce5d6d8ac9724f/examples/builder/Program.cs) illustrates the separation of operational contracts from model exposure. Its minimal idea is:

```csharp
interface IHomeBuilder
{
    void Address(string address);
}
// Each implementation decides where Address stores the value.
```

[01:14:46](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4486s) Do not introduce the interface merely because that flexibility might be useful someday. It adds code, adapters, and contracts that must be maintained ([01:14:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4495s)). Prematurely preparing every component for an imagined replacement model can cost more than it saves ([01:15:02](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4502s)).

[01:15:19](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4519s) When an actual new requirement arrives, making the existing class more general may be easier than maintaining a large abstract hierarchy from the start. This advice does not forbid interfaces; it asks for a concrete need that justifies them. The lesson's abstract-builder detour exposes both the flexibility and the extra unfinished work.

## Separate configuration from final creation

[01:17:40](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4660s) Finally split configuration and final creation into two objects. The configuration builder exposes setup; a **final builder** exposes only terminal Build. Factories can create and connect the pair with the appropriate concrete types.

[Related unfinished split-builder state](https://github.com/AntonC9018/uniCourse_csharp/blob/ff2cc72527a8a97cf7b756d006ce5d6d8ac9724f/examples/builder/Program.cs) contains ICityFinalBuilder and a holder for configuration and final-builder references. A shortened illustration of the required shared-state relationship is:

```csharp
interface ICityFinalBuilder
{
    ICity Build();
}
sealed class CityFinalBuilder : ICityFinalBuilder
{
    private readonly CityBuilder _configured;
    public CityFinalBuilder(CityBuilder configured) { _configured = configured; }
    public ICity Build() => _configured.Build();
}
// Both roles must refer to the same configured construction state.
```

This is an illustrative completion of the proposed role, not a complete class present in the cited commit. It assumes a CityBuilder whose result implements ICity.

[01:17:45](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4665s) CityFinalBuilder should refer to the **same** CityBuilder used for configuration. At [01:17:53](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4673s), the caller invokes final creation through that final-builder role. Its result must come from the configured state, not from a fresh empty builder. The transcript continues this explanation through [01:18:50](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4730s); the supplied broader intervals group this final discussion.

The lesson ends with a design boundary: mutable staging enables incremental setup, Build validates and converts it, and consumers rely on the finished model's stability. The working sample remains immutable by convention rather than deeply enforced. Full ImmutableArray design, advanced diagnostics, factory-method details, generalized home defaults, persistence, dynamic storage, and the completed alternative-builder implementations are outside the completed demonstration.

<details>
<summary>Why would creating a new CityBuilder inside CityFinalBuilder.Build be wrong?</summary>

It would discard the configuration accumulated through the original builder. Separating API roles must not separate the underlying configured state.
