# Виртуальные методы, абстрактные классы и интерфейсы

Этот урок даёт практический ответ на один вопрос: когда несколько типов предлагают одну и ту же операцию, какая реализация выполняется? Начнём с животного и птицы, проследим вызовы через ссылки и таблицы виртуальных методов, а затем применим те же идеи, чтобы превратить функции меню в объекты, несущие поведение и данные. [00:00:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=10s)

Термины, которые встречаются по ходу:

- **Класс, базовый класс, производный класс, наследование и «является»:** класс описывает свои экземпляры. Производный класс расширяет базовый и должен быть пригоден везде, где ожидается этот базовый тип. **Интерфейс** выражает контракт поведения, который реализует класс; его также можно использовать как тип ссылки.
- **Объект, ссылка и получатель:** объект — это конкретный экземпляр; ссылка идентифицирует этот объект; получатель — объект, на котором выполняется метод экземпляра. **Поле** хранит данные в объекте, а **статическое поле** принадлежит типу.
- **Статический тип и тип времени выполнения:** статический тип принадлежит переменной или выражению и управляет поиском членов на этапе компиляции. Тип времени выполнения принадлежит фактическому объекту. **Приведение к базовому типу** (upcasting) позволяет посмотреть на объект производного типа через тип базового класса или реализованного интерфейса, не копируя объект.
- **Сокрытие методов и переопределение:** сокрытие объявляет отдельный одноимённый член; переопределение предоставляет новую реализацию унаследованной виртуальной операции. **Полиморфизм** позволяет одной и той же операции над общим типом ссылки вести себя по-разному для разных объектов.
- **Виртуальная диспетчеризация, статическое связывание и позднее связывание:** виртуальная диспетчеризация выбирает переопределение по типу времени выполнения получателя. Невиртуальный вызов имеет цель, зафиксированную поиском на этапе компиляции. Видео называет выбор реализации во время выполнения динамическим связыванием, или поздним связыванием; это не требует ключевого слова `dynamic` в C# и не делает метод экземпляра `static`.
- **Таблица виртуальных методов (vtable), слот и адрес кода:** концептуальная таблица урока связывает каждую виртуальную операцию со слотом, в котором хранится адрес кода её реализации. Показанные адреса — это метки, а не измеренные адреса процесса.
- **`virtual`, `override` и `abstract`:** `virtual` разрешает замену в потомках; `override` выполняет эту замену; абстрактный класс нельзя создать напрямую, а абстрактный метод объявляет операцию, не задавая тело.
- **`sealed` и девиртуализация:** запечатанный класс не может иметь подклассов; запечатанное переопределение нельзя переопределить снова. Девиртуализация — это оптимизация, превращающая виртуальную операцию в прямой вызов, когда её цель известна.
- **`this` и `base`:** `this` обозначает текущий получатель; `base` обращается к унаследованным членам и, для рассматриваемых здесь вызовов методов, напрямую выбирает базовую реализацию.
- **Параметр, возвращаемое значение, сигнатура, перегрузка и метод с телом-выражением:** параметры принимают аргументы вызова, а возвращаемое значение — результат метода; `void` означает отсутствие возвращаемого значения. Сигнатура различает методы по имени и сведениям о параметрах; перегрузки имеют общее имя, но принимают разные списки параметров. Тело из одного выражения можно записать с помощью `=>`. Ковариантный возвращаемый тип — это более производный тип возврата, разрешённый для некоторых переопределений; это современное уточнение, выходящее за рамки примеров видео.
- **Композиция и инкапсуляция:** композиция представляет объект с помощью данных или сотрудничающих компонентных объектов вместо подкласса для каждого свойства. Инкапсуляция удерживает детали реализации внутри объявляющего их типа.
- **Неявная и явная реализация интерфейса:** подходящий публичный метод класса может неявно удовлетворять интерфейсу; явно уточнённая реализация принадлежит одному указанному интерфейсу и доступна через него.
- **Приведение типа и шаблон типа:** приведение меняет то, как рассматривается значение; шаблон вида `value is ISpeak speaker` проверяет совместимость и вводит переменную с проверяемым типом.
- **Делегат, группа методов и объект действия:** делегат — это вызываемое значение, ссылающееся на поведение метода; группа методов — имя метода, используемое для выбора совместимого поведения. Объект действия предоставляет поведение через контракт класса или интерфейса и может также нести конфигурацию.
- **Обязательный член, инициализатор объекта и конструктор:** обязательный член должен быть инициализирован при создании объекта; инициализатор объекта задаёт значения членов после создания. Конструктор управляет тем, как создаётся экземпляр, а приватный конструктор ограничивает создание объявляющим типом.
- **Одиночный объект и `readonly`:** синглтон предоставляет один общий экземпляр. Поле `readonly` ограничивает присваивание своей ссылки; оно не делает автоматически неизменным сам объект по ссылке.
- **Свойство и резервное поле:** свойство даёт доступ к члену через аксессоры; резервное поле хранит данные, используемые аксессором. Разновидности свойств здесь отложены.
- **Выведенный тип и аннотация подавления null:** `var` выводит статический тип переменной из её инициализатора. `!` может подавлять предупреждения анализа nullable; никакой проверки во время выполнения он не даёт.
- **Модификаторы доступа:** `public` разрешает доступ снаружи, `private` ограничивает доступ объявляющим типом, а `protected` разрешает доступ из объявляющего класса и его потомков.
- **Сериализация и идентификатор:** сериализация представляет данные объекта для хранения или передачи; идентификатор различает сущность в этом представлении.

Для практики лабораторная работа репозитория [«Полиморфизм и интерфейсы»](../../../labs/1_basic/18_interface.md) предлагает реализовать команды меню один раз через делегаты, а другой — через интерфейсы.

Запись служит источником для последовательных состояний демонстрации ниже. В используемой рабочей копии нет зафиксированного исходного кода для этих конкретных фрагментов, поэтому они помечены как **упрощённые реконструкции состояний видео**, а не как точные версии из репозитория. Метка времени рядом с каждым примером задаёт его записанный контекст. Объявления классов и операторы места вызова показаны вместе ради объяснения; при сборке запускаемой программы эти операторы нужно поместить в метод выполнения содержащей их программы. Табличные схемы описывают модель диспетчеризации урока; реальные раскладки времени выполнения, выбор инструкций и оптимизации — это детали реализации.

Урок охватывает диспетчеризацию методов, контракты классов и интерфейсов, проектирование наследования, объекты действий и небольшой синглтон. Тела по умолчанию в интерфейсах, наследование интерфейсов, поведение `base` в конструкторах и разновидности свойств остаются за рамками показанного; итоговые исключения собраны в разделе [границы урока](#lesson-boundaries).

## От скрытых методов к диспетчеризации во время выполнения

На [00:00:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=10s) базовый класс намеренно минимален: у `Animal` нет полей, а его единственная операция печатает три знака вопроса. На [00:00:21](https://www.youtube.com/watch?v=82vaxb6o_rg&t=21s) `Bird : Animal` устанавливает наследование, а одноимённый метод печатает чириканье. Производный класс наследует форму базового, но простое повторение имени метода не делает его переопределением.

Упрощённое начальное состояние видео:

```csharp
class Animal
{
    public void Speak() => Console.WriteLine("???");
}
class Bird : Animal
{
    public new void Speak() => Console.WriteLine("chirp");
}

// Операторы в месте вызова:
Bird bird = new Bird();
bird.Speak();               // chirp
Animal animal = bird;
animal.Speak();             // ???
```

Явный модификатор `new` помечает **сокрытие метода** — отдельный одноимённый член; он делает намерение исходного примера явным. Если опустить этот модификатор, метод не станет переопределением.

На [00:00:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=29s) переменная типа `Bird` вызывает метод, видимый на `Bird`. На [00:00:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=47s) присваивание той же птицы переменной типа `Animal` — это законное **приведение к базовому типу**: любая птица является животным. На [00:01:00](https://www.youtube.com/watch?v=82vaxb6o_rg&t=60s) вызов через эту переменную выбирает `Animal.Speak`. Её **статический тип** — `Animal` — управляет поиском членов; компилятор не выбирает скрытый метод только потому, что объект случайно оказался птицей.

Содержательное изменение на [00:01:27](https://www.youtube.com/watch?v=82vaxb6o_rg&t=87s) состоит в том, чтобы сохранить общую ссылку типа `Animal` и при этом выбирать поведение по **типу времени выполнения** объекта. Сделайте операцию виртуальной:

1. На [00:01:58](https://www.youtube.com/watch?v=82vaxb6o_rg&t=118s) добавьте `virtual` к базовому методу.
2. Замените модификатор сокрытия в производном объявлении на `override`.
3. Выполните тот же вызов через базовый тип. На [00:02:06](https://www.youtube.com/watch?v=82vaxb6o_rg&t=126s) наблюдаемый результат — вывод птицы.

Упрощённое изменённое состояние:

```csharp
class Animal
{
    public virtual void Speak() => Console.WriteLine("???");
}
class Bird : Animal
{
    public override void Speak() => Console.WriteLine("chirp");
}

// Тот же объект и тот же вызов через тип Animal:
Animal animal = new Bird();
animal.Speak();             // chirp
```

Здесь **`virtual`** разрешает выбор реализации во время выполнения, а **`override`** предоставляет замену для этой унаследованной операции. Тот же синтаксис вызова теперь может выражать **полиморфизм**. По умолчанию методы невиртуальны; невиртуальный метод нельзя переопределить. [Справочник по C#: virtual](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/virtual).

<details>
<summary>Почему смена переменной на Animal поначалу изменила вывод?</summary>

Изменился поиск членов на этапе компиляции. Исходные методы были отдельными невиртуальными членами. После того как Animal.Speak стал виртуальным, а Bird переопределил эту операцию, вызов через тип Animal может выбрать реализацию Bird по фактическому получателю.

</details>

## Две ссылки и один объект

Разбор на [00:02:09](https://www.youtube.com/watch?v=82vaxb6o_rg&t=129s) отделяет две локальные переменные от информации времени выполнения, представляющей два типа. Упоминание `Animal` и `Bird` не означает, что был создан экземпляр каждого из классов.

Упрощённое состояние видео на [00:02:26](https://www.youtube.com/watch?v=82vaxb6o_rg&t=146s)–[00:02:50](https://www.youtube.com/watch?v=82vaxb6o_rg&t=170s):

```csharp
var bird = new Bird();       // выведенный статический тип: Bird
Animal animal = bird;       // копирует ссылку
animal.Speak();
```

1. `new Bird()` создаёт **объект Bird** и даёт ссылку на него.
2. `var` выводит **статический тип** переменной из её инициализатора, здесь — `Bird`; это не типизация времени выполнения.
3. Присваивание `bird` переменной `animal` копирует **ссылку**, а не поля объекта. Обе переменные указывают на один объект.
4. В `animal.Speak()` выражение слева от точки задаёт **получателя**, а `Speak()` называет запрошенную операцию. [00:03:18](https://www.youtube.com/watch?v=82vaxb6o_rg&t=198s)
5. Для виртуальной операции выбор во время выполнения приводит к реализации, связанной с фактическим типом получателя. [00:03:26](https://www.youtube.com/watch?v=82vaxb6o_rg&t=206s)

На [00:03:00](https://www.youtube.com/watch?v=82vaxb6o_rg&t=180s) схема памяти присваивает двум телам методов разные адреса кода. Эти тела могут сосуществовать, хотя операция называется одинаково. На рисунке ссылки трактуются как адреса объектов; управляемая ссылка не гарантирует, что объект навсегда останется по одному «сырому» числовому адресу.

## Модель таблицы виртуальных методов

На [00:03:43](https://www.youtube.com/watch?v=82vaxb6o_rg&t=223s) выбор во время выполнения требует служебных данных: как тип находит свою реализацию операции? animal.Speak();              // реализация Speak из Bird

## Сравните объекты базового типа и невиртуальные вызовы

На [00:06:00](https://www.youtube.com/watch?v=82vaxb6o_rg&t=360s) добавьте настоящий объект базового класса. Приведение птицы к базовому типу и создание животного дают разные типы времени выполнения.

Упрощённое состояние видео, виртуальные методы по-прежнему на месте:

```csharp
Animal first = new Bird();
Animal second = new Animal();
first.Speak();               // chirp
second.Speak();              // ???
```

На [00:06:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=374s) второй объект действительно является `Animal`. Хранение его в переменной не может изобрести более производный тип времени выполнения. На [00:06:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=389s) прослеживание его ссылки поэтому приводит к таблице Animal и адресу 100. На [00:06:54](https://www.youtube.com/watch?v=82vaxb6o_rg&t=414s)–[00:07:11](https://www.youtube.com/watch?v=82vaxb6o_rg&t=431s) одинаковый синтаксис вызова через тип `Animal` приводит к реализации Bird для первого получателя и к реализации Animal для второго.

Итог на [00:07:19](https://www.youtube.com/watch?v=82vaxb6o_rg&t=439s)–[00:07:44](https://www.youtube.com/watch?v=82vaxb6o_rg&t=464s): `virtual` устанавливает унаследованный слот операции, а `override` заменяет реализацию этого типа в слоте.

На [00:07:53](https://www.youtube.com/watch?v=82vaxb6o_rg&t=473s) рассмотрите удаление `virtual`. Тогда `override` не скомпилируется. Если производный член — скрытый обычный метод, у операции Animal в этой упрощённой модели нет виртуального слота.

Реконструированное невиртуальное состояние на [00:08:07](https://www.youtube.com/watch?v=82vaxb6o_rg&t=487s):

```csharp
class Animal
{
    public void Speak() => Console.WriteLine("???");
}
class Bird : Animal
{
    public new void Speak() => Console.WriteLine("chirp");
}

// Цель фиксирована статическим типом выражения:
Animal animal = new Bird();
animal.Speak();              // Animal.Speak
```

**Невиртуальный вызов** использует реализацию, выбранную по типу выражения, и пропускает выбор реализации времени выполнения. На [00:08:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=505s)–[00:08:43](https://www.youtube.com/watch?v=82vaxb6o_rg&t=523s) видео называет это **статическим вызовом**: цель известна на этапе компиляции. Это по-прежнему вызов метода экземпляра, и объект по-прежнему передаётся.

На [00:09:18](https://www.youtube.com/watch?v=82vaxb6o_rg&t=558s) выбор переопределения по получателю во время выполнения называется **динамической диспетчеризацией** или **поздним связыванием**. Держите эту терминологию отдельно от выражения `dynamic` в C#, которое откладывает языковое связывание, такое как выбор члена или перегрузки. [Спецификация привязки выражений C#](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/expressions#123-static-and-dynamic-binding).

## Продолжайте цепочку переопределений

На [00:09:34](https://www.youtube.com/watch?v=82vaxb6o_rg&t=574s) введите третий уровень — `Sparrow : Bird`. Унаследованное переопределение остаётся переопределяемым, если оно не `sealed`, поэтому повторно писать `virtual` не нужно.

Упрощённое состояние видео на [00:09:37](https://www.youtube.com/watch?v=82vaxb6o_rg&t=577s)–[00:09:53](https://www.youtube.com/watch?v=82vaxb6o_rg&t=593s):

```csharp
class Sparrow : Bird
{
    public override void Speak() => Console.WriteLine("sparrow");
}

// Bird — тип ссылки, Sparrow — тип объекта:
Bird bird = new Sparrow();
bird.Speak();                // sparrow
```

**`override`** повторно использует унаследованную виртуальную операцию на любой глубине цепочки наследования. Даже ссылка базового типа приводит к самому производному применимому переопределению. На [00:10:07](https://www.youtube.com/watch?v=82vaxb6o_rg&t=607s) на рисунке теперь есть информация о типах времени выполнения Animal, Bird и Sparrow с соответствующими таблицами. Выбор следует за типом времени выполнения объекта, а не за тем типом, который записан в локальной переменной.

На [00:10:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=625s)–[00:10:54](https://www.youtube.com/watch?v=82vaxb6o_rg&t=654s) унаследованный слот Speak уже присутствует во всех потомках; каждое переопределение меняет для этого слота именно свою реализацию. Ни дополнительного объявления `virtual`, ни ручного построения таблиц не требуется.

На [00:11:04](https://www.youtube.com/watch?v=82vaxb6o_rg&t=664s)–[00:11:19](https://www.youtube.com/watch?v=82vaxb6o_rg&t=679s) удалите производное переопределение. Если удалено объявление метода, унаследованный слот сохраняет унаследованную реализацию: адрес 100, если ни один промежуточный класс не переопределяет Animal.Speak. Если удалено только ключевое слово `override`, а одноимённое тело осталось, это объявление скрывает унаследованный член и не заменяет его виртуальный слот. Поэтому виртуальный вызов через базовый тип по-прежнему приводит к унаследованной реализации.

## Поля и скрытый получатель

На [00:11:39](https://www.youtube.com/watch?v=82vaxb6o_rg&t=699s) виртуальные методы могут обращаться к **полям** так же, как обычные методы экземпляра. Поле хранит данные в каждом объекте; скрытый получатель **`this`** идентифицирует конкретный объект, чьи поля использует метод. Производный объект содержит унаследованные поля и может добавлять свои.

На [00:11:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=707s) производный метод мог бы напечатать унаследованное `Name`. На [00:11:57](https://www.youtube.com/watch?v=82vaxb6o_rg&t=717s)–[00:12:07](https://www.youtube.com/watch?v=82vaxb6o_rg&t=727s) демонстрация добавляет производные данные и печатает по одному разу на потомка. В этой упрощённой реконструкции поле с числом потомков в производном классе называется `Children`; его счётчик цикла `i` увеличивается после каждого вывода. Суть — повторяющееся поведение из производного метода, а не точная реконструкция написания поля.

Упрощённое состояние видео с полями и циклом:

```csharp
class Animal
{
    public required string Name;
    public virtual void Speak() => Console.WriteLine(Name);
}
class Bird : Animal
{
    public required int Children;
    public override void Speak()
    {
        for (int i = 0; i < Children; i++)
            Console.WriteLine("chirp");
    }
}

// В отдельном месте вызова:
Animal animal = new Bird { Name = "sparrow", Children = 5 };
animal.Speak();
```

На [00:12:12](https://www.youtube.com/watch?v=82vaxb6o_rg&t=732s) при создании нужно задать и унаследованные, и производные обязательные члены. **Инициализатор объекта** задаёт значения членов уже созданного экземпляра. Это ограничение **обязательных членов**, а не правило, что каждое обычное поле всегда нужно инициализировать явно. [Справочник по C#: required](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/required).

На [00:12:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=745s) наблюдаемый запуск печатает чириканье пять раз и не выполняет метод Animal. На [00:12:34](https://www.youtube.com/watch?v=82vaxb6o_rg&t=754s) унаследованное имя остаётся сохранённым в объекте, хотя это переопределение его никогда не читает. Диспетчеризация производной реализации не удаляет унаследованные данные.

На [00:12:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=768s)–[00:13:19](https://www.youtube.com/watch?v=82vaxb6o_rg&t=799s) отличите ссылку на получателя от такой строки, как его имя: локальная переменная хранит ссылку на объект, а не копию его имени или всех его полей. Виртуальный вызов действует на этот объект.

На [00:13:19](https://www.youtube.com/watch?v=82vaxb6o_rg&t=799s)–[00:14:46](https://www.youtube.com/watch?v=82vaxb6o_rg&t=886s) аргумент безопасности таков:

1. Среда выполнения выбирает реализацию Bird только для получателя, совместимого с Bird.
2. Поэтому этот метод может использовать собственные члены Bird и унаследованные члены Animal.
3. Если у Bird нет переопределения, выбор сохраняет унаследованную реализацию; тело Animal может полагаться на то, что получатель — как минимум Animal.
4. Производные типы могут добавлять поля и виртуальные операции, не делая унаследованные недействительными. [00:14:52](https://www.youtube.com/watch?v=82vaxb6o_rg&t=892s)–[00:15:02](https://www.youtube.com/watch?v=82vaxb6o_rg&t=902s)

Игнорирование лишних полей на рисунке объясняет, почему производный объект можно рассматривать как объект базового типа; это не значит, что приведение физически усекает или копирует объект.

Важное явное уточнение на [00:15:18](https://www.youtube.com/watch?v=82vaxb6o_rg&t=918s)–[00:15:31](https://www.youtube.com/watch?v=82vaxb6o_rg&t=931s): внутри метода Bird **статический тип `this` — это Bird**, объявляющий класс. Объект, который он обозначает, может иметь тип времени выполнения Bird или потомка вроде Sparrow. Диспетчеризация не заставляет тип `this` на этапе компиляции меняться вместе с вызывающим кодом. [Спецификация доступа к this в C#](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/expressions#12814-this-access).

## Добавьте второй виртуальный метод

На [00:15:41](https://www.youtube.com/watch?v=82vaxb6o_rg&t=941s) виртуальный метод может начинаться на любом уровне. Добавьте `FlapWings` в Bird на [00:15:46](https://www.youtube.com/watch?v=82vaxb6o_rg&t=946s); у Animal такой операции нет. Sparrow может переопределить его на [00:16:04](https://www.youtube.com/watch?v=82vaxb6o_rg&t=964s).

Упрощённое состояние видео:

```csharp
class Animal
{
    public virtual void Speak() => Console.WriteLine("???");
}
class Bird : Animal
{
    public override void Speak() => Console.WriteLine("chirp");
    public virtual void FlapWings() => Console.WriteLine("bird flaps");
}
class Sparrow : Bird
{
    public override void Speak() => Console.WriteLine("sparrow");
    public override void FlapWings() => Console.WriteLine("sparrow flaps");
}

// Операторы в месте вызова:
Animal animal = new Sparrow();
// animal.FlapWings();        // ошибка: отсутствует в контракте Animal
Bird bird = new Sparrow();
bird.Speak();
bird.FlapWings();
```

На [00:16:11](https://www.youtube.com/watch?v=82vaxb6o_rg&t=971s) выражение типа Animal не может вызвать `FlapWings`, доступный только в Bird. Статический тип управляет доступными членами, даже когда получатель времени выполнения — Sparrow. На [00:16:22](https://www.youtube.com/watch?v=82vaxb6o_rg&t=982s) смена типа выражения на Bird делает этот вызов законным. На [00:16:32](https://www.youtube.com/watch?v=82vaxb6o_rg&t=992s) записанный запуск выполняет обе реализации Sparrow.

На [00:16:38](https://www.youtube.com/watch?v=82vaxb6o_rg&t=998s) тела методов из одного оператора сокращаются с помощью **синтаксиса с телом-выражением**. `=>` вводит выражение, образующее тело; оно сохраняет и операцию, и поведение диспетчеризации. Например, реконструированное `public override void Speak() => Console.WriteLine("sparrow");` — короткая форма тела, содержащего этот единственный оператор.

На [00:16:50](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1010s)–[00:17:44](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1064s) в модели теперь два независимых слота:

| Тип | Speak | FlapWings |
| --- | --- | --- |
| Animal | 100 | отсутствует |
| Bird | 200 | 300 |
| Sparrow | 400 | 500 |

`virtual` вводит слот в объявляющем классе и его потомках. `override` меняет реализацию этой операции в производном типе; на другой слот он не влияет. На [00:17:54](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1074s) без соответствующего переопределения слот сохранил бы унаследованный адрес.

На [00:18:11](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1091s)–[00:18:22](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1102s) оба вызова идут по одной и той же цепочке: ссылка → получатель → тип времени выполнения → слот выбранной операции → путь кода. Количество других виртуальных методов это правило не меняет.

## Расширьте реализацию с помощью base

На [00:18:31](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1111s) переопределение может добавлять поведение, сохраняя существующее базовое поведение. Копирование тела базового метода хрупко: оно может быть сложным или зависеть от **инкапсулированных** данных, к которым производный класс не имеет доступа. [00:18:55](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1135s)

Упрощённое состояние видео на [00:19:09](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1149s):

```csharp
class Sparrow : Bird
{
    public override void FlapWings()
    {
        Console.WriteLine("prepare");
        base.FlapWings();    // напрямую выбирает реализацию Bird
        Console.WriteLine("finish");
    }
}
```

**`base`** обращается к членам базового класса. Для этого вызова метода он напрямую выбирает унаследованную реализацию вместо повторной диспетчеризации текущего получателя к переопределению Sparrow. Получатель остаётся тем же объектом; отдельный базовый объект не создаётся.

На [00:19:20](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1160s)–[00:19:24](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1164s) компилятор знает, к какой базовой реализации относится содержащий метод Sparrow. Более позднее переопределение подкласса не заменяет цель этого вызова с уточнением через `base`.

На [00:19:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1165s) повторные вызовы с уточнением через `base` законны и выполняются в порядке исходного кода. На [00:19:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1169s)–[00:20:06](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1206s) другие доступные методы экземпляра базового класса тоже можно вызывать через `base` из подходящего кода экземпляра в производном классе. Правила доступности по-прежнему действуют; примеры урока касаются методов, а не конструкторов и произвольных статических контекстов.

## Вызовы на this остаются виртуальными

Вопрос на [00:20:13](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1213s): использует ли вызов одного виртуального метода из другого автоматически реализацию того же класса? Перед ответом упростите пример:

1. На [00:20:32](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1232s) удалите лишнюю перегрузку FlapWings из Sparrow.
2. На [00:20:34](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1234s) удалите посторонний дополнительный вызов.
3. На [00:20:40](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1240s) удалите ненужную ссылку на Animal.
4. На [00:20:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1247s) оставьте Speak, виртуальный FlapWings у Bird и переопределение FlapWings у Sparrow.

Упрощённое состояние видео:

```csharp
class Bird
{
    public virtual void Speak()
    {
        this.FlapWings();
    }
    public virtual void FlapWings() => Console.WriteLine("bird flaps");
}
class Sparrow : Bird
{
    public override void FlapWings() => Console.WriteLine("sparrow flaps");
}

// Операторы в месте вызова:
Bird bird = new Sparrow();
bird.Speak();                // унаследованное тело вызывает Sparrow.FlapWings
```

На [00:20:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1259s) `this.FlapWings()` — виртуальный вызов на текущем получателе. Его статический тип — Bird, но тип времени выполнения получателя — Sparrow, поэтому выполняется переопределение Sparrow. На [00:21:08](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1268s) удаление `this.` ничего не меняет: неквалифицированный вызов метода экземпляра по-прежнему использует того же получателя и ту же виртуальную операцию.

На [00:21:13](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1273s) `base` — это не способ для Bird выбрать собственное тело: из Bird он ссылался бы на базовый класс Bird. Поэтому обычные вызовы на `this` не заставляют использовать тело FlapWings по умолчанию из Bird, когда получатель — Sparrow.

Решение на [00:21:22](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1282s)–[00:21:33](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1293s) выносит логику по умолчанию в **приватный невиртуальный вспомогательный метод**. Приватный доступ удерживает его внутри Bird; невиртуальное поведение фиксирует цель вызова.

Упрощённое изменённое состояние:

```csharp
class Bird
{
    private void FlapWingsDefault() => Console.WriteLine("bird flaps");

    public virtual void FlapWings() => FlapWingsDefault();
    public virtual void Speak() => FlapWingsDefault();
}
class Sparrow : Bird
{
    public override void FlapWings() => Console.WriteLine("sparrow flaps");
}
```

Теперь Speak может осознанно выполнять логику по умолчанию из Bird. Выбирайте обычный виртуальный вызов, когда потомки должны настраивать поведение, и этот вспомогательный метод — когда должно выполняться поведение по умолчанию.

<details>
<summary>Если Bird.Speak вызывает FlapWings без this, участвует ли Sparrow?</summary>

Да. Неквалифицированный вызов метода экземпляра неявно передаёт того же получателя. Удаление this не превращает виртуальную диспетчеризацию в вызов с уточнением через base и не делает его невиртуальным.

</details>

## Наследование должно означать «является»

На [00:21:46](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1306s) **наследование** означает **«является»**, а не просто «было создано из» или «имеет похожий код». Если A производится из B, каждый A должен быть пригоден как B. Для Bird и Animal каждая птица является животным. [00:21:55](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1315s)

Разбор A/B/C на [00:22:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1323s)–[00:22:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1345s) предостерегает от изобретения общего базового класса только ради переиспользования кода. Производный экземпляр несёт и унаследованные члены, обнажая несоответствие, если он логически не является экземпляром базового типа.

На [00:22:35](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1355s) история происхождения семьи бабушка → мать → дочь подсказывает неверную иерархию программирования. Исправление на [00:22:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1379s): `Daughter : Mother` утверждало бы, что каждая дочь — ещё и мать, а не что мать её родила. Перестановка категорий иллюстрирует нужное отношение: бабушка является матерью, а мать — чьей-то дочерью. [00:23:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1394s) Это учебная аналогия; настоящей модели семьи понадобились бы собственные доменные решения.

На [00:23:36](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1416s)–[00:24:11](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1451s) пример из игры подходит куда лучше. **Идентификатор** различает сущность для **сериализации**, хранения или передачи её данных. Монстр — сущность; орк — монстр.

Упрощённая иерархия состояния видео:

```csharp
class Entity
{
    public int Id;
}
class Monster : Entity
{
    public int Health;
    public int Attack;
}
class Orc : Monster { }
```

Поэтому у каждого Orc есть идентичность сущности, а также здоровье и атака монстра. Это унаследованные части одного и того же объекта, а отношение типов выражает, что орк может использоваться везде, где ожидается монстр или сущность.

## Представьте свойства данными и композицией

На [00:24:17](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1457s) рассмотрим Animal → FlyingAnimal → BlackFlyingAnimal → Hawk. Кодирование независимых свойств подклассами становится хрупким: чёрный нелетающий медведь не помещается под BlackFlyingAnimal. [00:24:40](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1480s)

На [00:24:53](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1493s) добавление BlackAnimal намекает вынести дублирующееся чёрное поведение в этот класс, но тогда BlackFlyingAnimal потребовал бы и BlackAnimal, и FlyingAnimal в качестве родителей класса. [00:25:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1510s)–[00:25:13](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1513s)

Простая демонстрация размещает цвет и признак умения летать прямо на Animal.

```csharp
class Animal
{
    public required string Name;

// Операторы в месте вызова:

```

На [00:26:02](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1562s) рекомендация — хранить такие свойства в данных или в составных компонентных объектах. ## Абстрактные и запечатанные классы

На [00:26:32](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1592s) текущий обычный класс Animal по-прежнему можно создать. Желаемое ограничение на [00:26:40](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1600s)–[00:26:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1607s) — сохранить Animal как тип ссылки и базовую категорию, создавая только конкретные виды вроде птиц или млекопитающих.

Сделайте его **абстрактным классом** — классом, который нельзя создать напрямую. Упрощённое изменённое состояние на [00:27:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1623s):

```csharp
abstract class Animal
{
    public virtual void Speak() => Console.WriteLine("???");
}
class Bird : Animal { }

// Операторы в месте вызова:
// var animal = new Animal(); // ошибка компиляции
Animal animal = new Bird();   // legal base-typed reference
```

Записанный пример прямого создания перестаёт компилироваться. Абстрактный класс всё ещё может содержать поля и реализованные методы; объявление класса абстрактным не делает автоматически абстрактными все его методы.

На [00:27:15](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1635s) противоположное ограничение наследования — **`sealed`**, то есть у класса нет подклассов. На [00:27:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1645s)–[00:27:40](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1660s) пример со Sparrow мотивирует использовать обычные экземпляры Bird с именем вместо ещё одного класса.

Независимое упрощённое состояние видео с запечатанным классом:

```csharp
sealed class Bird : Animal
{
    public required string Name;
    public override void Speak() => Console.WriteLine(Name);
}

// var bird = new Bird { Name = "sparrow" };
// class Sparrow : Bird { }  // ошибка компиляции
```

На [00:27:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1679s) запечатывание сообщает, что класс окончательный и предназначен для прямого использования. На [00:28:12](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1692s)–[00:28:44](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1724s) знание о том, что получатель типа Bird не может принадлежать подклассу Bird, может включить **девиртуализацию**: компилятор времени выполнения вправе выбрать прямой вызов, потому что цель известна. Это возможность оптимизации, а не гарантия C#, что каждый такой вызов использует определённую машинную инструкцию. Наблюдаемое поведение метода остаётся тем же.

На [00:28:44](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1724s) невиртуальный метод аналогично имеет фиксированную реализацию; на [00:28:46](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1726s) другой способ достижения этой оптимизации отложен. Следующий раздел сужает запечатывание до одной переопределяемой операции.

## Запечатайте одно переопределение

На [00:28:56](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1736s) запечатайте переопределённый метод вместо запечатывания всего класса. **Запечатанное переопределение** сохраняет унаследованный виртуальный контракт, но запрещает дальнейшие переопределения этой операции.

Упрощённое состояние видео:

```csharp
class Animal
{
    public virtual void Speak() => Console.WriteLine("???");
}
class Bird : Animal
{
    public sealed override void Speak() => Console.WriteLine("chirp");
}
class Sparrow : Bird
{
    // public override void Speak() { } // ошибка: унаследованный член запечатан
}
```

На [00:29:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1743s) попытка переопределить запечатанный член даёт показанную ошибку компилятора: переопределение невозможно, так как член запечатан. Правильный синтаксис — `sealed override`, а не новое объявление `sealed virtual`. [Справочник по C#: sealed](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/sealed).

На [00:29:16](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1756s)–[00:29:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1765s) модель сохраняет реализацию Bird в унаследованном слоте для Bird и его подклассов. Поэтому вызов через тип Bird имеет фиксированную цель переопределения и может быть оптимизирован напрямую.

На [00:29:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1788s) вызов через тип Animal по-прежнему остаётся виртуальной операцией: другой подтип Animal может реализовать Speak иначе. Конкретный компилятор времени выполнения может оптимизировать известные случаи, но запечатывание одной ветви не убирает полиморфизм из контракта Animal.

## Требуйте поведение абстрактными методами

На [00:30:05](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1805s) сделайте саму операцию **абстрактной**: объявляющий класс задаёт метод, но не даёт тела. Абстрактный метод экземпляра участвует в виртуальном контракте, не требуя дополнительного модификатора `virtual`.

Упрощённое состояние видео:

```csharp
abstract class Animal
{
    public abstract void Speak();
}
class Bird : Animal
{
    public override void Speak() => Console.WriteLine("chirp");
}
class Sparrow : Bird { }     // inherits Bird's implementation
```

На [00:30:16](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1816s)–[00:30:57](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1857s) у объекта не может быть абстрактный Animal как точный тип времени выполнения, поскольку Animal нельзя создать. Получателем является конкретный потомок. В табличной модели абстрактный Speak у Animal объявляет слот без исполняемого тела по умолчанию.

Утверждение, что таблица абстрактного класса «не используется», касается диспетчеризации для экземпляра, чей точный тип времени выполнения — этот абстрактный класс. Его контракты, реализованные члены и информация о типе по-прежнему важны для потомков; abstract их не стирает.

На [00:30:57](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1857s)–[00:31:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1874s) Bird должен предоставить реализацию, чтобы быть конкретным. Удаление переопределения даёт ошибку на этапе компиляции. Промежуточный абстрактный подкласс может оставить операцию абстрактной; реализация нужна каждому конкретному потомку.

На [00:31:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1885s)–[00:31:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1908s) Sparrow не обязан переопределять снова: реализация Bird уже удовлетворяет требованию, и Sparrow наследует её. Важное условие — реализация где-то на унаследованном пути, а не повторное объявление в каждом потомке.

## Параметры, возвращаемые значения и перегрузки

На [00:32:00](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1920s) виртуальные методы могут принимать параметры и возвращать значения; `void Speak()` был лишь простейшей демонстрацией. **Переопределение** должно совпадать с сигнатурой параметров и доступностью унаследованной операции. В примерах сохраняется один и тот же тип возврата; современный C# также допускает определённые ковариантные типы возврата, чему это видео не учит. [Справочник по C#: override](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/override).

На [00:32:23](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1943s) **перегрузки** используют одно имя с разными списками параметров. Каждая виртуальная перегрузка в табличной модели — самостоятельная операция.

Упрощённое состояние видео:

```csharp
class Animal
{
    public virtual void Speak() => Console.WriteLine("???");
    public virtual void Speak(string message) => Console.WriteLine(message);
}
class Bird : Animal
{
    public override void Speak() => Console.WriteLine("chirp");
    public override void Speak(string message) => Console.WriteLine("bird: " + message);
}

// Операторы в месте вызова:
Animal animal = new Bird();
animal.Speak();              // безараметрическая операция, реализация Bird
animal.Speak("hello");       // строковая операция, реализация Bird
```

На [00:32:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1949s) и [00:32:57](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1977s) список аргументов различает эти операции. Для таких обычных статически типизированных вызовов **выбор перегрузки происходит сначала на этапе компиляции**; затем виртуальная диспетчеризация выбирает переопределение выбранной сигнатуры. Это не сканирование во время выполнения, выбирающее любую одноимённую перегрузку после входа в таблицу. [Спецификация разрешения перегрузок C#](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/expressions#1264-overload-resolution).

## Введите контракт интерфейса

На [00:33:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1994s) **интерфейс** похож на абстрактный класс в одном важном отношении: он задаёт операции, которые должны предлагать реализации. На [00:33:18](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1998s) введите операцию крыльев отдельно от контракта Speak у Animal. По соглашению C# имена интерфейсов начинаются с префикса `I` в именах интерфейсов; префикс полезен, но не требуется языком. [00:33:19](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1999s)–[00:33:32](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2012s)

Упрощённое начальное состояние видео с интерфейсом на [00:33:37](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2017s):

```csharp
abstract class Animal
{
    public abstract void Speak();
}
interface IFlapWings
{
    void FlapWings();
}
class Bird : Animal, IFlapWings
{
    public override void Speak() => Console.WriteLine("chirp");
    // FlapWings is initially missing: this class does not compile.
}
```

Список после двоеточия выражает два разных факта: Bird **наследует** Animal и **реализует** IFlapWings. Он не даёт Bird двух родителей класса. Схема урока использует таблицу иерархии классов для виртуальных методов класса и отдельное отображение диспетчеризации интерфейса для контракта интерфейса. [00:33:44](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2024s)

На [00:33:58](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2038s) синтаксис вызова остаётся обычным: точка и скобки. На [00:34:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2043s) объявление, заканчивающееся `;`, не имеет тела. Для показанного простого контракта экземпляра член интерфейса неявно является public и abstract; явное написание `public` законно, но избыточно. [00:34:18](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2058s)–[00:34:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2087s)

Интерфейс нельзя создать. [00:34:24](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2064s) Современные интерфейсы могут также объявлять тела по умолчанию и другие формы членов; поведение реализации по умолчанию явно отложено на [00:34:11](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2051s). Различие урока «нет полей» означает отсутствие **полей экземпляра** для состояния отдельного объекта, а не то, что современные интерфейсы никогда не могут объявлять статическое состояние. [Справочник по C#: interface](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/interface).

На [00:34:51](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2091s) компилятор сообщает, что Bird не предоставил FlapWings. Добавьте подходящую публичную реализацию на [00:35:01](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2101s):

```csharp
class Bird : Animal, IFlapWings
{
    public override void Speak() => Console.WriteLine("chirp");
    public void FlapWings() => Console.WriteLine("bird flaps");
}
```

Это **неявная реализация интерфейса**: публичный метод класса совпадает с именем, параметрами и типом возврата операции интерфейса. `override` используется для Speak, потому что Animal объявляет этот виртуальный контракт; FlapWings не нуждается в нём лишь для удовлетворения интерфейсу.

На [00:35:12](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2112s)–[00:35:45](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2145s) демонстрация различает наследование класса и членство в интерфейсе и допускает реализацию как рядом с абстрактным базовым классом, так и без пользовательского базового класса. Интерфейс даёт контракт поведения, а не унаследованное состояние экземпляра.

На [00:35:52](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2152s) после удаления операции базового класса из варианта сохранение `override` на методе без соответствующего переопределяемого члена класса вызывает ошибку компилятора. Одного членства в интерфейсе недостаточно, чтобы считать это переопределением метода класса. На [00:36:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2170s) реализующий класс сам может объявить этот метод `virtual`; тогда его потомки смогут переопределить его обычным образом.

## Один объект, рассмотренный через интерфейс

На [00:36:16](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2176s)–[00:36:36](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2196s) реализация IFlapWings означает, что Bird пригоден как значение типа IFlapWings. **Приведение к интерфейсу** хранит ссылку на тот же объект; оно не создаёт объект интерфейса и не копирует птицу.

Упрощённое состояние видео:

```csharp
Bird bird = new Bird();
IFlapWings wings = bird;
wings.FlapWings();

// wings.Speak();             // ошибка: нет в IFlapWings
// new IFlapWings();          // ошибка: интерфейс нельзя создать
```

На [00:36:36](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2196s) переменная типа интерфейса создаётся или присваивается, а затем используется для вызова. Понимайте это как объявление ссылки, подобное приведённому выше, а не как конструктор с именем `FlapWings.FlapWings()`.

На [00:36:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2189s) и [00:36:54](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2214s) **статический тип интерфейса** ограничивает доступные операции своим контрактом. Объект Bird по-прежнему содержит своё прочее поведение и данные, но выражение типа IFlapWings не открывает Speak.

На [00:37:01](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2221s)–[00:37:15](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2235s) схема памяти снова копирует только ссылку на объект. На [00:37:15](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2235s)–[00:38:07](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2287s) у объекта один тип времени выполнения — Bird, и его информация о диспетчеризации содержит раздельные отображения для класса и интерфейса:

| Контракт в этом примере | Операция | Конкретная реализация |
| --- | --- | --- |
| Иерархия классов Animal | Speak | Bird.Speak |
| Интерфейс IFlapWings | FlapWings | Bird.FlapWings |

## Используйте два интерфейса без пользовательского базового класса

## Виртуальные методы класса могут реализовывать контракты интерфейсов

На [00:42:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2549s) сделайте неявно реализующий метод Speak у Bird виртуальным и добавьте переопределение в подклассе. На [00:42:42](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2562s) создайте подкласс.

## Явно разделите одинаковые сигнатуры

## Перестройте функции меню в объекты действий

На [00:46:45](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2805s) контракт действий меню мог бы быть интерфейсом или абстрактным классом. Язык не навязывает один проект. **Объект действия** — это экземпляр, который предоставляет поведение через общую операцию, возможно неся с собой данные.

Исходный проект передаёт вызываемое поведение общему исполнителю. Упрощённое связанное состояние меню, реконструированное для сравнения на [00:47:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2834s):

```csharp
static void Greeting(string name) => Console.WriteLine("Hello, " + name);

static void ExecuteAction(System.Action<string> action, string name)
{
    action(name);
}

// В месте вызова:
ExecuteAction(Greeting, "Ada");
```

Здесь **делегат** — это вызываемое значение, а `Greeting` — **группа методов**, преобразованная в совместимый делегат. Исполнителю не нужно знать, какой именно метод приветствия передан.

На [00:46:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2808s)–[00:47:08](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2828s) замените этот вызываемый параметр **абстрактным классом действия**, у которого метод Execute — абстрактная операция экземпляра. Следующая промежуточная реконструкция сохраняет параметр с именем до следующей переработки:

```csharp
abstract class Action
{
    public abstract void Execute(string name);
}
class GreetingAction : Action
{
    public override void Execute(string name)
        => Console.WriteLine("Hello, " + name);
}

// В классе, содержащем меню:
static void ExecuteAction(Action action, string name)
{
    action.Execute(name);
}
```

`Action` в этой демонстрации — пользовательский класс; `System.Action` — тип делегата из библиотеки, использованный в более ранней реконструкции.

На [00:46:55](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2815s)–[00:47:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2834s) абстрактный Action нельзя создать напрямую, поэтому исполнитель получает конкретного потомка. Он знает **статический тип** Action, тогда как объект сохраняет **тип времени выполнения**. На [00:47:39](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2859s) создайте GreetingAction и дайте ему нестатическое переопределение, потому что Execute — контракт экземпляра.

На [00:47:43](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2863s)–[00:47:50](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2870s), затем снова на [00:48:35](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2915s)–[00:48:42](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2922s), вызов `action.Execute(...)` выбирает конкретное переопределение получателя. Передача GreetingAction приводит к первой инструкции этого метода. Механизм диспетчеризации тот же, что уже прослежен для Animal и Bird.

На [00:47:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2834s)–[00:47:33](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2853s) сравнение касается упаковки поведения: простой делегат предоставляет одну вызываемую сигнатуру; контракт класса может предоставлять несколько отдельно названных операций через одну ссылку на объект. Картинка с одним адресом функции у урока — упрощение. Делегаты могут ссылаться на методы экземпляра с данными цели и объединять несколько записей вызова. Эти возможности не превращают делегат в контракт класса с несколькими методами. [Руководство по C#: делегаты](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/delegates/).

Ни одно из представлений не лучше во всех случаях. Следующее изменение показывает, почему объекту, несущему явно названную конфигурацию, может лучше подойти для этого меню.

4. Задайте его обязательное имя при создании. [00:49:16](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2956s)–[00:49:23](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2963s)

Упрощённое изменённое состояние видео:

```csharp
abstract class Action
{
    public abstract void Execute();
}
class GreetingAction : Action
{
    public required string Name;
    public override void Execute() => Console.WriteLine("Hello, " + Name);
}

// В классе, содержащем меню:
static void ExecuteAction(Action action) => action.Execute();

// В месте вызова:
ExecuteAction(new GreetingAction { Name = "Ada" });
```

**Обязательный член** заставляет при создании задать Name; **инициализатор объекта** задаёт его у нового экземпляра. Теперь имя хранится рядом с выбором реализации, поэтому аргумент с именем во время выполнения не нужен.

На [00:49:23](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2963s)–[00:49:34](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2974s) ссылка на объект упаковывает и поведение, и конфигурацию. Тип времени выполнения ведёт к реализации Execute; поля объекта дают этой реализации данные. Каждое производное действие может добавлять свою конфигурацию, не меняя абстрактный базовый контракт.

На [00:49:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2987s) то же преобразование по-прежнему требуется для остальных действий меню. Greeting — первый разобранный случай, а не завершённая перестройка меню.

## Завершите остальные классы действий

На [00:49:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2999s) преобразуйте Addition из функции в AdditionAction. Перенесите вспомогательный метод чтения в приватный метод, оставив реализацию ввода внутри действия. На [00:50:11](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3011s) выделите функцию без операции в NothingAction.

Упрощённое изменённое состояние видео:

```csharp
class AdditionAction : Action
{
    private static int Read() => int.Parse(Console.ReadLine()!);

    public override void Execute()
    {
        int first = Read();
        int second = Read();
        Console.WriteLine(first + second);
    }
}
class NothingAction : Action
{
    public override void Execute() { }
}

// Обновлённые места вызова:
ExecuteAction(new AdditionAction());
ExecuteAction(new NothingAction());
```

Однострочный Read выше намеренно сокращён, чтобы сосредоточиться на размещении методов; это не утверждение, что в записи вспомогательный метод проверки ввода заменён именно таким телом. Применяя перестройку к настоящему меню, сохраните проверочное поведение исходного вспомогательного метода. Аннотация «прочь от null» `!` в примере лишь подавляет предупреждения анализа nullable; она не делает отсутствующий или некорректный ввод безопасным.

На [00:50:23](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3023s)–[00:50:35](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3035s) **абстрактный** Execute требует, чтобы даже NothingAction предоставил тело. Его явное пустое переопределение означает «это действие намеренно ничего не делает». Конкретный производный класс не может просто опустить метод.

На [00:50:35](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3035s)–[00:50:45](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3045s) замена абстрактного объявления виртуальным пустым телом изменила бы эту страховку: забытое переопределение молча унаследовало бы поведение по умолчанию «ничего не делать». Abstract делает обязанность видимой компилятору.

На [00:50:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3048s) места вызова теперь создают AdditionAction и NothingAction вместо упоминания старых групп методов. Исполнитель остаётся единообразным: принимает Action и полиморфно вызывает Execute.

## Используйте stateless-действие как синглтон

На [00:50:56](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3056s) у AdditionAction нет конфигурации или полей на экземпляр, и он не меняет состояние объекта между выполнениями. Само по себе чтение нового ввода из консоли не требует нового экземпляра действия.

На [00:50:56](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3056s)–[00:51:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3070s) **синглтон** предоставляет один общий экземпляр, вместо того чтобы создавать свежий экземпляр для каждого выбора в меню. Это позволяет избежать повторных выделений маленького объекта, когда нет отдельного состояния экземпляра, которое нужно сохранять. GreetingAction, у которого Name различается между приветствиями, мотивирует другой выбор.

Постройте синглтон в показанном порядке:

1. На [00:51:24](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3084s) ограничьте создание извне **приватным конструктором**.
2. На [00:51:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3119s) попытка создать действие извне, даже с инициализатором объекта, не удаётся: создание всё равно требует доступа к этому конструктору.
3. На [00:52:20](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3140s) добавьте **статическое поле**, связанное с типом, а не с каждым экземпляром, которое хранит общий объект.
4. На [00:52:27](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3147s) используйте это поле в месте вызова.
5. На [00:52:34](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3154s) добавьте **readonly**, чтобы обычная последующая замена общей ссылки была невозможна.

Упрощённое итоговое состояние видео с синглтоном:

```csharp
class AdditionAction : Action
{
    private AdditionAction() { }

    public static readonly AdditionAction Instance = new AdditionAction();

    private static int Read() => int.Parse(Console.ReadLine()!);

    public override void Execute()
    {
        int first = Read();
        int second = Read();
        Console.WriteLine(first + second);
    }
}

// В месте вызова:
ExecuteAction(AdditionAction.Instance);
// new AdditionAction();                 // ошибка: приватный конструктор
// AdditionAction.Instance = null!;      // ошибка: поле readonly
```

Приватный конструктор доступен инициализатору поля внутри AdditionAction, поэтому этот инициализатор может создать объект. Внешние вызывающие повторно используют полученную ссылку.

На [00:52:36](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3156s)–[00:52:55](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3175s) показанная попытка переприсвоить поле readonly не компилируется. Точное правило шире, чем «присвоено ровно один раз при объявлении»: поля readonly можно также присваивать в контексте конструктора объявляющего типа, включая статический конструктор для статического поля. Обычный вызывающий код не может их переприсвоить. Здесь readonly фиксирует ссылку; он не помешал бы изменениям полей внутри изменяемого общего объекта. [Справочник по C#: readonly](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/readonly).

<details>
<summary>Почему AdditionAction используется совместно, а GreetingAction создаётся с именем?</summary>

В этой демонстрации у AdditionAction нет конфигурации на экземпляр, поэтому все вызывающие могут использовать один и тот же объект. GreetingAction хранит конкретное Name, поэтому разным приветствиям могут понадобиться разные настроенные объекты. Решение следует из данных и времени жизни объекта, а не только из того, что оба предоставляют Execute.

</details>
