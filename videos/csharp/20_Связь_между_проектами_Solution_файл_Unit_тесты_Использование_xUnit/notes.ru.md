# Связь между проектами, файл Solution, Unit-тесты, использование xUnit

## Цель и словарь терминов

[00:00:00](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=0s) Построим запускаемый пример: в одном проекте лежит функция, а другой проект её использует. Смысл в том, чтобы увидеть, что дают тесты: можно заменить реализацию, сохранив её известное поведение, и получить полезную ошибку, если случайно изменить это поведение. Пример переводит возраст кошки в выдуманный человеческий эквивалент; это программное правило, а не биологическая модель.

Урок вводит эти термины в том порядке, в котором они становятся полезны:

- **Проект, консольный шаблон и .NET SDK:** проект группирует исходные файлы и параметры сборки; консольный шаблон даёт минимальную заготовку исполняемого приложения; SDK предоставляет инструменты вроде команды `dotnet`.
- **CLI:** интерфейс командной строки, где команды вводятся в терминале.
- **MSBuild, компилятор и сборка:** MSBuild координирует сборку; компилятор C# переводит C#; сборка (assembly) — это скомпилированная единица, полученная из проекта.
- **Файл проекта и XML:** `.csproj` — это конфигурационный документ в XML; XML выражает структуру именованными открывающими и закрывающими тегами.
- **Свойства сборки, цели и общие импорты:** свойства хранят настройки, цели описывают действия сборки, а импортируемые файлы поставляют конфигурацию. `Directory.Build.props` и `Directory.Build.targets` — соглашения об именах общих файлов.
- **Целевой фреймворк, неявные using, nullable и тип вывода:** эти настройки выбирают целевой API .NET, автоматически импортируемые пространства имён, анализ значений, связанных с null, и то, производит ли проект исполняемый файл или библиотеку.
- **Библиотека, ссылка на проект и относительный путь:** библиотека поставляет код вызывающему коду; ссылка на проект связывает один проект с другим; относительный путь находит файл от каталога файла, который на него ссылается.
- **Solution, IDE и IntelliSense:** solution перечисляет проекты, которыми управляют вместе; интегрированная среда разработки вроде Rider или Visual Studio даёт редактирование и навигацию; IntelliSense даёт автодополнение кода и связанную помощь.
- **Unit-тест, ожидаемое значение, фактическое значение, утверждение и регрессия:** unit-тест проверяет изолированное поведение; expected — эталонный ответ, actual — вычисленный ответ, утверждение проверяет их соотношение, а регрессия — это ранее работавшее поведение, сломанное изменением.
- **Граничный случай и ошибка на единицу:** граничный случай находится на границе диапазона или рядом с ней; ошибка на единицу считает на один элемент больше или меньше.
- **Рефакторинг и сопровождаемость:** рефакторинг меняет структуру, сохраняя поведение; сопровождаемость — это лёгкость понимания и изменения этой структуры.
- **Интервал, коэффициент, глубина, накопитель и магическая константа:** интервал — диапазон лет, коэффициент — его вклад за один год, глубина — число достигнутых внутри него лет, накопитель собирает итог, а магическая константа скрывает происхождение числового значения.
- **Таблица соответствий и кусочно-заданное правило:** таблица соответствий хранит заранее вычисленные пары вход-выход; кусочно-заданное правило выбирает формулу по диапазону входа.
- **Debug.Assert, интерполированная строка, new с выводом типа и выражение коллекции:** Debug.Assert — отладочная проверка; интерполированная строка подставляет значения выражений в текст; new с выводом типа выводит конструируемый тип из контекста; выражение коллекции использует скобки для создания коллекции, например массива.
- **Именованная константа, абстракция, конфигурация, массив и цикл:** именованная константа придаёт фиксированному значению смысл; абстракция отделяет общую операцию от частных правил; конфигурация хранит эти правила; массив хранит несколько элементов; цикл повторяет операцию по ним.
- **Класс, структура, record struct, метод, пространство имён и атрибут:** класс или структура определяют тип; record struct — это тип значения с генерируемыми record членами; метод — функция, принадлежащая типу; пространство имён группирует имена; атрибут прикрепляет метаданные к объявлению.
- **Ссылка на пакет, test SDK, раннер и обнаружение:** ссылка на пакет подключает зависимость; test SDK и раннер поддерживают выполнение; обнаружение находит методы и наборы данных, которые можно запустить как тесты.
- **xUnit, NUnit, Fact, Theory, InlineData и Assert.Equal:** xUnit и NUnit — библиотеки тестирования для .NET; Fact в xUnit помечает один тест, Theory помечает параметризованный тест, InlineData поставляет строку аргументов, а Assert.Equal сравнивает ожидаемое и фактическое значения.
- **Интеграционный тест, сериализация, разбор, JSON и HTML:** интеграционный тест задействует несколько компонентов вместе; сериализация превращает данные в сохраняемое представление, разбор читает это представление, JSON — структурированный формат данных, а HTML описывает веб-документы.
- **Снимок, подтверждение и diff:** снимок — сохранённый вывод, используемый как эталон; подтверждение принимает проверенный эталон; diff показывает различия между сохранённым и новым выводом.

Для более ранней практики по компиляции и [redacted] посмотрите [лабораторную работу о проекте](../../../labs/1_basic/02_project.md) в репозитории. Это отдельный лабораторный документ, а не свидетельство установки или промежуточного кода этого урока.

Порядок построения выбран намеренно: создать и связать проекты, задать эталонную функцию, написать проверки без библиотеки тестирования, переписать функцию с проверкой её результатов, а затем перенести те же случаи в xUnit. Интеграционные тесты и тесты со снимками показываются позже на другом приложении. Пользовательские импорты файлов сборки, проверка производственной конфигурации, настоящее представление бесконечного интервала и оптимизация аллокаций остаются за пределами реализованного примера.

## Общие параметры сборки

[00:01:01](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=61s) **Файл проекта**, то есть `.csproj`, хранит конфигурацию в **XML**: именованные теги содержат свойства и списки ссылок. Он записывает параметры сборки проекта и зависимости от пакетов. [00:01:19](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=79s) Поправка здесь касается ответственности за сборку: вы не вызываете `csc`, **компилятор** C#, напрямую, чтобы собрать эти проекты. **MSBuild** — это движок сборки, координирующий операцию. [00:01:31](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=91s) Он запускает компиляцию как часть сборки исходников в **сборку**, то есть скомпилированную единицу. Это не значит, что MSBuild заменяет компилятор или что для каждого исходного файла нужен отдельный вызов компилятора.

[00:01:36](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=96s) MSBuild может импортировать документы `.props` и `.targets` наряду с основным файлом проекта. **Свойства сборки** хранят значения; **цели** описывают работу сборки. [00:01:42](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=102s) Общая конфигурация избавляет от повторения одних и тех же настроек в каждом дочернем проекте. [00:02:02](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=122s) Соглашение об именах для **общего импорта** `Directory.Build.props` поставляет свойства проектам с кодом и тестам, лежащим ниже его каталога. Соглашение об имени важно: произвольный файл `.props` не импортируется автоматически только потому, что он существует.

[Закоммиченные общие свойства](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/Directory.Build.props) сохраняют эту схему. Приведённый рядом пример — это фактическая группа свойств, сокращённая только за счёт отбрасывания прочих секций проекта:

```xml
<Project>
  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
```

Здесь **целевой фреймворк** выбирает `net9.0`; **неявные using** включают импорты пространств имён от SDK; **nullable** включает анализ потенциально нулевых значений. **Тип вывода** управляет тем, получается исполняемый файл или библиотека.

## Ссылка на библиотеку с кодом

[00:03:23](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=203s) По соглашению тесты живут в собственной **сборке**, то есть в скомпилированной единице, которую создаёт отдельный тестовый проект. Инструменты тогда могут находить и выполнять их своей обычной настройкой. [00:03:29](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=209s) Технически тесты можно поместить в тот же проект, но урок избегает дополнительной ручной настройки.

[00:03:38](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=218s) Тестовый проект должен уметь вызывать функцию из проекта с кодом. **Ссылка на проект** объявляет эту зависимость. [00:03:58](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=238s) Добавьте элемент `ProjectReference` с путём в `Include` на `.csproj` проекта с кодом. [Закоммиченный ручной тестовый проект](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/tests/tests.csproj) содержит эту ссылку и свой на тот момент параметр вывода исполняемого файла:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="../code/code.csproj" />
  </ItemGroup>
</Project>
```

В примере закоммиченные обратные слэши приведены к прямым ради читаемости. `ItemGroup` группирует элементы ссылок; `Include` определяет ссылаемый файл. **Относительный путь** разрешается от каталога файла тестового проекта: `..` или `../` поднимает в родительский каталог, затем `code/code.csproj` спускает в соседний каталог.

[00:04:05](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=245s) Это предпочтительнее жёстко заданного абсолютного пути. [00:04:10](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=250s) Абсолютные пути зависят от раскладки файловой системы конкретной машины и операционной системы, поэтому они могут сломаться на Linux, Windows или macOS, когда кто-то другой откроет эту копию. Сами по себе они не недопустимы в этих системах. [00:04:13](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=253s) Ссылка делает код из проекта с кодом доступным тестовому проекту; обычные правила видимости в C# по-прежнему действуют.

[00:04:23](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=263s) Проект с кодом теперь должен давать **библиотеку**, то есть код, который потребляет другая часть программы, а не исполняемый файл, запускаемый сам по себе. [00:04:32](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=272s) Это и есть роль хранителя функции. [00:04:38](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=278s) Удалите его запись `OutputType`, чтобы применилось значение по умолчанию SDK для библиотеки. [Закоммиченный проект с кодом](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/code.csproj) соответственно предельно минимален:

```xml
<Project Sdk="Microsoft.NET.Sdk">
</Project>
```

[00:04:42](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=282s) Замените программу из консольного шаблона вызываемым вспомогательным методом. [Закоммиченный вспомогательный класс](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/Helper.cs) — это **более поздняя связанная реализация**, а не точный снимок этой первой заглушки; он подтверждает публичную статическую вспомогательную функцию, используемую вызывающим кодом.

```csharp
public static class Helper
{
    public static int GetHumanAge(int catAge)
    {
        // The conversion rule is filled in next.
        return 0;
    }
}
```

Эта заглушка — упрощённая реконструкция. **Класс** определяет тип; `static` позволяет вызывающим использовать функцию без создания экземпляра; `public` делает её доступной другому проекту; `int` объявляет целочисленные вход и результат. Функция принадлежит типу, поэтому это **метод**.

## Построение первого преобразования возраста

[00:08:33](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=513s) Проверяемый код переводит целочисленный возраст кошки в человеческий эквивалент. [00:09:05](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=545s) Начните с особых случаев: ноль лет даёт ноль, а один год даёт 15. [00:09:09](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=549s) Значит, коэффициент первого года равен 15. **Коэффициент** здесь — это число человеческих эквивалентных лет, даваемое одним кошачьим годом. [00:09:17](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=557s) Первая произнесённая оценка отдаёт второму году 7, давая примерно 22 в сумме. Эта оценка предварительная: реализация и последующая явная поправка используют **8**, давая **23**. Не сохраняйте 22 как окончательный ожидаемый ответ.

[00:09:51](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=591s) Для включающего **интервала**, то есть диапазона, с 3 по 7 начните с итога за первые два года и прибавляйте по 3 за каждый достигнутый год в диапазоне. В начале вычитание начала интервала даёт ноль, поэтому для включающего подсчёта нужно `+ 1`. [00:10:16](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=616s) За пределами интервала считаем первые два года и весь блок 3–7, затем прибавляем вклад хвоста. [00:10:33](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=633s) Коэффициент хвоста поправлен с 3 на **2**.

[Сохранённый вариант на ветвях](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/Helper.cs) — это **связанное более позднее экспериментальное состояние**, а не точный исходный вариант ниже: у этого закоммиченного старого метода коэффициент второго года равен 15 и изменён коэффициент хвоста. [Окончательные тестовые случаи](https://github.com/AntonC9018/uniCourse_csharp/blob/e4b890a75d5e014ab00227c27ff6a35965acb9a1/examples/tests_example/tests/Tests.cs) закрепляют исправленное учебное правило. Эта упрощённая реконструкция выражает правило явно:

```csharp
static int Baseline(int age)
{
    if (age == 0) return 0;
    if (age == 1) return 15;
    if (age == 2) return 23;
    if (age >= 3 && age <= 7)
        return 23 + (age - 3 + 1) * 3;
    return 38 + (age - 8 + 1) * 2;
}
```

Ветви `if` выбирают случай; `return` завершает функцию её результатом; `&&` требует выполнения обоих сравнений; `>=` и `<=` включают границы. Последней ветке по-прежнему не хватает проверки отрицательных возрастов — об этом баге скоро пойдёт речь.

[00:10:36](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=636s) Полный блок 3–7 обязан использовать собственный коэффициент **3**, прежде чем хвост использует **2**. [00:10:43](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=643s) Это годы 3, 4, 5, 6, 7: пять лет, а не семь. [00:10:52](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=652s) Произнесённая в записи арифметика включает 21 и предварительный итог 44, и [00:11:11](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=671s) трактует этот ответ как основу, которую можно проверить вручную. Эти ремарки объясняют, зачем нужен эталон с известным ответом, но они не являются последовательным выводом окончательного правила. Пять лет по 3 дают 15; окончательный итог за семь лет равен `15 + 8 + 5 * 3 = 38`. Число 44 было бы ответом окончательного правила для возраста 10, а не 7.

[00:11:26](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=686s) Как только версия, дающая ответы, принята как эталон, следующая задача — зафиксировать её известное поведение в тестах. Биологические коэффициенты намеренно приблизительны; урок о программном поведении и его сохранении.

## Переписывание суммы как вкладов интервалов

[00:20:56](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1256s) **Интервал** — группа лет с общим коэффициентом, то есть их вкладом за один год. Разделяйте группы вместо того, чтобы прятать прежние итоги внутри каждой более поздней ветви. [00:21:27](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1287s) Разберитесь со второй группой в один год. [00:21:54](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1314s) Годы с 3 по 7 дают по 3 каждый, а годы с 8 и далее — по 2.

[00:22:18](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1338s) **Накопитель** — это переменная, которая начинается с нуля и собирает каждый вклад. [00:22:31](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1351s) Последний диапазон прибавляет по 2 за каждый достигнутый год после предыдущих блоков. [00:22:37](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1357s) Это первое аддитивное переписывание использует явные условия, а не цикл, хотя цикл тоже сработал бы.

[Закоммиченная обобщённая вспомогательная функция](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/Helper.cs) — это **более позднее связанное состояние**, а не точная копия этой промежуточной аддитивной функции. Следующая упрощённая реконструкция сохраняет правило интервалов, установленное [окончательными ожиданиями](https://github.com/AntonC9018/uniCourse_csharp/blob/e4b890a75d5e014ab00227c27ff6a35965acb9a1/examples/tests_example/tests/Tests.cs):

```csharp
static int Additive(int age)
{
    int total = 0;
    if (age >= 1) total += 15;
    if (age >= 2) total += 8;
    if (age >= 3) total += Math.Min(5, age - 3 + 1) * 3;
    if (age >= 8) total += (age - 8 + 1) * 2;
    return total;
}
```

`+=` прибавляет к накопителю. `Math.Min(a, b)` возвращает меньший из аргументов, ограничивая вклад интервала.

Промежуточная функция меняет форму вычисления: каждый интервал даёт вклад один раз. Она всё ещё не обеспечивает задуманную ошибку для отрицательных возрастов.

<details>
<summary>Почему здесь Math.Min, а не Math.Max?</summary>

При возрасте 4 достигнутая глубина равна 2, а длина блока — 5. Нам нужны 2 года вклада, а не все 5. При возрасте 8 достигнутая глубина была бы 6, но этот блок может дать только 5. Меньшее значение верно в обоих случаях.

[Закоммиченный цикл](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/Helper.cs) — это **более позднее согласованное состояние с началом отсчёта в нуле**, отличное от первоначальной версии с включающим началом, которая исправляется в видео. Этот сокращённый пример сохраняет её фактические вычисления:

```csharp
int ret = 0;
int start = 0;
foreach (var interval in config.Intervals)
{
    int end = start + interval.Length;
    if (catAge > start)
    {
        int depth = catAge - start;
        ret += Math.Min(interval.Length, depth) * interval.Coefficient;
    }
    start = end;
}
return ret;
```

Здесь `start` считает годы, уже отнесённые к предыдущим диапазонам, поэтому `catAge - start` — это глубина в следующем диапазоне. Положительная глубина ограничивается через `Math.Min`. Следующий раздел следует за конфигурацией из записи, а затем объясняет, почему слепая смена начала отсчёта приводит к багу.

## Исправление начала отсчёта интервалов

[00:35:53](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2153s) Первый обобщённый прогон неверен: вход ноль даёт 15. Интервал первого прожитого года отсчитывался от нуля. **Ошибка на единицу** — это расхождение на одну единицу там, где начинается или заканчивается отсчёт; вот конкретный пример.

[00:36:18](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2178s) Предлагается перенести поправку начала отсчёта в другое место формулы. [00:36:26](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2186s) `1` должна встречаться ровно один раз в нужном месте. [00:36:32](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2192s) Простое переключение начала на ноль с использованием строгого сравнения поначалу кажется эквивалентным. [00:36:40](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2200s) Более внимательный разбор отвергает эту предварительную правку в записанном виде; во время этой демонстрации сохраняется работающая форма с включающим началом.

[Закоммиченная вспомогательная функция](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/Helper.cs) — это **более поздний вариант с началом отсчёта в нуле**, а не точный снимок отвергнутой частичной правки. Она согласованно меняет сравнение и глубину. Эти упрощённые эквивалентные формулировки показывают все части, которые должны меняться вместе:

```csharp
// Inclusive lived-year start.
int start = 1;
if (age >= start)
    total += Math.Min(length, age - start + 1) * coefficient;

// Boundary after already-counted years, as in the committed helper.
int boundary = 0;
if (age > boundary)
    total += Math.Min(length, age - boundary) * coefficient;
```

Для последовательных интервалов продвигайте либо начало, либо границу на длину интервала. Поправка в видео касается несогласованного промежуточного сочетания; согласованная формула с началом отсчёта в нуле может работать, и закоммиченная вспомогательная функция это демонстрирует.

[00:36:45](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2205s) Существующие тесты делают такую замену и её исправления безопасными для попытки: они проверяют те же выходные данные, хотя внутренности изменились существенно. Уроку не требуется, чтобы ученик полагался на визуальное сходство формул.

<details>
<summary>Что произойдёт, если начало равно нулю, но глубина по-прежнему использует age - start + 1?</summary>

При возрасте ноль вычисленная глубина была бы единицей, если условие разрешает вход, что неверно засчитало бы первый прожитый год. Перенос начала отсчёта требует поменять сравнение и глубину вместе, а затем заново прогнать сохранённые случаи для нуля и границ.

</details>

## Обнаружение и запуск Fact

[00:38:56](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2336s) Импортируйте пространство имён `Xunit` и объявите тестовый **класс**, то есть тип, содержащий тестовые методы. [00:39:05](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2345s) **Метод** — это функция, объявленная внутри такого типа; она становится обнаруживаемой как тест, когда помечена подходящим **атрибутом**, то есть метаданными в квадратных скобках. [00:39:10](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2350s) `[Fact]` объявляет один непараметризованный тест xUnit.

[Окончательный файл параметризованного теста](https://github.com/AntonC9018/uniCourse_csharp/blob/e4b890a75d5e014ab00227c27ff6a35965acb9a1/examples/tests_example/tests/Tests.cs) — это **более позднее связанное состояние**, а не точный временный Fact. Упрощённая промежуточная форма сохраняет прежнюю отладочную проверку:

```csharp
using System.Diagnostics;
using Xunit;

public class Tests
{
    [Fact]
    public void Test1()
    {
        var config = CreateConfig();
        Debug.Assert(Helper.GetHumanAge_New(config, 0) == 0);
    }

    // CreateConfig is the factory described in the preceding sections.
}
```

Это иллюстрация формы с опущенной фабрикой. `public void` объявляет доступный метод, не возвращающий значение. Класс и атрибут дают структуру теста; для проверки поведения всё равно нужно содержательное тело.

1. [00:39:20](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2360s) Откройте обозреватель тестов в IDE.
2. Посмотрите обнаруженный тест.
3. Щёлкните по этому тесту правой кнопкой и запустите его отдельно.
4. [00:39:31](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2371s) Запись показывает, что раннер выполняет его.
5. [00:40:08](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2408s) Прогон завершается успешно.

**Обнаружение** означает поиск запускаемых тестов; оно отдельно от их успешности. [00:40:12](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2412s) Урок также показывает неприятности после попытки с более новыми версиями пакетов: IDE может перестать видеть тесты. Считайте это продемонстрированной проблемой инструмента и версий, а не доказательством, что любая более новая версия не работает. ## Замена дублирования на Theory

[00:40:23](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2423s) Одна и та же логика теста должна выполняться со многими наборами данных. Копирование тела в `Test1`, `Test2` и так далее дублирует проверку поведения. [00:40:35](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2435s) **Параметризованный тест** вместо этого переиспользует один метод с аргументами. Фактическое изменение — **Fact → Theory** с одним или несколькими атрибутами `InlineData`; сам по себе InlineData не заменяет Fact.

[00:40:46](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2446s) **Theory** помещает тест, управляемый данными. **InlineData** поставляет аргументы для одного запуска: здесь входной возраст и ожидаемый выход. [00:41:24](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2484s) Метод получает эти значения как параметры, сохраняя вход и ответ явными для каждого случая.

[Закоммиченный тест xUnit](https://github.com/AntonC9018/uniCourse_csharp/blob/e4b890a75d5e014ab00227c27ff6a35965acb9a1/examples/tests_example/tests/Tests.cs) сохраняет эту структуру. Упрощённый пример без фабрики конфигурации:

```csharp
[Theory]
[InlineData(0, 0)]
[InlineData(1, 15)]
[InlineData(2, 23)]
public void Test(int input, int expected)
{
    var config = CreateConfig();
    var actual = Helper.GetHumanAge_New(config, input);
    Assert.Equal(expected, actual);
}
```

Каждая строка InlineData поставляет значения для `input` и `expected` именно в таком порядке. Тело вычисляет `actual` по проверяемой реализации.

[00:41:34](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2494s) Вспомогательные функции **Assert** в xUnit — это тестовые утверждения, проверки, созданные для сообщения об упавшем тесте. [00:41:43](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2503s) **Assert.Equal** получает **сначала expected, затем actual** и сообщает о расхождении с обоими значениями. Это даёт более полезный вывод теста, чем голое отладочное условие.

[00:41:50](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2510s) Исходный тест-обёртка больше не нужен, раз параметризованный метод покрывает те же случаи, поэтому удалите его. [00:41:55](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2515s) Удалите неиспользуемые импорты после перехода с отладочных утверждений. Закоммиченный окончательный файл всё ещё содержит неиспользуемый импорт `System.Diagnostics`; это безобидный остаток, а не зависимость Assert.Equal. Сокращённый учебный пример его опускает.

## Разбор девяти наборов данных

[00:42:01](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2521s) Добавьте выбранные пары вход-выход как строки InlineData. Это **девять выбранных случаев**, а не все возможные целые входы. [Закоммиченные строки данных](https://github.com/AntonC9018/uniCourse_csharp/blob/e4b890a75d5e014ab00227c27ff6a35965acb9a1/examples/tests_example/tests/Tests.cs) являются авторитетными значениями; компактный пример ниже включает их все:

```csharp
[Theory]
[InlineData(0, 0)]
[InlineData(1, 15)]
[InlineData(2, 23)]
[InlineData(3, 26)]
[InlineData(4, 29)]
[InlineData(6, 35)]
[InlineData(7, 38)]
[InlineData(8, 40)]
[InlineData(15, 54)]
// Attached to Test(int input, int expected), shown above.
```

[00:42:10](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2530s) Соберите проект и снова посмотрите обнаружение. [00:42:22](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2542s) Обозреватель тестов показывает девять отдельных случаев, хотя параметризованный метод только один. Одна строка означает один набор входов, один запуск и один независимо сообщаемый результат.

[00:42:45](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2565s) Пары включают **0 → 0** и **8 → 40**. Сокращённая формулировка в записи вокруг 40 не должна превращаться в утверждение, что вход 40 ожидает выход 40; такой строки здесь нет. [00:42:52](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2572s) Алфавитный порядок обозревателя для чисел тоже может выглядеть странно. Текстовый порядок и числовой различаются: метка, начинающаяся с «15», может отсортироваться раньше метки, начинающейся с «2». Это меняет порядок отображения, а не то, что проверяет каждый тест.

<details>
<summary>Как один тестовый метод может выглядеть как девять тестов?</summary>

Theory даёт общее тело. Каждый атрибут InlineData предоставляет отдельный набор аргументов. Обнаружение разворачивает эти строки в независимо запускаемые и отчитываемые случаи.

</details>

## Изменение коэффициента, чтобы доказать падение тестов

[00:43:01](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2581s) Намеренно измените коэффициент в правилах реализации и запустите набор тестов. Падения показывают, что тесты проверяют наблюдаемое поведение, а не проходят, не задействуя преобразование. Это полезная самопроверка после введения набора тестов.

[00:43:32](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2612s) Демонстрация меняет последний коэффициент на 8, чтобы локализовать, какие случаи зависят от него. Произнесённое «только последний» сразу уточняется в расшифровке: **и возраст 8, и возраст 15 достигают этого интервала**. С закоммиченными девятью строками и остальными неизменными правилами разошлись бы оба ожидания; утверждать, что упадёт ровно один, неверно.

[Закоммиченные окончательные конфигурация и ожидания](https://github.com/AntonC9018/uniCourse_csharp/blob/e4b890a75d5e014ab00227c27ff6a35965acb9a1/examples/tests_example/tests/Tests.cs) — это **неизменённый эталон**, а не сохранённая копия намеренного изменения. Этот упрощённый эксперимент показывает правку:

```csharp
// Reference tail:
new Helper.Interval(Length: 99999, Coefficient: 2);

// Deliberate mutation for the demonstration:
new Helper.Interval(Length: 99999, Coefficient: 8);
```

При возрасте 8 изменённый результат был бы `38 + 1 * 8 = 46` вместо 40. При возрасте 15 это было бы `38 + 8 * 8 = 102` вместо 54. Более ранние случаи остаются ниже хвоста и не используют его коэффициент. Поэтому отчёт о тестах помогает определить затронутое правило. После эксперимента восстановите эталонный коэффициент, если важно сохранить исходное поведение.

## Проверка нескольких компонентов вместе

[00:43:47](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2627s) **Интеграционный тест** проверяет несколько компонентов, работающих вместе, а не только изолированную функцию. [00:44:04](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2644s) Он может тестировать как всю собранную систему, так и непосредственный результат взаимодействия.

[00:43:55](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2635s) Конкретный пример, описанный здесь, — это круговой обмен расписанием:

1. Прочитать сериализованное расписание из файла.
2. **Разобрать** сохранённое представление, истолковав его как структурированные данные.
3. Восстановить объект расписания.
4. **Сериализовать** этот объект, превратив его обратно в сохраняемое представление.
5. Сравнить два документа **JSON**, то есть структурированных представления данных, на эквивалентность.

Это проверяет состав чтения, разбора, восстановления и сериализации. Если сравнение семантическое на эквивалентность, одинаковые пробельные отступы и форматирование свойств не требуются.

В проверенной истории урока не нашлось собственного коммита с точным тестом расписания для этого другого приложения. Его источником служит состояние видео [00:43:55](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2635s); это концептуальная реконструкция, а не исполняемый код из того приложения:

```text
file JSON → parsed representation → schedule object → JSON
compare original and reconstructed JSON for equivalence
```

Интеграционное тестирование вводится как более широкий уровень проверки; пример с возрастом кошки остаётся конкретной реализацией unit-тестирования.

## Автоматизация ожидаемого вывода с помощью снимков

[00:44:22](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2662s) Раньше ожидаемые ответы получались так: запустить эталонную функцию, скопировать вывод и сохранить его. **Тест со снимком** автоматизирует этот порядок: **снимок** — это сохранённый вывод, используемый как эталон сравнения. [00:44:32](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2672s) Задайте вход; при первом прогоне фреймворк генерирует вывод и записывает его в отдельный файл. Сгенерированный результат всё равно нужно проверить, прежде чем ему можно доверять.

[00:44:41](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2681s) Преподаватель называет тесты со снимками особенно ценным инструментом и говорит, что использует их по всему своему проекту. Это объясняет выбор демонстрации; это его суждение о полезности, а не всеобщий рейтинг техник тестирования.

[00:45:00](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2700s) Пример другого приложения проверяет разбор для онлайн-журнала. **HTML** — это формат веб-документа, который читается. [00:45:18](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2718s) Изначально примера ожидаемого вывода не существует; первый прогон обработки создаёт его, а человек проверяет, выглядит ли он разумно.

[00:45:31](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2731s) Тест загружает страницу урока, извлекает данные функцией разбора, помещает извлечённые данные в представление результата/формы и делает снимок. [00:45:46](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2746s) Сохранённая форма похожа на JSON, но не является строгим JSON, что подчёркивает читаемость для проверки. Снимку необязательно самому соответствовать синтаксису JSON, чтобы быть полезным эталоном.

Точный исходник онлайн-журнала не входит в проверенные принадлежащие уроку файлы; эти состояния видео и служат свидетельством. Упрощённый конвейер рядом с демонстрацией [00:45:31](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2731s):

```text
lesson HTML
  → extraction function
  → extracted lesson data / result form
  → readable saved snapshot
```

Эта заметка не подставляет вместо показанного кода посторонний тест со снимками из репозитория и не заявляет о недоступном неизменяемом коммите-источнике.

## Разбор различия снимков

[00:46:00](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2760s) Если сохранённый вывод и новый вычисленный вывод расходятся, тест со снимком сообщает **diff**, то есть отображение их различий, вместо того чтобы молча пройти. [00:46:23](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2783s) Запуск показанного теста открывает окно сравнения с изменённой строкой. [00:46:33](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2793s) Конкретное расхождение — **новый вывод 3 против сохранённого вывода 6**.

[00:46:40](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2800s) Выберите, какая версия правильна. **Подтверждение** означает явное принятие проверенного вывода как эталона; это не автоматическое доказательство, что программа права.

1. Посмотрите фактический вывод и сохранённый снимок рядом.
2. [00:46:54](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2814s) Если сохранённое значение 6 правильно, исправьте код так, чтобы он давал это значение.
3. Если новое значение 3 правильно, подтвердите его как новый эталон.
4. [00:47:03](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2823s) Перезапустите тот же тест: после подтверждения нового эталона демонстрация проходит.

Состояние видео [00:46:33](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2793s) служит источником этого точного расхождения для другого приложения. Компактная реконструкция показанного сравнения:

```diff
- stored: 6
+ received: 3
```

Слова «stored» и «received» здесь — пояснительные подписи, а не точная строка файла. Подтверждение изменения лишь ради зелёного результата лишило бы тест ценности; решение должно следовать задуманному поведению.

<details>
<summary>Следует ли принимать каждый новый созданный снимок?</summary>

Нет. Сверьте его с задуманным поведением. Корректный новый вывод может заменить сохранённый эталон; некорректный означает, что нужно исправить код. Подтверждение записывает это решение для будущих сравнений.

</details>

## Подтверждение первого снимка и повторный запуск теста

[00:47:12](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2832s) Если файла снимка нет, первый прогон сообщает об отсутствии эталона и создаёт кандидата. [00:47:25](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2845s) Проверьте кандидата и подтверждайте его только тогда, когда его содержимое верно.

1. Запустите тест с выбранным входом.
2. Прочитайте новый сгенерированный вывод.
3. Подтвердите правильный эталон.
4. [00:47:33](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2853s) Запустите снова: сравните текущий результат с сохранённым снимком.
5. [00:47:38](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2858s) При неизменном входе и неизменном коде показанный вывод совпадает и тест проходит.
6. [00:47:51](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2871s) Измените входной HTML и запустите снова.
7. [00:48:05](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2885s) Изучите получившийся вариант и различие так же, как изучали прежний вывод.

Последний повторный запуск обсуждается как сравнение с уже существующим ожиданием для этого входа, а не как автоматически подтверждённый новый вариант. Его результат зависит от выбранного входного HTML. Если изменение этого входа меняет задуманный вывод, правка должна быть отражена в проверенном ожидании. Никакое ожидание не должно обновляться само без подтверждения.

Состояния видео [00:47:25](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2845s) и [00:48:05](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2885s) служат источником этого итогового порядка работы; точный код теста другого приложения не был доступен как проверенный неизменяемый файл. Упрощённое представление:

```text
first run: input → candidate output → review → approved snapshot
later run: same input → current output → compare with approved snapshot
changed input: changed output → inspect diff → approve or fix
```

[00:48:25](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2905s) Тот же способ проверки работает и когда вы намеренно изменили вход теста: изучите фактический и сохранённый вывод, решите, какой представляет задуманное поведение, и сохраните это решение как новый или оставленный эталон.

Тестирование со снимками здесь продемонстрировано, а его установка, полные исходники приложения и производственная политика стабильных данных снимков остаются за пределами урока. Существенное ограничение общее с порождёнными числовыми ожиданиями: подтверждённый исходный уровень защищает известное поведение, включая любую ошибку, которую по ошибке подтвердили.
