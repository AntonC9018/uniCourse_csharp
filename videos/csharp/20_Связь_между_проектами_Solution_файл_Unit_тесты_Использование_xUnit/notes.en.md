# Purpose and vocabulary

[00:00:00](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=0s) Build a runnable example with one project containing a function and another project exercising it. The point is to see what tests buy you: you can replace an implementation, keep its known behavior, and get a useful failure when you accidentally change it. The example converts a cat's age to a made-up human-age equivalent; it is a programming rule, not a biological model.

The lesson introduces these terms in the order in which they become useful:

- **Project, console template, and .NET SDK:** a project groups source files and build settings; a console template supplies a minimal executable starting point; the SDK supplies tools such as the `dotnet` command.
- **CLI:** a command-line interface, where commands are entered in a terminal.
- **MSBuild, compiler, and assembly:** MSBuild coordinates the build; the C# compiler translates C#; an assembly is the compiled unit produced from a project.
- **Project file and XML:** a `.csproj` is an XML configuration document; XML expresses structure with named opening and closing tags.
- **Build properties, targets, and shared imports:** properties hold settings, targets describe build actions, and imported files supply configuration. `Directory.Build.props` and `Directory.Build.targets` are conventional shared filenames.
- **Target framework, implicit usings, nullability, and output type:** these settings select the .NET API target, automatically imported namespaces, null-related analysis, and whether a project produces an executable or a library.
- **Library, project reference, and relative path:** a library supplies code to callers; a project reference connects one project to another; a relative path locates a file from the referring file's directory.
- **Solution, IDE, and IntelliSense:** a solution lists projects managed together; an integrated development environment such as Rider or Visual Studio provides editing and navigation; IntelliSense supplies code completion and related assistance.
- **Unit test, expected value, actual value, assertion, and regression:** a unit test checks an isolated behavior; expected is the reference answer, actual is the computed answer, an assertion checks their relationship, and a regression is previously working behavior broken by a change.
- **Boundary case and off-by-one error:** a boundary case lies at or beside a range limit; an off-by-one error counts one item too many or too few.
- **Refactoring and maintainability:** refactoring changes structure while preserving behavior; maintainability is the ease of understanding and changing that structure.
- **Interval, coefficient, depth, accumulator, and magic constant:** an interval is a range of years, a coefficient is its per-year contribution, depth is the number of years reached within it, an accumulator collects the total, and a magic constant hides the reason for a numeric value.
- **Lookup table and piecewise rule:** a lookup table stores precomputed input-output pairs; a piecewise rule selects a formula according to the input's range.
- **Debug.Assert, interpolated string, target-typed new, and collection expression:** Debug.Assert is a debugging check; an interpolated string inserts expression values into text; target-typed new infers a constructed type from context; a collection expression uses brackets to construct a collection such as an array.
- **Named constant, abstraction, configuration, array, and loop:** a named constant gives a fixed value a meaning; abstraction separates a general operation from particular rules; configuration stores those rules; an array holds several entries; a loop repeats an operation over them.
- **Class, struct, record struct, method, namespace, and attribute:** a class or struct defines a type; a record struct is a value type with record-generated members; a method is a function belonging to a type; a namespace groups names; an attribute attaches metadata to a declaration.
- **Package reference, test SDK, runner, and discovery:** a package reference brings in a dependency; the test SDK and runner support execution; discovery finds the methods and data sets that can be run as tests.
- **xUnit, NUnit, Fact, Theory, InlineData, and Assert.Equal:** xUnit and NUnit are .NET testing libraries; xUnit's Fact marks one test, Theory marks a parameterized test, InlineData supplies a row of arguments, and Assert.Equal compares expected and actual values.
- **Integration test, serialization, parsing, JSON, and HTML:** an integration test exercises several components together; serialization turns data into a stored representation, parsing reads that representation, JSON is a structured data format, and HTML describes web documents.
- **Snapshot, approval, and diff:** a snapshot is a saved output used as a reference; approval accepts a reviewed reference; a diff displays differences between stored and newly produced output.

# Build the first age conversion

[00:08:33](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=513s) The code under test converts an integer cat age into a human-age equivalent. [00:08:45](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=525s) A **unit test** will check this isolated function so that replacing its implementation does not silently change its answers.

[00:09:05](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=545s) Start with the special cases: zero years yields zero, and one year yields 15. [00:09:09](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=549s) The first-year coefficient is therefore 15. A **coefficient** here is the number of human-equivalent years contributed by one cat year. [00:09:17](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=557s) The first spoken estimate assigns 7 to the second year, giving approximately 22 in total. That estimate is provisional: the implementation and later explicit correction use **8**, giving **23**. Do not preserve 22 as the final expected answer.

[00:09:51](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=591s) For the inclusive **interval**, or range, 3 through 7, begin with the first two years' total and add 3 per year reached in the range. [00:10:16](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=616s) Beyond the interval, count the first two years and the full 3–7 block, then add the tail's contribution. [00:10:33](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=633s) The tail coefficient is corrected from 3 to **2**.

The [retained branch-based helper](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/Helper.cs) is a **related later experimental state**, not the exact baseline below: that committed old method has a second-year coefficient of 15 and a changed tail coefficient. This simplified reconstruction expresses that rule explicitly:

```csharp
static int Baseline(int age)
{
    if (age == 0) return 0;
    if (age == 1) return 15;
    if (age == 2) return 23;
    if (age >= 3 && age <= 7)
        return 23 + (age - 3 + 1) * 3;
    return 38 + (age - 8 + 1) * 2;
}
```

The `if` branches select a case; `return` ends the function with its result; `&&` requires both comparisons to hold; `>=` and `<=` include the endpoints. The final branch still lacks validation of negative ages, a bug discussed shortly.

[00:10:36](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=636s) The full 3–7 block must use its own coefficient, **3**, before the tail uses **2**. [00:10:43](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=643s) The years are 3, 4, 5, 6, 7: five years, not seven. [00:10:52](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=652s) The recording's spoken arithmetic includes 21 and a provisional total of 44, and [00:11:11](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=671s) treats that answer as a hand-checkable basis. Those remarks explain why a known-answer baseline is wanted, but are not a consistent derivation of the final rule. Five years at 3 contribute 15; the final seven-year total is `15 + 8 + 5 * 3 = 38`. The number 44 would be the final rule's answer at age 10, not age 7.

[00:11:26](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=686s) Once an answer-producing version is accepted as the reference, the next task is to freeze its known behavior in tests. # Use tests as a behavior reference

[00:11:40](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=700s) A function can give the right answers and still have a structure you want to improve. [00:11:59](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=719s) The goal is both correct behavior and an implementation organized as intended. [00:12:08](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=728s) Replacing an awkward function with a clearer one should keep the same outputs. [00:12:22](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=742s) These are two separate criteria: tests check results; the design of the rewrite addresses the structure.

**Refactoring** changes structure while preserving observable behavior. [00:12:47](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=767s) Tests make that change safer by retaining known answers independently of the implementation being edited. [00:13:31](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=811s) This is the main purpose emphasized here: detect a **regression**, previously working behavior broken by a code change. [00:13:32](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=812s) The earlier correct function supplies a reference against which the new one can be judged.

[00:13:57](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=837s) A second use is to isolate a concrete bug with exactly the input on which it appears. [00:14:06](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=846s) A test calls the function with a known input, gets the **actual value**, the computed result, and compares it with the **expected value**, the reference result. An **assertion** expresses the required relationship.

[00:14:21](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=861s) Exhaustively trying all inputs is unnecessary for this exercise. [00:14:50](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=890s) Choose a small subset representing the relevant ranges, particularly their boundaries, rather than attempting an unlimited domain. This provides evidence about selected behavior, not a mathematical proof of correctness for every input. A test generated from a flawed baseline can preserve the flaw.

# Rewrite the sum as interval contributions

[00:20:56](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1256s) An **interval** is a group of years sharing a coefficient, their per-year contribution. Separate the groups instead of hiding earlier totals inside each later branch. [00:21:16](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1276s) Age zero contributes nothing: although the label “0 through 0” names one value, it represents **zero lived years**, not a mathematically empty closed interval. The first lived-year group is 1 through 1 and contributes 15.

[00:21:27](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1287s) Resolve the second one-year group. [00:21:39](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1299s) The spoken value 7 is corrected to **8**; [00:21:49](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1309s) it is added to the value accumulated from the first year. [00:21:54](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1314s) Years 3 through 7 each contribute 3, and years 8 onward each contribute 2.

[00:22:18](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1338s) An **accumulator** is a variable that starts at zero and collects each contribution. [00:22:31](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1351s) The final range adds 2 for each year reached after the earlier blocks. [00:22:37](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1357s) This first additive rewrite uses explicit conditions rather than a loop, even though a loop would also work.

The [committed generalized helper](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/Helper.cs) is a **later related state**, not an exact copy of this intermediate additive function. The following simplified reconstruction preserves the interval rule established by the [final expectations](https://github.com/AntonC9018/uniCourse_csharp/blob/e4b890a75d5e014ab00227c27ff6a35965acb9a1/examples/tests_example/tests/Tests.cs):

```csharp
static int Additive(int age)
{
    int total = 0;
    if (age >= 1) total += 15;
    if (age >= 2) total += 8;
    if (age >= 3) total += Math.Min(5, age - 3 + 1) * 3;
    if (age >= 8) total += (age - 8 + 1) * 2;
    return total;
}
```

`+=` adds to the accumulator. `Math.Min(a, b)` returns the smaller of its arguments, limiting an interval's contribution.

1. [00:22:42](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1362s) Add the first one-year block if at least one year has been lived.
2. Add the second one-year block if at least two years have been lived.
3. [00:22:57](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1377s) For age three or above, calculate how much of the 3–7 block has been reached.
4. [00:23:12](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1392s) Measure its **depth**, the number of years reached within the block, as `age - 3 + 1`. At age 3 the depth is 1, not 0.
5. [00:23:30](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1410s) Its inclusive length is `7 - 3 + 1 = 5`.
6. [00:23:42](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1422s) Cap the depth so a later age cannot add more than the five years in that block.
7. [00:23:50](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1430s) The verbal “maximum” is corrected to **minimum**: choose the smaller of the full length and reached depth.
8. [00:24:02](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1442s) Multiply that capped depth by 3.
9. [00:24:08](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1448s) Apply the same contribution idea to the remaining range.
10. [00:24:18](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1458s) With an actually unbounded tail there is no upper cap; add its reached depth times 2.
11. [00:24:38](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1478s) The tail depth is `age - 8 + 1`, or `age - 7`. At age 8 it is **1**, not 7.
12. [00:24:45](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1485s) Add that depth multiplied by the tail coefficient.

The intermediate function changes the shape of the calculation: each interval contributes once. It still does not enforce the intended error for negative ages.

<details>
<summary>Why does Math.Min belong here rather than Math.Max?</summary>

At age 4 the reached depth is 2 and the block length is 5. We need 2 years of contribution, not all 5. At age 8 the reached depth would be 6, but this block may contribute only 5. The smaller value is correct in both cases.

</details>

# Choose abstraction according to expected change

[00:30:46](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1846s) A further improvement is an array of intervals and a loop over them. **Abstraction** separates the calculation mechanism from its particular rules; **configuration** is the data holding those rules. This makes adding a rule a data change rather than another branch.

[00:31:01](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1861s) The example's rule is unlikely to change; the remaining repetitive detail could be generated by an AI coding tool and left alone. [00:31:09](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1869s) The design tradeoff is time spent now versus benefit from future changes. Readable abstractions pay off when someone will actually modify the code.

[00:31:25](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1885s) For a stable coefficient function, the simple explicit version can be enough. [00:31:37](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=1897s) A changing game rule is a contrasting example: enemy health or attack might grow by one rate over four levels and another rate over the next three. A **record struct** is a value-type declaration that generates record-style members; `readonly` prevents mutation of its instance state. The positional declaration creates the named properties:

The `[]` after `Interval` means an array of intervals. `Config` groups that array into one parameter. This is a compact representation, not a full configuration-validation system.

[00:33:40](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2020s) Compute the end as current start plus this interval's length.

[00:33:53](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2033s) Limit a contribution at the range boundary instead of counting past it. [00:34:04](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2044s) For the inclusive-start version, reached depth is `age - start + 1`; it is **capped** by the interval length, not added to that length. [00:34:22](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2062s) Multiply the covered depth by the coefficient, then advance the start to the computed end.

The [committed loop](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/Helper.cs) is a **later consistent zero-origin state**, distinct from the initial inclusive-start version that is corrected in the video.
```csharp
int ret = 0;
int start = 0;
foreach (var interval in config.Intervals)
{
    int end = start + interval.Length;
    if (catAge > start)
    {
        int depth = catAge - start;
        ret += Math.Min(interval.Length, depth) * interval.Coefficient;

}
return ret;
```

# Fix the interval counting origin

[00:35:53](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2153s) The first generalized run is wrong: input zero produces 15. It counted the first lived-year interval from zero. An **off-by-one error** is a mismatch of one unit in where counting begins or ends; this is a concrete example.

[00:36:07](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2167s) Move the inclusive interval start to 1. [00:36:13](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2173s) The next run returns the expected values and the calculation reads clearly. [00:36:15](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2175s) Another spelling of the initialization is considered to avoid the mistake. [00:36:18](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2178s) The proposal is to move the origin adjustment elsewhere in the formula. [00:36:26](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2186s) The `1` must occur in the right place exactly once. [00:36:32](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2192s) Merely switching the start to zero and using a strict comparison initially looks equivalent. [00:36:40](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2200s) Closer inspection rejects that tentative edit as written; the working inclusive-start form is kept during this demonstration.

The [committed helper](https://github.com/AntonC9018/uniCourse_csharp/blob/b333fe75bfe90c7d2c965c1a57f477497887e5e2/examples/tests_example/code/Helper.cs) is a **later zero-origin variant**, not an exact capture of the rejected partial edit. It changes the comparison and depth consistently. These simplified equivalent formulations show all parts that must move together:

```csharp
// Inclusive lived-year start.
int start = 1;
if (age >= start)
    total += Math.Min(length, age - start + 1) * coefficient;

// Boundary after already-counted years, as in the committed helper.
int boundary = 0;
if (age > boundary)
    total += Math.Min(length, age - boundary) * coefficient;
```

For successive intervals, advance either start or boundary by the interval length. The video correction concerns an inconsistent intermediate combination; a consistent zero-origin formula can work, and the committed helper demonstrates it.

[00:36:45](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2205s) Existing tests make this replacement and its corrections safe to attempt: they check the same outputs even though the internals have changed substantially. The lesson does not need the learner to trust visual similarity between formulas.

<details>
<summary>What would happen if start were zero but depth still used age - start + 1?</summary>

</details>

# Replace duplication with a Theory

[00:40:23](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2423s) The same test logic must run with many data sets. Copying the body into `Test1`, `Test2`, and so on duplicates the behavior check. The actual change is **Fact → Theory**, with one or more `InlineData` attributes; InlineData does not replace Fact on its own.

[00:40:46](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2446s) **Theory** marks the data-driven test. **InlineData** supplies the arguments for one invocation: here, input age and expected output. # Test several components together

[00:43:47](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2627s) An **integration test** exercises several components working together, rather than just an isolated function. [00:44:04](https://www.youtube.com/watch?v=9DBoMknXbVQ&t=2644s) It may test a whole assembled system as well as the immediate result of an interaction.
