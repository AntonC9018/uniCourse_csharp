# Строим город поэтапно и сохраняем смысл готового результата

[00:00:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=0s) Урок развивает **паттерн «строитель» (builder)** на примере небольшого города с жителями и их домами. Начнём с обычных объектов, покажем ошибку с изменяемостью, а затем отделим редактируемую конфигурацию от готового города. Дальнейшие изменения добавляют общие значения по умолчанию, типизированные идентификаторы, общие методы конфигурации и альтернативные интерфейсы строителя.

Используемые на этом пути термины:

- **Доменная модель, сущность и агрегат:** данные, представляющие задачу; гражданин или дом — это сущность, а город объединяет связанные сущности.
- **Ссылка и граф объектов:** ссылка указывает на объект; ссылки между объектами образуют граф. Первая модель имеет связи «житель — дом», но намеренно не хранит сеть соседей по дому.
- **Массив, список, индекс, словарь и кэш:** массив имеет фиксированное число ячеек; список может расти; индекс обозначает ячейку; словарь сопоставляет ключи значениям; кэш хранит результат или выполненный ранее поиск.
- **Изменяемая и неизменяемая модель:** редактируемое состояние против состояния, которое остаётся фиксированным после создания. **Неглубокая защита** фиксирует значение или ссылку члена; **глубокая неизменяемость** защищает также всё, что доступно через них.
- **Конструктор, аксессор и резервное поле:** код инициализации, код чтения или записи свойства и хранилище, лежащее в основе свойства. **Свойство только для чтения** открывает чтение без сеттера; **readonly** запрещает переприсваивание поля; **init** разрешает присваивание свойства во время инициализации. **required** требует от вызывающей стороны инициализировать член, не проверяя его смысл.
- **Обнуляемое значение и оператор подавления проверки null:** значение, которого может не быть, и постфиксный `!`, подавляющий предупреждение компилятора о nullability без проверки самого значения.
- **Строитель и терминальный Build:** объект, управляющий незавершённой конфигурацией, и операция, которая её проверяет и создаёт итоговый результат.
- **Fluent API и неизменяемая копия:** вызовы конфигурации, сцепленные через возвращаемые значения; изменяемый fluent-строитель возвращает сам себя, а неизменяемый вариант создаёт новое значение.
- **Делегат, лямбда и фабрика:** вызываемое значение, встроенная функция вида `x => ...` и код, создающий объекты. Делегат конфигурации позволяет фабрике управлять тем, когда выполняется конфигурация.
- **Область видимости блока и область конфигурации:** блок ограничивает видимость локальной переменной; область конфигурации несёт значения по умолчанию, копируемые в создаваемые через неё объекты.
- **Единственная ответственность и инкапсуляция:** разделение таких задач, как хранение данных и создание объектов, и сокрытие деталей реализации за операциями. В этом примере изменяемые данные намеренно оставлены открытыми, а проверки и преобразования помещены в строители.
- **Проверка, исключение и контракт:** проверка допустимости входа, сообщение об ошибке через выброс исключения и описание предусловий (требований до вызова) и постусловий (гарантий после него). **Проверка наличия** выясняет, было ли значение передано; **проверка диапазона** — какие из переданных значений допустимы.
- **Сентинел (sentinel):** зарезервированное значение, означающее «не передано», в отличие от обычного допустимого значения.
- **Преобразование, сериализация и десериализация:** изменение одного представления в другое, запись данных в передаваемое представление и чтение обратно. Build в этом уроке в основном преобразует модели в памяти; сериализатор для базы данных или файла не реализуется.
- **struct, record struct и строго типизированный ID:** тип значения, тип значения с генерируемыми равенством по значению и хешированием и специализированная обёртка, идентифицирующая один вид сущности вместо нетипизированного числа.
- **Перегрузка, типобезопасность и необязательный ID:** методы с общим именем, но разными типами параметров; проверки компилятора против смешивания несовместимых категорий; и представление идентификатора, явно допускающее отсутствие.
- **Время жизни, сборка мусора и слабая ссылка:** как долго объект остаётся частью программы, автоматическое освобождение памяти и ссылка, которая сама по себе не удерживает свою цель.
- **Интерфейс, абстрактный строитель и переопределение (override):** контракт, реализуемый разными типами; абстракция строителя, способная скрывать разные модели или результаты; и замещающая реализация виртуального или абстрактного члена.
- **new с целевым типом, делегирование и дескриптор (handle):** синтаксис создания, тип которого берётся из контекста; пересылка операции другому объекту; и значение, сопоставляющее идентичность с контекстом, необходимым для её разрешения.
- **Метод расширения и this:** статический метод, вызываемый синтаксисом экземпляра, и текущий экземпляр; `this` у первого параметра метода расширения указывает его получателя.
- **Диспетчеризация интерфейса:** выбор реализации члена интерфейса для фактического получателя; сами методы расширения остаются статическими вызовами.
- **Явная реализация интерфейса:** член, предоставляемый именно через интерфейс, рядом с конкретным API, способным сохранить более специфичные типы.
- **Обёртка и финальный строитель:** объект вокруг другого объекта и отдельный объект, предоставляющий финальное создание из того же настроенного состояния.
- **ImmutableArray и разреженное множество (sparse set):** вариант неизменяемой коллекции в C# и альтернативная структура хранения по ключам; оба лишь упоминаются, но глубоко не реализуются.

Для практики этот урок сопровождается лабораторной работой [Builder](../../../labs/2_design/03_builder.md). Её упражнения развивают демонстрацию; SQL, персистентность через ORM, полноценные автоматизированные тесты и продвинутая агрегация ошибок в записи не завершены.

Примеры кода ниже — сокращённые учебные фрагменты, а не единая программа для копирования. Ссылки на коммиты указывают на изученный исторический исходный код. «Связанное состояние» означает, что коммит содержит нужный механизм, но не является точным снимком соответствующего момента записи. Коммиты с ID и абстрактным строителем содержат незавершённый код. Рабочий город называется неизменяемым по соглашению; публичные массивы и изменяемые поля элементов не делают его глубоко неизменяемым.

Это разрешение не делает безопасной любую операцию над жителем без дома: операция, читающая дом, обязана учитывать отсутствие.

## Что защищает неизменяемость

[00:02:42](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=162s) **Аксессор init** позволяет присваивать свойство при инициализации объекта и запрещает обычное последующее присваивание. Цель — предотвратить случайные изменения уже созданного города ([00:02:53](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=173s)). **Неизменяемый** означает, что состояние фиксировано после создания; **изменяемый** — что оно может меняться ([00:03:04](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=184s), [00:04:08](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=248s)).

[Связанное состояние исходного кода](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) показывает свойства города с `init` и ссылку на город, хранящуюся в конструкторе. Это две разные защиты:

```csharp
sealed class City
{
    public required Citizen[] Citizens { get; init; }
    public required Home[] Homes { get; init; }
}
sealed class CityLogic
{
    private readonly City _city;
    public CityLogic(City city) { _city = city; }
}
// city.Citizens = anotherArray; // обычное последующее переприсваивание запрещено
// city.Citizens[0] = anotherCitizen; // содержимое массива остаётся изменяемым
```

[00:03:14](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=194s) Компонент, получающий город, хочет, чтобы другой код не менял молча данные, от которых он зависит. Получение обычной ссылки на объект не даёт исключительного владения: кто-то ещё может удерживать ту же ссылку и менять объект во время вызова или между вызовами ([00:03:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=204s), [00:03:44](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=224s)). Настоящая неизменяемость позволяет компоненту полагаться на стабильные данные и сейчас, и позже ([00:03:53](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=233s)).

[00:04:12](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=252s) Изменяемый город можно вместо этого скопировать в приватное хранилище, принадлежащее компоненту. Устойчивая независимая копия может потребовать копирования и вложенных изменяемых данных, что стоит времени и памяти. Копирование только внешней ссылки не является защитой.

[00:04:35](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=275s) **Конструктор** — это код инициализации, выполняемый при создании экземпляра. Передача города через конструктор фиксирует, какой город использует логика. **Свойство только для чтения** открывает чтение без сеттера; оно не является по своей природе приватным. Его модификатор доступа определяет, кто может его читать. На [00:04:57](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=297s) важное ограничение состоит в том, что вызывающие не могут ему присваивать. **Поле readonly** точно так же не может быть переприсваиваемо обычным методом; его можно инициализировать при объявлении или в конструкторе объявляющего типа ([00:05:01](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=301s), [00:05:11](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=311s)). Ни то, ни другое не замораживает ссылочный объект. Присваивание в конструкторе, свойства только для чтения и поля readonly — полезные ограничения уровня языка, но не достаточные доказательства глубокой неизменяемости.

## Ломаем кэшированный поиск изменением

[00:05:18](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=318s) Свежее сканирование может отражать текущих жителей при каждом вызове. Чтобы не сканировать массив многократно, введите **кэш** — поиск, подготовленный ранее. **Словарь** сопоставляет ключ значению; здесь он сопоставляет имя жителя **индексу** массива, а не самому объекту Citizen ([00:05:29](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=329s)). Из-за этого его корректность зависит от того, чтобы массив сохранял тех же жителей в тех же ячейках.

[Связанное состояние исходного кода](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) содержит кэшированный поиск и CityChanger, используемые в этой демонстрации. Сокращённая реализация:

```csharp
// В конструкторе CityLogic:
for (int i = 0; i < city.Citizens.Length; i++)
    byName[city.Citizens[i].Name] = i;

// В Search:
if (!byName.TryGetValue(name, out int index))
    return null;
return city.Citizens[index];

// В CityChanger.Change:
city.Citizens[0] = new Citizen { Name = "Joe", Age = 18 };
```

Код сохранил ссылку на город и кэшированную позицию, а не замороженный снимок с John. Кэширование прямой ссылки на Citizen дало бы другое поведение: замена одной лишь ячейки массива не заменила бы эту кэшированную ссылку. Показанный дефект — это в точности кэш индексов поверх изменяемого хранилища ([00:08:48](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=528s)). На [00:08:57](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=537s) именно в этом состоит смысл изменяемого объекта: разрешённое изменение.

## Отделяем неглубокую защиту от неизменяемости

[00:09:13](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=553s) Защита свойства от переприсваивания — это **неглубокая защита**. **Глубокая неизменяемость** запретила бы также изменение ячеек массива и полей объектов жителя и дома. В C# есть неизменяемые типы коллекций, такие как ImmutableArray, элементы которых нельзя перезаписать присваиванием по индексу; неизменяемая коллекция всё же не замораживает изменяемые объекты, хранящиеся внутри неё.

[Связанное состояние исходного кода](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) сохраняет явный комментарий «не должен изменяться» рядом с изменяемыми массивами и публичными полями сущностей. Упрощённая иллюстрация:

```csharp
// Это неизменяемая модель, и её нельзя изменять.
sealed class City
{
    public required Citizen[] Citizens { get; init; }
    public required Home[] Homes { get; init; }
}
// Соглашение всё же может быть нарушено:
city.Citizens[0] = new Citizen { Name = "Joe", Age = 18 };
city.Citizens[0].Name = "Changed";
```

[00:09:45](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=585s) Исправление касается предположения логики: она была написана для неизменного города, но получила изменяемый. Безопасность требует настоящей гарантии стабильности ([00:10:01](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=601s)). Либо сделайте независимую копию отдельной функцией копирования, либо потребуйте от всей программы обращаться с общим городом как с неизменяемым. Когда потребители только читают его или заменяют новым экземпляром, зависимая логика становится проще ([00:10:17](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=617s)).

[00:10:42](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=642s) На этом этапе ячейки массива и объекты элементов остаются изменяемыми. Выбранный подход — **концептуальная неизменяемость**, соглашение, выраженное в комментарии и поддерживаемое каждым потребителем ([00:10:56](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=656s), [00:11:11](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=671s)). На [00:11:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=684s) снова рассматривается свойство только для чтения: оно не позволяет заменить ссылку на массив, но по-прежнему разрешает войти в массив и менять ячейки. Это ограничение данной модели, а не утверждение, что глубоко неизменяемые модели на C# невозможны.

[00:11:44](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=704s) Урок намеренно не разбирает глубоко ImmutableArray, потому что хочет перенести проектную идею на другие языки. Члены с доступом только для чтения или readonly могут ограничивать отдельные присваивания; struct хранит значения, а не отдельно выделенные ссылочные объекты, но сам по себе struct не запрещает изменение ([00:11:56](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=716s)). Каждый программист, работающий с этим соглашением, должен избегать изменения готовой модели ([00:12:11](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=731s)).

## Переносим создание в промежуточную область

[00:12:21](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=741s) У **массива** фиксированная длина и нет операции добавления. **Список** — это изменяемая расширяемая коллекция, нужная, пока число жителей ещё определяется. Свойство-массив, инициализируемое только при создании, тоже нельзя заменить позже. Это создаёт проблему построения: ещё до того как готовый объект передан кому-либо, все его требуемые зависимости уже должны быть на месте ([00:12:31](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=751s), [00:12:49](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=769s)).

[00:13:33](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=813s) Прежде чем расширять механизмы неизменяемости, рассмотрите прямую инициализацию. ## Знакомим типы строителей до их реализации

[00:15:54](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=954s) Чтобы сделать возможным поэтапный синтаксис конфигурации, сначала введите нужные ему типы. CityBuilder — внешний строитель ([00:16:05](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=965s)); его операция создания жителя должна возвращать CitizenBuilder, который и настраивает этого жителя ([00:16:08](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=968s)).

[Связанное состояние исходного кода](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) — это более поздняя реализованная версия, а не точный снимок этих пустых тел методов. Упрощённый набросок API:

```csharp
sealed class CityBuilder
{
    public CitizenBuilder Citizen() => /* регистрируем модель */ throw new NotImplementedException();
    public HomeBuilder Home() => /* регистрируем модель */ throw new NotImplementedException();
}
sealed class CitizenBuilder
{
    public void Name(string name) { /* позже: сохранить имя */ }
    public void Age(int age) { /* позже: сохранить возраст */ }
    public void Home(HomeBuilder home) { /* позже: сохранить модель дома */ }
}
sealed class HomeBuilder { }
```

На [00:16:44](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1004s) принимайте HomeBuilder, чтобы дом оставался настраиваемым; не требуйте готовый Home слишком рано. [00:17:03](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1023s) Следствие изменяемого поэтапного создания — более слабая полнота, проверяемая компилятором. Более ранний стиль создания с данными через required или через конструктор может требовать инициализации на определённой границе. Строитель позволяет жителю существовать до того, как задано его имя. [00:17:26](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1046s) Отсутствующее обязательное значение можно обнаружить при построении всего города. **Ошибка проверки** означает, что завершённая конфигурация не может дать приемлемый результат. ## Выбираем fluent-конфигурацию или неизменяемые копии

[00:17:44](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1064s) **Fluent API** объединяет вызовы конфигурации в одно выражение. Каждый вызов возвращает значение, на котором можно вызвать следующий. В изменяемом fluent-строителе это значение — тот же самый строитель ([00:17:52](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1072s), [00:18:06](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1086s)).

[Состояние fluent-строителя](https://github.com/AntonC9018/uniCourse_csharp/blob/1b854ac5ffdf93de5bd0410f39849f7889a1d280/examples/builder/Program.cs) содержит методы, возвращающие `this`. Сокращённый пример:

```csharp
public CitizenBuilder Name(string name)
{
    Model.Name = name;
    return this;
}
// city.Citizen().Name("John").Age(18).Home(home);
```

[00:18:17](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1097s) Возврат CitizenBuilder из Name поддерживает цепочку. Само по себе сцепление не требует изменения: альтернатива работает с **неизменяемыми копиями** — новыми значениями, сохраняющими все неизменённые поля ([00:18:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1104s)). На [00:18:30](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1110s) плата за это — выделения и расход памяти. WithHome может создать совершенно нового жителя с другим домом и скопировать остальные поля ([00:18:35](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1115s)); затем WithName может создать ещё одну замену с другим именем ([00:18:43](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1123s)). Эта альтернатива описана, но не реализована как выбранный строитель города. Fluent-стиль описывает синтаксис вызовов; изменяют ли вызовы состояние или копируют его — отдельное проектное решение.

## Рассмотрим делегат конфигурации

[00:18:50](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1130s) Другой стиль конфигурации принимает **делегат**, вызываемое значение, и выполняет конфигурацию внутри него. **Лямбда** — это встроенная функция вида `john => ...`. [Связанное состояние исходного кода](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) использует отдельные вызовы; это родственный механизм строителя, а не закоммиченная реализация делегатной альтернативы. Иллюстративная форма вызова:

```csharp
// Альтернативный набросок API, отсутствующий в закоммиченном CityBuilder:
city.Citizen(john =>
{
    john.Name("John");
    john.Age(18);
    john.Home(home);
});
```

[00:18:58](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1138s) Метод создания получает обратный вызов и управляет его вызовом. Внутри задайте имя и, если это уместно, дом ([00:19:04](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1144s)). Предполагаемая выгода в том, что локальная переменная жителя не доступна последующему коду как наполовину настроенный объект ([00:19:13](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1153s), [00:19:16](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1156s)).

[00:19:37](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1177s) John — локальный параметр, чья видимость заканчивается вместе с блоком обратного вызова. Типы параметров могут выводиться из делегата, ожидаемого API ([00:19:47](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1187s)). **Фабрика**, код, отвечающий за создание объекта, может также решить запустить обратный вызов позже ([00:19:50](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1190s)). Это проектные решения уровня API: C# не запрещает захватывать строитель во внешнюю переменную, поэтому сам по себе обратный вызов не является гарантией отсутствия утечки во время выполнения.

[00:19:58](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1198s) Плата в том, что локальная переменная John недоступна после конфигурации. Создайте дом до обратного вызова или внутри него ([00:20:06](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1206s)); если не сохранять и не возвращать ссылку, последующий код не сможет настроить этот локальный объект ([00:20:12](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1212s)). Вариант может возвращать созданный объект конфигурации, чтобы настройка продолжилась снаружи ([00:20:19](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1219s)).

[00:20:30](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=1230s) Реализация идёт по самой простой схеме: настроить изменяемую модель, а затем преобразовать её в предполагаемый неизменяемый результат. Варианты с обратными вызовами и неизменяемыми копиями здесь не реализуются.

## Храним конфигурацию в изменяемых моделях

```csharp
public CityScopeBuilder(CityBuilder city)
{

}
public CitizenBuilder Citizen()
{
    var citizen = CityBuilder.Citizen();

    if (defaults.Age != MutableCitizen.InvalidAge) citizen.Model.Age = defaults.Age;
    if (defaults.Name is { } name) citizen.Model.Name = name;
    if (defaults.Home is { } home) citizen.Model.Home = home;
    return citizen;
}
// CityBuilder.Scope(): return new(this);
```

```csharp
public Home Get(HomeId id) => Homes[id.Value];
```

[00:51:02](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3062s) Возврат null для несуществующего ID обсуждается как политика поиска. ## Используем перегрузки для сохранения типа сущности

[00:53:10](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3190s) Голый int не говорит, обозначает ли его значение дом или жителя. Два метода Get(int) нельзя различить только по типу возврата, поэтому нетипизированный проект обычно нуждается в именах вида GetHome и GetCitizen ([00:53:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3204s)).

[Связанное незавершённое состояние с ID](https://github.com/AntonC9018/uniCourse_csharp/blob/dcfd6225dc8e41c7cbdc4e86a79a7bf0b5c1f869/examples/builder/Program.cs) вводит различные обёртки HomeId и CitizenId и перегрузки. Сокращённый API:

```csharp
readonly record struct CitizenId(int Value);
readonly record struct HomeId(int Value);

public Citizen Get(CitizenId id) => Citizens[id.Value];
public Home Get(HomeId id) => Homes[id.Value];

// Get(new CitizenId(0)) selects Citizen.
// Get(new HomeId(0)) selects Home.
```

[00:53:39](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3219s) Ещё одна обёртка идентификатора позволяет использовать то же имя метода для другой сущности. Для поиска жителя изученный тип — **CitizenId**, а не CityId. CityId обозначал бы город и был бы отдельной сущностью.

[00:54:03](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3243s) **Перегрузка** использует то же имя метода, но другой тип параметра. На [00:54:10](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3250s) именно тип параметра выбирает операцию над сущностью. С CitizenId город разрешает жителя через Get ([00:54:29](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3269s)); без различных типов-обёрток вызывающий обязан выбрать отдельно именованную операцию ([00:54:45](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3285s)).

[00:54:59](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3299s) С голыми числами случайный вызов GetHome с индексом жителя может скомпилироваться. Он может молча вернуть дом вместо предполагаемого жителя ([00:55:17](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3317s)). Различные типы ID предотвращают такую путаницу: HomeId не является CitizenId, а правильная перегрузка Get выбирается по типу аргумента ([00:55:34](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3334s)). Две выгоды — меньше повторения имён сущностей в местах вызова и защита на этапе компиляции от смешивания категорий ключей ([00:55:37](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3337s)).

Эта **типобезопасность** не доказывает, что ключ существует, находится в диапазоне или принадлежит именно этому городу. Это отдельные проверки времени выполнения или проверки принадлежности.

Его тип подсказывает компилятору выбрать операцию с домом. Допустимость и принадлежность числового ключа по-прежнему требуют контракта поиска города и любых проверок времени выполнения.

## Понимаем плоское хранение и управление временем жизни

[00:55:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3355s) ID добавляют работы по реализации, но и прямые ссылки требуют работы при создании и преобразовании ([00:56:03](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3363s)). Строителю на основе ссылок понадобилось отображение «изменяемое → неизменяемое». ID может оставаться тем же ключом в разных представлениях, делая такое отображение отношений ненужным.

[Связанное незавершённое состояние с ID](https://github.com/AntonC9018/uniCourse_csharp/blob/dcfd6225dc8e41c7cbdc4e86a79a7bf0b5c1f869/examples/builder/Program.cs) фиксирует это намерение, включая удаление отображения домов на этапе построения. Упрощённое итоговое присваивание:

```csharp
// Once the whole ID migration is completed:
var citizen = new Citizen
{
    Name = name,
    Age = mut.Age,
    Home = mut.Home // same optional ID, not a converted Home reference
};
```

[00:56:13](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3373s) ID — это **ключ**, а не обязательно навсегда индекс массива. При хранении на основе словаря город может спросить, существует ли сущность с таким ключом. Это отделяет логическое **время жизни** — период, когда сущность принадлежит системе, — от времени жизни конкретного объекта в памяти.

[00:56:22](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3382s) Сильная ссылка на объект сохраняет достижимость своей цели. **Слабая ссылка** сама по себе не удерживает цель, но исчезновение цели тогда определяется **сборкой мусора** — автоматическим освобождением памяти, — а не правилами удаления сущностей программы.

Описанные преимущества:

- [00:56:51](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3411s) Более простая **десериализация**, восстанавливающая данные из сохранённого представления: чтение ключей вместо восстановления и пересвязывания графа объектных ссылок.
- [00:57:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3420s) Явное управление временем жизни: ключ можно проверить по текущему хранилищу даже после удаления сущности.
- [00:57:14](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3434s) Плоское хранение отношений: жители и дома ссылаются на сущности по ID, а не по прямым объектным ссылкам между сущностями.
- [00:57:27](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3447s) Более простое создание: словари отношений могут исчезнуть, когда ID сохраняются при преобразовании.

«Плоское» относится к ссылкам между сущностями; город по-прежнему владеет коллекциями объектов. Урок не реализует полноценную персистентность, удаление или production-систему управления временем жизни.

[00:57:35](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3455s) Работа с ID позволяет коду утверждать тождество или существование, не изучая каждое свойство дома. Таким образом, идентификатор сужает доступные операции до тех пор, пока вызывающий его не разрешит ([00:58:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3480s)). Это может уменьшить связанность между сущностями.

## Явно представляем отсутствующий дом

[00:58:06](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3486s) У жителя может не быть дома, поэтому представление через ID должно выражать отсутствие. **Сентинел**, зарезервированное значение вроде -1, может кодировать «нет» ([00:58:12](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3492s)). **Необязательный ID** упаковывает эту возможность в отдельный тип, вместо того чтобы оставлять её скрытой числовой договорённостью ([00:58:25](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3505s)).

[Связанное незавершённое состояние с ID](https://github.com/AntonC9018/uniCourse_csharp/blob/dcfd6225dc8e41c7cbdc4e86a79a7bf0b5c1f869/examples/builder/Program.cs) содержит OptionalHomeId и необязательную перегрузку Get. Сокращённая форма исходного кода:

```csharp
readonly record struct OptionalHomeId
{
    public static readonly HomeId NoHomeId = new(-1);
    public readonly HomeId Id;
    public bool IsNull => Id == NoHomeId;
    public OptionalHomeId(HomeId id) { Id = id; }
    public OptionalHomeId() : this(NoHomeId) { }
}
public Home? Get(OptionalHomeId id)
{
    if (id.IsNull) return null;
    return Get(id.Id);
}
```

Реализуйте это по шагам:

1. [00:58:39](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3519s) Добавьте конструктор без параметров, устанавливающий значение отсутствия.
2. [00:58:47](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3527s) Примите соглашение «нет дома» = -1.
3. [00:58:56](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3536s) Назовите это значение статическим полем readonly, а не повторяйте литерал. Это не константа времени компиляции `const` данного типа record struct.
4. [00:59:07](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3547s) Используйте синтаксис конструктора для инициализации маркера или необязательного значения. В изученном коде статический маркер вызывает числовой конструктор HomeId; конструктор OptionalHomeId без параметров делегирует ему.
5. [00:59:15](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3555s) Добавьте предикат отсутствия, названный в исходном коде IsNull.
6. [00:59:26](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3566s) Измените член жителя на OptionalHomeId.
7. [00:59:32](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3572s) Добавьте Get(OptionalHomeId). На [00:59:40](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3580s) возвращайте null при отсутствии, иначе делегируйте Get(HomeId).

[00:59:46](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3586s) Отсутствие теперь видно в типе и в результате `Home?`. Обнуляемые ссылочные аннотации могут выражать, предполагается ли ссылка обнуляемой, но они не добавляют проверок времени выполнения, запрещающих произвольной ссылке быть null ([01:00:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3600s)). OptionalHomeId — это пользовательский struct, а не `Nullable<HomeId>`.

Есть и краевой случай типа значения: `new OptionalHomeId()` вызывает объявленный конструктор без параметров, тогда как `default(OptionalHomeId)` и обнулённые элементы массива — нет. В этом проекте значение ID у default равно нулю, а не -1. Поэтому такое представление через сентинел не делает автоматически каждое необязательное значение по умолчанию равным «нет».

[01:00:10](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3610s) Плата — дополнительные типы-обёртки и перегрузки. Доступ по ID также добавляет проход через общий контекст города вместо немедленного доступа через сохранённую ссылку на Home ([01:00:20](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3620s), [01:00:40](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3640s)). Необязательный поиск может не дать Home, поэтому вызывающие обязаны обрабатывать обнуляемый результат ([01:00:56](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3656s)).

## Проносим идентификаторы через строители

[01:01:05](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3665s) Примените ту же идею ID к строителям. Вместо прямого хранения ссылки на MutableCitizen строитель жителя может хранить свой CitizenId и владеющего CityBuilder. **Геттер** разрешает текущую изменяемую модель из этого общего контекста ([01:01:17](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3677s)).

[Связанное незавершённое состояние с ID](https://github.com/AntonC9018/uniCourse_csharp/blob/dcfd6225dc8e41c7cbdc4e86a79a7bf0b5c1f869/examples/builder/Program.cs) имеет следующую форму строителя вместе с устаревшими вызывающи, которые всё ещё требуют миграции:

```csharp
public readonly CitizenId Id;
public readonly CityBuilder Builder;
public MutableCitizen Model => Builder.Model.Citizens[Id.Value];

public CitizenBuilder(CityBuilder builder, CitizenId citizenId)
{
    Builder = builder;
    Id = citizenId;
}
```

На этом промежуточном этапе изменение конструктора без изменения всех вызовов фабрик приводит к ошибкам компиляции. Это показывает предполагаемую форму дескриптора, а не завершённую сквозную реализацию.

[01:01:27](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3687s) Повторение пары «ID плюс владеющий строитель» в каждом строителе сущностей мотивирует общую структуру **обёртки** или дескриптора. Она заменила бы два поля и два аргумента одним переиспользуемым значением ([01:01:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3715s)). Обёртка инкапсулирует повторяющуюся логику разрешения; урок лишь набрасывает это улучшение, не предоставляя завершённого обобщённого фреймворка дескрипторов.

[01:02:07](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3727s) Важное упрощение Build в том, что ID отношений уже существуют. Ему не нужно строить отдельные словари связей с домами ([01:02:30](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3750s)). Ячейки сущностей могут нести эти ID напрямую. На [01:02:41](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3761s) существующая настройка полей всё ещё может использовать геттер Model, хотя строитель больше не хранит вторую ссылку на модель. Геттер должен разрешать модель через правильный владеющий контекст; «неизменённый синтаксис конфигурации» не означает, что каждый устаревший вызов или присваивание уже компилируется.

## Разделяем конфигурацию через методы расширения

[01:02:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3775s) Строитель жителя и область повторяют конфигурацию Name, Age и Home. Уберите эту продублированную логику присваиваний ([01:03:07](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3787s)). **Метод расширения** — это статический метод, определённый вне класса получателя, но вызываемый обычным синтаксисом экземпляра ([01:03:18](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3798s)).

[Состояние общей конфигурации](https://github.com/AntonC9018/uniCourse_csharp/blob/abda83011ba294a41288fa5aa2469ba0b51c1f8d/examples/builder/Program.cs) содержит интерфейс и методы расширения. Сокращённая реализация:

```csharp
interface ICitizenBuilder
{
    MutableCitizen Model { get; }
}
sealed class CitizenBuilder : ICitizenBuilder
{
    public MutableCitizen Model { get; }
    public CitizenBuilder(MutableCitizen model) { Model = model; }
}
static class CitizenBuilderExtensions
{
    public static void Name(this ICitizenBuilder builder, string name)
    {
        builder.Model.Name = name;
    }
}
// john.Name("John");
```

[01:03:27](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3807s) Введите ICitizenBuilder только с геттером Model. На [01:03:50](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3830s) перенесите общие методы в CitizenBuilderExtensions. На [01:04:06](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3846s) эти статические методы становятся единственной реализацией операций конфигурации. На [01:04:33](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3873s) поставьте `this` перед типом первого параметра, чтобы компилятор распознал получателя расширения.

Широкое утверждение записи о том, что в C# нет реализаций интерфейсов по умолчанию, требует оговорки: современный C# их поддерживает. Этот рефакторинг выбирает методы расширения; в примере тела интерфейсов по умолчанию не используются.

[01:04:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3895s) Геттер предоставляет настраиваемую изменяемую модель. **Автосвойство только для чтения** в классе имеет сгенерированное компилятором хранилище — **резервное поле** — и геттер; его можно присвоить во время создания. Реализованное вручную свойство может вместо этого возвращать уже существующее поле ([01:05:19](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3919s)). Объявление интерфейса `Model { get; }` задаёт контракт геттера; само по себе оно не создаёт поле хранилища в реализующем классе.

[01:05:46](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3946s) Область предоставляет `Model => CitizenBuilder.Model`, пересылая своему строителю значений по умолчанию. Общие расширения затем могут настраивать любого получателя без дублирования присваиваний полей. На [01:05:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3955s) получатель делает свою модель доступной через этот геттер. Возврат строителя — отдельное изменение fluent API: расширения в этом коммите возвращают void.

[01:06:02](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3962s) Убедитесь, что класс объявляет реализацию **ICitizenBuilder**. Кажущееся упоминание IEnumerable в транскрипте не соответствует изученной реализации; перечисление — не то, что делает эти методы конфигурации возможными. Существующие вызовы сохраняют форму, когда реализован правильный интерфейс. Обращение к геттеру интерфейса может повлечь диспетчеризацию интерфейса, тогда как сами методы расширения статичны ([01:06:18](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3978s)). На [01:06:35](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=3995s) логика установки полей переехала в одно общее место, избавив от повторений в области и в строителе жителя.

## Возвращаем тот же строитель для fluent-вызовов

[01:06:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4015s) Само по себе имя «строитель» не делает API fluent. Реализация должна возвращать то, на чём можно вызвать следующий метод конфигурации. Для изменяемой fluent-версии возвращается тот же объект ([01:07:07](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4027s)).

[Состояние fluent-строителя](https://github.com/AntonC9018/uniCourse_csharp/blob/1b854ac5ffdf93de5bd0410f39849f7889a1d280/examples/builder/Program.cs) содержит эту реализацию с возвратом конкретного типа:

```csharp
public CitizenBuilder Age(int age)
{
    if (age < 0) throw new InvalidOperationException("Invalid age");
    Model.Age = age;
    return this;
}
public CitizenBuilder Name(string name)
{
    Model.Name = name;
    return this;
}
// city.Citizen().Age(18).Name("John");
```

[01:07:31](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4051s) Нового жителя теперь можно настроить одним оператором без промежуточной локальной переменной. Этот коммит исследует конкретные fluent-методы, а не просто делает fluent все расширения из предыдущего коммита; это последовательные варианты API.

[01:07:42](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4062s) Компактность имеет и отладочную цену. Несколько операций в одной строке затрудняют остановку между вызовами обычными точками останова. Когда вызов выбрасывает исключение, номер строки может указывать на составное выражение, а не на то, какой шаг конфигурации не удался ([01:08:06](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4086s)). Отладчики всё же могут заходить внутрь методов или использовать точки останова на методах; забота урока — потеря удобных отдельных строк исходного кода.

[01:08:22](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4102s) Выгода здесь в основном в лаконичном синтаксисе и меньшем числе временных переменных. Для сложной настройки отдельные операторы могут быть удобнее для изучения.

[01:08:44](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4124s) Строители могут также оборачивать несколько объектов и предоставлять полезное представление их текущего состояния. Вложенные **обёртки**, объекты вокруг других объектов, могут показывать незавершённое значение на нескольких уровнях ([01:08:57](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4137s)). Это более широкое наблюдение о проектировании, а не утверждение, что незавершённая конфигурация этого города уже корректна или что Build можно пропустить.

## Скрываем разные модели за контрактами строителей

[01:09:21](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4161s) **Абстрактный строитель** может скрывать собственную модель или создавать другое итоговое представление ([01:09:35](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4175s)). «Абстрактный» здесь описывает роль в API; это не обязательно буквально абстрактный класс C#. Если реализации хранят разные модели, общий интерфейс должен предоставлять операции конфигурации, а не заставлять каждый строитель показывать MutableCitizen ([01:09:40](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4180s)).

[Связанное незавершённое состояние абстрактного строителя](https://github.com/AntonC9018/uniCourse_csharp/blob/ff2cc72527a8a97cf7b756d006ce5d6d8ac9724f/examples/builder/Program.cs) содержит операционные интерфейсы, но многие тела и члены интерфейсов не завершены. Упрощённый вариант fluent-интерфейса, обсуждавшийся при переходе:

```csharp
interface ICitizenBuilder
{
    ICitizenBuilder Name(string name);
    ICitizenBuilder Age(int age);
    ICitizenBuilder Home(IHomeBuilder home);
}
sealed class CitizenBuilder : ICitizenBuilder
{
    public CitizenBuilder Name(string name)
    {
        Model.Name = name;
        return this;
    }
    ICitizenBuilder ICitizenBuilder.Name(string name) => Name(name);
    // Age and Home implementations omitted in this teaching sketch.
}
```

[01:09:53](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4193s) Такой контракт может возвращать интерфейс, чтобы обобщённые клиенты продолжали настройку, не завися от конкретной модели. Изученный коммит абстрактного строителя вместо этого использует методы конфигурации с void; не путайте это сокращённое fluent-отклонение с его точным полным кодом.

[01:10:19](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4219s) Объявите, что конкретная реализация реализует интерфейс, и предоставьте требуемые члены. **Явная реализация интерфейса** определяет член специально для вызовов через интерфейс. Она может пересылать публичному методу, чей тип возврата — конкретный строитель ([01:10:31](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4231s)).

[01:10:56](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4256s) Прямые вызовы конкретного типа могут сохранять более специфичный тип строителя, тогда как вызовы через тип интерфейса предоставляют только общий контракт. Это разные члены, а не обычные перегрузки, различающиеся только типом возврата. Конкретная идентичность строителя важна, когда код клиента использует дополнительные конкретные операции ([01:11:05](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4265s)); общий интерфейс намеренно их не предоставляет.

## Адаптируем конкретные строители к общим интерфейсам

[01:11:22](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4282s) Общий интерфейс создаёт неудобную границу для Home. Конкретный метод ожидает собственный HomeBuilder, а интерфейс принимает IHomeBuilder. Адаптер должен проверить переданный строитель, прежде чем пересылать его.

[Связанное незавершённое состояние абстрактного строителя](https://github.com/AntonC9018/uniCourse_csharp/blob/ff2cc72527a8a97cf7b756d006ce5d6d8ac9724f/examples/builder/Program.cs) использует проверку и приведение в явных реализациях интерфейса. Сокращённый закоммиченный адаптер:

```csharp
void ICitizenBuilder.Home(IHomeBuilder home)
{
    Debug.Assert(home is HomeBuilder);
    Home((HomeBuilder)home);
}
public void Home(HomeBuilder home)
{
    Model.Home = home.Home;
}
```

[01:11:49](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4309s) Интерфейс допускает другую реализацию IHomeBuilder, тогда как этот метод предполагает конкретную. Предполагаемое использование также исходит из того, что дом приходит из того же контекста создания. Проверка только на конкретный тип не устанавливает принадлежность.

[01:12:14](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4334s) Поместите обработку менее специфичного параметра в явный член интерфейса. Прямые вызовы используют типизированный метод Home(HomeBuilder); вызовы через интерфейс — адаптер. На [01:12:45](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4365s) конкретное использование сохраняет прежнее поведение. На [01:12:54](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4374s) обобщённый код клиента может работать через общий интерфейс. Показанная проверка — диагностика для разработки, а не надёжная production-проверка типа или принадлежности; неудачное приведение всё равно может выбросить исключение.

[01:13:03](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4383s) Добавьте недостающую операцию Scope в ICityBuilder. Вынесите повторяющиеся операции создания в общий интерфейс. В изученном исходном коде члены — это **Citizen() и Home()**, а не WithCity и WithHome ([01:13:25](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4405s), [01:13:33](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4413s)).

Получившаяся форма контракта:

```csharp
interface ICityScopeCommon
{
    ICitizenBuilder Citizen();
    IHomeBuilder Home();
}
interface ICityBuilder : ICityScopeCommon
{
    ICityScopeBuilder Scope();
}
interface ICityScopeBuilder : ICitizenBuilder, ICityScopeCommon { }
```

[01:13:42](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4422s) Общие члены создания остаются; адаптер конфигурации Home обрабатывает зависимость от конкретной модели. На [01:13:57](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4437s) использование подходящих интерфейсов в зависимостях может уменьшить часть приведений к конкретным типам. **Интерфейсы C# наследуют другие интерфейсы, а не конкретные классы строителей.** Замена конкретного параметра интерфейсом также не устраняет требования принадлежности. Эта часть записи носит разведочный характер, и закоммиченное состояние абстрактного строителя остаётся незавершённым.

## Платите за абстракцию только тогда, когда она нужна

[01:14:16](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4456s) Создание на основе интерфейсов может позволить реализации хранить одну модель, отдельные поля, данные где-то ещё или совершенно иное представление. Это полезно, когда вызывающие должны поддерживать действительно разные строители.

[Связанное незавершённое состояние абстракции](https://github.com/AntonC9018/uniCourse_csharp/blob/ff2cc72527a8a97cf7b756d006ce5d6d8ac9724f/examples/builder/Program.cs) иллюстрирует отделение операционных контрактов от открытия модели. Его минимальная идея:

```csharp
interface IHomeBuilder
{
    void Address(string address);
}
// Each implementation decides where Address stores the value.
```

[01:14:46](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4486s) Не вводите интерфейс только потому, что эта гибкость когда-нибудь может пригодиться. Он добавляет код, адаптеры и контракты, которые нужно поддерживать ([01:14:55](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4495s)). Преждевременная подготовка каждого компонента к воображаемой замене модели может обойтись дороже, чем сэкономит ([01:15:02](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4502s)).

[01:15:19](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4519s) Когда действительно приходит новое требование, сделать существующий класс более общим может оказаться проще, чем с самого начала поддерживать большую абстрактную иерархию. Этот совет не запрещает интерфейсы; он требует конкретной потребности, оправдывающей их. Отступление урока в абстрактный строитель показывает и гибкость, и дополнительную незавершённую работу.

## Пусть строители создают разные реализации города

[01:15:42](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4542s) Если разные строители создают разные реализации города, тип возврата Build должен выражать общий контракт результата. Один вариант — абстрактный базовый класс City ([01:15:54](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4554s)); другой — **интерфейс ICity**, предоставляющий поиск сущностей ([01:16:00](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4560s)).

[Связанное незавершённое состояние интерфейса результата](https://github.com/AntonC9018/uniCourse_csharp/blob/ff2cc72527a8a97cf7b756d006ce5d6d8ac9724f/examples/builder/Program.cs) содержит ICity, реализацию City, набросок DynamicCity и отдельные интерфейсы строителей. В нём отсутствуют тела и есть несовместимые члены, поэтому это не продемонстрированная завершённая реализация. Сокращённый предполагаемый контракт:

```csharp
interface ICity
{
    Citizen Citizen(CitizenId id);
    Home Home(HomeId id);
}
// Possible array-backed member:
public Home Home(HomeId id) => Homes[id.Value];
// Possible dictionary-backed member:
// public Home Home(HomeId id) => Homes[id.Value];
```

[01:16:05](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4565s) Город по умолчанию может использовать массивы, а динамический город — словари или **разреженное множество (sparse set)**, альтернативу хранения по ключам, упомянутую здесь только. Каждая реализация должна удовлетворять одним и тем же операциям, извлекая данные из своих коллекций ([01:16:16](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4576s)). Тождество по одному ключу и контракт поиска важнее для клиентов, чем лежащая в основе коллекция.

[01:16:24](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4584s) Разные реализации финального построения могут создавать эти разные города. **Переопределение (override)** замещает виртуальный или абстрактный член базового класса в подклассе; отдельные реализации интерфейса также могут давать разное поведение Build без наследования. Изученные конкретные классы sealed и не содержат завершённой иерархии переопределений. На [01:17:26](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4646s) путь по умолчанию задуман как создающий City на основе массивов.

[01:17:34](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4654s) Этот City должен действительно реализовывать общие операции поиска. Соседняя реализация может строиться из собственной модели и предоставлять свои операции со своим хранилищем ([01:17:39](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4659s)). Запись описывает эту схему; исторические тела, которые выбрасывают NotImplementedException или не имеют возврата, не доказывают, что всё было завершено или проверено.

## Разделяем конфигурацию и финальное создание

[01:17:40](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4660s) Наконец разделим конфигурацию и финальное создание на два объекта. Строитель конфигурации предоставляет настройку; **финальный строитель** предоставляет только терминальный Build. Фабрики могут создавать и связывать эту пару с подходящими конкретными типами.

[Связанное незавершённое состояние разделённых строителей](https://github.com/AntonC9018/uniCourse_csharp/blob/ff2cc72527a8a97cf7b756d006ce5d6d8ac9724f/examples/builder/Program.cs) содержит ICityFinalBuilder и держатель ссылок на конфигурацию и финальный строитель. Сокращённая иллюстрация требуемого отношения общих состояний:

```csharp
interface ICityFinalBuilder
{
    ICity Build();
}
sealed class CityFinalBuilder : ICityFinalBuilder
{
    private readonly CityBuilder _configured;
    public CityFinalBuilder(CityBuilder configured) { _configured = configured; }
    public ICity Build() => _configured.Build();
}
// Both roles must refer to the same configured construction state.
```

Это иллюстративное завершение предложенной роли, а не полный класс, присутствующий в указанном коммите. Оно предполагает CityBuilder, результат которого реализует ICity.

[01:17:45](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4665s) CityFinalBuilder должен ссылаться на **тот же** CityBuilder, который использовался для конфигурации. На [01:17:53](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4673s) вызывающий выполняет финальное создание через эту роль финального строителя. Его результат должен исходить из настроенного состояния, а не из свежего пустого строителя. Транскрип продолжает это объяснение до [01:18:50](https://www.youtube.com/watch?v=lIKqnGtzQrA&t=4730s); приведённые более широкие интервалы группируют это заключительное обсуждение.

Урок заканчивается проектной границей: изменяемая промежуточная стадия позволяет настраивать объект постепенно, Build проверяет и преобразует её, а потребители полагаются на стабильность готовой модели. Рабочий пример остаётся неизменяемым по соглашению, а не по глубокому контролю. Полный проект на ImmutableArray, продвинутая диагностика, детали фабричного метода, обобщённые значения по умолчанию для домов, персистентность, динамическое хранилище и завершённые реализации альтернативных строителей находятся за рамками завершённой демонстрации.

## История изменений кода

Эти изученные состояния исходного кода перечислены от старых к новым. Незавершённые записи — это состояния разработки, а не успешные сборки.

- [c79a352](https://github.com/AntonC9018/uniCourse_csharp/blob/c79a3523fbee1e5fc4916628888cf269c26a0f67/examples/builder/Program.cs) — Строитель 1: рабочее преобразование на основе ссылок и значения по умолчанию области.
- [dcfd622](https://github.com/AntonC9018/uniCourse_csharp/blob/dcfd6225dc8e41c7cbdc4e86a79a7bf0b5c1f869/examples/builder/Program.cs) — Сломанный код с ID: типизированные ID и необязательный поиск, миграция не завершена.
- [abda830](https://github.com/AntonC9018/uniCourse_csharp/blob/abda83011ba294a41288fa5aa2469ba0b51c1f8d/examples/builder/Program.cs) — Интерфейс для методов конфигурации: один контракт Model и общие расширения.
- [1b854ac](https://github.com/AntonC9018/uniCourse_csharp/blob/1b854ac5ffdf93de5bd0410f39849f7889a1d280/examples/builder/Program.cs) — Fluent-строитель: конкретные методы конфигурации возвращают получателя.
- [ff2cc72](https://github.com/AntonC9018/uniCourse_csharp/blob/ff2cc72527a8a97cf7b756d006ce5d6d8ac9724f/examples/builder/Program.cs) — Абстрактный строитель: альтернативные контракты и роли финального создания, незавершено.
- [c6d7b18](https://github.com/AntonC9018/uniCourse_csharp/blob/c6d7b18cfbd1b0b8607b9434feb38dce0aae681f/examples/builder/Program.cs) — Возврат к рабочему строителю: итоговое состояние репозитория восстанавливает пример на основе ссылок.

Компактные примеры приведённых выше изменений, в том же порядке:

```csharp
// c79a352: изменяемый дом -> существующий итоговый дом
var home = mut.Home != null ? mutToImmutHome[mut.Home] : null;
// dcfd622: необязательный типизированный ID -> поиск через город
Home? resolved = c.Get(c.Citizens[0].Home);
// abda830: общая конфигурация через контракт модели
public static void Name(this ICitizenBuilder b, string name) { b.Model.Name = name; }
// 1b854a: fluent-конфигурация возвращает получателя
public CitizenBuilder Name(string name) { Model.Name = name; return this; }
// ff2cc72: разделённый контракт финального создания
interface ICityFinalBuilder { ICity Build(); }
// c6d7b18: восстановление рабочей сборки с прямыми ссылками и демонстрации возраста
var c = city.Build(); // configured ages: 18, 32, 32
```
