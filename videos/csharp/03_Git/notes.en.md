# Git: save, revisit, and share a project

[00:00:00](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=0s) The goal of this lesson is to turn a folder of working files into a project whose versions you can record, inspect, recover, and share. You will first work entirely on your computer, then connect that history to GitHub, develop one change on a separate branch, and bring the merged result back to your local files. The demonstration uses a small C++ program, although the course exercise applies these Git operations to your own project.

These terms will recur as the project develops:

- **Console, command, argument, option:** the console is the text-entry window; a command requests an action, an argument supplies information such as a filename, and an option changes how the command acts. **Help** documents available commands. **HTML** is the page format displayed by the demonstrated help viewer. **Clone** means copying a repository and its history.
- **Git, GitHub, repository, local, remote, protocol:** Git manages versions of files; GitHub hosts Git repositories and collaboration tools. A repository holds recorded project states and their history. Local work lives on this computer; a remote repository is another copy reached through a connection. A protocol specifies how the communicating programs exchange information.
- **Working directory and .git:** the working directory contains the files you edit; the hidden `.git` directory contains the local repository's history and settings.
- **Commit, message, identifier or hash, history, log, pager:** a commit records a prepared project state as one unit of changes. Its message explains the work, and its identifier distinguishes it from other commits. History connects these recorded states; a log displays them. A pager is an interactive viewer that may display a long log.
- **Untracked, tracked, modified, staging area:** an untracked file exists on disk without being managed by Git. A tracked file is under Git's management. Modified means its contents have changed. The staging area holds the versions selected for the next commit; adding a file there and committing it are separate steps.
- **Author identity and configuration scope:** commits store an author name and email. Configuration scope determines whether settings apply to this repository alone or, with `--global`, across repositories for the current user.
- **Source, C++, compiler, g++, executable, build output:** source is readable program text, here written in C++. A compiler translates it into a runnable executable; `g++` is the compiler used here. Build output is what compilation generates. **Architecture** is the machine design targeted by the build; **binary machine code** is the executable instruction representation. **Library functions** are reusable operations used by a program. Bytes and kilobytes (KB) measure file size.
- **.gitignore, ignore rule, wildcard, extension:** `.gitignore` specifies untracked files to omit from ordinary additions and status output. Each rule describes a name or pattern. The wildcard `*` matches variable filename text; an extension is an ending such as `.exe`.
- **Diff, restore, checkout:** a diff displays differences between file versions. Restore replaces working files from a selected source state. Checkout selects a commit or a branch and makes its state available in the working directory.
- **Branch, master, branch pointer, common commit:** a branch names a line of development; its pointer identifies the commit at its tip. `master` is the main branch name used in this recording. A common commit belongs to the histories of both branches before their later work separates.
- **Rebase, merge, merge commit, squash:** rebase reapplies a branch's own changes on a different base. Merge joins lines of history; a merge commit explicitly records that join. Squash combines the result of several commits into one commit.
- **Pull request, source branch, target or base branch:** a pull request proposes integration on GitHub. The source branch provides changes; the target, also called the base, is the branch that will receive them.
- **Remote name, origin, URL, HTTPS, SSH:** a remote name is a short label for a repository address. `origin` is the usual label for the principal remote; a URL is its address. HTTPS and SSH are alternative connection methods.
- **Upstream, push, pull, authentication:** an upstream associates a local branch with a remote branch. Push sends committed work; pull obtains and incorporates remote work. Authentication establishes permission to access the hosting account, separately from the author recorded in a commit.

## Choose how branch work enters the main history

[00:25:01](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1501s) The recommended workflow keeps `master` as the main line and starts a separate working branch from it. New feature or lab work happens on that branch before integration.

[00:25:13](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1513s) A **pull request** proposes that integration on GitHub. It belongs to the hosting service rather than the Git command set. The **source branch** supplies the changes, and the **target**, or base branch, receives them.

[00:25:45](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1545s) **Merge** joins histories. The variant explained here adds a **merge commit**, an entry that records the joining of two branches. [00:25:51](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1551s) Before merging into master, the instructor recommends updating the working branch by rebasing it onto master. [00:26:06](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1566s) The reason is to have the working branch already incorporate the main line's latest changes, making the subsequent integration simpler in this example. That preparation is not a promise that every possible combination of changes will be free of conflicts.

The preparation described in the recording is:

```cmd
git checkout experiment
git rebase master
```

[00:26:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1581s) **Squash** offers a different history shape: several commits' changes are combined into one resulting commit. [00:26:34](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1594s) Suppose one commit adds a file and another edits it. Squashing records their combined result in one entry instead of keeping those two entries separately in the target history.

A simplified sketch of that explanation is:

```text
Working branch:  commit adding file -> commit editing file
Squashed entry:  one commit with their combined result
```

These choices affect how history documents the work. The pull request demonstrated later uses the variant with an additional merge commit.

## Give the local project a remote address

[00:26:56](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1616s) GitHub now enters the workflow as a place to store a **remote repository**, an online copy beyond the computer holding your local project. [00:27:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1641s) This makes it possible to copy the project onto another machine, commit work locally, send it through GitHub, and obtain that work on another computer.

Set up the connection in this order:

1. [00:27:43](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1663s) Create a GitHub repository for the project. The lesson describes this as an online folder containing Git.
2. [00:28:00](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1680s) Leave it empty for this first connection to an existing local project. Avoiding pre-created files avoids having a separate initial remote state to reconcile with your existing work.
3. [00:28:05](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1685s) Add the connection with `git remote add`.
4. [00:28:19](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1699s) Choose a **remote name**, the short label that commands will use to look up this connection. [00:28:25](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1705s) `origin` is the convention for the principal remote; the name is a choice, rather than a special branch.
5. [00:28:33](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1713s) Supply the repository's **URL**, its address. The GitHub address shown accepts either the version ending in `.git` or the version without that suffix.
6. [00:28:42](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1722s) Use **HTTPS**, the connection method chosen for the introduction. **SSH** is mentioned as an alternative needing additional setup, which is not demonstrated here.
7. [00:28:50](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1730s) Confirm the configured address with `git remote show origin`.

The connection steps reduce to this example; replace OWNER and REPOSITORY with your address:

```cmd
git remote add origin https://github.com/OWNER/REPOSITORY.git
git remote show origin
```

At this intermediate point Git knows where the other repository is. The address alone has not sent the local history there.

## Publish the main branch with an upstream

[00:29:04](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1744s) Attempting the first `git push` reports that the branch has no **upstream**, the association between a local branch and its remote counterpart. **Push** sends committed work to the remote; the initial association tells later short push commands where that work should go.

1. [00:29:22](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1762s) Associate local master with master at origin. Git looks up the address stored under the remote name `origin`; master identifies the branch at that destination.
2. [00:29:58](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1798s) Follow the browser sign-in requested by the demonstrated installation. **Authentication** establishes permission to access the hosting service.
3. [00:30:15](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1815s) After authorization succeeds, the GitHub page shows the uploaded files and history. This is the first visible confirmation that the saved local work has reached the remote.

The first command below represents the failing attempt; the retry both sets the association and sends the work:

```cmd
git checkout master
git push
git push --set-upstream origin master
```

[00:30:43](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1843s) The uploaded commits display an author different from the account that owns the repository. [00:31:00](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1860s) This is consistent with the local author configuration. Commit authorship is the name and email saved when the commit is made; authentication is the permission used to send it. Uploading does not rewrite those author fields to match the logged-in account.

<details>
<summary>If you push using a different GitHub login, will the recorded author name become that login?</summary>

No. The commit already contains its author information. The login determines access to the destination, while the published commit retains the author information recorded locally.

</details>
