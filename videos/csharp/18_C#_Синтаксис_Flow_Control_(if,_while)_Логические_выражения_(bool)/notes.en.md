# C# flow control and bool expressions

## Lesson purpose and vocabulary

[00:00:00](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=0s) The aim is to explain the syntax behind decisions and repetition that earlier lessons used only in passing. A small “guess the number” game supplies the problem: choose a hidden number, read a guess, give a hint, and eventually repeat until the guess succeeds.

[00:00:11](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=11s) A check produces a value that can be saved and reused. Understanding that value connects the two subjects of the lesson: `bool` expressions and flow control.

The vocabulary you will meet is:

- **Flow control** determines which statement runs next. A **statement** is an instruction; a **block** groups statements inside `{ }`. A **branch** is an alternative execution path. **Indentation** is leading whitespace used to make structure readable.
- An **expression** computes a value. An **operator** performs an operation on its **operands**, the expressions it receives. **Assignment** (`=`) stores a value; **equality** (`==`) compares values; **inequality** (`!=`) checks that they differ. The **relational operators** `<`, `>`, `<=`, and `>=` compare order.
- **`bool`**, short for *boolean*, is the type with the two primitive logical values **`true`** and **`false`**. A **bool expression** computes one of those values. A **condition** uses that value to decide whether to execute code.
- **Negation** (`!`) reverses a bool value. **Logical AND** (`&&`) requires both operands to be true; **logical OR** (`||`) requires at least one to be true. Their **short-circuit**, or **lazy**, evaluation skips an operand when the result is already known. A **side effect**, such as printing, is an observable action during evaluation.
- **`if`** executes its attached statement when its condition is true. **`else`** supplies the false path. **`else if`** is an `if` used as the statement attached to an `else`. **Nesting** places one statement or block inside another.
- A **loop** repeats a statement or block, called its **body**. An **iteration** is one pass. **`while`** checks before each pass; **`while (true)`** has no stopping condition of its own. **`do ... while`** checks after the body, so the body runs at least once. **`for`** is another loop form named in the opening.
- **`break`** leaves the nearest enclosing loop. **`continue`** skips the rest of the current iteration and advances to the next condition check in the loops used here. **`return`** leaves the whole function, optionally providing its result.
- A **variable** stores a typed value. **Declaration** introduces it; **initialization** gives it an initial value. **Definite assignment** means the compiler can establish that a local variable has a value before it is read. **Scope** is the region where its name is available. A **sentinel** is an artificial value used to mark a special state.
- A **function** is callable code. A **function call** evaluates its **arguments**, the supplied values; **parameters** receive those values inside the function. A function's **return value** is its result.
- **`Random`** supplies pseudorandom numbers through `Next`. Its **`maxValue` parameter** is an exclusive upper bound. The **remainder operator** `%` gives the remainder after division.
- **Console input** arrives as text. **Parsing** attempts to convert that text to a number. **`int.TryParse`** reports success with a bool and writes the number through an **`out` parameter**, a parameter assigned by the called function.

## Combine checks with short circuit operators

[00:05:56](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=356s) Each comparison is a logical expression, so its result can be combined with another logical expression. The next example asks both whether `a` differs from `b` and whether `a` equals seven.

[00:06:18](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=378s) Logical AND, written `&&`, requires both checks to be true. This follows the same operation as the [related committed AND examples](https://github.com/AntonC9018/uniCourse_csharp/blob/19d6c57ba17ef64ef9c65d22808e2c3f682768c2/labs/1_basic/06_bool.md):

```csharp

```

1. At [00:06:35](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=395s), evaluate the left operand first: `5 != 6` is `true`.
2. At [00:06:46](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=406s), consider the alternative: if the left operand were false, AND would already be false and the right operand would not be evaluated.
3. Here the left operand is true, so at [00:07:00](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=420s) evaluate the right operand: `5 == 7` is false.
4. At [00:07:14](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=434s), `true && false` gives false. Both operands would need to be true for AND to give true.

[00:07:25](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=445s) Logical OR, written `||`, also evaluates left first. Change the operator:

```csharp

```

At [00:07:31](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=451s), a true left operand settles OR as true; the right operand is skipped. At [00:07:42](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=462s), a false left operand requires the right check. If that is false too, the entire result is false.

[00:07:54](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=474s) This is short-circuit, or lazy, evaluation: compute the second operand only when the first cannot decide the result. At [00:08:05](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=485s), the practical consequence is highlighted: a side effect in the skipped operand never happens.

| Operator | Left result | Is the right operand evaluated? |
| --- | --- | --- |
| `&&` | `false` | No; the result is already false |
| `&&` | `true` | Yes |
| `||` | `true` | No; the result is already true |
| `||` | `false` | Yes |


[00:16:01](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=961s) An explicit final `num > r` check is unnecessary for these integers. If the number is neither equal to `r` nor less than it, it must be greater.

[00:16:23](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=983s) An `if` together with its attached `else` counts as one statement. That entire inner pair can therefore be attached to the outer `else`. At [00:16:51](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1011s), removing the optional braces compresses the same chain:

```csharp
if (num == r) Console.WriteLine("Correct!");
else if (num < r) Console.WriteLine("Guess higher.");
else Console.WriteLine("Guess lower.");
```

The final `else` binds to the nearest available inner `if`; an extra outer block is not required for the chain. This explains the syntax, while braces remain the recommended way to display each branch's contents.

[00:17:05](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1025s) The recorded run still starts once and supplies a higher/lower hint. Correct branch selection has not yet created repetition.

## Repeat the input and comparison

[00:17:07](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1027s) To keep asking until the guess succeeds, identify the repeating portion first: reading a number and comparing it with the hidden number. At [00:17:09](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1029s), the proposed structure is an infinite loop with an explicit exit added inside.

1. Keep choosing the hidden number outside the repeating body, so it stays the same throughout the game.
2. Put input and comparison inside the body.
3. At [00:17:17](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1037s), identify a correct guess as the event that must leave the loop.

[00:17:22](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1042s) A `while` loop evaluates its bool condition before every iteration. An iteration is one pass through the body. Literal `true` always permits another pass:

```csharp
int r = new Random().Next(100);
while (true)
{
    int num = ReadNumber();
    CompareGuess(num, r);
}
```

This is a structural intermediate state; the input helper is completed later. At [00:17:30](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1050s), termination is deliberately postponed, so this version does not stop even after a correct guess.

[00:17:33](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1053s) A loop also attaches to one statement. A block groups several instructions; braces can be omitted for a single statement, using the same rule as `if`.

[00:18:04](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1084s) Finishing the body goes back to the loop's condition, rather than directly to the statement after the loop. While the condition remains true, the body repeats.

## Use break and continue inside the guessing loop

[00:18:20](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1100s) `break` exits the nearest enclosing loop. At [00:18:40](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1120s), its destination is clarified: the first statement after that loop, not another statement inside its body.

[00:18:55](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1135s) `continue` ends only the current iteration. In a `while`, it goes to the condition check before the next pass. For `while (true)`, that immediately permits another pass. This is an early transfer of control, distinct from `return`, which exits a function. See the [related committed break-and-continue examples](https://github.com/AntonC9018/uniCourse_csharp/blob/19d6c57ba17ef64ef9c65d22808e2c3f682768c2/labs/1_basic/07_flow_control.md) and the [C# jump-statement reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/jump-statements).

[00:19:06](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1146s) Put the unsuccessful cases first and the successful action last:

```csharp
while (true)
{
    int num = ReadNumber();

    if (num > r)
    {
        Console.WriteLine("Guess lower.");
        continue;
    }
    if (num < r)
    {
        Console.WriteLine("Guess higher.");
        continue;
    }

    Console.WriteLine("Correct!");
    break;
}
Console.WriteLine("Game finished.");
```

[00:19:35](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1175s) The greater-than and less-than checks choose the direction of the hint. At [00:19:40](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1180s), matching the less-than case excludes both equality and greater-than; it needs only its hint.

[00:19:52](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1192s) Each `continue` prevents the remaining checks and success message from running for a wrong guess. At [00:20:06](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1206s), equality need not be tested explicitly: an integer neither less nor greater than `r` must equal it.

[00:20:15](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1215s) Trace the three paths:

1. A high guess prints “Guess lower,” then `continue` skips the rest of the body.
2. A low guess prints “Guess higher,” then `continue` skips the rest.
3. An equal guess reaches success and `break`; execution continues after the loop.

[00:20:38](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1238s) The loop condition is reevaluated for each pass, including the next pass requested by `continue`. It happens to be the constant true here.

If an inner loop were added, which loop would a `break` inside it leave?

<details>
<summary>Answer</summary>

The nearest enclosing loop: the inner one. Execution would resume after that inner loop, still inside the outer loop if that is where the following statement lies.

</details>

## Move the exit test into the loop condition

[00:20:41](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1241s) Explore a different design. Move the number declaration outside the loop and remove `break`. A declaration introduces the variable; declaring it outside makes its name available to a condition outside the body.

```csharp
int num;
while (true)
{
    num = ReadNumber();
    if (num > r)
    {
        Console.WriteLine("Guess lower.");
        continue;
    }
    if (num < r)
    {
        Console.WriteLine("Guess higher.");
        continue;
    }
    Console.WriteLine("Correct!");
    // break removed
}
```

[00:20:54](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1254s) Without the exit, a correct guess reaches the end of the body and prompts again. Success alone does not stop an infinite loop.

[00:21:08](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1268s) The alternative is a loop condition that means “the number has not been guessed.” Move success printing after the loop:

```csharp
// Intermediate attempt: does not compile.
int num;
while (num != r)
{
    num = ReadNumber();
    if (num > r)
    {
        Console.WriteLine("Guess lower.");
    }
    else if (num < r)
    {
        Console.WriteLine("Guess higher.");
    }
}
Console.WriteLine("Correct!");
```

[00:21:34](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1294s) The intended behavior is to ask again while the guess is wrong and stop asking when it is right. At [00:21:37](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1297s), the check is described as moved from inside the body to the expression evaluated before each pass. At [00:21:44](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1304s), false is what stops the loop.

[00:21:59](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1319s) A body exit test and a loop continuation test therefore use opposite truth values: leave when `num == r`; keep looping when `num != r`.

[00:22:08](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1328s) This version exposes definite assignment: the compiler rejects reading the uninitialized local `num` in the first condition check. Declaring a local variable does not assign it a usable value.

[00:22:22](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1342s) The body needs to run at least once to obtain input before any exit check reads that input. That requirement motivates moving the check to the end.

## Try do while and compare the designs

[00:22:32](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1352s) A `do ... while` loop evaluates its condition after the body. Replace the opening `while` with `do`, put `while (condition)` after the closing brace, and add the required semicolon:

```csharp
int num;
do
{
    num = ReadNumber();
    if (num > r)
    {
        Console.WriteLine("Guess lower.");
    }
    else if (num < r)
    {
        Console.WriteLine("Guess higher.");
    }
}
while (num != r);
Console.WriteLine("Correct!");
```

The first pass assigns `num` before the condition reads it. Subsequent passes occur only while the condition is true. In this loop form, a `continue`, if used, would go to the condition at the bottom before another pass; it would not bypass that check.

[00:22:46](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1366s) Keeping a top-tested `while` would instead require initialization with a sentinel: an artificial starting value chosen not to represent real input. The lesson considers that worse than expressing the real requirement that input must happen first.

[00:23:02](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1382s) Compare scope, the region where a variable's name can be used. This `do ... while` form must declare the checked variable outside the body so the condition can access it. At [00:23:14](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1394s), that is contrasted with `while (true)` plus `break`, where the guess can be declared inside the body beside its uses. This is a property of this rewrite, not a rule requiring every variable in every do-while loop to be outside it.

[00:23:22](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1402s) The exit is also less visible in this design. At [00:23:31](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1411s), the comparison logic has two roles: the inner branches decide whether to print hints, while the loop condition separately decides whether another guess is needed. When neither hint branch applies, nothing is printed inside the body; success is handled after the loop.

[00:23:43](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1423s) With `break`, reaching the end of the unsuccessful checks naturally meant success and exit. The condition-based form restates that logic as its inverse in the continuation condition. Even if a saved bool flag is used, that flag still needs updating in the body and reading in the condition.

[00:24:05](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1445s) For this example, the instructor recommends `while (true)` with an explicit `break` when success is reached. It keeps the guess local and puts the reason for leaving next to the exit. This is a style recommendation illustrated by the game; the lesson still explains the valid condition-based and do-while alternatives.

## A failed parse is not a guess of zero

[00:24:17](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1457s) A remaining input problem appears: when the input helper returns zero after a failed conversion, the caller treats that zero as a real guess. This intermediate helper illustrates the flaw:

```csharp
static int ReadNumber()
{
    string? input = Console.ReadLine();
    if (!int.TryParse(input, out int num))
    {
        Console.WriteLine("Not a number.");
        return 0;
    }
    return num;
}
```

[00:24:28](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1468s) Preserve the distinction between parse failure and the value of the output parameter. For the `int.TryParse(string, out int)` overload used here, failure returns `false` and writes zero to the `out` variable; it does **not** preserve that variable's previous value. The [official TryParse parameter contract](https://learn.microsoft.com/en-us/dotnet/api/system.int32.tryparse?view=net-10.0#system-int32-tryparse(system-string-system-int32@)) confirms this correction.

Both the failed parse's zero and an explicit `return 0` on the error path must not be mistaken for successful user input. Zero is within the hidden number's range, so the game cannot use it alone to signal failure. The success bool is what distinguishes conversion success from failure.

What happens if the hidden number is zero and this helper receives `hello`?

<details>
<summary>Answer</summary>

The helper reports a parsing error but returns zero. A caller that compares only the returned integer can wrongly declare the guess correct. Retrying inside the helper prevents invalid text from becoming a guess.

</details>

## Retry input inside its own function

[00:24:44](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1484s) Identify the input operation's repeating unit: reading a new string, attempting conversion, and handling failure or returning a number. Wrap that whole operation in a loop. Repeating only parsing would keep retrying the same bad text.

[00:25:02](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1502s) On parse failure, print the error and use `continue` instead of returning zero:

```csharp
static int ReadNumber()
{
    while (true)
    {
        Console.Write("Enter a number: ");
        string? input = Console.ReadLine();
        if (!int.TryParse(input, out int num))
        {
            Console.WriteLine("Not a number. Try again.");
            continue;
        }
        return num;
    }
}
```

1. Read fresh console text.
2. Parse it. The bool return value indicates success; the `out` variable holds the numeric result.
3. On failure, report the problem and restart the iteration.
4. On success, return the integer to the guessing game.

[00:25:11](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1511s) Here `continue` returns to the `while (true)` check and then the first statement of the body. It skips the later `return num`; it does not mean “execute the next line.”

[00:25:24](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1524s) A successful parse needs no `break`. `return` exits the whole function and therefore also stops executing its loop. The [related committed return-inside-while example](https://github.com/AntonC9018/uniCourse_csharp/blob/19d6c57ba17ef64ef9c65d22808e2c3f682768c2/labs/1_basic/07_flow_control.md) demonstrates that same control transfer:

```csharp
// Successful path inside ReadNumber's loop:
return num; // leaves the function, not just the loop
```

[00:25:35](https://www.youtube.com/watch?v=mj9E9BhOAhU&t=1535s) The completed structure keeps requesting input until a valid integer is entered. Combined with the guessing loop, it separates two repetitions: the helper retries invalid text; the game retries valid but incorrect guesses.

The lesson validates conversion to an integer. Additional game rules, such as rejecting integer guesses outside 0–99, and handling the end of the console input stream are beyond the demonstrated implementation.
