# Virtual methods, abstract classes, and interfaces

This lesson builds a practical answer to one question: when several types offer the same operation, which implementation runs? Start with an animal and a bird, trace calls through references and virtual method tables, then use the same ideas to turn menu functions into objects that carry behavior and data. [00:00:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=10s)

The terms used along the way are:

- **Class, base class, derived class, inheritance, and is-a:** a class describes its instances. A derived class extends a base class and must be usable wherever that base type is expected. An **interface** expresses a behavior contract that a class implements; it is also usable as a reference type.
- **Object, reference, and receiver:** an object is a particular instance; a reference identifies that object; the receiver is the object on which an instance method runs. A **field** stores data in an object, while a **static field** belongs to the type.
- **Static type and runtime type:** the static type belongs to the variable or expression and governs compile-time member lookup. The runtime type belongs to the actual object. **Upcasting** views a derived object through a base-class or implemented-interface type without copying the object.
- **Method hiding and overriding:** hiding declares a separate same-named member; overriding supplies a new implementation of an inherited virtual operation. **Polymorphism** lets the same operation on a common reference type behave differently for different objects.
- **Virtual dispatch, static binding, and late binding:** virtual dispatch selects an override using the receiver's runtime type. A nonvirtual call has its target fixed by compile-time lookup. The video calls runtime implementation selection dynamic or late binding; this does not require C#'s `dynamic` keyword or make an instance method a `static` method.
- **Virtual method table (vtable), slot, and code address:** the lesson's conceptual table associates each virtual operation with a slot holding its implementation's code address. The illustrated addresses are labels, not measured process addresses.
- **`virtual`, `override`, and `abstract`:** `virtual` allows replacement in descendants; `override` makes that replacement; an abstract class cannot be constructed directly, and an abstract method declares an operation without supplying a body.
- **`sealed` and devirtualization:** a sealed class cannot have subclasses; a sealed override cannot be overridden again. Devirtualization is an optimization that turns a virtual operation into a direct call when its target is known.
- **`this` and `base`:** `this` denotes the current receiver; `base` accesses inherited members and, for the method calls here, selects the base implementation directly.
- **Parameter, return value, signature, overload, and expression-bodied method:** parameters receive call arguments, and a return value is a method's result; `void` means no returned value. A signature distinguishes methods by name and parameter information; overloads share a name but accept different parameter lists. A single-expression body can use `=>`. A covariant return is a more derived return type permitted by certain overrides; it is a modern clarification beyond the video's examples.
- **Composition and encapsulation:** composition represents an object using data or collaborating component objects instead of a subclass for every property. Encapsulation keeps implementation details inside their owning type.
- **Implicit and explicit interface implementation:** a matching public class method can satisfy an interface implicitly; an explicitly qualified implementation belongs to one named interface and is accessed through that interface.
- **Cast and type pattern:** a cast converts how a value is viewed; a pattern such as `value is ISpeak speaker` checks compatibility and introduces a variable with the tested type.
- **Delegate, method group, and action object:** a delegate is a callable value referring to method behavior; a method group is a method name used to select compatible behavior. An action object offers behavior through a class or interface contract and may also carry configuration.
- **Required member, object initializer, and constructor:** a required member must be initialized when constructing an object; an object initializer supplies member values after construction. A constructor controls how an instance is created, and a private constructor restricts creation to the declaring type.
- **Singleton and `readonly`:** a singleton exposes one shared instance. A readonly field restricts assignment to its reference; it does not automatically make the referenced object immutable.
- **Property and backing field:** a property exposes accessor-based member access; a backing field stores data used by an accessor. Property variants are deferred here.
- **Inferred type and null-forgiving annotation:** `var` infers a variable's static type from its initializer. `!` can suppress nullable-analysis warnings; it provides no runtime validation.
- **Access modifiers:** `public` permits outside access, `private` confines access to the declaring type, and `protected` permits access from the declaring class and its descendants.
- **Serialization and identifier:** serialization represents an object's data for storage or transfer; an identifier distinguishes an entity in that representation.

For practice, the repository's [polymorphism and interfaces lab](../../../labs/1_basic/18_interface.md) asks for menu commands implemented once with delegates and once with interfaces.

## From hidden methods to runtime dispatch

```csharp
class Animal
{
    public void Speak() => Console.WriteLine("???");
}
class Bird : Animal
{
    public new void Speak() => Console.WriteLine("chirp");
}

// Statements at the call site:
Bird bird = new Bird();
bird.Speak();               // chirp
Animal animal = bird;
animal.Speak();             // ???
```

The explicit `new` modifier marks **method hiding**, a separate same-named member; it makes the initial example's intention clear. Omitting that modifier does not turn the method into an override.

At [00:00:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=29s), a `Bird` variable calls the method visible on `Bird`. At [00:00:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=47s), assigning the same bird to an `Animal` variable is legal **upcasting**: every bird is an animal. At [00:01:00](https://www.youtube.com/watch?v=82vaxb6o_rg&t=60s), calling through that variable selects `Animal.Speak`. Its **static type**, `Animal`, controls member lookup; the compiler does not choose the hidden method merely because the object happens to be a bird.

The motivating change at [00:01:27](https://www.youtube.com/watch?v=82vaxb6o_rg&t=87s) is to keep that common `Animal` reference while selecting behavior from the object's **runtime type**. Make the operation virtual:

1. At [00:01:58](https://www.youtube.com/watch?v=82vaxb6o_rg&t=118s), add `virtual` to the base method.
2. Replace the derived declaration's hiding modifier with `override`.
3. Run the same base-typed call. At [00:02:06](https://www.youtube.com/watch?v=82vaxb6o_rg&t=126s), the observed result is the bird's output.

Simplified changed state:

```csharp
class Animal
{
    public virtual void Speak() => Console.WriteLine("???");
}
class Bird : Animal
{
    public override void Speak() => Console.WriteLine("chirp");
}

// Same object and same Animal-typed call:
Animal animal = new Bird();
animal.Speak();             // chirp
```

Here **`virtual`** permits runtime implementation selection, and **`override`** supplies a replacement for that inherited operation. The same call syntax can now express **polymorphism**. Methods are nonvirtual by default; a nonvirtual method cannot be overridden. [C# virtual reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/virtual).

## The virtual method table model

At [00:03:43](https://www.youtube.com/watch?v=82vaxb6o_rg&t=223s), runtime selection needs bookkeeping: how does a type identify its implementation of an operation? The lesson answers with a **virtual method table**, or vtable, associated with each type. A **slot** is one entry for an operation; its **code address** tells the conceptual dispatch mechanism where that implementation starts. [00:04:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=243s)

The table state illustrated at [00:04:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=250s)–[00:05:06](https://www.youtube.com/watch?v=82vaxb6o_rg&t=306s) is:

| Runtime type | Inherited Speak slot |
| --- | --- |
| Animal | 100: Animal.Speak |
| Bird | 200: Bird.Speak |

These are illustrative addresses. The slot belongs to the inherited virtual operation, not merely to any method with the text `Speak` in its name. `Bird` has that slot because `Animal` declared the operation virtual. **Overriding** replaces the implementation associated with the inherited slot; it does not introduce a second slot for that override.

If `Bird` supplied no override, its slot would retain the inherited address 100. [00:05:13](https://www.youtube.com/watch?v=82vaxb6o_rg&t=313s)

For the reconstructed virtual call `animal.Speak()` discussed at [00:05:26](https://www.youtube.com/watch?v=82vaxb6o_rg&t=326s):

```csharp
Animal animal = new Bird();
animal.Speak();              // Bird's Speak implementation
```

Trace the model in order:

1. Read the reference from the variable.
2. Reach the receiver object.
3. Follow the object's runtime-type information.
4. Read that type's slot for the selected virtual operation.
5. Invoke the code identified by the slot. [00:05:55](https://www.youtube.com/watch?v=82vaxb6o_rg&t=355s)

The variable's static type determines that `Speak` is a legal operation; the receiver's runtime type determines which override executes.

At [00:20:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1259s), `this.FlapWings()` is a virtual call on the current receiver. Its static type is Bird, but the receiver's runtime type is Sparrow, so Sparrow's override runs. At [00:21:08](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1268s), dropping `this.` changes nothing: the unqualified instance call still uses that receiver and the virtual operation.

At [00:21:13](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1273s), `base` is not a way for Bird to select Bird's own body: from Bird it would refer to Bird's base class. Ordinary calls on `this` therefore do not force Bird's default FlapWings body when the receiver is a Sparrow.

The solution at [00:21:22](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1282s)–[00:21:33](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1293s) extracts default logic into a **private nonvirtual helper**. Private access keeps it inside Bird; nonvirtual behavior fixes the call target.

Simplified changed state:

```csharp
class Bird
{
    private void FlapWingsDefault() => Console.WriteLine("bird flaps");

    public virtual void FlapWings() => FlapWingsDefault();
    public virtual void Speak() => FlapWingsDefault();
}
class Sparrow : Bird
{
    public override void FlapWings() => Console.WriteLine("sparrow flaps");
}
```

Speak can now deliberately run Bird's default logic. Choose an ordinary virtual call when descendants should customize behavior, and this helper when the default must run.

<details>
<summary>If Bird.Speak calls FlapWings without this, does Sparrow still participate?</summary>

Yes. An unqualified instance call supplies the same receiver implicitly. Removing this does not turn virtual dispatch into a base-qualified or nonvirtual call.

</details>

## Inheritance must mean is a

At [00:21:46](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1306s), **inheritance** means **is-a**, not merely “was created by” or “has some similar code.” If A derives from B, every A must be usable as a B. For Bird and Animal, every bird is an animal. [00:21:55](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1315s)

The A/B/C review at [00:22:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1323s)–[00:22:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1345s) warns against inventing a common base only to reuse code. A derived instance also carries inherited members, exposing a mismatch if it is not logically a base instance.

At [00:22:35](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1355s), a grandmother → mother → daughter family-origin story suggests the wrong programming hierarchy. The correction at [00:22:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1379s) is that `Daughter : Mother` would assert that every daughter is also a mother, not that a mother gave birth to her. Reversing the categories illustrates the intended relation: a grandmother is a mother, and a mother is someone's daughter. [00:23:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1394s) This is a teaching analogy; a real family model would need its own domain decisions.

At [00:23:36](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1416s)–[00:24:11](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1451s), a game example has a more suitable chain. An **identifier** distinguishes an entity for **serialization**, storing or transferring its data. A monster is an entity; an orc is a monster.

Simplified video-state hierarchy:

```csharp
class Entity
{
    public int Id;
}
class Monster : Entity
{
    public int Health;
    public int Attack;
}
class Orc : Monster { }
```

Every Orc therefore has entity identity and monster health and attack. These are inherited parts of the same object, and the type relationship conveys that an orc can be used wherever a monster or entity is expected.

## Represent properties with data and composition

At [00:24:17](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1457s), consider Animal → FlyingAnimal → BlackFlyingAnimal → Hawk. Encoding independent properties as subclasses becomes fragile: a black nonflying bear cannot fit beneath BlackFlyingAnimal. [00:24:40](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1480s)

At [00:24:53](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1493s), adding BlackAnimal suggests extracting the duplicated black behavior into that class, but then BlackFlyingAnimal would need both BlackAnimal and FlyingAnimal as class parents. C# permits only one direct base class. Multiple implemented interfaces, introduced later, do not remove that restriction. [00:25:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1510s)–[00:25:13](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1513s)

At [00:25:17](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1517s)–[00:25:24](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1524s), **composition** is the alternative: represent independently varying properties as data, or assemble objects from components, rather than demanding a subclass for each combination. The simple demonstration puts colour and a flying flag directly on Animal.

Simplified changed video state at [00:25:31](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1531s):

```csharp
class Animal
{
    public required string Name;
    public required string Colour;
    public bool CanFly;
}

// Statements at the call site:
var bear = new Animal { Name = "bear", Colour = "black", CanFly = false };
var hawk = new Animal { Name = "hawk", Colour = "black", CanFly = true };
```

At [00:25:44](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1544s), values distinguish the black bear from the black hawk without per-property subclasses. At [00:26:02](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1562s), the recommendation is to put such properties in data or composed component objects. Colour and flying ability vary independently; a class hierarchy should express a meaningful type relation.

At [00:26:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1574s)–[00:26:24](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1584s), the continuing review notes that a model distinguishing animal kinds consistently might introduce Mammal rather than use the generic Animal as though it meant specifically mammal. That leads to the next question: should the generic Animal category be directly constructible at all?

## Abstract and sealed classes

At [00:26:32](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1592s), the current ordinary Animal class can still be instantiated. The desired restriction at [00:26:40](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1600s)–[00:26:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1607s) is to retain Animal as a reference type and base category, while constructing only concrete kinds such as birds or mammals.

Make it an **abstract class**, a class that cannot be instantiated directly. Simplified changed state at [00:27:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1623s):

```csharp
abstract class Animal
{
    public virtual void Speak() => Console.WriteLine("???");
}
class Bird : Animal { }

// Statements at the call site:
// var animal = new Animal(); // compile-time error
Animal animal = new Bird();   // legal base-typed reference
```

The recorded direct-construction example stops compiling. An abstract class may still contain fields and implemented methods; making the class abstract does not automatically make each method abstract.

At [00:27:15](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1635s), the opposite inheritance restriction is **`sealed`**, meaning a class has no subclasses. At [00:27:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1645s)–[00:27:40](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1660s), the Sparrow example motivates using ordinary Bird instances with a name instead of another class.

Independent simplified sealed-class video state:

```csharp
sealed class Bird : Animal
{
    public required string Name;
    public override void Speak() => Console.WriteLine(Name);
}

// var bird = new Bird { Name = "sparrow" };
// class Sparrow : Bird { }  // compile-time error
```

At [00:27:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1679s), sealing communicates that the class is final and intended for direct use. At [00:28:12](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1692s)–[00:28:44](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1724s), knowing that a Bird receiver cannot belong to a Bird subclass can enable **devirtualization**: a runtime compiler may choose a direct call because the target is known. This is an optimization opportunity, not a C# guarantee that every such call uses a particular machine instruction. The method's observable behavior remains the same.

At [00:28:44](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1724s), a nonvirtual method similarly has a fixed implementation; at [00:28:46](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1726s), another way of reaching the optimization is deferred. The next section narrows sealing to one overridden operation.

## Seal one override

At [00:28:56](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1736s), seal an overridden method instead of sealing the whole class. A **sealed override** retains the inherited virtual contract but prevents further overrides of that operation.

Simplified video state:

```csharp
class Animal
{
    public virtual void Speak() => Console.WriteLine("???");
}
class Bird : Animal
{
    public sealed override void Speak() => Console.WriteLine("chirp");
}
class Sparrow : Bird
{
    // public override void Speak() { } // error: inherited member is sealed
}
```

At [00:29:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1743s), attempting to override the sealed member produces the shown compiler error that it cannot be overridden because it is sealed. The legal syntax is `sealed override`, not a new `sealed virtual` declaration. [C# sealed reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/sealed).

At [00:29:16](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1756s)–[00:29:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1765s), the model keeps Bird's implementation in the inherited slot for Bird and its subclasses. A Bird-typed call consequently has a fixed override target and may be optimized directly.

At [00:29:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1788s), an Animal-typed call is still a virtual operation: another Animal subtype might implement Speak differently. A particular runtime compiler can optimize known cases, but sealing one branch does not remove polymorphism from the Animal contract.

## Require behavior with abstract methods

At [00:30:05](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1805s), make the operation itself **abstract**: the declaring class specifies the method but supplies no body. An abstract instance method participates in the virtual contract without requiring an additional `virtual` modifier.

Simplified video state:

```csharp
abstract class Animal
{
    public abstract void Speak();
}
class Bird : Animal
{
    public override void Speak() => Console.WriteLine("chirp");
}
class Sparrow : Bird { }     // inherits Bird's implementation
```

At [00:30:16](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1816s)–[00:30:57](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1857s), an object cannot have abstract Animal as its exact runtime type, since Animal cannot be constructed. The receiver is a concrete descendant. In the table model, Animal's abstract Speak declares the slot without a default executable body.

The claim that an abstract class's table is “unused” concerns dispatch on an instance whose exact runtime type is that abstract class. Its contracts, implemented members, and type information still matter to descendants; abstract does not erase them.

At [00:30:57](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1857s)–[00:31:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1874s), Bird must supply an implementation to be concrete. Deleting the override gives a compile-time error. An intermediate abstract subclass may leave the operation abstract; it is every concrete descendant that must have a usable implementation.

At [00:31:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1885s)–[00:31:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1908s), Sparrow need not override again: Bird's implementation already satisfies the requirement, and Sparrow inherits it. The important condition is an implementation somewhere along its inherited path, not a repeated declaration in every descendant.

## Parameters return values and overloads

At [00:32:00](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1920s), virtual methods can take parameters and return values; `void Speak()` was only the simplest demonstration. An **override** must match the inherited operation's parameter signature and accessibility. The examples retain the same return type; modern C# also permits certain covariant return types, which this video does not teach. [C# override reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/override).

At [00:32:23](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1943s), **overloads** use the same name with different parameter lists. Each virtual overload is an independent operation in the table model.

Simplified video state:

```csharp
class Animal
{
    public virtual void Speak() => Console.WriteLine("???");
    public virtual void Speak(string message) => Console.WriteLine(message);
}
class Bird : Animal
{
    public override void Speak() => Console.WriteLine("chirp");
    public override void Speak(string message) => Console.WriteLine("bird: " + message);
}

// Statements at the call site:
Animal animal = new Bird();
animal.Speak();              // parameterless operation, Bird implementation
animal.Speak("hello");       // string operation, Bird implementation
```

At [00:32:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1949s) and [00:32:57](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1977s), the argument list distinguishes these operations. For these ordinary statically typed calls, **overload selection happens at compile time first**; virtual dispatch then picks an override of the selected signature. It is not a runtime scan that chooses any same-named overload after entering the table. [C# overload-resolution specification](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/expressions#1264-overload-resolution).

## Introduce an interface contract

At [00:33:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1994s), an **interface** resembles an abstract class in one important respect: it specifies operations that implementations must offer. At [00:33:18](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1998s), introduce a wings operation separately from Animal's Speak contract. C# convention prefixes interface names with `I`; the prefix is helpful but not required by the language. [00:33:19](https://www.youtube.com/watch?v=82vaxb6o_rg&t=1999s)–[00:33:32](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2012s)

Simplified initial interface video state at [00:33:37](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2017s):

```csharp
abstract class Animal
{
    public abstract void Speak();
}
interface IFlapWings
{
    void FlapWings();
}
class Bird : Animal, IFlapWings
{
    public override void Speak() => Console.WriteLine("chirp");
    // FlapWings is initially missing: this class does not compile.
}
```

The colon list expresses two distinct facts: Bird **inherits** Animal and **implements** IFlapWings. It does not give Bird two class parents. The lesson's diagram uses a class-hierarchy table for class virtual methods and a separate interface dispatch mapping for the interface contract. [00:33:44](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2024s)

At [00:33:58](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2038s), call syntax remains ordinary dot-and-parentheses syntax. At [00:34:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2043s), a declaration ending in `;` has no body. For the simple instance contract shown, the interface member is implicitly public and abstract; explicitly writing `public` is legal but unnecessary. [00:34:18](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2058s)–[00:34:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2087s)

An interface cannot be instantiated. [00:34:24](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2064s) Modern interfaces can also declare default bodies and other member forms; default implementation behavior is explicitly deferred at [00:34:11](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2051s). The lesson's “no fields” distinction means no **instance fields** for per-object state, not that modern interfaces can never declare any static state. [C# interface reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/interface).

At [00:34:51](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2091s), the compiler reports that Bird has not supplied FlapWings. Add a matching public implementation at [00:35:01](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2101s):

```csharp
class Bird : Animal, IFlapWings
{
    public override void Speak() => Console.WriteLine("chirp");
    public void FlapWings() => Console.WriteLine("bird flaps");
}
```

This is **implicit interface implementation**: the class's public method matches the interface operation's name, parameters, and return type. `override` is used for Speak because Animal declares that virtual contract; FlapWings does not need it merely to satisfy an interface.

At [00:35:12](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2112s)–[00:35:45](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2145s), the demonstration distinguishes class inheritance from interface membership, and permits implementation alongside an abstract base or without a custom base class. The interface contributes a behavior contract rather than inherited instance storage.

At [00:35:52](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2152s), after removing the base-class operation from a variant, keeping `override` on a method with no corresponding overridable class member causes a compiler error. Interface membership alone is not a class-method override. At [00:36:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2170s), the implementing class may itself declare that method `virtual`; then its descendants can override it normally.

## One object viewed through an interface

At [00:36:16](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2176s)–[00:36:36](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2196s), implementing IFlapWings means that Bird is usable as an IFlapWings value. **Upcasting to an interface** stores a reference to the same object; it does not construct an interface object or copy the bird.

Simplified video state:

```csharp
Bird bird = new Bird();
IFlapWings wings = bird;
wings.FlapWings();

// wings.Speak();             // error: not in IFlapWings
// new IFlapWings();          // error: an interface is not constructible
```

At [00:36:36](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2196s), the interface-typed variable is created or assigned and then used for the call. Interpret this as a reference declaration such as the one above, not as a constructor named `FlapWings.FlapWings()`.

At [00:36:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2189s) and [00:36:54](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2214s), the **static interface type** limits available operations to its contract. The Bird object still contains its other behavior and data, but an IFlapWings expression does not expose Speak.

At [00:37:01](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2221s)–[00:37:15](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2235s), the memory drawing again copies only an object reference. At [00:37:15](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2235s)–[00:38:07](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2287s), the object has one runtime type, Bird, whose dispatch information contains distinct class and interface mappings:

| Contract in this example | Operation | Concrete implementation |
| --- | --- | --- |
| Animal class hierarchy | Speak | Bird.Speak |
| IFlapWings interface | FlapWings | Bird.FlapWings |

Each shown contract contains one operation, so each illustrated table has one slot. Speak's slot is in the class hierarchy mapping, and FlapWings's slot is in the interface mapping. An IFlapWings table does not thereby acquire a Speak entry.

At [00:38:07](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2287s)–[00:38:12](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2292s), each entry identifies executable implementation code. A single object can offer both contracts; separate references do not imply separate copies of its fields.

## Follow an interface call

The interface call analysis at [00:38:19](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2299s)–[00:38:28](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2308s) adds a selection step to the earlier virtual-call model: choose the dispatch mapping for the requested interface, then choose its operation.

Simplified video call under analysis:

```csharp
Bird bird = new Bird();
IFlapWings wings = bird;
wings.FlapWings();
```

At [00:38:35](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2315s), a class virtual call uses the class hierarchy in which its operation was introduced. At [00:38:51](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2331s), assigning the interface variable still copies the same reference. At [00:38:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2339s)–[00:39:25](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2365s), trace an interface call as follows:

1. Read the reference stored in `wings`.
2. Reach the object and its runtime-type information.
3. Use the **static interface contract**, IFlapWings, to identify the needed interface mapping for that runtime type.
4. Locate the mapping's FlapWings operation.
5. Invoke its concrete implementation. [00:40:22](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2422s)
6. When that invocation returns, continue at the caller's next instruction. [00:40:31](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2431s)

At [00:39:32](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2372s)–[00:39:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2399s), the reason for runtime mapping is that an IFlapWings variable may refer to any compatible implementing class, not just Bird. Such classes may implement different sets of interfaces; the drawing cannot assume a single fixed table position in every object type.

At [00:39:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2399s), a class can implement many interfaces while inheriting one class. It cannot inherit arbitrary numbers of classes. At [00:40:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2414s), executing the call resolves the requested interface operation in this conceptual model. Actual runtimes can cache or optimize that resolution; the lesson does not promise a literal linear search or independently allocated table on every call.

The slot's code address is used to invoke the method. A method does not return the address of the caller's next instruction as its C# result; the machine's call/return mechanism resumes the caller. The distinction matters for the transcript's wording about continuing “from an address.”

## Use two interfaces without a custom base class

At [00:40:34](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2434s), extend the example to two interfaces. Replace the Animal contract with **ISpeak**, remove the now-inapplicable `override`, and change the call site's type. [00:40:39](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2439s)–[00:41:02](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2462s)

Simplified changed video state:

```csharp
interface ISpeak
{
    void Speak();
}
interface IFlapWings
{
    void FlapWings();
}
class Bird : ISpeak, IFlapWings
{
    public void Speak() => Console.WriteLine("chirp");
    public void FlapWings() => Console.WriteLine("bird flaps");
}

// Statements at the call site:
Bird bird = new Bird();
ISpeak speaker = bird;
IFlapWings wings = bird;
speaker.Speak();
wings.FlapWings();
```

At [00:40:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2447s), Bird has no explicitly declared custom base class; it still implicitly derives from `object`. Neither interface supplies instance fields. Interfaces resemble abstract behavior contracts here, but are not interchangeable with abstract classes that also carry shared instance state.

At [00:41:07](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2467s)–[00:41:32](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2492s), the Speak call uses ISpeak's mapping instead of the former Animal hierarchy mapping. The receiver's actual type selects the concrete implementation, and the caller resumes when it returns.

At [00:41:32](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2492s)–[00:41:50](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2510s), interface compatibility follows the familiar type-checking idea: if Bird implements ISpeak, a Bird can be used where ISpeak is expected. Known upcasts are implicit; a **cast** explicitly asks to view a compatible value as another type.

Simplified conversion and pattern state at [00:42:03](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2523s):

```csharp
object value = new Bird();
ISpeak speaker = (ISpeak)value;   // explicit conversion
speaker.Speak();

if (value is ISpeak checkedSpeaker)
    checkedSpeaker.Speak();        // pattern checks and declares the variable
```

The **type pattern** combines a compatibility test with a variable declaration. At [00:42:08](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2528s), further interface-typing elaboration stops because the relevant idea is the same compatibility mechanism already used for class inheritance.

## Virtual class methods can implement interface contracts

At [00:42:29](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2549s), make Bird's implicitly implementing Speak method virtual and add a subclass override. At [00:42:42](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2562s), construct the subclass.

Simplified video state:

```csharp
class Bird : ISpeak, IFlapWings
{
    public virtual void Speak() => Console.WriteLine("bird");
    public void FlapWings() => Console.WriteLine("bird flaps");
}
class Sparrow : Bird
{
    public override void Speak() => Console.WriteLine("sparrow");
}

// Statements at the call site:
ISpeak speaker = new Sparrow();
speaker.Speak();                    // sparrow
Bird bird = new Sparrow();
bird.Speak();                       // sparrow
```

At [00:42:46](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2566s), the recorded run prints the overridden implementation through the interface reference. “Overloaded” in a description of this result should be read as **overridden**: the demonstrated change replaces an inherited virtual implementation, rather than adding a different parameter list.

At [00:43:00](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2580s)–[00:43:18](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2598s), the model now includes both the class hierarchy's Speak operation and its ISpeak mapping. Bird's public virtual implementation satisfies the interface; Sparrow's override is reached through either route. This is not a requirement to write a second interface implementation in Sparrow.

At [00:43:30](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2610s), two interfaces may declare identical operations. At [00:44:00](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2640s), a single matching public method can implement both:

```csharp
interface ISpeak1
{
    void Speak();
}
class Bird : ISpeak, ISpeak1
{
    public virtual void Speak() => Console.WriteLine("bird");
}
class Sparrow : Bird
{
    public override void Speak() => Console.WriteLine("sparrow");
}
```

At [00:44:12](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2652s), both interface mappings can lead to the same virtual implementation path. Replacing that class operation with an override changes the observed implementation for both contracts in this example.

## Separate identical signatures explicitly

At [00:44:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2654s)–[00:44:17](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2657s), the new goal is different output for the same operation name depending on whether the same object is viewed as ISpeak or ISpeak1.

The first attempt at [00:44:19](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2659s) does not compile. Simplified failed video state:

```csharp
class Bird : ISpeak, ISpeak1
{
    public void Speak() => Console.WriteLine("Speak");
    public void Speak() => Console.WriteLine("Speak1"); // duplicate signature
}
```

Two methods with identical names and parameter lists cannot be distinguished just by their bodies. These are not two overloads.

At [00:45:06](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2706s)–[00:45:13](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2713s), use **explicit interface implementation**: remove `public` and qualify each method name with its interface.

Simplified corrected video state:

```csharp
class Bird : ISpeak, ISpeak1
{
    void ISpeak.Speak() => Console.WriteLine("Speak");
    void ISpeak1.Speak() => Console.WriteLine("Speak1");
}

// Same object, two interface views:
var bird = new Bird();
ISpeak first = bird;
ISpeak1 second = bird;
first.Speak();                       // Speak
second.Speak();                      // Speak1
// bird.Speak();                     // no public Speak member here
```

At [00:45:20](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2720s), the observed outputs are Speak and Speak1 respectively. At [00:45:30](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2730s), each interface operation has its own implementation mapping. Explicit implementations are accessible through the corresponding interface rather than as public methods on Bird. [C# explicit interface implementation guide](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/interfaces/explicit-interface-implementation).

At [00:45:50](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2750s), an interface may declare several methods, each with its own operation entry in the lesson's table model.

## Refactor menu functions into action objects

At [00:46:45](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2805s), the menu's action contract could have been an interface or an abstract class. The language does not force one design. An **action object** is an instance that exposes behavior through a common operation, optionally carrying data with it.

The starting design passes callable behavior to a common executor. Simplified related menu state, reconstructed for the comparison at [00:47:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2834s):

```csharp
static void Greeting(string name) => Console.WriteLine("Hello, " + name);

static void ExecuteAction(System.Action<string> action, string name)
{
    action(name);
}

// At a call site:
ExecuteAction(Greeting, "Ada");
```

Here the **delegate** is a callable value, and `Greeting` is a **method group** converted to a compatible delegate. The executor does not need to know which particular greeting method was supplied.

At [00:46:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2808s)–[00:47:08](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2828s), replace that callable parameter with an **abstract action class** whose Execute method is an abstract instance operation. The following intermediate reconstruction keeps the name parameter until the next refactoring:

```csharp
abstract class Action
{
    public abstract void Execute(string name);
}
class GreetingAction : Action
{
    public override void Execute(string name)
        => Console.WriteLine("Hello, " + name);
}

// In the menu's containing class:
static void ExecuteAction(Action action, string name)
{
    action.Execute(name);
}
```

This demonstration's `Action` is a custom class; `System.Action` is the framework delegate type used in the earlier reconstruction.

At [00:46:55](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2815s)–[00:47:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2834s), abstract Action cannot be directly constructed, so the executor receives a concrete descendant. It knows the **static type** Action, while the object retains its **runtime type**. At [00:47:39](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2859s), create GreetingAction and give it a nonstatic override, because Execute is an instance contract.

At [00:47:43](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2863s)–[00:47:50](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2870s), then again at [00:48:35](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2915s)–[00:48:42](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2922s), `action.Execute(...)` selects the receiver's concrete override. Supplying a GreetingAction reaches that method's first instruction. The dispatch mechanism is the same one already traced for Animal and Bird.

At [00:47:14](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2834s)–[00:47:33](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2853s), the comparison is about packaging behavior: a simple delegate provides one callable signature; a class contract can provide several separately named operations through one object reference. The lesson's single-function-address picture is a simplification. Delegates may refer to instance methods with target data and can combine multiple invocation entries. Those capabilities do not turn a delegate into a multi-method class contract. [C# delegate guide](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/delegates/).

Neither representation is universally better. The next change demonstrates why an object carrying explicitly named configuration can suit this menu.

## Store greeting configuration in the action

At [00:48:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2928s), GreetingAction gains information associated with that particular greeting. Put the name in a **field**, data stored in the action object, rather than passing it to every execution.

Apply the change in order:

1. At [00:49:00](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2940s), remove the name argument from Execute and read the stored field.
2. At [00:49:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2950s), delete the standalone greeting function.
3. At [00:49:16](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2956s), replace the method-group value with a constructed GreetingAction.
4. Supply its required name during construction. [00:49:16](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2956s)–[00:49:23](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2963s)

Simplified changed video state:

```csharp
abstract class Action
{
    public abstract void Execute();
}
class GreetingAction : Action
{
    public required string Name;
    public override void Execute() => Console.WriteLine("Hello, " + Name);
}

// In the menu's containing class:
static void ExecuteAction(Action action) => action.Execute();

// At a call site:
ExecuteAction(new GreetingAction { Name = "Ada" });
```

The **required member** makes construction supply Name; the **object initializer** sets it on the new instance. A name is now stored alongside the choice of implementation, so no execution-time name argument is necessary.

At [00:49:23](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2963s)–[00:49:34](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2974s), the object reference packages both behavior and configuration. The runtime type leads to Execute's implementation; the object's fields supply that implementation's data. Each derived action can add its own configuration without changing the abstract base contract.

At [00:49:47](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2987s), the same conversion is still required for the other menu actions. Greeting is the first worked case, not the completed menu refactoring.

## Finish the other action classes

At [00:49:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=2999s), convert Addition from a function to AdditionAction. Move the read helper into a private method, keeping the input implementation inside the action. At [00:50:11](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3011s), extract the no-operation function into NothingAction.

Simplified changed video state:

```csharp
class AdditionAction : Action
{
    private static int Read() => int.Parse(Console.ReadLine()!);

    public override void Execute()
    {
        int first = Read();
        int second = Read();
        Console.WriteLine(first + second);
    }
}
class NothingAction : Action
{
    public override void Execute() { }
}

// Updated call sites:
ExecuteAction(new AdditionAction());
ExecuteAction(new NothingAction());
```

The one-line Read above is intentionally shortened to focus on method placement; it is not a claim that the recording replaced its existing input-validation helper with this exact body. Keep the original helper's validation behavior when applying the refactoring to a real menu. The sample's null-forgiving `!` only suppresses nullable-analysis warnings; it does not make missing or invalid input safe.

At [00:50:23](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3023s)–[00:50:35](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3035s), **abstract Execute** requires even NothingAction to provide a body. Its explicit empty override means “this action intentionally does nothing.” A concrete derived class cannot simply omit the method.

At [00:50:35](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3035s)–[00:50:45](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3045s), replacing the abstract declaration with a virtual empty body would change that safeguard: a forgotten override would silently inherit the default no-operation behavior. Abstract makes the obligation visible to the compiler.

At [00:50:48](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3048s), call sites now construct AdditionAction and NothingAction instead of naming the old function groups. The executor remains uniform: receive Action and invoke Execute polymorphically.

## Reuse a stateless action as a singleton

At [00:50:56](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3056s), AdditionAction has no per-instance configuration or fields and does not change object state between executions. Reading new console input does not by itself require a new action instance.

At [00:50:56](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3056s)–[00:51:10](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3070s), a **singleton** exposes one shared instance rather than constructing a fresh instance for each menu selection. This can avoid repeated allocation of a small object when there is no distinct instance state to preserve. GreetingAction, whose Name differs between greetings, motivates a different choice.

Build the singleton in the demonstrated order:

1. At [00:51:24](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3084s), restrict outside construction with a **private constructor**.
2. At [00:51:59](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3119s), trying to construct the action from outside, even with an object initializer, fails: construction still needs access to that constructor.
3. At [00:52:20](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3140s), add a **static field**, associated with the type rather than each instance, that holds the shared object.
4. At [00:52:27](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3147s), use that field at the call site.
5. At [00:52:34](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3154s), add **readonly** to prevent ordinary later replacement of the shared reference.

Simplified final singleton video state:

```csharp
class AdditionAction : Action
{
    private AdditionAction() { }

    public static readonly AdditionAction Instance = new AdditionAction();

    private static int Read() => int.Parse(Console.ReadLine()!);

    public override void Execute()
    {
        int first = Read();
        int second = Read();
        Console.WriteLine(first + second);
    }
}

// At a call site:
ExecuteAction(AdditionAction.Instance);
// new AdditionAction();                 // error: private constructor
// AdditionAction.Instance = null!;      // error: readonly field
```

The private constructor is accessible to the field initializer inside AdditionAction, so that initializer can create the object. Outside callers reuse the resulting reference.

At [00:52:36](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3156s)–[00:52:55](https://www.youtube.com/watch?v=82vaxb6o_rg&t=3175s), the demonstrated attempt to reassign the readonly field fails to compile. The precise rule is broader than “assigned exactly once at declaration”: readonly fields can also be assigned in the corresponding declaring type's constructor context, including a static constructor for a static field. They cannot be reassigned by ordinary later caller code. Readonly fixes the reference here; it would not prevent mutations of fields inside a mutable shared object. [C# readonly reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/readonly).

<details>
<summary>Why share AdditionAction but construct GreetingAction with a name?</summary>

AdditionAction has no per-instance configuration in this demonstration, so all callers can reuse it. GreetingAction stores a particular Name, so distinct greetings may need distinct configured objects. The decision follows the object's data and lifetime, not just the fact that both expose Execute.

</details>
