# Inherited member lookup and composition

[00:00:00](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=0s) This lesson asks two connected questions: how does C# find a member when classes inherit from one another, and is inheritance a useful way to model an animal's abilities? Start with a small base/derived example, build a working animal hierarchy, then replace the capability hierarchy with composition.

The vocabulary you will need is:

- **Class, object, and reference:** a class defines a type; an object is an instance of that type; a reference lets a variable refer to that object.
- **Member, field, and method:** a member belongs to a class; a field stores state; a method performs an operation.
- **Inheritance, base class, and derived class (subclass):** a derived class extends a base class and inherits its members. The examples use publicly accessible members.
- **Compiler, scoping, and member lookup:** the compiler checks and translates source code; scoping and lookup determine which member a name refers to.
- **Access modifier:** a keyword controlling accessibility; the samples use `public` to permit access from their call sites.
- **Instance and static methods:** an instance method operates with an object as its receiver; a static method belongs to a type and has no instance receiver.
- **Static type and runtime type:** the static type is the type known to the compiler for an expression; the runtime type is the actual class of the referenced object.
- **Name hiding and `new`:** a derived declaration introduces its own same-named member; the `new` modifier explicitly acknowledges that it hides an inherited member.
- **Virtual method, override, and dynamic dispatch:** `virtual` permits a derived implementation; `override` supplies it; dynamic dispatch chooses that implementation using the runtime object.
- **Polymorphism:** using a common type to work with objects whose implementations may differ; its detailed treatment is deferred.
- **Base-type conversion, narrowing, and cast:** a derived reference can be used as a base reference; narrowing obtains a more specific type; an explicit cast requests a conversion.
- **Array and loop:** an array holds a sequence of elements of one declared element type; a loop processes those elements.
- **Type check and declaration pattern:** `is Sparrow s` tests compatibility and, on success, binds a reference with the specified type to `s`.
- **Composition, capability, and module:** composition assembles an object from collaborating objects; a capability is an ability such as swimming; a module implements one such ability.
- **Factory function and constructor:** a factory assembles and returns an object; a constructor initializes an instance when it is created with `new`.
- **Object initializer:** the braces after object creation assign fields or properties.
- **String interpolation:** `$"...{expression}..."` embeds an expression's value in text.
- **Null, nullable reference, and non-null pattern:** `null` means no referenced object; `?` allows that absence in a reference-type declaration; `is not null` or `is { }` tests for a present value. The empty property pattern `{ }` is the latter pattern's syntax.
- **Interface:** a contract that different types can implement; it is mentioned at the end as a partial alternative, not developed here.

## Inherited fields and methods

[00:00:14](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=14s) A **base class** supplies state and operations that a **derived class** inherits. In `class Derived : Base`, the colon declares inheritance. A **field** stores data on the object, so a derived object can read its inherited public field under the same name. The **access modifier** `public` permits access from these call sites.

Initial video state, simplified:

```csharp
class Base
{
    public int Value;
    public void BaseMethod() => Console.WriteLine(Value);
}

class Derived : Base
{
    public int Extra;
    public void Method() => Console.WriteLine(Extra);
}

// At the call site:
Derived d = new Derived();
d.Value = 10;  // inherited field
d.Extra = 20;  // field added by Derived
```

[00:00:28](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=28s) An **instance method** is called through an object reference. Its declaration may be in the derived class or an accessible base class. The receiver stays `d`: call `d.Method()` for the added method and `d.BaseMethod()` for the inherited method. A base-typed reference can also call the base member. Simplified call-site state:

```csharp
d.Method();
d.BaseMethod();

Base b = d;
b.BaseMethod();
```

[00:00:48](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=48s) Inherited **scoping** means the base member remains reachable through the derived object. Moving an operation into the base class does not force callers to abandon their derived reference. Be precise about syntax: `Base.Method()`, with `Base` as a class name, cannot call an ordinary instance method without a receiver.

[00:00:57](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=57s) Next, change the methods to **static methods**, which have no instance receiver. The linked video state is reconstructed here:

```csharp
class Base

    public static void BaseMethod() { }
}

class Derived : Base
{
    public static void Method() { }
}

Derived.BaseMethod();

// d.BaseMethod(); // invalid for a static method
```

[00:01:04](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=64s) Static methods must be accessed using a type name, even if an object happens to exist. “No instance” here means no instance receiver for the method, not that the program cannot contain objects. [00:01:11](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=71s) Either `Derived.BaseMethod()` or `Base.BaseMethod()` reaches the inherited static member.

[00:01:19](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=79s) **Member lookup** is the compiler's resolution of a member name. In this simple example, when it cannot find `BaseMethod` in `Derived`, it continues through the base classes and finds the declaration in `Base`. [00:01:33](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=93s) That search happens at compilation. The running program does not repeatedly search class declarations to resolve this non-virtual call.

[00:03:33](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=213s) Replace hiding with a **virtual method** and an **override**. ## Replace the hierarchy with composition

[00:08:44](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=524s) The working hierarchy illustrates what inheritance can do; it is not a recommendation to model animal capabilities this way. [00:08:54](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=534s) The design advice is to use inheritance sparingly and prefer **composition** for this scenario.

[00:08:59](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=539s) **Composition** means building an animal from collaborating objects. A **capability** is an ability such as swimming or flying, and a **module** is a separate object that implements that ability. Give the general `Animal` shared data and a name, then give capability modules access to that animal.

[00:09:06](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=546s) Simplified composition video state:

```csharp
class Animal
{
    public string Name = "";
    public int AgeInDays;
    public SwimModule? Swimming;
    public FlyModule? Flying;

    public void Print() =>
        Console.WriteLine($"{Name}: {AgeInDays} days");
}

class SwimModule
{
    Animal animal;

    public SwimModule(Animal animal)
    {
        this.animal = animal;
    }

    public void Swim() =>
        Console.WriteLine($"{animal.Name} swims");
}

class FlyModule
{
    Animal animal;

    public FlyModule(Animal animal)
    {
        this.animal = animal;
    }

    public void Fly() =>
        Console.WriteLine($"{animal.Name} flies");
}
```

A **constructor**, such as `SwimModule(Animal animal)`, initializes a newly created module. `this.animal` names its field, while the unqualified `animal` on the right names the parameter. The module holds a **reference** to the shared animal, so its operation can use the same name and data. No inheritance declaration connects these three classes.

The **nullable reference** annotations `SwimModule?` and `FlyModule?` permit **null**, meaning an absent module. An animal can have swimming, flying, both, or neither. Name handling belongs to the common animal data rather than separate subclass implementations.

## Check for a module before calling it

[00:11:19](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=679s) A module field may be **null**, meaning no capability object is present. Calling a method through an absent reference would fail, so check before invoking the operation. Simplified first video-state form:

```csharp
foreach (Animal animal in animals)
{
    SwimModule? swimming = animal.Swimming;
    if (swimming != null)
    {
        swimming.Swim();
    }
}
```

The recording also shows checking the field directly. Both forms ask whether the capability exists rather than whether the animal has a particular species type.

[00:11:39](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=699s) Shorten the check with a **declaration pattern**, which binds a usable module reference on success. Simplified revised video state:

```csharp

{
    swimming.Swim();
}
```

[00:11:46](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=706s) This looks like the earlier subtype test, but the input field already has the declared type `SwimModule?`. There is no narrower runtime type to discover: for this expression, success amounts to the field being non-null. The general syntax can test runtime compatibility when the input type is less specific.

[00:11:54](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=714s) Remove the repeated module type with an **empty property pattern**, `{ }`. This **non-null pattern** matches a present value and can bind it to a variable. Simplified final check in the recording:

```csharp
if (animal.Swimming is { } swimming)
{
    swimming.Swim();
}

// A non-null test without capturing a new variable:
if (animal.Swimming is not null)
{
    animal.Swimming.Swim();
}
```

The two forms express a non-null check, but only the first shown form binds `swimming`. Do not combine the spellings into `is not null swimming`. The empty pattern does not request a different type or copy the module object: its variable holds the evaluated field reference. See Microsoft's [property-pattern explanation](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/patterns/property-positional-patterns).

[00:12:11](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=731s) The advantage is that the client no longer names a species or repeats a concrete module type in its test. If the field's declared type changes while still offering the needed operation, this presence-check form can remain the same.

[00:12:32](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=752s) Swimming and flying belong to separate **modules**, not to the bird type. Shared client code can read these fields and use capabilities wherever needed. This is the reuse benefit that the following inheritance sketch struggles to reproduce without repeated implementations or a more complicated hierarchy.

## Why the inheritance alternative becomes awkward

[00:12:49](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=769s) Return to inheritance to expose the design pressure. A penguin swims, a sparrow flies, and a duck needs both. Simplified inheritance sketch from this video state:

```csharp
class Animal { }

class Penguin : Animal
{
    public void Swim() { }
}

class Sparrow : Animal
{
    public void Fly() { }
}

class Duck : Animal
{
    public void Swim() { } // repeats the swimming operation
    public void Fly() { }  // repeats the flying operation
}
```

[00:13:01](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=781s) The discussion also considers overriding behaviour. An **override** replaces a matching virtual base implementation, as in the earlier dispatch demonstration; the sketch above only shows the capability duplication and does not claim its methods override anything. Empty bodies are placeholders: real behaviour might print information or compute data, making duplication more costly.

[00:13:20](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=800s) One possible escape is a shared **static function** called by each class's method. That can centralize the implementation, but reuse then comes from an ordinary helper call rather than inheriting that behaviour. The classes still add forwarding methods; inheritance contributes little to that reuse. The video sketches this option without developing it into a complete design.

[00:13:34](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=814s) Another problem is the call site. An `Animal` reference cannot invoke `Swim` merely because `Penguin` and `Duck` independently declare it: `Animal` must expose an appropriate common member. Simplified failing call-site state:

```csharp
Animal animal = new Penguin();
// animal.Swim(); // invalid: Animal declares no Swim member
```

[00:14:05](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=845s) To inherit one swimming implementation, introduce a shared swimming base class. But a duck also needs a shared flying implementation. [00:14:29](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=869s) C# permits a class to inherit from only **one base class**, so it cannot simply inherit both a swimming class and a flying class. Attempts to fit every capability combination into a class hierarchy accumulate similar classes and duplicated code. This is the limitation illustrated here, rather than a claim that inheritance can never reuse code.

[00:14:44](https://www.youtube.com/watch?v=y1KNWcgUUMU&t=884s) **Interfaces**—contracts that types implement—can partly express multiple capabilities. In the ordinary interface-contract approach being discussed, each class still needs to supply an implementation or delegate to shared code; merely declaring that contract does not supply the two desired class implementations. Modern C# also supports default interface implementations, so “interfaces can never contain reusable implementations” would be too broad. That feature is **not taught here**; Microsoft's [inheritance documentation](https://learn.microsoft.com/en-us/dotnet/csharp/tutorials/inheritance) describes it.

The lesson ends with the design tradeoff: keep common animal data in one place and compose independent capabilities when their combinations vary. Detailed polymorphism, full interface design, and default interface implementations remain outside the lesson.
