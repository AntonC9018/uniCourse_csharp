# Shadowing a local with a local-function parameter is legal since C# 8; the editor message is not a compile error

- Ledger TP-054 (transcript 590480–602150ms) claims that when a parameter shadows an enclosing local, "the compiler rejects such code with an error". The transcript at t=596–602s agrees ("Компилятор даже даёт ошибку").
- The `factual_verification` worker (run 295, session `ses_ee52f49d6ffet9R7k0ozsh3F0N`) disproved the error claim by compiling `int a = 9; int result = SumOperation(1, 2);` with `int SumOperation(int a, int b) { return a + b; }` under .NET 11 (`dotnet run` printed `3`, only a CS0219 unused-variable warning). Since C# 8 a local-function parameter may legally shadow an enclosing local; hiding the outer name is not a failure to compile.
- What the recording shows at t=602s ("a is a local variable with the same name") is an editor description of the name collision, not proof of a compile error. The note (00:10:02) preserves exactly this distinction and cites [local-function rules](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/local-functions).
- Companion check from the same session: `int sum; sum = ReadSum();` where `ReadSum` returns `sum` genuinely fails with `error CS0165: Use of unassigned local variable 'sum'` (`dotnet build`), so the note's definite-assignment claim at 00:09:13 is a real compile-time error, unlike the shadowing case. Initializing first (`int sum = 0;`) makes the capture valid.
