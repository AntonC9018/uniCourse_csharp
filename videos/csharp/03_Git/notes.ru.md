# Git: от локальной папки до смерженного изменения на GitHub

Этот урок выстраивает полный путь: от проверки Git в консоли Windows до фиксации локальных изменений, восстановления файлов, работы в отдельной ветке, публикации на GitHub, слияния pull request и возврата результата на компьютер. Шаги идут по порядку: каждая следующая операция опирается на состояние, созданное раньше.

Используемая по ходу терминология:

- **Консоль / команда / аргумент / опция:** консоль принимает текстовые команды; команда запрашивает операцию, аргумент передаёт значение, например имя файла, а опция вроде `--help` задаёт поведение. **HTML** — формат веб-документа, используемый показанной здесь страницей справки.
- **Git / GitHub:** Git записывает версии проекта; GitHub хранит Git-репозитории онлайн и даёт средства совместной работы. **Репозиторий** содержит записанную историю проекта. **Локальный** значит на этом компьютере; **удалённый** — другой репозиторий, доступный через соединение.
- **Рабочий каталог / .git:** рабочий каталог содержит файлы, которые вы редактируете; скрытая папка `.git` хранит записи и настройки локального репозитория.
- **Коммит / сообщение / идентификатор:** коммит записывает состояние проекта как единицу изменений, его сообщение описывает работу, а идентификатор (хеш) отличает эту запись истории. **История / log / постраничный просмотр:** история — это последовательность коммитов; `git log` показывает её, иногда через постраничный просмотр, который ждёт навигации или выхода.
- **Неотслеживаемый / отслеживаемый / изменённый:** неотслеживаемый файл лежит на диске, но Git его не отслеживает; отслеживаемый файл уже передан под управление Git; изменённый файл отличается от записанного или подготовленного состояния.
- **Индекс (staging area) / add:** индекс хранит версии файлов, подготовленные для следующего коммита; `git add` кладёт изменения туда. Индексация и коммит — разные действия.
- **Автор / область настройки:** коммит записывает имя и почту автора. Настройка на уровне репозитория действует для одного проекта; `--global` задаёт значения по умолчанию для текущего пользователя во всех репозиториях.
- **Исходник / компилятор / исполняемый файл:** исходник — читаемый текст программы; компилятор вроде `g++` превращает исходник C++ в исполняемую программу. **Результат сборки** — это созданный файл. **Архитектура** описывает конструкцию машины целевого компьютера; **двоичный машинный код** — исполняемое представление. **Библиотечные функции** дают переиспользуемую функциональность. Байты и килобайты (КБ) измеряют размер файла.
- **.gitignore / правило / подстановочный знак / расширение:** `.gitignore` содержит правила игнорирования неотслеживаемых файлов. Знак вроде `*` соответствует произвольному тексту; расширение — это окончание имени файла, например `.exe`.
- **Diff / restore / checkout:** diff показывает различия между состояниями файла; restore возвращает рабочие файлы к выбранному записанному состоянию; checkout выбирает состояние коммита или ветки.
- **Ветка / master / указатель ветки / общий коммит:** ветка называет линию работы, а её указатель определяет текущий коммит. `master` — имя основной ветки в этой записи. Общий коммит принадлежит историям обеих веток до их расхождения.
- **Rebase / merge / squash:** rebase повторяет изменения ветки поверх обновлённой базы; merge объединяет истории веток и может создать коммит слияния; squash сливает изменения нескольких коммитов в один итоговый коммит.
- **Pull request / источник / цель:** pull request — это предложение на GitHub влить одну ветку в другую. Ветка-источник даёт работу; целевая (базовая) ветка её принимает.
- **Имя удалённого репозитория / origin / URL / HTTPS / SSH:** имя удалённого репозитория сокращает адрес, по соглашению `origin` для основного соединения. URL задаёт этот адрес. HTTPS и SSH — способы соединения; в примере используется HTTPS.
- **Upstream / push / pull / аутентификация:** upstream связывает локальную ветку с её удалённым аналогом; push отправляет коммиты в удалённый репозиторий; pull забирает и встраивает удалённые изменения. Аутентификация разрешает доступ к сервису и не связана с автором, записанным в коммите.

Связанное [курсовое упражнение по Git](https://AntonC9018.github.io/uniCourse_csharp/ru/labs/basic/git/) даёт задачи для практики. Оно не является свидетельством установки или промежуточных состояний кода из записи.

Предоставленные материалы не указывают на неизменяемый коммит репозитория с этим демонстрационным проектом. Примеры ниже — упрощённые последовательности команд или схемы поведения рядом со ссылками на записанные состояния; пути, имена веток, значения автора и сообщения даны для иллюстрации. Они не претендуют на воспроизведение недоступного исходного блоба.

## Разделение Git и GitHub

[00:01:56](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=116s) **Git** — инструмент записи версий. **GitHub** — сервис, который использует Git для хранения репозиториев онлайн. Репозиторий — это записанная история проекта, и Git может создать его и работать с ним полностью локально, без подключения к GitHub.

[00:02:20](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=140s) Удалённый репозиторий — это другая копия, доступная через соединение. GitHub — лишь один из возможных хостингов; его может предоставить и другой провайдер, поддерживающий протокол Git.

[00:02:33](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=153s) **Область и порядок:** операции с GitHub намеренно отложены, пока урок настраивает локальные операции в папке проекта. Для следующих локальных коммитов не нужен ни онлайн-аккаунт, ни публикация.

## Индексация первого исходника

[00:03:54](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=234s) Используйте `git status`, чтобы посмотреть текущее состояние репозитория. На этом этапе в рабочей папке лежит начальный исходник C++; упрощённое имя файла ниже — `a.cpp`.

1. [00:04:04](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=244s) Первый вывод status сообщает, что коммитов нет, а исходник не отслеживается.
2. [00:04:11](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=251s) **Неотслеживаемый** значит, что файл существует на диске, но Git ещё не начал его отслеживать. Одного нахождения в папке недостаточно, чтобы сохранить его в истории.
3. [00:04:19](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=259s) Выполните `git add` с именем файла. Это начинает отслеживание и помещает текущую версию в **индекс** — набор изменений, подготовленных к следующему коммиту.
4. [00:04:28](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=268s) Теперь status показывает новый файл среди изменений, готовых к коммиту. Коммитов всё ещё нет.
5. [00:04:47](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=287s) Индексация не создаёт отдельную запись истории. Нужен коммит, чтобы это стало сохранённым состоянием, к которому можно вернуться.

Упрощённая последовательность перехода от неотслеживаемого к проиндексированному:

```cmd
git status
git add a.cpp
git status
```

Нет. Файл подготовлен к коммиту, но в записанной истории коммитов по-прежнему нет. Индексация и запись — разные шаги.

## Настройка автора и создание первого коммита

[00:05:07](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=307s) Используйте `git commit -m "..."`, чтобы записать проиндексированное состояние. Здесь `-m` — опция сообщения; кавычки сохраняют описание как один аргумент. [00:05:17](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=317s) **Сообщение коммита** — это документация, сохраняемая вместе с коммитом, поэтому описывайте, что изменилось, а не считайте его одноразовым текстом в консоли.

Записанная первая попытка представлена этой упрощённой командой:

```cmd
git commit -m "Add source file"
```

[00:05:40](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=340s) Попытка не удаётся, потому что у Git не настроен автор. Следуйте конфигурации, предложенной в сообщении об ошибке, и повторите команду.

[00:06:01](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=361s) **Автор** — это имя и почта, записываемые в коммит; это не логин GitHub. Почта не обязана совпадать с аккаунтом GitHub. [00:06:12](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=372s) Преподаватель объясняет, что Git не проверяет принадлежность указанного адреса при записи, поэтому само поле автора не является доказательством личности.

[00:06:32](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=392s) **Область настройки** определяет, где применяются эти значения. `--global` задаёт значения по умолчанию для текущего пользователя во всех репозиториях, включая будущие проекты. [00:06:51](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=411s) Если опустить этот флаг при настройке здесь, значения сохранятся только для этого репозитория. [00:07:15](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=435s) В демонстрации и имя, и почта настраиваются локально для этого проекта.

Упрощённая локальная настройка и повтор, соответствующие записанному исправлению:

```cmd
git config user.name "Example Author"
git config user.email "author@example.com"
git commit -m "Add source file"
```

Чтобы выбрать более широкую область, обсуждаемую в записи, те же настройки получают опцию:

```cmd
git config --global user.name "Example Author"
git config --global user.email "author@example.com"
```

[00:07:25](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=445s) После настройки повторная команда коммита выполняется успешно. [00:07:37](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=457s) Её результат существует только в локальном репозитории `.git`. Успешный локальный коммит ничего не публикует в интернет.

## Просмотр записанного состояния

[00:07:54](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=474s) Коммит сохраняет состояние исходника на момент записи. [00:08:06](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=486s) Его **идентификатор**, то есть хеш, и сообщение отличают эту версию от последующих.

[00:08:14](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=494s) `git log` показывает **историю**: идентификаторы, имя и почту автора, дату и сообщение. По этим полям вы узнаёте нужное состояние и позже выбираете его.

Упрощённый просмотр истории только что записанного исходника:

```cmd

```

На этом этапе исходник одновременно присутствует в рабочей папке и сохранён в первой записи истории.

## Сборка программы и сохранение исходника

1. [00:08:40](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=520s) Скомпилируйте исходник C++ командой `g++`. **Компилятор** превращает читаемый исходник в **исполняемый файл** — созданную программу, которую может запустить операционная система.
2. [00:09:04](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=544s) Задайте имя результата опцией `-o`, опцией выходного файла. Изменение её аргумента меняет имя созданной программы.
3. [00:09:15](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=555s) Запустите полученный исполняемый файл.

Упрощённая последовательность сборки и запуска, соответствующая записи:

```cmd
g++ a.cpp -o main.exe
main.exe
```

[00:09:26](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=566s) Исполняемый файл — это **результат сборки**, файл, созданный из исходника. Обычно его исключают из Git, потому что его можно собрать заново. [00:09:37](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=577s) Хранение исходника позволяет другому человеку собрать программу под **архитектуру** своего компьютера.

[00:09:47](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=587s) Исходник — это текст, поэтому Git может показывать изменения построчно. Исполняемый файл содержит **двоичный машинный код**, который для такого просмотра исходника гораздо менее полезен. [00:10:06](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=606s) В демонстрации сравнивается исходник в 104 байта с исполняемым файлом размером около 60 КБ: байты и КБ измеряют размер, а исключение сгенерированного результата уменьшает объём хранимого. [00:10:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=621s) Преподаватель объясняет лишний размер в этом примере включёнными **библиотечными функциями** — переиспользуемой функциональностью, используемой программой. Это объяснение показанного примера, а не фиксированное правило размера для любого результата компиляции.

[00:10:33](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=633s) После компиляции status показывает исполняемый файл как неотслеживаемый. Сборка файла не индексировала его и не сделала коммит.

Упрощённая проверка этого записанного промежуточного состояния:

```cmd
git status
```

## Игнорирование результатов сборки и запись правил

[00:10:40](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=640s) Чтобы случайно не индексировать исполняемые файлы при следующих добавлениях, создайте `.gitignore`. **Правило игнорирования** говорит Git, какие неотслеживаемые файлы не включать в обычные добавления и вывод status.

1. Запишите имя первого исполняемого файла. [00:11:10](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=670s) Теперь status показывает новый `.gitignore`, а исполняемый файл исчезает из обычного списка неотслеживаемых.

   Упрощённое первое правило и его проверка, соответствующие записанному состоянию:

   ```gitignore
   main.exe
   ```

   ```cmd
   git status
   ```

2. [00:11:17](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=677s) Особое имя `.gitignore` важно точно: Git сам интерпретирует его содержимое как правила.
3. [00:11:29](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=689s) Соберите ещё один исполняемый файл с другим именем. Первое правило называет только первый файл, поэтому второй по-прежнему появляется в status.
4. [00:11:44](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=704s) Каждое имя файла пишите на отдельной строке. [00:11:55](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=715s) Добавление второго имени убирает из status и второй исполняемый файл.

   Упрощённое промежуточное состояние с двумя именами:

   ```gitignore
   main.exe
   other.exe
   ```

5. [00:12:03](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=723s) Замените отдельные имена шаблоном с подстановочным знаком. **Подстановочный знак** `*` соответствует произвольному тексту, а **расширение** `.exe` — это окончание имени файла. Так одно правило покрывает оба исполняемых файла.

   Упрощённая замена, соответствующая этому записанному изменению правила:

   ```gitignore
   *.exe
   ```

6. [00:12:24](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=744s) Добавьте сам `.gitignore` и сделайте коммит. Правила — это текст проекта, который стоит записать, даже хотя сгенерированные файлы исключены.

   Упрощённая последовательность для сохранения записанного состояния правил:

   ```cmd
   git add .gitignore
   git commit -m "Ignore executable files"
   git log
   ```

[00:12:49](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=769s) Теперь log различает два этапа: добавление исходника и коммит с правилами игнорирования.

<details>
<summary>Почему игнорирование первого исполняемого файла не скрыло второй?</summary>

Буквальное имя файла соответствует только этому имени. Для второго имени нужно своё правило, либо подходит шаблон вроде *.exe, который совпадает с обоими.

</details>

## Правка, просмотр и коммит исходника

[00:13:07](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=787s) Следующая правка убирает две строки исходника, роль которых — держать консоль открытой после работы программы. Цель — дать выполнению завершиться без этих ожиданий.

Транскрипт задаёт поведение правки, но не точные конструкции. Этот упрощённый **эскиз поведения** представляет начальное и итоговое состояния исходника; это не дословный и не исполняемый листинг C++:

```text
Before:
    perform the program's existing work
    first console-wait statement
    second console-wait statement
    finish

After:
    perform the program's existing work
    finish
```

1. [00:13:17](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=797s) После правки `git status` помечает отслеживаемый исходник как **изменённый**: его текущий текст отличается от сохранённой версии.
2. [00:13:25](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=805s) Просмотрите **diff** — отображение различий — командой `git diff`. В этом показанном состоянии правка не индексирована, поэтому сравнение показывает текущие изменения относительно сохранённого исходника. Точнее, обычный diff сравнивает рабочий файл с проиндексированной версией; здесь она всё ещё совпадает с последним коммитом.
3. [00:13:50](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=830s) Вывод показывает две удалённые строки, подтверждая задуманную правку.
4. [00:14:12](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=852s) Проиндексируйте изменённый отслеживаемый файл через `git add` и запишите новое состояние ещё одним коммитом.

Упрощённая последовательность просмотра и записи, соответствующая этим записанным шагам:

```cmd
git status
git diff
git add a.cpp
git commit -m "Remove console waits"
```

Так появляется более поздняя версия, а ранний исходник сохраняется в истории.

4. [00:16:07](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=967s) Сделайте коммит проиндексированных файлов как одной единицы изменений.

[00:16:33](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=993s) Теперь удалите закоммиченные файлы из рабочего каталога. Это убирает копии, которые вы видите на диске, но не ранние версии в истории репозитория.

[00:16:46](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1006s) **Restore** возвращает рабочие файлы к выбранному записанному состоянию. В этом примере удаление не индексировано и не закоммичено, и `git restore .` возвращает файлы с их прежним кодом.

Упрощённая команда восстановления для этого записанного незакоммиченного удаления:

Результат показывает, чем сохранённый коммит отличается от простого наличия файлов в папке.

## Просмотр истории после закоммиченного удаления

[00:17:52](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1072s) Повторите удаление и на этот раз запишите его: отсутствие файлов становится частью нового записанного состояния.

Упрощённые команды после удаления файлов в записанном примере:

```cmd
git add .
git commit -m "Delete earlier files"
```

[00:18:04](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1084s) Теперь `git restore .` не восстанавливает их. У restore нет незакоммиченного удаления, которое можно отменить: само текущее записанное состояние не содержит этих файлов.

Чтобы увидеть более раннее состояние:

1. [00:18:18](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1098s) Запустите `git log` и выберите идентификатор коммита до удаления.
2. [00:18:44](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1124s) Если история показывается в **постраничном просмотре** — интерактивном просмотрщике, нажмите `q`, чтобы выйти и вернуться к вводу команд.
3. [00:18:48](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1128s) Используйте `git checkout` с этим старым идентификатором. **Checkout** выбирает состояние коммита или ветки; файлы снова появляются, если выбранный старый коммит их содержит.
4. [00:19:08](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1148s) Используйте `git checkout master`, чтобы вернуться к текущему состоянию основной ветки. Её закоммиченное удаление снова скрывает ранние файлы.

Упрощённая записанная навигация, где `OLD_COMMIT_ID` — идентификатор, скопированный из log:

```cmd
git log
git checkout OLD_COMMIT_ID
git checkout master
```

<details>
<summary>Почему restore работает до коммита с удалением, но не после?</summary>

До коммита записанное состояние ещё содержит файлы. После коммита их отсутствие и есть записанное состояние. Выберите более ранний коммит, чтобы посмотреть версию, где файлы есть.

</details>

## Создание независимой рабочей ветки

[00:19:30](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1170s) Чтобы продолжить со старого коммита, создайте там именованную ветку. **Ветка** называет линию работы; она даёт последующим изменениям линию, независимую от `master`. [00:19:47](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1187s) Это удобно для экспериментальной функции, которую вы хотите развивать отдельно от основного состояния проекта.

3. [00:20:13](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1213s) Сравните состояния: экспериментальная ветка содержит ранние файлы, а `master` — их удаление.
4. [00:20:32](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1232s) Используйте log, чтобы посмотреть историю выбранной ветки.
5. [00:20:39](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1239s) Переключайтесь по имени ветки через checkout, чтобы переходить между этими состояниями.

Упрощённое создание и просмотр ветки, соответствующие записи:

```cmd
git checkout experiment
```

[00:20:54](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1254s) Добавьте файл D в экспериментальной ветке, проиндексируйте и закоммичьте. Его точный начальный текст не установлен предоставленным транскриптом; важное изменение состояния в том, что эта ветка теперь записывает ещё один файл.

Упрощённая последовательность после создания D в этом записанном состоянии:

## Перенос экспериментальной ветки на master через rebase

[00:22:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1341s) **Rebase** повторяет собственные поздние изменения ветки на новой базе, которую даёт другая ветка. Здесь экспериментальной работе нужна более новая база master.

[00:22:59](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1379s) Обе ветки делят коммит, добавивший ранние файлы. После этого общего коммита master удаляет эти файлы, а experiment добавляет D. [00:23:19](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1399s) Объяснение сначала находит эту общую точку, чтобы отличить общую историю от новой работы. [00:23:31](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1411s) Ожидаемый результат последователен: сохранить удаление из master, затем применить экспериментальное добавление D.

Упрощённая схема истории для этих записанных состояний; буквы — метки, а не настоящие идентификаторы коммитов:

```text
Before:
    shared file addition -> deletion             (master)
                         -> add D                (experiment)

After rebasing experiment:
    shared file addition -> deletion             (master)
                                     -> add D    (experiment)
```

1. Выберите ветку, базу которой хотите обновить.
2. [00:23:56](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1436s) Запустите `git rebase master` из этой ветки.
3. [00:24:10](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1450s) Посмотрите результат: история теперь включает удаление из master, за которым следует экспериментальное добавление. Указатели веток по-прежнему определяют разные коммиты; master ещё не перешёл на самый новый коммит experiment.

Упрощённые команды, соответствующие записанному rebase:

```cmd
git checkout experiment
git rebase master
git log
```

[00:24:31](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1471s) **Граница применимости:** урок отмечает, что ветки без общего коммита — более сложный случай, и разбирать его не будет. Этот пример опирается на общую историю.

[00:24:39](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1479s) Общие коммиты в объяснённом примере не повторяются. [00:24:43](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1483s) Затем запись обновляет master относительно экспериментальной ветки, подводя оба указателя к одному коммиту, а значит и к одному текущему состоянию.

Упрощённая последовательность этого записанного продолжения, продвигающего master по уже общей линии:

```cmd
git checkout master
git rebase experiment
```

<details>
<summary>Сразу после rebase ветки experiment на master — получил ли master тоже D?</summary>

Нет. Теперь experiment содержит базу master и добавление D, но master всё ещё указывает на коммит с удалением. Более позднее обновление master подводит обе ветки к одной вершине.

</details>

## Выбор способа интеграции ветки

[00:25:01](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1501s) Преподаватель советует сохранять `master` как основную ветку и делать новые изменения в отдельной рабочей ветке на её основе.

[00:25:13](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1513s) **Pull request** — это предложение GitHub влить рабочую ветку в основную. Это функция сервиса, а не команда Git. **Источник** даёт изменения; **цель**, также называемая базовой веткой, их принимает.

[00:25:45](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1545s) **Merge** объединяет истории. Описанный здесь вариант создаёт отдельный **коммит слияния** — запись истории, фиксирующую объединение. [00:25:51](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1551s) Перед этой интеграцией преподаватель советует выполнить rebase рабочей ветки на master. [00:26:06](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1566s) Названная причина — упростить интеграцию, сначала сделав рабочую базу включающей изменения master. Это описание показанного рабочего процесса, а не гарантия, что все будущие слияния пройдут без конфликтов.

Упрощённая подготовительная последовательность, соответствующая этой рекомендации:

```cmd
git checkout experiment
git rebase master
```

[00:26:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1581s) **Squash** сливает изменения нескольких коммитов в один итоговый коммит. [00:26:34](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1594s) Например, добавление файла одним коммитом и его правка другим могут стать одной записью истории с объединённым результатом.

Упрощённая схема записанного объяснения squash:

```text
Working history: add file -> edit file
Squashed result: one commit containing the final file
```

Эти варианты дают разную форму истории. Поздняя демонстрация pull request использует коммит слияния.

## Подключение пустого репозитория на GitHub

[00:26:56](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1616s) GitHub хранит **удалённый репозиторий** — онлайн-копию, доступную за пределами этого компьютера. [00:27:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1641s) Такая копия позволяет перенести проект на другую машину и передавать изменения через GitHub при продолжении работы между компьютерами.

1. [00:27:43](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1663s) Создайте репозиторий на GitHub для этого проекта: урок описывает его как удалённую папку с Git внутри.
2. [00:28:00](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1680s) Начните с пустого удалённого репозитория для уже существующего локального проекта. Избегайте начальных файлов в удалённом репозитории, которые могли бы конфликтовать с уже созданной локально историей.
3. [00:28:05](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1685s) Добавьте это подключение локально командой `git remote add`.
4. [00:28:19](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1699s) Выберите **имя удалённого репозитория** — короткое имя, которое позже используют команды для этого адреса. [00:28:25](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1705s) По соглашению имя основного удалённого репозитория — `origin`.
5. [00:28:33](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1713s) Передайте его **URL** — адрес репозитория. Показанный адрес GitHub может заканчиваться на `.git`, а может и не содержать этот суффикс.
6. [00:28:42](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1722s) Используйте **HTTPS** — способ соединения, выбранный для этого вводного примера. **SSH** — альтернатива, которой, как отмечено, нужна дополнительная настройка.
7. [00:28:50](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1730s) Проверьте адрес командой `git remote show origin`.

Упрощённые команды подключения для записанной настройки; замените владельца и имя репозитория:

```cmd
git remote add origin https://github.com/OWNER/REPOSITORY.git
git remote show origin
```

Добавление подключения записывает адрес, но само по себе не выгружает существующие локальные коммиты.

## Публикация master и различие автора коммита и логина

[00:29:04](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1744s) Первый `git push` не удаётся, потому что у этой локальной ветки нет **upstream** — связи с её аналогом в удалённом репозитории.

1. [00:29:22](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1762s) При отправке свяжите локальный master с веткой master в `origin`. `origin` разрешается в URL, записанный ранее; это имя удалённого репозитория, а не имя ветки.
2. [00:29:58](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1798s) Пройдите аутентификацию в браузере, запрошенную показанной настройкой. **Аутентификация** разрешает доступ к хостинговому сервису.
3. [00:30:15](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1815s) После успешной авторизации GitHub показывает выгруженные файлы и историю, подтверждая, что записанная локальная работа опубликована.

Упрощённая последовательность первой отправки, соответствующая сбою и исправлению:

```cmd
git checkout master
git push
git push --set-upstream origin master
```

Первый push выше представляет демонстрируемую неудачную попытку. `--set-upstream` при повторе записывает связь ветки, а также отправляет её коммиты.

[00:30:43](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1843s) На GitHub виден автор коммита, отличный от владельца репозитория. [00:31:00](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1860s) Это следует из настроенных ранее имени и почты автора: **авторство коммита** хранится вместе с коммитом, а **логин** разрешает отправку. Публикация сохраняет записанного автора и не заменяет его аккаунтом, которым выполнялась выгрузка.

## Локальный коммит, затем отправка следующей правки

1. [00:31:17](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1877s) Добавьте текст `world` в D и сделайте ещё один локальный коммит.
2. [00:31:33](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1893s) Новая запись истории по-прежнему существует только локально. GitHub не изменился оттого, что коммит удался.
3. [00:31:51](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1911s) Выполните `git push`; только что отправленный коммит появится на GitHub.

Упрощённая схема изменения содержимого для записанной правки D; существующий текст и оформление не воспроизводятся:

```text
D before: existing content
D after:  existing content plus "world"
```

Упрощённая последовательность записи и публикации того же изменения:

```cmd
git add D
git commit -m "Update D with world"
git push
```

Теперь, когда upstream у master настроен, этот push использует сохранённую связь с удалённой веткой.

## Подготовка и публикация рабочей ветки

1. [00:32:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1941s) Вернитесь в экспериментальную ветку и обновите её от master перед следующей правкой, чтобы работа началась на актуальной базе.
2. [00:32:39](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1959s) Снова отредактируйте D и закоммитьте правку в этой ветке, оставив новую работу отдельной для будущего pull request.

Упрощённая последовательность для записанного построения; точный новый текст транскриптом не приводится:

```cmd
git checkout experiment
git rebase master
```

Отредактируйте D, затем продолжите ту же записанную процедуру:

```cmd
git add D
git commit -m "Change D on the working branch"
```

3. [00:32:59](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1979s) Экспериментальная ветка ещё не опубликована. Её первая отправка требует собственной связи upstream; связь master не настраивает каждую ветку.
4. [00:33:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2001s) После публикации GitHub показывает, что экспериментальная ветка опережает master на один коммит. Этот лишний коммит и есть работа для интеграции.

Упрощённая первая публикация этой записанной рабочей ветки:

```cmd
git push --set-upstream origin experiment
```

## Создание и слияние pull request

1. [00:33:46](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2026s) Создайте **pull request** на GitHub — предложение влить опубликованную рабочую ветку в основную.
2. [00:33:57](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2037s) Выберите `experiment` как источник, а `master` как цель/базу. Сравнение показывает изменения, которые есть в источнике и отсутствуют в цели.
3. [00:34:10](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2050s) Создайте запрос и примените его действие слияния, чтобы внести эти изменения в master на GitHub.
4. [00:34:28](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2068s) После слияния удалённую рабочую ветку можно удалить, потому что её дополнительная работа уже включена в master.
5. [00:34:39](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2079s) Посмотрите историю master на GitHub. В ней есть и переданный коммит работы, и дополнительный коммит слияния, фиксирующий интеграцию через pull request.

Упрощённая схема истории для записанного результата; это вариант с коммитом слияния, а не более ранняя иллюстрация со squash:

```text
Remote master after merge:
    earlier master history
    working-branch change to D
    pull-request merge commit joining the histories
```

Выбранное направление «источник → цель» важно: master принимает лишнюю работу experiment.

## Возврат слитого результата в локальный master

[00:35:01](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2101s) Переключение на локальный master после слияния на GitHub само по себе не забирает новые коммиты. Локальная ветка сохраняет прежнее состояние. [00:35:16](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2116s) Заберите удалённую работу отдельно, чтобы локальные файлы отражали результат pull request.

1. [00:35:24](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2124s) Выберите нужную локальную ветку, затем выполните `git pull`. **Pull** забирает и встраивает изменения из настроенной удалённой ветки.
2. [00:35:28](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2128s) D обновляется, и `git log` теперь показывает два полученных коммита: изменение рабочей ветки и коммит слияния pull request.

Упрощённая последовательность, соответствующая записанной финальной синхронизации:

```cmd
git checkout master
git pull
git log
```

Итоговое локальное состояние отражает слияние на GitHub. Локальное редактирование, коммиты, публикация и приём удалённой работы — каждый раз отдельное действие.
