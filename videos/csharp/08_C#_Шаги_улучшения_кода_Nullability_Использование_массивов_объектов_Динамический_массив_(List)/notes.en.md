These are the terms used along the way:

- **Array, element, index, and length:** an array contains a fixed number of same-typed cells; an element is a cell's value, its index identifies the cell starting at zero, and length is the number of cells.
- **Entity, record, state, and stats:** an entity is one participant in the game; a record here means a group of data describing it, not a requirement to use the C# record keyword. State is the game's current data; stats are the participant's health and attack values. The examples name their types `Stats`, `Enemy`, and `GameState`.
- **Refactoring and duplication:** refactoring reorganizes code while preserving its intended behavior; duplication repeats the same logic in several places.
- **Class, struct, field, and public:** a class defines a reference type; a struct defines a value type. A field stores data belonging to an instance, and `public` permits access from other code.
- **Object, reference, stack, and heap:** an object is a created instance; a reference identifies an object rather than containing its fields. The recording sketches local variables in temporary or stack memory and objects in dynamic or heap memory. These sketches explain relationships, not a promise about optimized physical storage or numeric addresses.
- **Allocation, `new`, and dereferencing:** allocation reserves storage; `new` constructs an instance; dereferencing uses a reference to read or write the referenced object's members.
- **`null`, nullable analysis, annotation, and diagnostic:** `null` means no object is referenced. Nullable analysis checks the intended presence or absence of references at compile time, when code is translated before execution; runtime is when the program executes; an annotation such as `Stats?` permits absence. A diagnostic reports a problem: a warning need not prevent compilation, whereas an error does.
- **Initialization, object initializer, and `required`:** initialization supplies starting values; an object initializer assigns members in the construction expression; `required` makes callers explicitly supply a member when constructing an instance.
- **Type inference, target-typed `new()`, and `var`:** inference lets the compiler determine a type. In `Stats p = new();`, the left side determines the constructed type; in `var p = new Stats();`, the right side determines the local variable's type.
- **Function or method, parameter, argument, `void`, and return value:** a function groups instructions; a method is a function associated with a type. A parameter names an input in the declaration; an argument supplies it at a call. `void` means no result is returned; a return value carries a computed result to the caller.
- **String, literal, and interpolation:** a string is reference-typed text; a literal writes a value directly, such as `6` or `"Rat"`; interpolation inserts values into text using `$"...{value}..."`.
- **Loop, iteration, `for`, `foreach`, `while`, `break`, `continue`, and `return`:** a loop repeats a body, with one pass called an iteration. `for` advances through an explicit start, condition, and update; `foreach` visits collection elements; `while` repeats while a condition is true. `break` leaves a loop, `continue` skips to its next iteration, and `return` leaves the current function.
- **Boolean, flag, guard, condition, negation, and or:** a Boolean is `true` or `false`; a flag stores such a decision; a guard tests whether an operation should proceed; a condition is the expression being tested. Logical negation (`!`) reverses a Boolean; logical or (`||`) accepts either of two conditions.
- **Scope and factory function:** scope is the region where a name can be used; a factory function constructs and returns a ready-to-use object.
- **Dynamic array, `List<T>`, generic argument, and backing array:** a dynamic array grows through managed storage. `List<T>` is .NET's growable list; `T` specifies the element type, the generic argument. Its backing array is the internal fixed-size storage replaced when more room is needed; Count is the number of entries currently in the list.
- **Collection expression, add, and filtering:** a collection expression such as `[a, b]` supplies elements for a target collection type. Adding appends an element; filtering removes elements selected by a condition.
- **Lambda, predicate, delegate, overload, and polymorphism:** a lambda such as `enemy => enemy.Stats.Health <= 0` supplies a small function; a predicate returns a Boolean decision. A delegate represents callable behavior, an overload is another form of a callable operation, and polymorphism lets one interface or operation represent different behavior. The video uses the filter syntax but postpones these deeper mechanics.

## Element types and local type inference

[00:27:03](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=1623s) Arrays share the same fixed-cell idea; their **element type** determines what each cell contains:

- An integer array stores numbers.
- An array of class instances stores references to objects.
- An array of structs stores each struct's field values in the element itself. A reference-typed field inside a struct still contains a reference.

[00:27:32](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=1652s) **Var** requests compile-time local type inference. [00:27:34](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=1654s) Since the assigned expression produces a `GameState`, that is the local's type. The video-state comparison can be shortened to:

{

    Enemies = new Enemy[0]

{
    Player = new Stats { Health = 10, Attack = 5 },

These alternatives use the later grouped `Enemies` field to keep the sample short. Both locals are statically typed `GameState`. `var` does not mean their type can change later. ## Give the repeated combat an explicit loop

[00:33:40](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2020s) If the player lives and at least one enemy lives, control must go back to the beginning of the round. [00:34:14](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2054s) Reuse that beginning instead of writing another copy.

[00:34:22](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2062s) The recording considers jumping back to a labeled point, then recommends a loop. A bare **return** does not jump to the round's beginning: it leaves the function. The restarting jump discussed in the transcript is a label-directed jump; the clearer structure is an infinite `while` loop with explicit exits. [Microsoft's jump-statement reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/jump-statements) distinguishes return from loop control.

[00:34:30](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2070s) Replace function-level exits with **break** when the desired action is leaving this repeated-round loop. [00:34:40](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2080s) **While** repeats as long as its condition is true; `while (true)` always starts another iteration unless a body exit stops it.

The shortened resulting video state is:

```csharp
while (true)
{
    if (state.Player.Health <= 0 || !AnyEnemyAlive(state.Enemies))
        break;

    foreach (var enemy in state.Enemies)
    {
        if (enemy.Stats.Health <= 0)
            continue;

        Attack(state.Player, enemy.Stats, enemy.Name);
        if (state.Player.Health <= 0)
            break; // exits the enemy pass
    }

    PrintHealth(state.Player, "Player");
    foreach (var enemy in state.Enemies)
        PrintHealth(enemy.Stats, enemy.Name);
}
```

The `||` operator means “or”: either stopping condition is enough. The inner break prevents another enemy exchange; the outer break ends round repetition. The next guard observes any deaths from the previous pass.

[00:34:53](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2093s) In the recorded run, every enemy is attacked in the first round and health is printed. In the next round, two enemies hit the player, the player dies, and surviving enemies keep their reduced health. [00:35:02](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2102s) Giving the player **50 health** lets it survive into the second round and defeat all enemies. That test verifies repetition and the alternative stopping condition.

The expected outcome depends on the input stats, but the control rule does not: do not run another enemy exchange after player death, and do not begin another combat round after every enemy is dead.

## A fixed array cannot grow

[00:35:12](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2112s) With repetition working, the next design question is initially left open: how can a new enemy appear after each round? [00:35:42](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2142s) The proposed enemy has **one attack and one health**. This requires a container whose element count can grow.

[00:35:56](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2156s) An ordinary array's **length** is fixed at creation. Changing a cell is allowed; appending a sixth cell to a five-cell array is not.

[00:36:09](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2169s) One manual workaround would be:

1. Allocate a new array one element longer.
2. Copy the old enemy references into it.
3. Put the new enemy reference in the last cell.
4. Replace the reference to the old container with the reference to the new one.

A shortened reconstruction of that proposed video-state workaround is:

```csharp
Enemy[] bigger = new Enemy[enemies.Length + 1];
for (int i = 0; i < enemies.Length; i++)
    bigger[i] = enemies[i];
bigger[enemies.Length] = newEnemy;
enemies = bigger;
```

Here `for` is the index-controlled loop form: start `i` at zero, repeat while it is below the old length, and increment it with `i++`. The copied values are references to the existing enemies; this does not clone their stats.

[00:36:18](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2178s) .NET provides a more convenient **dynamic array**, a growable collection managed for the caller. [00:36:28](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2188s) A `List<T>` tracks an internal backing array and replaces that storage with a larger array when it lacks room. The backing array itself still has fixed length; the list manages replacement and preserves the elements.

## Change the enemy container to List

[00:36:38](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2198s) **List<T>** is the growable list type. The name between angle brackets is its **generic argument**, the type of each element. Change the enemy container from `Enemy[]` to `List<Enemy>`.

[00:37:07](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2227s) The collection stores whole enemy records. [00:37:17](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2237s) Its element argument must therefore be `Enemy`, not the earlier stats-only type.

[00:37:21](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2241s) A **collection expression** supplies initial elements with square brackets and uses the destination type to choose the collection. This shortened video-state reconstruction keeps two illustrative initial entries:

```csharp
List<Enemy> enemies =
[
    new Enemy
    {
        Name = "Enemy 1",
        Stats = new Stats { Attack = 6, Health = 10 }
    },
    new Enemy
    {
        Name = "Goblin",
        Stats = new Stats { Attack = 1, Health = 10 }
    }
];
```

The same square-bracket element syntax can initialize an array or a list in a compatible language version. It is not an instruction to allocate an ordinary array regardless of the destination. Collection expressions require C# 12 or later; this is a syntax clarification, not a separate installation step taught in the lesson. [Microsoft's collection-expression reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/collection-expressions) describes the target typing.

[00:37:31](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2251s) Update the declaration that holds the enemies in the game state as well. Any helper parameter previously accepting an enemy array must match the changed collection type. A shortened continuation of this video-state conversion is:

```csharp
class GameState
{
    public required Stats Player;
    public required List<Enemy> Enemies;
}

bool AnyEnemyAlive(List<Enemy> enemies)
{
    foreach (var enemy in enemies)
        if (enemy.Stats.Health > 0)
            return true;
    return false;
}
```

The stored records and their field accesses remain the same. `foreach` can still visit each enemy; only the container type and the declarations that depend on it have changed.

## Remove dead enemies by a condition

[00:39:37](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2377s) Dead enemies can disappear from the list instead of being retained and skipped forever. Use the list's high-level removal API to select them, rather than manually shifting surviving entries.

[00:40:02](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2402s) The unusual argument syntax names an element, then gives a condition. [00:40:04](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2404s) The condition is stats health less than or equal to zero. This reconstructed video-state change removes every dead entry:

```csharp
state.Enemies.RemoveAll(enemy => enemy.Stats.Health <= 0);
```

A **lambda** supplies a small function inline. Here `enemy` is its parameter name; `=>` separates that name from its body. The body is a **predicate**, a Boolean test. For each entry, a true result means “remove this enemy.” This is selection by a condition, not a loop that runs only while a condition remains true.

[00:40:13](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2413s) Once dead entries are removed between combat passes, every enemy present at the next pass's start is alive. The explicit dead-enemy skip at the top of that pass can be dropped under that invariant. Keep the player-death break: filtering enemies does not prevent the player from dying during an exchange.

[00:40:23](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2423s) The recorded run shows that the killed rat disappears and only the following rat appears; the killed one is not processed again. [00:40:36](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2436s) Giving an enemy more health makes its longer survival visible in the final output. Dead entries are removed, and once the final surviving enemy dies the loop ends rather than adding another round's rat.

[00:40:51](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2451s) The next round now fights only entries still present in the list. A shortened final-flow reconstruction makes the order explicit:

```csharp
while (true)
{
    if (state.Player.Health <= 0 || state.Enemies.Count == 0)
        break;

    foreach (var enemy in state.Enemies)
    {
        Attack(state.Player, enemy.Stats, enemy.Name);
        if (state.Player.Health <= 0)
            break;
    }

    PrintHealth(state.Player, "Player");
    foreach (var enemy in state.Enemies)
        PrintHealth(enemy.Stats, enemy.Name);

    state.Enemies.RemoveAll(enemy => enemy.Stats.Health <= 0);

    if (state.Player.Health <= 0 || state.Enemies.Count == 0)
        break;

    AddEnemy(state, new Enemy
    {
        Name = "Rat",
        Stats = new Stats { Attack = 4, Health = 100 }
    });
}
```

This is a clarified reconstruction, not a claim that this exact arrangement was committed. **Count** is the number of current list entries. After filtering, zero count means no enemies remain. Removal and spawning happen after the enemy iteration, and the exit check happens before spawning, so a completed game does not acquire another rat.

[00:41:03](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2463s) The lesson explicitly postpones the exact mechanics of delegates, related callable forms, and polymorphism. A **delegate** represents callable behavior, an **overload** is another form of an operation, and **polymorphism** concerns different behavior through a common operation or interface; they are named here to mark the boundary, not taught in depth.

[00:41:18](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2478s) It is enough at this stage to read the filter's shape: a named element, a Boolean condition, and a collection operation using it. [00:41:24](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2484s) That reading explains the observed removal without requiring the deferred machinery.

<details>
<summary>Why check for game completion before adding the next rat?</summary>

If all enemies have died, adding a rat first makes the list nonempty again. If the player has died, spawning first creates an unnecessary enemy. Filter and check the stopping conditions before scheduling another round's spawn.

</details>

## The list is another reference object

[00:41:31](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2491s) **List<T> is a reference type**. A list variable contains a reference to the list object, just as an array variable contains a reference to an array object.

The final video-state memory idea can be shortened to:

```csharp
List<Enemy> enemies = new List<Enemy>();
List<Enemy> sameList = enemies; // another reference to the same list object
```

[00:41:39](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2499s) The list object, in turn, keeps a reference to its current backing array. That array's enemy cells hold references to enemies, whose stats and names are further references. Growing the list replaces its internal storage without asking the game code to recreate every enemy.

[00:41:46](https://www.youtube.com/watch?v=zeuNRQBdwuY&t=2506s) The recording skips deeper implementation detail about this extra reference level. The lesson's endpoint is practical: group one entity's data, write each action once, iterate over a collection, and use a growable container when enemies can be added or removed.

Scope boundaries matter throughout: `required` is mentioned and temporarily postponed before its later demonstration; initialization questions are then set aside to resume refactoring; class-array memory is paused and explained separately; spawning is first raised as an open question and then addressed with a list. Delegate/polymorphism mechanics and deeper list internals remain deferred at the end. They are not prerequisites for following the demonstrated construction.
