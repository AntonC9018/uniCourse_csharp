# Console input, output parameters, and validation

## Purpose and terms

[00:00:00](https://www.youtube.com/watch?v=SSTFFX5heuY&t=0s) The goal is to turn text entered in the console into usable numbers without restarting the program after every typing mistake. The construction proceeds from a blocking read, to conversion, to an output parameter, to a retry loop, to a reusable input function, and finally to validation of several values together.

The vocabulary needed for that construction is:

- **Console input and output:** text received from or sent to the console. The **Console method family** includes functions such as **Console.ReadLine**, which reads a line; **Console.Write**, which prints without adding a line break; and **Console.WriteLine**, which prints and adds a line break.
- **Sequential execution and blocking:** instructions normally run one after another, from top to bottom. A blocking instruction waits for an event before the following instruction can run.
- **string, int, and bool:** a string is text, an int holds a whole number, and a bool holds true or false. Typing digits does not automatically turn a string into an int.
- **Nullable input, null, and redirected input:** a nullable string, written **string?**, may contain text or null, meaning no string value. Redirected input comes from a source such as a file rather than the live console. **End of input** means that source has no more lines.
- **Null-forgiving operator:** the postfix **!** tells nullable analysis in the compiler to treat an expression as non-null. It suppresses a warning; it does not supply a missing value.
- **Concatenation and arithmetic:** concatenation joins strings; arithmetic performs numeric operations. The meaning of **+** depends on the operand types.
- **Parsing, int.Parse, and exceptions:** parsing converts a textual representation into a value. int.Parse returns an integer for suitable numeric text. An exception is a runtime error signal; an unhandled exception stops this sample program.
- **Parameter, argument, and out parameter:** a parameter is a named input or output slot in a function declaration; an argument is what the caller supplies. An out parameter lets a function initialize a variable belonging to the caller.
- **Local variable, stack, address, reference, and initialization:** a local belongs to a block or function. The stack is the lesson's model for temporary call storage. An address identifies a storage location; a reference gives access to that location. Initialization writes the variable's first usable value.
- **Call expression and return value:** calling a function can itself produce a value. **return** ends the function and can hand that value to the caller. A **void** function has no return value; a **static** helper can be called without an object instance.
- **int.TryParse, inline out declaration, and success flag:** TryParse attempts conversion, writes the integer through out, and returns a bool indicating success. An inline out declaration creates that output variable at the call site. A flag is a variable recording a yes-or-no state.
- **Scope and lifetime:** scope determines where a name can be used; lifetime concerns how long its storage is needed. Moving code into a block or function changes which variables it can access.
- **Loop and iteration:** a loop repeats a body; an iteration is one pass through it. **while** checks its condition before the body; **do-while** checks after the body. **while (true)** is an infinite loop until some explicit action leaves it.
- **Condition operators:** prefix **!** means logical negation of a bool, and **||** means “or.” A condition is an expression whose true-or-false result controls a branch or loop.
- **Branch, label, goto, continue, and break:** an **if** branch runs when its condition is true. A label names a destination for goto. continue skips the rest of the current iteration; break exits the loop.
- **Function extraction and abstraction:** extraction moves repeated logic into a function. The resulting abstraction gives the caller a named operation, hiding the steps that implement it.
- **Class, object, field, method, and new:** a class describes objects; an object holds values in fields; a method is a function associated with the type or object. The new expression creates an object.
- **Validation and validity rules:** validation checks whether values are correct and allowable for the program. Being parseable is one requirement; satisfying rules such as “B must be at least twice A” is another.
- **Debugging:** examining execution and intermediate values to find why behavior differs from what was intended.

[00:17:34](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1054s) The copies vary in the name shown to the user and the caller variable receiving the answer.

Build the helper in these steps:

1. [00:17:41](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1061s) Declare an int return type, because the caller needs a validated positive integer.
2. [00:17:48](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1068s) Make the displayed variable name a string parameter. A **parameter** is declared in the helper; the caller supplies an **argument**, such as "A".
3. [00:17:55](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1075s) Move the common body into the helper. The original caller variable is not visible there, so introduce a local parsed value.
4. [00:18:02](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1082s) That local may be declared inside the helper's loop, since the successful result is handled in the same iteration.
5. [00:18:14](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1094s) Replace break with return value. **return** leaves the whole function and hands the value back, rather than merely leaving the loop.
6. [00:18:20](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1100s) Combine declaration with out at the TryParse call.
7. [00:18:42](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1122s) Remove both input loops from the caller and call the helper once for each variable.

The resulting helper video state is represented by:

```csharp
int a = InputInt("A");
int b = InputInt("B");
Console.WriteLine(a + b);

static int InputInt(string name)
{
    while (true)
    {
        Console.Write("Enter " + name + ": ");
        string text = Console.ReadLine()!;
        bool success = int.TryParse(text, out int value);
        if (!success)
            continue;

        if (value <= 0)
        {
            Console.WriteLine("Number must be positive.");
            continue;
        }

        return value;
    }
}
```

InputInt is an **abstraction**: its name lets the caller request a usable integer without repeating the input, parse, retry, and range-check steps. Its own out variable receives the parsed number; its return value initializes the caller's a or b. There is no need to make this helper's return value another out parameter.

## Keep reading and checks in separate steps

[00:19:05](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1145s) Consider expressing the same retry with do-while and placing parsing and checks in its condition. The lesson rejects this compressed form. [00:19:16](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1156s) It would mix reading the string, parsing it, checking conversion success, and checking the numeric rule inside loop control.

[00:19:23](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1163s) A **while** loop checks its condition first. A condition that relies on a value read only in the body cannot use that body-produced value before the first pass. Putting ReadLine directly into the condition would itself perform a read, but would create the crowded expression being criticized.

[00:19:30](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1170s) A **do-while** executes its body once before testing its condition, then repeats while the condition is true. [00:19:44](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1184s) In the illustrated compressed arrangement, only printing the input request fits neatly inside the do body; the read and validation end up in the condition.

[00:19:55](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1195s) Declaring the ReadLine result inside the do block prevents the outside condition from using that name. [00:20:00](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1200s) The name's scope ends with that block. This is a problem with that declaration placement, not a rule forbidding reads in every do-while body.

[00:20:08](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1208s) The result of parsing must also remain available where it is checked. In the attempted condition-based version, that requires arranging the read before the parse/check expression and providing a separate output variable. [00:20:12](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1212s) Save the parsing outcome rather than silently discarding it. [00:20:15](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1215s) A failed parse must trigger another iteration. [00:20:28](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1228s) Successful parsing of zero or a negative value must also trigger another iteration.

The proposed compressed video state can be illustrated as follows; it is an alternative being rejected, not the helper's final form:

```csharp
int value;
do
{
    Console.Write("Enter a positive integer: ");
}
while (!int.TryParse(Console.ReadLine()!, out value) || value <= 0);
```

Here || means “or”: retry for failed parsing or an unacceptable parsed value. The read occurs before its result can be parsed, but several operations have been crammed into one condition.

[00:20:31](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1231s) That arrangement offers no clear place to print different errors after each failure. [00:20:42](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1242s) The emphatic correction is to stop compressing the operations into one line. [00:20:49](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1249s) Use an infinite loop and leave it manually when the input is valid.

[00:20:54](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1254s) The preferred structure keeps each operation on its own line so more logic can be inserted after it. [00:21:06](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1266s) Repeat and exit conditions can be separate checks, one after another. [00:21:12](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1272s) This also helps **debugging**, examining intermediate steps and values. Read, parse, check success, check acceptability, and return are individually visible in InputInt.

## Validate the values together

[00:21:16](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1276s) Move from reading a single usable number to **validation**: deciding whether values are correct and allowable under the program's rules.

[00:21:21](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1281s) A class now holds A and B in fields. A **class** describes the data, an **object** is an instance containing that data, and a **field** stores one of its values. Reading positive integers into those fields still does not prove that the object satisfies every rule.

[00:21:26](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1286s) “Valid” means correct and allowable. [00:21:37](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1297s) The concrete rule is B >= 2 * A: B must be at least twice A. [00:21:40](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1300s) Put the check in a validation method, a function associated with the object.

[00:21:45](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1305s) Return false for B < 2 * A. [00:21:50](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1310s) Otherwise return true. This initial validation video state is equivalent to:

```csharp
class Values
{
    public int A;
    public int B;

    public bool Validate()
    {
        if (B < 2 * A)
            return false;

        return true;
    }
}
```

The two branches cover the rule: equality is valid, while anything below twice A is invalid.

[00:21:53](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1313s) Extend the example to C and require C > A + B. A single method can check more than one rule. The check must describe the **violation**, so [00:22:25](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1345s) the condition is corrected to C <= A + B before returning false. The corresponding intermediate video state is:

```csharp

{
    if (B < 2 * A)
        return false;

    if (C <= A + B)
        return false;

    return true;
}
```

[00:22:03](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1323s) The intended pattern is to validate immediately after reading the values, store the bool result, and request data again when the result is false.

## Retry invalid objects

[00:22:28](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1348s) Wrap the complete input step in a loop. Invalid data repeats the input; valid data ends the loop. Using the existing InputInt helper, the simplified object-input video state is:

```csharp
{
    data.A = InputInt("A");
    data.B = InputInt("B");
    data.C = InputInt("C");

    bool isValid = data.Validate();
    if (isValid)
        break;
}
```

The new expression creates the object. Access through the dot writes its fields or calls its method. The caller's isValid is a **flag**, a bool recording whether the whole object meets the rules.

[00:23:02](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1382s) In the recorded run, input keeps repeating until valid data is supplied. The validation result directly controls whether the loop stops.

[00:23:18](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1398s) The first drawback is poor feedback: the user is not told why the object failed validation. [00:23:26](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1406s) Another observation is that the rule checks can be examined independently instead of being fused into one complicated condition.

[00:23:36](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1416s) Some checks could, in principle, be moved into the reading procedure and performed as the needed values become available. ## Explain the first violated rule

[00:24:07](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1447s) Improve the feedback by printing exactly which rule failed. ## Report every violated rule

[00:24:39](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1479s) To report every broken rule, stop returning from the failure branches. Instead, use an **isValid flag**, a bool that remembers whether any check has failed.

[00:24:44](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1484s) Each branch sets the flag while allowing the function to continue. [00:24:50](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1490s) Return the flag only after all checks have run. The working form of this final validation video state is:

```csharp
public bool Validate()
{
    bool isValid = true;

    if (B < 2 * A)
    {
        Console.WriteLine("B must be at least twice A.");
        isValid = false;
    }

    if (C <= A + B)
    {
        Console.WriteLine("C must be greater than A + B.");
        isValid = false;
    }

    return isValid;
}
```

The initial value must be true: the object remains valid unless a rule fails. Starting isValid at false and only assigning false in these branches would reject every object, including one satisfying all the rules. This is the initialization required by the explanation and final valid-input result; false belongs in the failure branches.

[00:25:02](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1502s) Entering even one failure branch makes the final answer false. A later satisfied rule does not restore true. [00:25:06](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1506s) Every violated condition prints its own message because execution continues to the remaining checks.

Follow the procedure:

1. Assume validity at the start of each call.
2. Check one rule and print a message if it is violated.
3. Record false for that violation, then keep checking.
4. Repeat for every rule.
5. Return the accumulated verdict once.

The caller still gets one bool. The user can see several printed errors, but the caller has not received a list of those errors as data.

## Interpret the validation tests and limits

[00:25:26](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1526s) A single violated validity rule is enough to make the whole object invalid. The method still checks each rule separately so that every violation can be announced. The final video tests use these two rules, B >= 2 * A and C > A + B; both must hold for the complete object to be valid.

The recorded tests and their meanings are:

| Video test | A, B, C | B >= 2 * A | C > A + B | Result |
| --- | --- | --- | --- | --- |
| [00:25:32](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1532s) | 2, 3, 1 | False: 3 < 4 | False: 1 <= 5 | Two error messages; validation is false |
| [00:25:39](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1539s) | 2, 5, 4 | True: 5 >= 4 | False: 4 <= 7 | One error message; validation is still false |
| [00:25:45](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1545s) | Values satisfying both rules | True | True | No error messages; validation is true |

Two messages in the first run mean two **violations**, not two satisfied clauses. One satisfied rule in the second run does not cancel the other rule's failure. The valid-input run proceeds without announcing a violation; this validation method returns a bool and does not throw an exception.

For a compact reconstruction of the final video behavior, connect that method to this caller:

```csharp
bool isValid = data.Validate();
if (isValid)
    break; // inside the surrounding input loop
```

[00:25:52](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1552s) When validation returns true, the caller reaches break and leaves the input loop. This break is the successful exit, not termination caused by a violated rule. In the earlier version, return false ended the validation method early; in the final version, failure branches continue checking.

[00:26:00](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1560s) This approach fits a caller that needs only a yes-or-no validity signal while the user receives the printed explanation. [00:26:03](https://www.youtube.com/watch?v=SSTFFX5heuY&t=1563s) If the calling code must know which exact rules failed, more advanced reporting techniques are required and are deliberately deferred.

<details>
<summary>Self-explanation: why does A = 2, B = 5, C = 4 remain invalid?</summary>

B meets the first rule, but C must exceed A + B, which is 7. C = 4 violates that second rule. Any one failed rule makes the complete object's validation result false.

</details>
