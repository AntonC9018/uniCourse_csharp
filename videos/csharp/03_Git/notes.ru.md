# Git: сохранить, пересмотреть и поделиться проектом

[00:00:00](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=0s) Цель урока — превратить папку с рабочими файлами в проект, версии которого можно записывать, просматривать, восстанавливать и передавать. Сначала вы работаете только на своём компьютере, затем подключаете эту историю к GitHub, разрабатываете одно изменение в отдельной ветке и возвращаете слитый результат в локальные файлы. Демонстрация использует небольшую программу на C++, хотя упражнение курса применяет эти операции Git к вашему собственному проекту.

Эти термины будут повторяться по ходу работы над проектом:

- **Консоль, команда, аргумент, опция:** консоль — это окно ввода текста; команда запрашивает действие, аргумент передаёт информацию, например имя файла, а опция меняет поведение команды. **Справка** документирует доступные команды. **HTML** — формат страниц, который отображает показанная программа просмотра справки. **Clone** означает копирование репозитория вместе с его историей.
- **Git, GitHub, репозиторий, локальный, удалённый, протокол:** Git управляет версиями файлов; GitHub размещает Git-репозитории и средства совместной работы. Репозиторий хранит записанные состояния проекта и их историю. Локальная работа находится на этом компьютере; удалённый репозиторий — это другая копия, доступная через соединение. Протокол задаёт, как обмениваются информацией взаимодействующие программы.
- **Рабочий каталог и .git:** рабочий каталог содержит файлы, которые вы редактируете; скрытый каталог `.git` содержит историю и настройки локального репозитория.
- **Коммит, сообщение, идентификатор или хеш, история, log, постраничный просмотр:** коммит записывает подготовленное состояние проекта как единицу изменений. Его сообщение объясняет работу, а идентификатор отличает его от других коммитов. История связывает эти записанные состояния, log их отображает. Постраничный просмотр — интерактивный просмотрщик, который может показывать длинный log.
- **Неотслеживаемый, отслеживаемый, изменённый, индекс:** неотслеживаемый файл существует на диске, но Git им не управляет. Отслеживаемый файл находится под управлением Git. Изменённый означает, что его содержимое поменялось. Индекс хранит версии, выбранные для следующего коммита; добавление файла туда и коммит — разные шаги.
- **Личность автора и область настройки:** коммиты хранят имя и почту автора. Область настройки определяет, действуют ли настройки только для этого репозитория или, с `--global`, во всех репозиториях текущего пользователя.
- **Исходник, C++, компилятор, g++, исполняемый файл, результат сборки:** исходник — это читаемый текст программы, здесь на C++. Компилятор переводит его в исполняемый файл; `g++` — используемый здесь компилятор. Результат сборки — то, что создаёт компиляция. **Архитектура** — конструкция машины, на которую настроена сборка; **двоичный машинный код** — исполняемое представление инструкций. **Библиотечные функции** — переиспользуемые операции, которые нужны программе. Байты и килобайты (КБ) измеряют размер файла.
- **.gitignore, правило игнорирования, подстановочный знак, расширение:** `.gitignore` задаёт неотслеживаемые файлы, которые нужно исключать из обычных добавлений и вывода status. Каждое правило описывает имя или шаблон. Подстановочный знак `*` соответствует произвольному тексту имени файла; расширение — это окончание вроде `.exe`.
- **Diff, restore, checkout:** diff показывает различия между версиями файла. Restore заменяет рабочие файлы из выбранного состояния. Checkout выбирает коммит или ветку и делает её состояние доступным в рабочем каталоге.
- **Ветка, master, указатель ветки, общий коммит:** ветка называет линию разработки; её указатель определяет коммит на её вершине. `master` — имя основной ветки в этой записи. Общий коммит принадлежит историям обеих веток до того, как их работа разошлась.
- **Rebase, merge, коммит слияния, squash:** rebase заново применяет собственные изменения ветки поверх другой базы. Merge соединяет линии истории; коммит слияния явно фиксирует это соединение. Squash объединяет результат нескольких коммитов в один.
- **Pull request, ветка-источник, целевая или базовая ветка:** pull request предлагает интеграцию на GitHub. Ветка-источник даёт изменения, а целевая, она же базовая, ветка их принимает.
- **Имя удалённого репозитория, origin, URL, HTTPS, SSH:** имя удалённого репозитория — короткая метка для адреса репозитория. `origin` — обычная метка для основного удалённого репозитория; URL — его адрес. HTTPS и SSH — альтернативные способы соединения.
- **Upstream, push, pull, аутентификация:** upstream связывает локальную ветку с удалённой. Push отправляет закоммиченную работу, pull получает удалённую работу и включает её. Аутентификация устанавливает право доступа к учётной записи хостинга — отдельно от автора, записанного в коммите.

Отработайте настройку в [лабораторной по Git](../../../labs/1_basic/03_git.md): там нужно инициализировать проект, игнорировать генерируемые файлы, настроить автора, сделать коммит и подключиться к GitHub.

Проверенный рабочий каталог содержит эту лабораторную, но не содержит исходного проекта, соответствующего записанной демонстрации. Поэтому примеры ниже ссылаются на устойчивые состояния видео, а не заявляют о конкретном блобе репозитория. Команды — сокращённые воспроизведения процедуры; пути, значения автора, сообщения и имя ветки `experiment` даны для иллюстрации. Эскизы исходника показывают только поведение, установленное транскриптом.

Урок охватывает сначала локальную часть, а затем один цикл публикации на GitHub и pull request. Справка по конкретным командам открывается, но клонирование не демонстрируется. Настройка SSH, ветки без общей истории и внутренняя реализация хранения в Git остаются за рамками примера.

## Что остаётся локальным

[00:01:56](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=116s) Git — программа управления версиями — может инициализировать репозиторий и записывать вашу работу вообще без интернет-сервиса. GitHub — хостинг, который использует Git для хранения репозиториев онлайн. Репозиторий — это записанная совокупность состояний проекта и их истории; **локальный** значит, что эта копия находится на вашем компьютере.

[00:02:20](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=140s) **Удалённый** репозиторий — это другой репозиторий, к которому вы подключаетесь. GitHub — лишь один хостинг, и подойдут другие провайдеры, поддерживающие протокол Git — правила обмена, используемые для передачи данных репозитория.

[00:02:33](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=153s) Работа в сети на этом этапе отложена. Сначала разберёмся, что происходит внутри папки проекта. Следующим записям истории не нужны ни учётная запись GitHub, ни выгрузка.

## Сделать папку проекта репозиторием

В проекте уже есть исходный файл. Инициализация добавляет хранилище версий вокруг этих рабочих файлов.

1. [00:02:48](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=168s) Перейдите в нужную папку проекта до запуска `git init`. **Рабочий каталог** содержит редактируемые файлы. Инициализация в другом месте создала бы репозиторий для того места, а не здесь.
2. [00:03:04](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=184s) После инициализации осмотрите папку: появился скрытый каталог `.git`.
3. [00:03:09](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=189s) Если Проводник его скрывает, откройте параметры папки, выберите «Вид» и включите показ скрытых файлов.
4. [00:03:18](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=198s) Этот каталог `.git` хранит локальные записи Git, включая историю состояний файлов в моменты их коммитов.
5. [00:03:35](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=215s) **Коммит** сохраняет одну единицу изменений как состояние проекта. Добавленные или отредактированные файлы становятся частью состояния, записанного на этом шаге.

Упрощённая последовательность команд для состояния после инициализации:

```cmd
cd /d C:\path\to\project
git init
```

Замените путь реальным расположением проекта. Урок объясняет, зачем нужна история, не разбирая, как Git реализует хранение внутри.

## Подготовить исходный файл к первому коммиту

[00:03:54](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=234s) Начните с `git status`, которая сообщает текущее состояние репозитория. Начальный рабочий файл — исходник C++; в примерах он называется `a.cpp`.

1. [00:04:04](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=244s) Status сообщает, что коммитов ещё нет, и показывает исходник как неотслеживаемый.
2. [00:04:11](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=251s) **Неотслеживаемый** значит, что файл есть в файловой системе, но Git ещё не взял под управление его изменения. Простое помещение файла в эту папку не записало версию.
3. [00:04:19](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=259s) Выполните `git add a.cpp`. Это ставит файл под отслеживание и копирует его текущую версию в **индекс** — состояние подготовки к следующему коммиту.
4. [00:04:28](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=268s) Снова выполните status. Теперь файл указан как новый среди изменений, готовых к коммиту, а коммитов в репозитории по-прежнему нет.
5. [00:04:47](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=287s) Завершите процесс коммитом, когда нужна запись истории, к которой можно вернуться. Добавление выбирает версию для записи; само по себе оно эту запись не создаёт.

Записанный переход можно проследить так:

```cmd
git status
git add a.cpp
git status
```

## Указать отсутствующего автора и записать файл

[00:05:07](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=307s) Следующее действие — `git commit -m "Add source"`. Опция `-m` передаёт сообщение, а кавычки сохраняют многословное описание как один аргумент. [00:05:17](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=317s) **Сообщение** — это документация, хранящаяся вместе с коммитом. Оно должно помогать будущему читателю понять изменение; Git не определяет за вас правильность описания.

Сокращённая версия записанной первой попытки:

```cmd
git commit -m "Add source"
```

[00:05:40](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=340s) Эта попытка не удаётся, потому что данные автора не настроены. Ошибка подсказывает настройки, которые нужно задать перед повтором.

[00:06:01](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=361s) **Личность автора** — это имя и почта, записываемые в коммит. Почта не обязана совпадать с адресом учётной записи GitHub. [00:06:12](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=372s) Git принимает введённый адрес, не проверяя, что он принадлежит вводящему, — как и объясняет урок. Поэтому одно лишь поле автора не подтверждает личность.

[00:06:32](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=392s) **Область настройки** говорит Git, где применяются настройки. `--global` создаёт значения по умолчанию для текущего пользователя во всех репозиториях, так что более поздний проект сможет использовать то же имя и почту. Это не значит настройку для всех пользователей компьютера. [00:06:51](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=411s) Без этой опции настройка из этого репозитория действует только для этого проекта.

[00:07:15](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=435s) Показанное исправление задаёт локально и имя, и почту. Подставьте собственные значения вместо иллюстративных:

```cmd
git config user.name "Example Author"
git config user.email "author@example.com"
```

Для более широкой области, обсуждаемой в [00:06:32](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=392s), альтернатива выглядит так:

```cmd
git config --global user.name "Example Author"
git config --global user.email "author@example.com"
```

[00:07:25](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=445s) После настройки повторите коммит. На этот раз Git успешно создаёт его:

```cmd
git commit -m "Add source"
```

[00:07:37](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=457s) Запись истории теперь находится в локальном репозитории `.git` этого проекта. Само по себе её создание ничего не опубликовало.

## Прочитать первую запись истории

[00:07:54](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=474s) Первый коммит хранит исходник в том состоянии, которое было выбрано для этой записи. Более поздние правки рабочего файла не заменят эту раннюю версию. [00:08:06](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=486s) **Идентификатор** коммита, он же хеш, отличает сохранённое состояние; сообщение объясняет, зачем существует эта запись.

[00:08:14](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=494s) Посмотрите **историю** — связанную запись коммитов — через **log**. `git log` показывает идентификаторы коммитов, имена и почту авторов, даты и сообщения. Вместе они помогают узнать нужную версию.

Проверка истории в этом состоянии видео:

```cmd
git log
```

Теперь у проекта есть одна записанная версия исходника, а также редактируемая копия в рабочем каталоге.

## Собрать исполняемый файл из записанного исходника

[00:10:40](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=640s) Новый исполняемый файл должен остаться пересобираемым результатом сборки. Чтобы не включать его в обычные добавления, создайте `.gitignore`. **Правило игнорирования** говорит Git, какие неотслеживаемые имена не включать в обычный вывод status и в стандартное индексирование.

5. ## Начать отдельную линию работы

[00:19:30](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1170s) Чтобы развивать проект из старого состояния, дайте этой работе собственную ветку. **Ветка** называет линию разработки; её **указатель** определяет её текущий коммит. ## Найти работу, уникальную для каждой ветки

[00:21:35](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1295s) Перед объединением работы определите **общий коммит** — последнюю запись истории, общую для обеих веток. Экспериментальное изменение, которое нужно перенести дальше, — то, что произошло после этой общей точки: добавление D.

1. [00:22:03](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1323s) Прочитайте экспериментальный log. В нём есть добавление D и нет коммита, удаляющего прежние файлы.

## Перенести experiment на новую историю master

[00:22:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1341s) **Rebase** меняет базу линии работы, заново применяя её собственные новые изменения поверх истории другой ветки. Здесь это включит в experiment более новую базу master, а затем применит его добавление D.

[00:22:59](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1379s) Общее состояние — коммит, добавивший прежние файлы. Оттуда master записал их удаление, а experiment — добавление D. [00:23:19](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1399s) Нахождение общего коммита отделяет общее прошлое от этих двух позднейших действий. [00:23:31](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1411s) Намечаемая последовательность теперь такова: сначала удаление из master, затем экспериментальное добавление D.

Этот символический эскиз отражает объяснение из видео. Метки — это описания, а не хеши коммитов:

```text
Before:
                  +-- delete earlier files       master
shared addition --+
                  +-- add D                      experiment

After experiment is rebased:
shared addition --> delete earlier files --> add D
                    master                  experiment
```

1. [00:23:56](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1436s) Переключитесь на обновляемую ветку и выполните там `git rebase master`. В этом примере это experiment.
2. [00:24:10](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1450s) Изучите её новую историю. Теперь она включает изменение master, а затем собственное добавление D в experiment. Master всё ещё указывает на коммит удаления, а experiment — на более позднее добавление.

Показанное обновление резюмируется так:

```cmd
git checkout experiment
git rebase master
git log
```

[00:24:31](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1471s) **Граница применимости:** объяснение предполагает ветки с общим коммитом. В записи упоминается, что ветки без него сложнее, но этот случай не разбирается.

[00:24:39](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1479s) Общая история в этом примере не повторяется второй копией тех же коммитов. [00:24:43](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1483s) Следующее обновление выполняется из master относительно experiment. Поскольку история experiment уже включает состояние master, master может продвинуться к тому же итоговому коммиту. Оба указателя веток тогда указывают на одно состояние.

Продолжение в записи представлено так:

```cmd
git checkout master
git rebase experiment
```

<details>
<summary>Сразу после rebase experiment на master в какой ветке есть добавление D?</summary>

В experiment. Её база теперь включает удаление из master, но master не сдвинулся только из-за того, что experiment был перенесён. Последующее обновление master совмещает две вершины.

</details>

## Выбрать, как работа ветки попадёт в основную историю

[00:25:01](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1501s) Рекомендуемый порядок работы сохраняет `master` основной линией и создаёт от неё отдельную рабочую ветку. Новая функциональность или работа над лабораторной происходит на этой ветке до интеграции.

[00:25:13](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1513s) **Pull request** предлагает такую интеграцию на GitHub. Он принадлежит хостингу, а не набору команд Git. **Ветка-источник** даёт изменения, а **целевая**, она же базовая, ветка их принимает.

[00:25:45](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1545s) **Merge** соединяет истории. Разобранный здесь вариант добавляет **коммит слияния** — запись, фиксирующую соединение двух веток. [00:25:51](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1551s) Перед слиянием в master преподаватель советует обновить рабочую ветку, перенеся её на master. [00:26:06](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1566s) Причина — чтобы рабочая ветка уже включала последние изменения основной линии, что в этом примере упрощает последующую интеграцию. Эта подготовка не обещает, что любое возможное сочетание изменений обойдётся без конфликтов.

Подготовка, описанная в записи:

```cmd
git checkout experiment
git rebase master
```

[00:26:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1581s) **Squash** предлагает другую форму истории: изменения нескольких коммитов объединяются в один итоговый коммит. [00:26:34](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1594s) Допустим, один коммит добавляет файл, а другой его правит. Squash записывает их объединённый результат одной записью, а не хранит эти две записи раздельно в целевой истории.

Упрощённый эскиз этого объяснения:

```text
Working branch:  commit adding file -> commit editing file
Squashed entry:  one commit with their combined result
```

Эти варианты влияют на то, как история документирует работу. Показанный далее pull request использует вариант с дополнительным коммитом слияния.

## Дать локальному проекту удалённый адрес

[00:26:56](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1616s) GitHub теперь входит в рабочий процесс как место хранения **удалённого репозитория** — онлайн-копии за пределами компьютера с вашим локальным проектом. [00:27:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1641s) Это позволяет скопировать проект на другую машину, коммитить работу локально, отправлять её через GitHub и получать эту работу на другом компьютере.

Настройте соединение в таком порядке:

1. [00:27:43](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1663s) Создайте репозиторий GitHub для проекта. Урок описывает его как онлайн-папку, внутри которой работает Git.
2. [00:28:00](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1680s) Оставьте его пустым при этом первом подключении к уже существующему локальному проекту. Отсутствие заранее созданных файлов избавляет от отдельного начального удалённого состояния, которое пришлось бы согласовывать с вашей работой.
3. [00:28:05](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1685s) Добавьте соединение командой `git remote add`.
4. [00:28:19](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1699s) Выберите **имя удалённого репозитория** — короткую метку, по которой команды будут находить это соединение. [00:28:25](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1705s) `origin` — соглашение для основного удалённого репозитория; это выбор имени, а не особая ветка.
5. [00:28:33](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1713s) Укажите **URL** репозитория, его адрес. Показанный адрес GitHub принимает и вариант с окончанием `.git`, и вариант без этого суффикса.
6. [00:28:42](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1722s) Используйте **HTTPS** — способ соединения, выбранный для вводного примера. **SSH** упоминается как альтернатива, требующая дополнительной настройки, здесь не показанной.
7. [00:28:50](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1730s) Подтвердите настроенный адрес командой `git remote show origin`.

Шаги подключения сводятся к этому примеру; замените OWNER и REPOSITORY своим адресом:

```cmd
git remote add origin https://github.com/OWNER/REPOSITORY.git
git remote show origin
```

На этом промежуточном этапе Git знает, где находится другой репозиторий. Один лишь адрес ещё не отправил туда локальную историю.

## Опубликовать основную ветку с upstream

[00:29:04](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1744s) Первая попытка `git push` сообщает, что у ветки нет **upstream** — связи между локальной веткой и её удалённым аналогом. **Push** отправляет закоммиченную работу в удалённый репозиторий; исходная связь говорит коротким последующим командам push, куда она должна уйти.

1. [00:29:22](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1762s) Свяжите локальный master с master в origin. Git находит адрес, сохранённый под именем удалённого репозитория `origin`; master определяет ветку в этом назначении.
2. [00:29:58](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1798s) Пройдите вход в браузере, запрошенный показанной установкой. **Аутентификация** устанавливает право доступа к хостингу.
3. [00:30:15](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1815s) После успешного разрешения страница GitHub показывает выгруженные файлы и историю. Это первое видимое подтверждение, что сохранённая локальная работа дошла до удалённого репозитория.

Первая команда ниже представляет неудачную попытку; повтор и задаёт связь, и отправляет работу:

```cmd
git checkout master
git push
git push --set-upstream origin master
```

[00:30:43](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1843s) Выгруженные коммиты показывают автора, отличного от учётной записи, владеющей репозиторием. [00:31:00](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1860s) Это соответствует локальной настройке автора. Авторство коммита — имя и почта, сохранённые при создании коммита; аутентификация — разрешение на его отправку. Выгрузка не переписывает поля автора под вошедшую учётную запись.

<details>
<summary>Если выполнить push под другим логином GitHub, станет ли имя автора этим логином?</summary>

Нет. Коммит уже содержит данные автора. Логин определяет доступ к назначению, а опубликованный коммит сохраняет автора, записанного локально.

</details>

## Отправить более поздний локальный коммит

Следующая правка делает разницу между записью и публикацией наглядной.

1. [00:31:17](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1877s) Добавьте `world` в D и сделайте локальный коммит изменённого файла.
2. [00:31:33](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1893s) Посмотрите на GitHub до отправки чего-либо. Нового коммита там всё ещё нет, хотя он есть в локальном репозитории.
3. [00:31:51](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1911s) Выполните `git push`. Новый коммит тогда появляется на GitHub.

Этот эскиз представляет только известное из записи изменение содержимого; полный начальный текст и оформление не приведены:

```text
D before: its existing text
D after:  its existing text with "world" added
```

Сопутствующая упрощённая последовательность команд:

```cmd
git add d.txt
git commit -m "Add world to D"
git push
```

Поскольку у master уже есть upstream, его push может использовать эту сохранённую связь. Отправка коммитов и обновление удалённой ветки — операция, отдельная от создания коммита; успешный push здесь не является автоматическим слиянием произвольных разошедшихся историй.

## Опубликовать следующий эксперимент отдельно

1. [00:32:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1941s) Вернитесь на экспериментальную ветку и обновите её изменениями master. Следующая работа начнётся с текущего состояния основной линии.
2. [00:32:39](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1959s) Снова отредактируйте D и сделайте коммит в experiment. Это создаёт новое изменение, которое можно предложить через pull request независимо от master.

Подготовка и запись показаны ниже. Отредактируйте файл между rebase и add; точный новый текст транскриптом не установлен:

```cmd
git checkout experiment
git rebase master
git add d.txt
git commit -m "Revise D in the experiment"
```

3. [00:32:59](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=1979s) Попробуйте опубликовать эту ветку. Раньше её на удалённом репозитории не было, поэтому ей нужен собственный upstream. Связь, настроенная для master, автоматически не настраивает experiment.
4. [00:33:21](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2001s) Настройте upstream ветки experiment и отправьте её. Теперь GitHub показывает опубликованную экспериментальную ветку на один коммит впереди master. Этот лишний коммит — только что записанная правка D.

Первая публикация этой ветки представлена так:

```cmd
git push --set-upstream origin experiment
```

Теперь на удалённом репозитории две именованные линии работы, причём экспериментальная несёт одно дополнительное изменение.

## Влить experiment в master через pull request

Используйте **pull request** GitHub — предложение сервиса перенести работу ветки в целевую, — чтобы интегрировать опубликованный experiment.

1. [00:33:46](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2026s) Откройте интерфейс pull request и создайте новый запрос.
2. [00:33:57](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2037s) Выберите experiment как **источник**, а master как **цель/базу**. Сравнение показывает изменения в experiment, которых нет в master; именно это направление определяет, какая ветка примет работу.
3. [00:34:10](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2050s) Создайте запрос, а затем примените его действие слияния. Изменение experiment попадёт в master на GitHub.
4. [00:34:28](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2068s) Удалённую рабочую ветку теперь можно удалить: её дополнительная работа уже включена в master.
5. [00:34:39](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2079s) Изучите удалённый log ветки master. В нём есть переданный коммит изменения и дополнительный коммит слияния, фиксирующий интеграцию через pull request.

Символический вид записанного результата с метками вместо настоящих хешей:

```text
                     +-- D edit on experiment --+
earlier master state +-------------------------+-- PR merge
                                                     master on GitHub
```

Лишняя запись слияния сохраняет факт соединения линий. Это показанный результат с коммитом слияния, а не альтернатива со squash одной записью, обсуждённая ранее.

## Получить слитую работу на этом компьютере

[00:35:01](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2101s) После слияния на GitHub переключитесь на локальный master. Его файлы и log всё ещё отражают прежнее локальное состояние: переключение веток локально не скачало удалённые коммиты.

[00:35:16](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2116s) Получите эти изменения явно, чтобы проект на компьютере совпадал со слитым удалённым проектом.

1. [00:35:24](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2124s) На нужной локальной ветке выполните `git pull`. **Pull** получает удалённые изменения и включает их в эту локальную ветку через её настроенное соединение.
2. [00:35:28](https://www.youtube.com/watch?v=fcxFAW1EE_A&t=2128s) Проверьте результат. D обновился, а log теперь включает две полученные записи — экспериментальное изменение и коммит слияния pull request.

Итоговая синхронизация представлена так:

```cmd
git checkout master
git pull
git log
```

Весь цикл дошёл до локальных рабочих файлов: правка изменила файл, добавление выбрало его версию, коммит записал её, push опубликовал, pull request интегрировал её удалённо, а pull вернул этот удалённый результат обратно.

<details>
<summary>Почему выбор master не показал слитое изменение, пока не отработал pull?</summary>

Слияние на GitHub изменило удалённый репозиторий. Локальный master оставался на прежнем коммите, пока удалённая работа не была получена и включена. Checkout выбрал уже доступное локальное состояние; pull обновил его.

</details>
