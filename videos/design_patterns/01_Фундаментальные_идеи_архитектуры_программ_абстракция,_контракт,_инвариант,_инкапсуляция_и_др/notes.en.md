# Purpose and vocabulary

[00:00:00](https://www.youtube.com/watch?v=mj771Sd298c&t=0s) Learn to read and design a function through what its caller must know, what it promises, and what it hides. The advanced labs assume basic programming skills and prior familiarity with architectural ideas such as abstraction, coupling, invariants, and interfaces. This lesson applies those ideas through a range check, duplicate removal, and sensor validation; it is not a fresh introduction to C# programming.

The vocabulary used below is:

- **Interface, signature, and prototype:** the caller-visible name, return type, and parameter names and types of an operation. Here “interface” does not specifically mean a C# `interface` declaration.
- **Implementation:** the instructions that perform an operation. A **parameter** is a named input in a declaration; an **argument** is the value supplied at a call.
- **Interval and bounds:** a range between a lower and an upper endpoint. An **inclusive** endpoint belongs to the interval; an **exclusive** endpoint does not. `[a,b]` includes both endpoints; `[a,b)` excludes the upper one.
- **Named argument:** C# syntax `parameterName: value` that identifies the receiving parameter. A **named constant** gives a fixed value a meaningful name; a **magic constant** is a literal whose purpose is unexplained.
- **Contract:** what a caller must supply and what it may rely on. Its **input contract**, or **precondition**, states the caller's obligations; its **output contract** states the operation's guarantees, including permitted effects.
- **External state and side effect:** data or observable activity beyond the returned value; changing it, including printing, is a side effect.
- **Guard:** a check that protects a precondition. An **assertion**, such as `Debug.Assert`, checks a development assumption. The **DEBUG compilation symbol** controls inclusion of these assertion calls; a conventional **Release build** omits them.
- **Public API and argument exception:** an API is an interface offered to other code; a public library API must handle callers outside the author's control. An argument exception reports invalid arguments at runtime. **NuGet** distributes .NET library packages.
- **Duplicate removal, or deduplication:** retain one occurrence of each distinct value under a specified equality rule.
- **Coupling:** the dependence of one part of a program on another; named here as prerequisite context rather than developed as a separate topic.
- **Abstraction:** a meaningful operation or data model that lets its user disregard implementation details. An **abstraction level** describes how much underlying mechanism a piece of code handles.
- **HashSet, List, and comparer:** a set tracks distinct members, a list accumulates an ordered sequence, and a comparer defines equality or ordering. **Ordinal** string comparison uses character values and distinguishes letter case; **OrdinalIgnoreCase** ignores case.
- **Semantic naming:** name a value or operation for its meaning in the program.
- **Normalization:** convert different representations of the same meaning into one internal form.
- **Invariant:** a condition established at construction and preserved by every operation throughout an object's lifetime.
- **Factory, private constructor, and get-only property:** a factory creates validated objects; a private constructor restricts direct creation; a get-only property exposes reading without exposing a setter.
- **Encapsulation:** keep representation-dependent operations and construction under the type's control, exposing only the access callers need.
- **Local reasoning:** understand a function from its own logic, its explicit inputs, and the contracts of the operations it calls.
- **Indirection:** reach an action through another name or call, adding a level the reader may need to follow.
- **Dependency, configuration, and global state:** a dependency is something an operation needs; configuration supplies settings; global state can be accessed without being passed as an argument.
- **Mutation and in-place operation:** mutation changes existing data; an in-place operation writes into the supplied object rather than producing an independent replacement.
- **Read-only view or span:** an input interface that offers reading without offering writes through that view. It does not freeze an object that another reference can still change.
- **Reference and alias:** a reference identifies an object; an alias is another reference to that same object. Copying a reference does not copy the object's contents.

## Implement duplicate removal

[00:09:48](https://www.youtube.com/watch?v=mj771Sd298c&t=588s) To implement the higher-level action, track seen names in a **HashSet**, a collection of distinct members, and accumulate first occurrences in a **List**, an ordered growing sequence.

The [related set-and-loop implementation](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#6-the-caller-and-implementation-work-at-different-levels) returns a read-only list view. This adapted sample returns the new array discussed in the recording:

```csharp
static string[] RemoveDuplicates(string[] names)
{
    var seen = new HashSet<string>(StringComparer.Ordinal);
    var result = new List<string>();

    foreach (string name in names)
    {
        if (seen.Add(name))
            result.Add(name);
    }

    return result.ToArray();
}
```

| --- | --- |

| `[10, 20)` | `[10, 20)` |
| `(9, 19]` | `[10, 20)` |

## Establish and preserve the invariant

[00:14:37](https://www.youtube.com/watch?v=mj771Sd298c&t=877s) An **invariant** is a condition the type establishes during construction and that all its operations must preserve. A public method must never leave the object in a state that breaks it. [00:15:00](https://www.youtube.com/watch?v=mj771Sd298c&t=900s) For the normalized interval, the invariant is `StartInclusive <= EndExclusive`. Equal normalized bounds describe an empty interval, because no integer can be both at least that start and less than that end.

[00:15:16](https://www.youtube.com/watch?v=mj771Sd298c&t=916s) Use a private constructor and a factory. The **factory** validates the request, normalizes the bounds, and creates the object only after the invariant is established.

```csharp
public sealed class Interval
{
    public long StartInclusive { get; }
    public long EndExclusive { get; }

    private Interval(long startInclusive, long endExclusive)
    {
        StartInclusive = startInclusive;
        EndExclusive = endExclusive;
    }

    public static Interval Create(
        int min, int max,
        Boundary minBoundary, Boundary maxBoundary)
    {
        if (min > max)
            throw new ArgumentException("Bounds are reversed.");

        long start = (long)min
            + (minBoundary == Boundary.Exclusive ? 1 : 0);
        long end = (long)max
            + (maxBoundary == Boundary.Inclusive ? 1 : 0);

        if (start > end)
            throw new ArgumentException("Invalid normalized interval.");

        return new Interval(start, end);
    }

    // Contains is added in the next section.
}
```

The excerpt assumes valid `Boundary` values. The related complete implementation also checks those enum arguments. Its internal `long` bounds avoid overflow when an inclusive `int.MaxValue` must become an exclusive endpoint one greater; the cast occurs before addition. That is an implementation detail supplied by the later supporting source, not an additional claim about what the recording demonstrates.

Follow the factory's steps:

1. [00:15:16](https://www.youtube.com/watch?v=mj771Sd298c&t=916s) Validate the requested bounds before constructing the object.
2. [00:15:34](https://www.youtube.com/watch?v=mj771Sd298c&t=934s) Normalize the lower bound: leave an inclusive bound alone; add one to an exclusive integer lower bound.
3. [00:15:34](https://www.youtube.com/watch?v=mj771Sd298c&t=934s) Normalize the upper bound: leave an exclusive bound alone; add one to an inclusive integer upper bound.
4. [00:15:48](https://www.youtube.com/watch?v=mj771Sd298c&t=948s) Check that the normalized start does not exceed the normalized end. Do not create an object that violates the invariant.
5. [00:15:55](https://www.youtube.com/watch?v=mj771Sd298c&t=955s) Return an object whose bounds have already been validated and are exposed only for reading.

[00:15:53](https://www.youtube.com/watch?v=mj771Sd298c&t=953s) The recording deliberately leaves the response to an invalid invariant open. Throwing, reporting construction failure, or another response must follow the project's requirements. The exception above is one illustrative choice, not a prescribed lesson outcome.

[00:15:55](https://www.youtube.com/watch?v=mj771Sd298c&t=955s) A **get-only property**, written `{ get; }`, exposes a getter but no public setter. Once the factory returns, clients cannot independently replace a bound. [00:16:08](https://www.youtube.com/watch?v=mj771Sd298c&t=968s) Since the bounds remain unchanged and their ordering was established at construction, the invariant holds for the object's lifetime.

Why validate in the factory rather than repeat the same check in every caller?

<details>
<summary>Answer</summary>

The factory owns construction. Every successfully created interval then carries the same guarantee, so callers and later operations can rely on its invariant instead of re-establishing it. Restricting subsequent writes is part of preserving that guarantee.

</details>

## Encapsulate operations for local reasoning

[00:16:22](https://www.youtube.com/watch?v=mj771Sd298c&t=982s) **Encapsulation** keeps concrete construction and representation-dependent operations under the type's control. Callers receive the operations and read access they need, without the ability to break the invariant. [00:16:34](https://www.youtube.com/watch?v=mj771Sd298c&t=994s) The private constructor makes `Create` the creation route for the class example, so validation cannot be skipped by directly invoking that constructor.

[00:16:52](https://www.youtube.com/watch?v=mj771Sd298c&t=1012s) Add `Contains`, which hides how the stored bounds are interpreted. The [related containment presentation](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#10-encapsulation-keeps-bound-interpretation-inside-the-interval) supplies this operation. Simplified addition to the previous type:

```csharp
public bool Contains(int value)
{
    bool result = value >= StartInclusive && value < EndExclusive;
    return result;
}

// Caller:
bool allowed = interval.Contains(rightSensorTemperature);
```

The comparison uses `>=` at the inclusive start and `<` at the exclusive end. Because construction already normalized the bounds, the method needs no original boundary flags.

[00:17:10](https://www.youtube.com/watch?v=mj771Sd298c&t=1030s) In this representation the two comparisons look obvious. A different representation might require different operations. [00:17:19](https://www.youtube.com/watch?v=mj771Sd298c&t=1039s) The caller's question remains the same: is the value inside? It need not know which stored fields or checks produce the answer.

[00:17:30](https://www.youtube.com/watch?v=mj771Sd298c&t=1050s) **Local reasoning** means understanding the code in front of you using its logic, explicit inputs, and the contracts of the functions it calls. The lesson deliberately keeps this reasoning local; it does not ask you to reconstruct the surrounding system.

The [related local-reasoning presentation](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#11-local-reasoning-means-using-the-contracts-of-your-dependencies) gives the same compact workflow:

```csharp
var uniqueNames = RemoveDuplicates(names);
ShowNames(uniqueNames);
```

[00:17:34](https://www.youtube.com/watch?v=mj771Sd298c&t=1054s) Each line has an understandable role: produce distinct names, then display the result. You need to know the duplicate-removal and display contracts; you do not need their algorithms or the rest of the application. The earlier no-side-effects promise belongs to the interval check and duplicate-removal contract, not to `ShowNames`, whose intended job includes displaying output.

## Centralize the all sensors check

[00:18:01](https://www.youtube.com/watch?v=mj771Sd298c&t=1081s) Consider code that repeats each sensor field in every checking function. Adding a new sensor then forces edits wherever those fields are listed. [00:18:09](https://www.youtube.com/watch?v=mj771Sd298c&t=1089s) There is another problem: a reader cannot tell whether the listed fields are the complete set or an intentionally chosen subset.

The [related sensor-field examples](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#12-a-caller-should-not-have-to-list-all-the-fields) show repeated knowledge of the representation. Here is a simplified intermediate state:

```csharp
bool allowed = interval.Contains(readings.Left)
    && interval.Contains(readings.Center)
    && interval.Contains(readings.Right);
SetIndicator(allowed);

// Another function repeats the same three-field check
// before deciding whether to sound an alarm.
```

[00:18:39](https://www.youtube.com/watch?v=mj771Sd298c&t=1119s) Inlining that enumeration does not state its completeness. [00:18:57](https://www.youtube.com/watch?v=mj771Sd298c&t=1137s) It also mixes representation-level detail with the function's higher-level purpose, such as setting an indicator or making an alarm decision.

[00:19:07](https://www.youtube.com/watch?v=mj771Sd298c&t=1147s) Extract the operation that owns both the enumeration and the checks. The [related AllWithin extraction](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#13-put-the-field-by-field-operation-in-one-place) centralizes the same rule:

```csharp
static bool AllWithin(Readings readings, Interval interval)
{
    return interval.Contains(readings.Left)
        && interval.Contains(readings.Center)
        && interval.Contains(readings.Right);
}

// Screen update:
bool allowed = AllWithin(readings, interval);
SetIndicator(allowed);
```

`Readings` is the sensor-data type whose fields the operation checks. `AllWithin` must promise that **every** relevant sensor reading is checked; its name would be misleading if the implementation silently omitted one.

[00:19:23](https://www.youtube.com/watch?v=mj771Sd298c&t=1163s) The caller now reasons about validating all readings, without deciding which fields exist. Field traversal and containment checking live together in the lower-level helper; the screen-level code deals with the verdict and the indicator.

This is still work to maintain: adding a sensor requires updating the centralized helper. The benefit is that each screen or alarm function no longer repeats that field knowledge. No new collection or iterator design is required for this lesson's extraction.

## Weigh the cost of indirection

[00:19:44](https://www.youtube.com/watch?v=mj771Sd298c&t=1184s) Try the same extraction technique on the input guard: move validation into `CheckArguments`, give it the function's parameters, and have it raise the exception. The [related guard-extraction comparison](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#14-another-call-can-help-or-just-make-you-look-elsewhere) shows why that extra level may add little value. The sample preserves the recording's strict input contract:

```csharp
// Before: the guard is directly visible.
if (minInclusive >= maxInclusive)
    throw new ArgumentException("Invalid bounds.");

// After: another call hides the same guard.
CheckArguments(value, minInclusive, maxInclusive);

// Separate helper:
static void CheckArguments(
    int value, int minInclusive, int maxInclusive)
{
    if (minInclusive >= maxInclusive)
        throw new ArgumentException("Invalid bounds.");
}
```

These before-and-after fragments are alternatives, not instructions to execute both guards. [00:19:46](https://www.youtube.com/watch?v=mj771Sd298c&t=1186s) The helper keeps validation associated with the operation, but now understanding it requires another lookup; `value` is not even needed for this particular bound check.

[00:20:00](https://www.youtube.com/watch?v=mj771Sd298c&t=1200s) Extraction can sometimes align validation with the rest of a larger function's abstraction level. [00:20:22](https://www.youtube.com/watch?v=mj771Sd298c&t=1222s) In this tiny example it hides essentially one already understandable action. The reader gains a name and a new layer to navigate without a substantial reduction in complexity.

[00:20:36](https://www.youtube.com/watch?v=mj771Sd298c&t=1236s) An abstraction can help or hurt. [00:20:45](https://www.youtube.com/watch?v=mj771Sd298c&t=1245s) Operations that were previously inline are now visible only by following the new name. [00:21:04](https://www.youtube.com/watch?v=mj771Sd298c&t=1264s) This is **indirection**: reaching the actual operation through another call or name. [00:21:26](https://www.youtube.com/watch?v=mj771Sd298c&t=1286s) Here it probably brings no benefit, but that is a judgment about this example, not a ban on validation helpers.

Compare the changes:

- `AllWithin` removes repeated knowledge of sensor layout from callers and states a completeness guarantee.
- `CheckArguments` merely relocates a short guard in the example. The reader must follow it to learn what is checked.

Ask what knowledge the extraction saves, what contract it establishes, and what extra navigation it adds. A helper earns its place through those benefits, not simply because extraction is possible.

## Keep the workflow at one abstraction level

[00:21:29](https://www.youtube.com/watch?v=mj771Sd298c&t=1289s) A block that reads names, directly manages a set and list, and then prints names moves from high-level intent down into an algorithm and back up again.

The [related before-and-after workflow](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#15-show-the-workflow-without-its-subordinate-algorithm) extracts duplicate removal. // Before:
```csharp
var names = ReadNames();

{
    if (seen.Add(name))
        unique.Add(name);

```

[00:21:50](https://www.youtube.com/watch?v=mj771Sd298c&t=1310s) Extract the concrete **deduplication** actions into the already introduced `RemoveDuplicates` abstraction. [00:22:08](https://www.youtube.com/watch?v=mj771Sd298c&t=1328s) The set, traversal, and result accumulation are hidden below the duplicate-removal name. [00:22:16](https://www.youtube.com/watch?v=mj771Sd298c&t=1336s) The first block mixes high, low, and high abstraction levels; the second states three workflow-level actions. An **abstraction level** is relative: an operation is higher with respect to the layers and concepts underneath it, not because it receives some universal numeric rank.

## Make configuration dependencies explicit

[00:22:33](https://www.youtube.com/watch?v=mj771Sd298c&t=1353s) A function can hide input data as well as an algorithm. **Configuration** supplies settings; a **dependency** is something the function needs to do its work. Reading configuration from **global state** adds a dependency that is absent from the parameter list.

[00:22:41](https://www.youtube.com/watch?v=mj771Sd298c&t=1361s) Pass the needed configuration explicitly instead. The [related explicit-input presentation](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#16-make-the-necessary-input-visible) illustrates this difference. Shortened reconstruction:

```csharp
// Hidden input:
bool IsAllowed(int temperature)
    => temperature <= Settings.MaximumTemperature;

// Visible input:
bool IsAllowed(int temperature, int maximumTemperature)
    => temperature <= maximumTemperature;
```

These declarations are alternatives. The first function's result depends on both its visible argument and whichever global setting happens to be present. The second states that setting as an input. Merely reading global state need not mutate it: a hidden dependency and a side effect are different concepts.

[00:22:50](https://www.youtube.com/watch?v=mj771Sd298c&t=1370s) Another suggested design groups settings into an abstraction and puts an `IsValid` operation there. The recorded proposal is related to the [presentation's advice on meaningful configuration abstractions](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#16-make-the-necessary-input-visible); the following is a schematic adaptation rather than committed exact code:

```csharp
// settings is supplied to this operation, not obtained globally.
bool IsAllowed(int temperature, TemperatureSettings settings)
    => settings.IsValid(temperature);
```

`TemperatureSettings` stands for a type owning the temperature rule; `IsValid` encapsulates the checks. Its implementation may hide precisely which individual settings participate, while the function signature still shows that a settings object is required.

[00:23:06](https://www.youtube.com/watch?v=mj771Sd298c&t=1386s) This abstraction can hide both the validation logic and its dependence on particular settings. [00:23:09](https://www.youtube.com/watch?v=mj771Sd298c&t=1389s) That means a reader no longer sees each specific setting in the outer function. The dependency on the settings object is still important and must remain explicit.

[00:23:22](https://www.youtube.com/watch?v=mj771Sd298c&t=1402s) Wrapping a global read inside a method does not remove the global data dependency. A self-contained function instead receives its configuration through a parameter. [00:23:31](https://www.youtube.com/watch?v=mj771Sd298c&t=1411s) This supports **local reasoning**: everything the operation needs is supplied locally, so understanding it does not require reconstructing the caller's whole global environment.

[00:23:51](https://www.youtube.com/watch?v=mj771Sd298c&t=1431s) The recording favors a settings abstraction supplied with the needed settings rather than an implicit global lookup. Use the abstraction to encapsulate a meaningful rule; use the signature to make the dependency visible. An abstraction may reduce detail without concealing the fact that input is required.

## Express mutation and observe shared data

[00:24:03](https://www.youtube.com/watch?v=mj771Sd298c&t=1443s) Parameter types can communicate parts of a contract. A **read-only view** offers reading without write operations through that view. The recording contrasts such an input, including a read-only span, with a mutable list. The later [parameter-access presentation](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#17-use-a-parameter-view-that-matches-the-intended-access) uses `IReadOnlyList` for the same distinction; it is a related type choice, not the exact recorded declaration.

```csharp
// Declaration shapes, not complete implementations:
IReadOnlyList<string> RemoveDuplicates(IReadOnlyList<string> names);

void SortInPlace(List<string> names);
```

`IReadOnlyList` offers reading and counting without collection writes through that interface. `List` offers mutation. A **read-only span** similarly provides a view that does not offer element writes through that span; it need not be interchangeable with every collection interface.

[00:24:16](https://www.youtube.com/watch?v=mj771Sd298c&t=1456s) When `RemoveDuplicates` promises not to modify its input, duplicates remain in the original data and disappear only from the newly returned result. A short example associated with the [related deduplication contract](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#5-a-useful-abstraction-can-hide-a-substantial-operation):

```csharp
var original = new List<string> { "Ann", "Ann" };
var unique = RemoveDuplicates(original);
// original still contains two entries.
// unique contains one entry.
```

[00:24:41](https://www.youtube.com/watch?v=mj771Sd298c&t=1481s) `SortInPlace` is an **in-place operation**: it sorts by rewriting the supplied list's own contents. It therefore needs writable access rather than the recording's read-only input. The name and contract should disclose this **mutation**, a change to an existing object.

[00:24:53](https://www.youtube.com/watch?v=mj771Sd298c&t=1493s) A mutable parameter means the caller must allow for possible mutation unless the contract says otherwise. [00:25:11](https://www.youtube.com/watch?v=mj771Sd298c&t=1511s) **Correction:** the spoken discussion also tries to infer non-mutation from the return type. Neither returning a value nor returning `void` establishes whether input is changed. A function can return a new value and mutate input, or return `void` and leave input alone. Use the operation's stated contract, its meaningful name, and the access offered by its parameter type together.

[00:25:18](https://www.youtube.com/watch?v=mj771Sd298c&t=1518s) A **reference** identifies an object. Passing a list as an ordinary parameter copies that reference value, not the list contents; this is not C#'s `ref` parameter mechanism. An **alias** is a second reference to the same object.

The [related shared-reference demonstration](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#18-two-references-can-observe-the-same-change) shows the consequence. This simplified example includes the sorting operation:

```csharp
static void SortInPlace(List<string> names)
    => names.Sort(StringComparer.Ordinal);

var original = new List<string> { "Bob", "Ann" };
IReadOnlyList<string> secondReference = original;

SortInPlace(original);
Console.WriteLine(secondReference[0]); // Ann
```

[00:25:32](https://www.youtube.com/watch?v=mj771Sd298c&t=1532s) Printing through the original or second reference observes the sorted contents: both identify the same object, so the first element is now `"Ann"`. This is an illustrative reconstruction of the recorded aliasing result, not a test run performed for these notes.

A read-only view restricts what its holder can do through that view. It does not make the underlying shared object immutable or prevent another owner from changing it. That precise limit is part of understanding the input contract.

Predict the original list after non-mutating duplicate removal, and after an in-place sort.

<details>
<summary>Answer</summary>

Duplicate removal leaves the original entries, including duplicates, unchanged and returns a separate result. An in-place sort changes the supplied list; every alias of that list observes its changed order.

</details>

## Decide which abstractions earn their place

[00:25:47](https://www.youtube.com/watch?v=mj771Sd298c&t=1547s) Return to the sensor example. The abstraction over the data lets callers stop reasoning about its concrete fields. [00:25:54](https://www.youtube.com/watch?v=mj771Sd298c&t=1554s) Its contract must promise that all relevant fields are taken into account.

The [related final comparison of callers](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#19-compare-the-knowledge-required-by-two-callers) asks what knowledge the helper removes. A compact version:

```csharp
// Representation-dependent caller:
bool allowed = interval.Contains(readings.Left)
    && interval.Contains(readings.Center)
    && interval.Contains(readings.Right);

// Caller relying on the all-readings contract:
bool allAllowed = AllWithin(readings, interval);
SetIndicator(allAllowed);
```

[00:26:06](https://www.youtube.com/watch?v=mj771Sd298c&t=1566s) Without the abstraction, a fourth sensor requires changing every caller that enumerates the fields. [00:26:19](https://www.youtube.com/watch?v=mj771Sd298c&t=1579s) With it, the field-dependent enumeration changes in one centralized operation. Callers continue to rely on its completeness guarantee. That concrete change explains the abstraction's value.

[00:26:24](https://www.youtube.com/watch?v=mj771Sd298c&t=1584s) Adding another wrapper around `SetIndicator` can be pointless if it only supplies another name for the same action. [00:26:38](https://www.youtube.com/watch?v=mj771Sd298c&t=1598s) A wrapper becomes meaningful when the indicator has a specific domain purpose, for example indicating whether a maximum-temperature setting is valid.

The [related semantic-naming discussion](https://github.com/AntonC9018/uniCourse_csharp/blob/7e53c72e223132cbd1278019f2b05d3654e658f5/presentations/source-notes.md#7a-names-can-express-meaning-in-the-system) supports that distinction; this recording-specific wrapper is a simplified illustration, not an exact state in that source:

```csharp
void SetMaxSetTemperatureIndicatorValue(bool value)
{
    SetIndicator(value);
}
```

[00:26:49](https://www.youtube.com/watch?v=mj771Sd298c&t=1609s) This wrapper is justified only if its name and placement encode real domain intent. A generic wrapper that merely renames an already clear action adds indirection without that benefit. Semantic meaning, centralized representation knowledge, and useful contracts are concrete reasons to introduce an abstraction; introducing another layer by itself is not one.

What must `AllWithin` promise, and why is the semantic indicator wrapper a separate decision?

<details>
<summary>Answer</summary>

AllWithin must check every relevant reading against the interval, not a hidden subset. It centralizes knowledge of sensor fields. The indicator wrapper earns its place only if it names a real application meaning; centralizing field enumeration does not automatically justify wrapping every subsequent call.

</details>

The lesson stays with local function reasoning and these small examples. A dedicated sensor type is deferred when first proposed; floating-point interval design is outside the integer normalization example; the factory's failure policy depends on project requirements. Public-library validation is discussed to explain why development assertions alone are insufficient, rather than to teach library packaging. No full-system architecture or universal rule for when every helper should be extracted is established.
