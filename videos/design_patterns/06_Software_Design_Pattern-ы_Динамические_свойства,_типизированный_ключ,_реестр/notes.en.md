# Dynamic properties, typed keys, and registries

[00:00:00](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=0s) This lesson builds a way for reusable execution code to carry data chosen by its caller. We begin with tree traversal and game systems, construct a pipeline, and repeatedly change its context representation until independent steps can share a context without scattering casts or accidentally reusing the same key.

The terms used in this journey are:

- **Abstraction and traversal:** an abstraction exposes an operation while hiding its implementation; traversal is the mechanism that visits tree nodes or pipeline steps in an ordered way.
- **Strategy and delegate:** a strategy supplies the behavior an abstraction applies. A delegate is a callable function value; an interface can express a strategy needing several callbacks.
- **Context and dynamic properties:** context is the data carried through an execution. Dynamic properties are entries that callers attach to that context without adding fields to its declared class. “Dynamic” here describes extensible storage, not C#'s `dynamic` keyword.
- **Pipeline, step, and builder:** a pipeline runs an ordered set of steps; a step performs one operation; a builder collects the configuration before constructing the pipeline.
- **Entity, system, capability, and component:** an entity represents a game object through its data. A system processes entities having the capabilities it needs. A component groups related data, such as inventory contents or health.
- **Mutable and immutable state:** mutable data can change after creation; immutable configuration stays fixed. A mutex or lock serializes access to shared mutable state. A race occurs when overlapping accesses produce an order-dependent result; contention is the waiting caused by synchronization.
- **Fat struct:** one statically declared data container includes every property the application might need, even when a particular operation uses very few of them.
- **Abstract base, interface, and cast:** an abstract base is an inheritance contract that cannot itself be instantiated. An interface describes required members. A cast asks for a value as another type and may fail at runtime.
- **Generics and type inference:** a generic type or method has a type parameter such as `TContext` or `T`; type inference lets the compiler determine an argument from a call. Static type safety means incompatible types can be rejected before execution.
- **Contravariance and covariance:** variance governs conversions between constructed generic interfaces or delegates. Contravariance lets a consumer of a broader reference type be used as a consumer of a narrower one; covariance works in the output direction.
- **Decorator:** a wrapper adds work before or after an existing operation, such as computing depth before a wrapped strategy uses it.
- **Key, array, and dictionary:** a key identifies an entry; an array stores numbered cells, while a dictionary associates keys with values. Sparse positional storage reserves unused gaps. Capacity is a storage-allocation hint. A collision occurs when unrelated entries use the same identity; a namespaced key includes an ownership prefix.
- **Typed key:** `Key<T>` carries an identity together with the compile-time type of the value stored under it. The key identifies data; the data remains in the context.
- **Object, value type, reference type, and boxing:** an `object` slot can hold values of different types. A value type such as `int` represents its data directly; a reference type such as a class or string is accessed through an object reference. Boxing wraps a value-type value in an object representation.
- **Flyweight, pool, and ECS:** A flyweight shares reusable objects; a pool reuses allocated objects. Entity Component System (ECS) organizes entities, component data, and systems, often storing data by component type.
- **Registry, singleton, and metadata:** a registry centralizes key creation. A singleton is one shared instance, which may still be referenced through ordinary instance variables. Metadata describes a key, for example its name or value type; introspection reads that description at runtime.
- **Nullability and constraints:** nullability expresses whether a value can be absent. A generic constraint restricts allowed type arguments; `notnull` states a non-null type expectation. The null-forgiving operator `!` suppresses a nullable warning without checking the value.
- **Constants and access boundaries:** a `const` is a compile-time constant; a `static readonly` field can hold an identity created once at runtime. An assembly is a compiled unit such as a library DLL; `internal` restricts access to that unit. An indexer is bracket-based access such as `items[key]`.
- **Hashing and hash sets:** a hash calculation maps a key to a number used to organize lookup. A hash set tracks distinct values and reports whether an insertion adds a new one.
- **Initialization syntax:** an object initializer assigns members immediately after construction. `required` requires a member to be initialized; `init` permits assignment during initialization. A sentinel is a reserved value meaning that a property is absent.
- **Game data:** world position locates an entity; a sprite is its image; a shader is rendering code, such as the code drawing water waves. Physics properties describe how an entity interacts with movement or collisions.

## Traversal and a depth-aware strategy

[00:00:04](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4s) A tree-walking abstraction knows how to visit nodes. It should not also decide every useful thing that can happen to a node. Supplying that behavior from outside makes the traversal reusable: sum numbers today, mutate nodes tomorrow, or collect a report later.

[00:00:22](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=22s) The operation applied at each node is the **strategy**, the chosen behavior. A simple delegate can add each node's number to a running sum. The **context** is the state that survives between visits: initialize `Sum` to zero, then accumulate into it. Keeping a sum in a strategy object's field is one way to package the operation and its data together.

[00:01:11](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=71s) A more demanding strategy needs the node's depth as well as the node itself. A single node-only delegate does not supply traversal-position information. An interface can instead expose an entering-child callback and an exiting-to-parent callback. Ordered callbacks let the strategy maintain depth without inspecting the tree's shape.

[00:01:46](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=106s) Depth-weighted accumulation adds `node.Value * depth`. The first level uses coefficient 1, the second 2, and the third 3. The spoken sketch mentions values including 1, 2, 4, and 6; these are example products, such as `2 * 2 = 4` and `2 * 3 = 6`, not a rule that four unit-valued nodes produce those four contributions.

[00:02:03](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=123s) The reconstructed operation is:

```csharp
sealed class WalkContext
{
    public int Depth;
    public int Sum;
}

// Sketch: enter the root as level 1, and balance each enter with an exit.
void Enter(WalkContext c) => c.Depth++;
void Visit(int nodeValue, WalkContext c) => c.Sum += nodeValue * c.Depth;
void Exit(WalkContext c) => c.Depth--;
```

[00:02:17](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=137s) Increment on entry and decrement on exit. Depth belongs to the shared context just as the sum does, because both must persist across node visits. The traversal owns callback order; the strategy owns what those callbacks mean. The code above is a video-based sketch, not a located repository implementation.

## Passing context through a fixed abstraction

[00:02:31](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=151s) A traversal paired with a strategy still does not fully explain dynamic properties. The difficult case is a **fixed grouping**: the abstraction and its strategy have already been configured together, but an outside caller needs to supply the data for a particular run.

[00:02:51](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=171s) The caller does not invoke the strategy directly. The traversal invokes it. Previously the strategy and a reference to its context could travel as one object, with the running sum stored in the strategy implementation. Once that strategy is fixed inside the grouping, attaching data at construction time is too early for per-run input.

[00:03:50](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=230s) Supplying context when the entire grouping is constructed can push communication toward globals or other shared captured state. The workaround is to serialize the run with a mutex and let all communication go through that shared state. It permits one thread to run at a time, but turns independent work into synchronized access to the same data.

[00:04:36](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=276s) The desired flow is instead: the caller supplies context to the abstraction; the abstraction carries it through traversal; the strategy reads or changes it; the caller inspects the result. The result could describe the data structure, or the operation could add a caller-chosen `X` to each node.

[00:05:04](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=304s) In the parameterized version, the operation prepares the data used by subsequent steps rather than calling the steps itself. `X` therefore travels in context: a caller cannot pass it directly to a callback that only the traversal calls.

[00:05:36](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=336s) The user chooses the strategy's steps, while the abstraction encapsulates their application to the structure. Those steps still need input that can only come from outside. That is the relevant condition for applying the context approach. ## A pipeline separates ordering from data

[00:06:12](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=372s) A **pipeline** is an ordered sequence of functions or step objects. Its traversal is simply a loop; its configured steps supply the strategy. Each step receives the same execution context, can update it, and leaves information that later steps or the caller can inspect.

The [related owner-history pipeline](https://github.com/AntonC9018/uniCourse_csharp/blob/a386c9c8c77cc4f67311059663399b5b793ed47d/examples/pipeline_library/Pipeline.cs) contains an ordered `Execute` loop and a context carrying a dog and previous owners. A shortened sample makes the separation visible:

```csharp
void Execute(Context context)
{
    foreach (var step in steps)
        step.Execute(context);
}

// The caller can inspect accumulated information after execution.
pipeline.Execute(context);
Console.WriteLine(context.PreviousOwners.Count);
```

[00:06:40](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=400s) The loop determines which step is called next. It passes context onward without interpreting the domain data. In the earlier example the pipeline accumulates previous owners, so the result and the number of former owners can be reported together.

[00:07:07](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=427s) The caller can invoke the traversal but does not change its implementation. The caller controls steps when building the pipeline; during a run, the caller selects the context rather than rebuilding the strategy.

[00:07:44](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=464s) A fixed list can be traversed repeatedly. The same pipeline configuration serves many runs, while each run gets its own data. This is why the strategy is applied through the abstraction rather than by directly calling each step.

[00:08:20](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=500s) If the loop examined the sum, name, or owner fields to decide how to execute, it would become coupled to this domain. At [00:08:36](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=516s) it merely hands context to each step unchanged; at [00:08:46](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=526s) the traversal logic stays identical regardless of the input. That indifference is the reason a context can often become **dynamic**: extensible contents matter to the steps, while the traversal need only transport the container.

## Shared mutable steps require locking

[00:18:22](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1102s) The pipeline configuration is intended to be **immutable**: after construction, its chosen steps and ordering stay fixed. Mutable input embedded in those steps undermines that goal. If two places, ideally two threads, reuse it at [00:18:37](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1117s), they also share the embedded execution data.

[00:18:56](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1136s) The existing mutable instance needs a lock around its use. The critical section is larger than just assigning a name:

1. [00:19:06](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1146s) Acquire the lock for this pipeline instance.
2. Set the run's context data.
3. Execute immediately while still holding the lock.
4. Release the lock only when the execution using that data has finished.

[00:19:23](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1163s) Otherwise thread A can set “собака,” thread B can replace it with “кошка,” and thread A can execute the wrong greeting. This is a **race**, an outcome determined by interleaving shared-state operations.

[00:19:37](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1177s) Locking avoids that race but causes **contention**: another thread blocks until the whole execution ends. Separating per-run context from fixed strategy configuration avoids this particular serialization.

[00:19:49](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1189s) Pass fresh input from outside on each `Execute` call instead of capturing it when creating the pipeline. The rule applies to any abstraction of this shape, not only a pipeline at [00:20:00](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1200s).

[00:20:08](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1208s) The name should arrive at invocation time. The caller invokes the whole pipeline, however, so a name parameter cannot be aimed directly at one encapsulated step. A common context parameter is the route to that step at [00:20:16](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1216s). Separate contexts also do not automatically make all code thread-safe: steps must avoid other shared mutable execution state, and callers must avoid simultaneously mutating the same context.

[00:22:27](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1347s) Build the arithmetic pipeline from two steps, adding five and then ten. Execute it with a newly created context, then print the resulting numeric field at [00:22:57](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1377s); the narration refers to the result field as an “id.” Do not infer an identifier algorithm from that spoken name: the demonstration concerns accumulated arithmetic data.

[00:23:07](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1387s) The recording reports that the current demonstration does not work. It leads into the design problem at [00:23:10](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1390s): one context has been extended to contain both greeting and arithmetic data. This is a reported intermediate failure, not proof that a class with two fields is itself invalid C#.

[00:23:24](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1404s) Mixing fields is not inherently impossible. Initialize unused members and let each pipeline ignore them. At [00:23:32](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1412s) one option is to put every field the application may ever need into one large context.

[00:23:40](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1420s) This is used in practice, especially in games. The name is **fat struct**, a single statically known container with all anticipated properties; the captions render it inconsistently as “F-struct” or “Fract.” Its advantage at [00:24:05](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1445s) is simplicity and fully known field access. The example repository even uses a class for this representation, so “struct” here is a design nickname rather than a requirement to use C# `struct`.

[00:24:16](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1456s) Its costs are unused fields and storage, and at [00:24:21](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1461s) knowledge of every domain that uses it. The decisive boundary appears at [00:24:41](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1481s): if a library owns the builder, pipeline, and fixed context type, its consumer cannot edit that type to add its own application data.

[00:25:10](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1510s) **Dynamic properties** solve that extensibility problem: consumer code attaches data to a library-defined context without changing the context's class declaration. Regardless of representation, the caller still must define the information it wants to pass to later stages at [00:25:21](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1521s).

## An abstract base allows caller-defined contexts

[00:25:23](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1523s) There are several ways to supply caller-defined data: an abstract base with derived contexts, generic parameters, or dictionary/array storage. The lesson now explores these in sequence; they are alternatives, not requirements to combine every technique.

[00:25:46](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1546s) First make context an **abstract base class**, an inheritance marker that cannot be directly instantiated, and remove its data fields. Steps accept instances whose classes derive from that base. The [related inheritance contracts](https://github.com/AntonC9018/uniCourse_csharp/blob/d5af1fb372be56a453e3b139990013c28e50198c/examples/property_dict/Subclassing.cs) similarly separates a common base from specialized data. A shortened reconstruction of this pipeline stage is:

```csharp
abstract class Context { }
sealed class GreetingContext : Context
{
    public required string Name;
}
sealed class MathContext : Context
{
    public int Sum;
    public int Multiplier = 1;
}
interface IPipelineStep
{
    void Execute(Context context);
}
```

[00:26:03](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1563s) The common parameter admits any derived context. At [00:26:11](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1571s) `object` could technically serve as an even broader base. The abstract class is useful because it documents intent and excludes unrelated objects at [00:26:14](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1574s). Explicit inheritance makes the data flow more controlled at [00:26:26](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1586s); it is not indispensable to the pattern at [00:26:37](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1597s).

[00:26:47](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1607s) The intermediate code fails to compile because call sites still need an actual context. An abstract base cannot be created with `new Context()`. Every pipeline needs a suitable concrete context at [00:26:50](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1610s).

[00:27:03](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1623s) Define the math context and its required members as well. It can carry additional information such as a multiplier at [00:27:11](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1631s), and multiple arithmetic steps can share it at [00:27:25](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1645s). Providing the data classes fixes construction, but the broad step signature does not yet tell each step which members it can use.

## Concrete casts move errors to runtime

[00:27:34](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1654s) Update every greeting invocation to create the concrete greeting context explicitly. The demonstration's greeting/print/grid names vary; this note uses `GreetingContext` for the name-bearing example. At [00:28:00](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1680s) the greeting step expects that concrete runtime type, while its parameter is still the abstract base.

The [related specialization by runtime type](https://github.com/AntonC9018/uniCourse_csharp/blob/d5af1fb372be56a453e3b139990013c28e50198c/examples/property_dict/Subclassing.cs) contains capability tests such as `character is not IMage`. This sample reconstructs the less forgiving concrete casts in the video:

```csharp
void Greet(Context context)
{
    var greeting = (GreetingContext)context;
    Console.WriteLine(greeting.Name);
}
void Add(Context context)
{
    var math = (MathContext)context;
    math.Sum += 5;
}
```

[00:28:05](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1685s) Cast the base parameter to the greeting type. At [00:28:12](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1692s) the math step needs an equivalent cast. A **cast** converts a reference to the requested type only if the actual object supports that type; inheriting a common base does not make sibling derived types interchangeable.

[00:28:28](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1708s) Every step needing specialized fields repeats a cast. Avoiding this repetition is deferred at [00:28:36](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1716s). A step already holding a `MathContext` reference would not need to cast that reference again at [00:28:39](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1719s), but an `Execute(Context)` parameter still requires narrowing before accessing math-only fields.

[00:28:50](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1730s) The compiler knows only the broad pipeline contract. It cannot establish that a particular configured pipeline expects a greeting context. At [00:29:12](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1752s) passing a math context to it is accepted by the call's static signature.

[00:29:24](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1764s) Execution then fails when the greeting step casts that math object to its expected type. This is a runtime invalid-cast failure, not a compilation error.

[00:29:34](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1774s) The approach trades static guarantees for flexibility. Generics partly recover those guarantees and are introduced later at [00:29:39](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1779s).

<details>
<summary>Predict: does giving two context classes the same abstract base make either safe for every step?</summary>

No. The base only permits them to enter the abstraction. A step casting to a sibling concrete type can still fail when it receives the wrong object. The step's true requirement is stronger than its declared parameter.
</details>

## Mixed operations need shared capabilities

[00:29:45](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1785s) A second limitation appears when one pipeline should both greet and do math. You can append the greeting step at [00:30:01](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1801s), but the abstract-base contract does not prove that all steps can consume the same object.

[00:30:02](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1802s) If one step casts to `MathContext` and another to the separate name-bearing context, one input cannot satisfy both unrelated concrete classes. The compiler does not enforce step compatibility in this broad-base version. The problematic cast happens inside the later step at [00:30:46](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1846s), so failure is deferred until execution. The narration's compiler wording around [00:30:23](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1823s) must be read together with that runtime explanation, not as a claim that this version already rejects the combination statically.

[00:30:54](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1854s) A common base supplies a common entry point but does not express every combination of specialized data. Returning to the game analogy at [00:31:00](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1860s), the system is the pipeline and processed entities are the contexts. Mixed functionality is common at [00:31:11](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1871s); many independent operations may need the same object.

[00:31:42](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1902s) The tree example makes another dependency visible. One operation computes a level; a second scales the current node by that level at [00:32:00](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1920s). The value is two, three, or one depending on depth, so the second operation depends on context produced by the first.

[00:32:08](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1928s) Extract level computation into its own strategy. A **decorator**, a wrapper around another strategy, runs that preparatory work before invoking the wrapped body at [00:32:17](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1937s). Further strategies can reuse the same depth-producing component at [00:32:26](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1946s), and a third strategy in another configured grouping can also depend on it at [00:32:58](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1978s).

[00:33:11](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=1991s) Reusing that decorator preserves the level-before-use ordering in both places. Even if the preparatory work is conceptually separate from the main operation, its output may be required by the main operation at [00:33:29](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2009s).

[00:33:44](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2024s) Walking the tree is expensive, so perform one traversal with many strategies attached to the same context. Writing each strategy as another local variable and call makes the traversal method grow at [00:34:00](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2040s). The next design step is to express just the capabilities each operation requires, instead of hardcoding every concrete strategy and context pairing.

## Interfaces make a combined context possible

[00:34:13](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2053s) An **interface** describes the members a step requires without demanding one particular implementation class. At [00:34:24](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2064s) introduce a narrow contract exposing the name, through a getter method or a property. At [00:34:37](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2077s) change the step's cast to the interface, and give arithmetic an equivalent contract for its data.

The [related capability interface example](https://github.com/AntonC9018/uniCourse_csharp/blob/d5af1fb372be56a453e3b139990013c28e50198c/examples/property_dict/Subclassing.cs) uses `IMage` and `MageTrait` for this separation. The reconstructed pipeline contracts are:

```csharp
interface IHasName { string Name { get; } }
interface IHasSum { int Sum { get; set; } }

sealed class CombinedContext : Context, IHasName, IHasSum
{
    public required string Name { get; init; }
    public int Sum { get; set; }
}

void Greet(Context c) => Console.WriteLine(((IHasName)c).Name);
void AddFive(Context c)
{
    var math = (IHasSum)c;
    math.Sum += 5;
}
```

[00:34:50](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2090s) A mixed pipeline requires an object implementing both interfaces. At [00:35:14](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2114s) create an additional combined context, declare all the needed data, and initialize that object at the call site. This repeats data declarations, but one object can now satisfy both capability contracts. In the sample, `init` limits name assignment to initialization; `required` asks callers to supply it.

[00:35:30](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2130s) After the missing combined object is created and initialized, the recording reports successful compilation. At [00:35:34](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2134s) the reason is the interface refactoring; the pipeline's execution loop did not need to change.

[00:35:52](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2152s) Depending on interfaces is valid and common. We have gained combinations, but `Execute(Context)` still relies on runtime casts. The next refactoring connects the declared input type to the builder and its steps.

## Type the builder pipeline and steps together

[00:36:01](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2161s) A **generic type parameter** stands for a type selected by the caller. Parameterize the builder with its context type; the constructed pipeline then requires that type at invocation at [00:36:18](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2178s). An incompatible argument becomes a compile-time error at [00:36:29](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2189s), and a step requiring the wrong context cannot be added at [00:36:37](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2197s).

The [related non-generic execution loop](https://github.com/AntonC9018/uniCourse_csharp/blob/a386c9c8c77cc4f67311059663399b5b793ed47d/examples/pipeline_library/Pipeline.cs) illustrates the loop retained during this refactoring; it does not contain this exact generic teaching state. This video-based sample shows where the type parameter must travel:

```csharp
interface IPipelineStep<TContext>
{
    void Execute(TContext context);
}

sealed class Pipeline<TContext>
{
    private readonly IPipelineStep<TContext>[] steps;
    public Pipeline(IPipelineStep<TContext>[] steps) => this.steps = steps;

    public void Execute(TContext context)
    {
        foreach (var step in steps)
            step.Execute(context);
    }
}

sealed class PipelineBuilder<TContext>
{
    private readonly List<IPipelineStep<TContext>> steps = new();
    public void Add(IPipelineStep<TContext> step) => steps.Add(step);
    public Pipeline<TContext> Build() => new(steps.ToArray());
}
```

[00:36:46](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2206s) Erase the hardcoded context from the library implementation. Apply the changes in order:

1. [00:36:54](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2214s) Replace the concrete parameter type with `TContext`, a generic placeholder.
2. [00:37:07](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2227s) Carry the same parameter through the step interface, builder, constructed pipeline, and execution method.
3. [00:37:15](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2235s) The library is now able to transport any selected context type without knowing its fields.
4. [00:37:25](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2245s) The intermediate program still fails because client code has not yet identified the concrete type expected by the builder and steps.
5. [00:37:37](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2257s) Construct a builder for the required type and update each step's `Execute` parameter to that type. Direct member access replaces casts.

[00:37:58](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2278s) The result is a declared contract: adding a step to a pipeline guarantees the step receives an input of the pipeline's selected type. At [00:38:01](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2281s) a `MathContext` step is reusable in any compatible math-context pipeline; a pipeline for an unrelated context cannot accept it.

[00:38:21](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2301s) Defining the missing math context makes that part compile. At [00:38:28](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2308s) the concrete arithmetic steps still need to be changed to `MathContext`, and the old shared context interface can be removed. The observation at [00:38:36](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2316s) is about this particular concrete-type design: making an interface generic does not by itself remove its declared context requirement.

[00:38:45](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2325s) Two errors remain, including the name/grid step expecting a different context from the math pipeline. At [00:39:16](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2356s) switching the builder to the name/grid type instead rejects the math steps. Commenting out an offending call at [00:39:35](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2375s) lets the remaining errors be examined separately.

[00:39:37](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2377s) Passing the combined grid/math context to a math-only pipeline also fails if those classes merely implement common interfaces and neither is assignable to the other. Use the expected type or redesign the contracts. A derived class could still be passed where its base is expected; generics enforce assignability, not exact runtime-class equality.

[00:39:49](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2389s) The abstraction remains reusable, but type checks now occur both when adding steps and when supplying execution context. At [00:40:03](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2403s) the concrete generic pipeline is complete. Its remaining limitation is composing steps that describe different required capabilities.

## Contravariance admits steps for capabilities

[00:40:06](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2406s) Changing a name step's concrete type to some combined concrete context would still leave arithmetic expecting another class. At [00:40:30](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2430s) move away from a specific concrete parameter and describe the step's required interface. At [00:40:34](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2434s) rename the generic context placeholder consistently: neutral names avoid confusing a type parameter with an actual context class.

[00:40:43](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2443s) Merely renaming a type parameter cannot establish that it implements an interface. The compiler needs a valid conversion between the step's declared requirement and the builder's selected context at [00:40:50](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2450s).

[00:41:05](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2465s) Declare the step's generic parameter with `in`. This is C#'s **contravariance modifier**, not an attribute and not the `in` modifier on an individual method argument. It is safe here because a step consumes context as input and does not produce it as an output at [00:41:11](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2471s).

No exact saved commit for this variance stage was located. The [related capability contracts](https://github.com/AntonC9018/uniCourse_csharp/blob/d5af1fb372be56a453e3b139990013c28e50198c/examples/property_dict/Subclassing.cs) shows the interface idea without generic variance. The simplified teaching state is:

```csharp
interface IPipelineStep<in TContext>
{
    void Execute(TContext context);
}

sealed class GreetingStep : IPipelineStep<IHasName>
{
    public void Execute(IHasName context) =>
        Console.WriteLine(context.Name);
}

// CombinedContext implements IHasName and IHasSum.
IPipelineStep<IHasName> broadConsumer = new GreetingStep();
IPipelineStep<CombinedContext> combinedConsumer = broadConsumer;
```

[00:41:47](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2507s) The lesson points to covariance and contravariance as further reading, reiterated at [00:41:51](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2511s). **Contravariance** means a consumer that can process any `IHasName` can safely process the narrower `CombinedContext` too at [00:41:57](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2517s). A context with extra capabilities is acceptable; one missing the required capability is not.

The [C# reference for generic `in`](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/in-generic-modifier) confirms this input direction and the reference-type restriction. Returning `TContext` from this interface would not be compatible with declaring it solely contravariant.

[00:42:01](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2521s) Give the name/grid step the same interface-based treatment. At [00:42:03](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2523s) the code still fails while the caller supplies a context that does not match the declared requirement. At [00:42:12](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2532s) correcting the caller's context restores compilation and the call works.

[00:42:21](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2541s) Now a pipeline selected for one combined concrete context can admit two unrelated step implementations: one consumes `IHasName`, the other consumes `IHasSum`. Both must be capabilities of that same passed object. Static typing remains, while steps need not name that concrete class.

<details>
<summary>Why can a consumer of IHasName be used with CombinedContext, but not the reverse?</summary>

Every CombinedContext in this example supplies a name, so the broader name consumer has everything it needs. A consumer requiring CombinedContext might also need a sum; an arbitrary IHasName implementation need not provide one.
</details>

## Replace static fields with dynamic storage

[00:42:34](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2554s) Up to this point every context has been **static** in its data shape: its class and interfaces decide what members exist. Even with generics at [00:42:42](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2562s), available data depends on the selected compile-time type. Earlier casts revealed the same limitation.

[00:43:13](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2593s) A field's existence and declared type are determined by the context class. The alternative at [00:43:25](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2605s) is one context type able to carry different data sets at runtime.

[00:43:35](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2615s) Create a new plain `Context` class. It starts empty, so nothing that uses the old fields can compile against it. At [00:43:45](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2625s) switch step signatures to that class and remove their context type parameters; at [00:43:47](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2627s) remove the remaining generic plumbing and old concrete context classes.

[00:43:49](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2629s) The intermediate result does not compile: there is no `Name` or `Sum` field to read or initialize. This is expected during the transition, not the final API.

[00:44:02](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2642s) The new protocol is **key-based storage**: put a value into the context under a key, and retrieve it later using the same key. For example, name at zero and sum at one at [00:44:16](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2656s), so independent steps can read their own entries at [00:44:18](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2658s).

The [related property-array example](https://github.com/AntonC9018/uniCourse_csharp/blob/d5af1fb372be56a453e3b139990013c28e50198c/examples/property_dict/PropertyArray.cs) stores objects in an array but searches them by component type, rather than using this video's positional keys. The simplified positional starting point is:

```csharp
sealed class Context
{
    public required object[] Data;
}
var context = new Context { Data = new object[2] };
context.Data[0] = "Антон";
context.Data[1] = 0;
```

[00:44:24](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2664s) A key could identify an array position, a dictionary entry, or an object found by searching a collection. At [00:44:29](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2669s) the lesson chooses `object[]` initially: an array whose cells can hold object representations of different types. The caller must create and initialize the array before execution. **Dynamic properties** here mean variable contents behind a common container, not runtime invocation through C# `dynamic`.

## Agree on the array keys and initialize the layout

[00:45:35](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=2735s) Replace unnamed positions with public constants, initially named `Name = 0` and `One = 1`.     public const int Sum = 0;
    public const int Date = 1;

## Sparse arrays and casts expose hidden contracts

[00:50:24](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3024s) A large collection of unrelated systems produces a large positional layout. One system uses positions two and three, another only position four at [00:50:45](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3045s). Nevertheless that second system must allocate five cells to include index four at [00:51:00](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3060s), leaving most cells unused at [00:51:07](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3067s).

[00:51:31](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3091s) Assigning an `int` to an `object` cell causes **boxing**, allocation of an object representation of that **value type**, whose value otherwise has a direct representation such as an integer. The lesson considers that a smaller immediate concern than type mismatches.

[00:51:53](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3113s) The essential contract is hidden: each key requires a particular value type, and every reader casts accordingly. Put an integer where the greeting expects a string at [00:52:02](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3122s) and retrieval fails at runtime.

The [related final typed-dictionary example](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) demonstrates the same wrong-identity/wrong-type danger with keys rather than array positions. A minimal positional failure is:

```csharp

```

[00:52:22](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3142s) There are two immediate repairs:

1. Store entries only for identities actually present, avoiding allocation of every intervening position.
2. [00:52:30](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3150s) Give key access a type-aware contract, so clients do not manually cast each retrieved object and accidentally write the wrong type.

The storage abstraction may still need a cast internally; the goal is to centralize and constrain it rather than pretend heterogeneous storage is statically typed all the way down.

## Boxing is a separate storage problem

[00:52:36](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3156s) Boxing is deliberately outside the framework repair completed here. Replacing the array with a dictionary and adding typed keys will not remove boxing of value types stored as objects.

[00:52:54](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3174s) The lesson mentions solving allocation concerns at a higher level with **flyweight** objects and a reusable **pool**, rather than directly boxing fresh values. These are sharing/reuse approaches, not implemented code in this lesson.

At [00:53:45](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3225s) callers pass an identifier and resolve data in the appropriate type-specific storage. ## Independent modules can collide on keys

[00:53:51](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3231s) The fourth, and hardest, issue is **key collision**, using the same storage identity for unrelated meanings. At [00:54:00](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3240s) an off-by-one error can write to zero instead of one. Name and numeric data end up under the same key at [00:54:12](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3252s).

[00:54:23](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3263s) The damage may stay hidden until a step retrieves the value and casts it. Startup and ordinary static checks on `object[]` do not detect the semantic mismatch.

[00:54:40](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3280s) One author maintaining a single shared list of keys is less likely to assign the same index twice accidentally. Independent modules each maintaining their own list at [00:54:55](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3295s) are a different problem: both can legitimately choose zero for unrelated data. Modules sharing a context can therefore conflict even if each list is internally correct at [00:55:08](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3308s).

[00:55:13](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3313s) Two approaches are string identities or a **registry**, a central allocator for keys. A registry assigns values at runtime at [00:55:30](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3330s), and every participating module must use the same allocator at [00:55:36](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3336s). Distinct allocations then produce distinct identities.

[00:55:52](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3352s) Numeric identities depend on initialization order: module A gets the low number if it registers first; reverse registration order and module B gets it instead. Code should retain and use the returned key rather than rely on a particular numeric value.

<details>
<summary>Does sharing a constant list inside one module prevent collisions with another module?</summary>

No. The other module can independently choose the same numbers. Both need a shared identity scheme, such as one registry or coordinated names, if their entries live in the same context.
</details>

## Hide storage behind typed keys

[01:00:29](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3629s) Keep the dictionary, but make it private inside context. The context becomes an **abstraction**, exposing operations without exposing object-valued storage. At [01:00:48](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3648s) its public methods must be strictly typed.

[01:01:05](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3665s) Internally the identity can remain an integer. Externally a **typed key**, `Key<T>`, combines that identity with the value type expressed by `T`. Clients no longer manipulate raw positions and then guess the type. A key gives access to a value; its identity is not the stored value itself.

The [related typed-key implementation](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) uses string identities and a readonly generic struct. Here is the integer version reconstructed from the recording:

```csharp
public readonly struct Key<T>
{
    public readonly int Value;
    public Key(int value) => Value = value;
}

static class Keys
{
    public static readonly Key<string> Name = new(0);
    public static readonly Key<int> Sum = new(1);
}
```

[01:01:21](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3681s) Context methods will accept a key to obtain data. At [01:01:32](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3692s) the implementation is not complete yet: lookup alone is insufficient until the matching add operation exists at [01:01:42](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3702s).

[01:01:38](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3698s) The key must carry everything needed to resolve its entry: the runtime identity chooses the dictionary entry, while its static generic type determines the public result type. At [01:01:46](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3706s) the value's key explicitly declares that type.

[01:02:01](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3721s) Replacing an integer constant with `const Key<int>` does not compile. ## Generic access moves casts into the context

[01:02:40](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3760s) `Get` must return the type associated with its key. `Key<int>` means an `int` result at [01:02:55](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3775s), not an `object` needing a caller cast. A compatible write accepts only an integer, so a string write is rejected at [01:03:07](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3787s).

[01:03:14](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3794s) The example changes the erroneous value back to numeric zero so it compiles. The caption says “ноль” (zero), not C# `null`; `null` is not a valid replacement for a non-nullable integer.

The [related generic Add and Get methods](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) hides a dictionary and performs its cast inside `Get<T>`. This simplified integer-identity extension includes the setter discussed in the video:

```csharp
sealed class Context
{
    private readonly Dictionary<int, object> data = new();

    public T Get<T>(Key<T> key) => (T)data[key.Value];
    public void Add<T>(Key<T> key, T value) => data.Add(key.Value, value!);
    public void Set<T>(Key<T> key, T value) => data[key.Value] = value!;
}

// Client code has no explicit casts.
var sum = context.Get(Keys.Sum);
context.Set(Keys.Sum, sum + 5);
// context.Set(Keys.Sum, "five"); // No compatible generic call.
```

[01:03:19](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3799s) Update callers to `Get`, eliminating their manual casts. Name comes back as string; sum comes back as integer. At [01:03:29](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3809s) a setter uses the same key-to-value-type relationship.

[01:03:41](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3821s) The compiler derives the generic argument from the key type. It does not examine the actual dictionary object to infer a type at runtime. The dictionary still stores objects, and the internal cast can fail if the identity/type association was corrupted.

[01:03:55](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3835s) Complete three operations: `Get` returns a value of `T`; `Set` writes a `T`; `Add` accepts a key and matching `T` and returns `void`. The key and value parameters must agree on the same `T`.

[01:04:20](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3860s) `Set` resembles `Get` but writes via the dictionary's bracket syntax. At [01:04:28](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3868s) the narration calls this an overloaded indexing operator. In C# the relevant construct is the dictionary's **indexer**, `data[key.Value] = value`; it is not a custom generic operator on `Key<T>`.

[01:04:34](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3874s) `Get` receives no value argument. It retrieves an object and casts it to the type determined by the key. At [01:04:46](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3886s) `T` is still unknown until the method declares `<T>`. A type parameter cannot simply appear in a non-generic method unless its containing type already declares it.

The `!` in this transitional sample is the null-forgiving operator: it suppresses a nullable warning; it does not validate or convert a value at runtime. The next stage must choose a coherent null contract rather than leave that detail implicit.

## Complete initialization and choose a null contract

[01:05:00](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3900s) Generic writes and object-valued storage raise a **nullability** question: does the API permit null values? The intermediate edit allows nullable dictionary values; at [01:05:16](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3916s) it also experiments with a nullable generic result. That is a temporary contract under construction.

[01:05:34](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3934s) The desired direction then becomes rejecting null input. For reference types, nullable annotations produce compiler warnings by default; projects can treat warnings as errors. They are not runtime checks. Non-nullable value types such as `int` cannot accept null directly. The [nullable-reference documentation](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/null-safety/nullable-reference-types) explains that annotations guide static analysis.

The [related saved typed context](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) uses a null-forgiving write and a cast on retrieval rather than a complete runtime null policy. This simplified, explicitly non-null extension of the teaching idea makes the policy visible:

```csharp
sealed class Context
{
    private readonly Dictionary<int, object> data = new();

    public void Add<T>(Key<T> key, T value) where T : notnull
    {
        ArgumentNullException.ThrowIfNull(value);
        data.Add(key.Value, value);
    }
    public T Get<T>(Key<T> key) where T : notnull =>
        (T)data[key.Value];

    public void Set<T>(Key<T> key, T value) where T : notnull
    {
        ArgumentNullException.ThrowIfNull(value);
        data[key.Value] = value;
    }
}

var context = new Context();
context.Add(Keys.Name, "Антон");
context.Add(Keys.Sum, 0);
var name = context.Get(Keys.Name); // Inferred as string.
var sum = context.Get(Keys.Sum);   // Inferred as int.
context.Set(Keys.Sum, sum + 5);
```

The **generic constraint** `where T : notnull` states the non-null type expectation; the runtime guard throws for an actual null. The constraints and guards above clarify the contract; they are not claimed as an exact transcription of the completed video code. If null is legitimate data, choose nullable storage and an API expressing that instead. A missing dictionary key is another condition: indexer lookup throws for absence; making the value nullable does not turn a missing key into a successful lookup.

At [01:06:13](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3973s) the call trace is: create container, call `Add`, repeat for each entry.

[01:06:22](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3982s) For the name call, the compiler infers `T` as `string` from the typed key and compatible value. At [01:06:39](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=3999s) the name key has numeric identity zero and stores the example name “Антон” under that identity. Zero is the key's number; the stored name is not null.

[01:06:52](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4012s) Storage converts the generic value to `object`. If `T` is a value type, this causes boxing at [01:07:02](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4022s). A string is already a **reference type**, a value accessed through an object reference, and is not boxed for that conversion.

[01:07:09](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4029s) The getter has no supplied value to infer from; the key's type is sufficient. The setter follows the same static relationship, but it still uses its value argument to perform the write. Any wording that the setter ignores that argument refers to determining the type, not to discarding the value. Generic type inference is performed by the compiler, not by the runtime.

[01:07:26](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4046s) Try the small calls yourself, as suggested in the recording. Predict the result of changing the sum write to a string before attempting it. At [01:07:32](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4052s) that wrong key/value pairing is rejected by the compiler; at [01:07:47](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4067s) retrieval already has the known return type.

[01:07:56](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4076s) Boxing remains outside this implementation's target. Moving casts into the context improves the public contract without changing object-backed storage.

<details>
<summary>What does Key&lt;int&gt; guarantee, and what does it leave unproven?</summary>

It connects ordinary Add/Set/Get calls to integer values and results. It does not prove that the entry exists, that a caller has not forged another typed key for the same identity, or that a concurrent operation will not mutate the container. It also does not eliminate boxing inside object storage.
</details>

## A registry allocates stable key identities

[01:08:02](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4082s) A **registry** centralizes key creation. The first version can be a central class with a counter starting at zero. Callers ask for fresh keys instead of writing identities themselves.

[01:08:27](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4107s) A generic `NextKey<T>` method chooses the key's value type. At [01:08:33](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4113s) it constructs and returns a key holding the next identity. At [01:08:40](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4120s) preserve the current counter value locally, increment the counter, and return the saved identity.

No exact saved numeric-registry state was located. The [related manually created typed keys](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) shows the construction that registration replaces. This reconstructed allocator makes the ordering explicit:

```csharp
sealed class KeyRegistry
{
    private int counter;

    public Key<T> NextKey<T>()
    {
        var identity = counter;
        counter++;
        return new Key<T>(identity);
    }
}
```

[01:08:49](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4129s) Subsequent calls yield different identities because the counter is advanced before the method completes. Nothing executes after `return` in this method; the returned number is the old value, while the stored counter is already ready for the next call.

[01:08:56](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4136s) A static class with static state becomes global state when used by many systems and is harder to reuse. At [01:09:05](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4145s) prefer an instantiable registry held as one shared **singleton**, rather than making the class inherently static. A singleton is one chosen instance, not a requirement that all members be static.

[01:09:09](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4149s) Ideally the shared instance lives outside consuming classes, keeping them less structurally dependent on a global. At [01:09:15](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4155s) a stricter design could give each context its own specialized key type and registry so keys for unrelated container APIs cannot be mixed.

[01:10:02](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4202s) That specialized design is explicitly left unimplemented because it takes too much time. At [01:10:08](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4208s) a generalized registry usually suffices; common implementation can sit behind wrappers or static convenience methods. At [01:10:12](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4212s) a wrapper may expose methods specialized for one context's key type. At [01:10:16](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4216s) this wrapper is again deferred and the demonstration keeps the simpler version.

## Register each key once and account for concurrency

[01:10:21](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4221s) Introduce one shared registry instance, referred to as `KeyRegistry` in the demonstration. The implementation has a static access point because key declarations use it during startup at [01:10:32](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4232s). That does not require the underlying registry class to be static. A shared instance can also be passed through an ordinary reference at [01:11:24](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4284s).

The [related stable key fields](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) declares its manually created keys as `static readonly` fields. This reconstructed variant gets those identities from the registry:

```csharp
static class ApplicationKeys
{
    private static readonly KeyRegistry Registry = new();

    public static readonly Key<string> Name = Registry.NextKey<string>();
    public static readonly Key<int> Sum = Registry.NextKey<int>();
}
```

[01:11:33](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4293s) Request each key exactly once, for example with `NextKey<string>()`, and store the result in a field. At [01:11:38](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4298s) a getter that calls `NextKey` on every access is wrong: each read would allocate a new identity and lose the connection to the value already stored.

[01:11:40](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4300s) One shared allocator removes accidental duplication between correctly registered keys, provided allocation is serialized and the counter's range is not exhausted. Separate registries used with the same context would not supply that guarantee.

[01:11:43](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4303s) Two threads can race while reading and updating the counter. Atomic operations are the suggested research task; a concurrent allocator is not implemented. Stable key fields eliminate repeated registration but do not solve simultaneous initial registration. Nor does a thread-safe allocator alone make concurrent writes to an ordinary context dictionary safe.

<details>
<summary>Why does a key field work while a property that calls NextKey on every read fails?</summary>

The field retains one identity. The property would produce a different identity each time, so insertion and lookup would address different entries even though the property has the same source-code name.
</details>

## Registry metadata makes values inspectable

[01:11:49](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4309s) Allocating keys through one registry allows a different key store or backing representation without changing the principle. At [01:12:41](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4361s) registration can also record the type associated with each identity.

[01:12:58](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4378s) A method such as `GetOfKey(key)` can return the registered value type. At [01:13:12](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4392s) a caller knowing only the numeric identity can query that metadata even without a statically named key field. This is **introspection**, examining descriptions of stored entries at runtime.

[01:13:30](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4410s) Add `PrintCurrentData` to the context for debugging. At [01:13:35](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4415s) it loops through entries and prints one line describing the type associated with each identity.

[01:13:48](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4428s) Type alone is often too little information. Supply a name when creating a key at [01:13:52](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4432s), and maintain a collection such as `keyNames` mapping identities to readable names at [01:13:55](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4435s).

No exact saved introspection implementation was located. The [related context dictionary](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) supplies the entries that such a loop would inspect. A simplified reconstruction, with `GetName` and `GetOfKey` representing registry queries, is:

```csharp
void PrintCurrentData()
{
    foreach (var (identity, value) in data)
    {
        Console.WriteLine(
            $"{registry.GetName(identity)}: {value} " +
            $"({registry.GetOfKey(identity)})");
    }
}
```

[01:14:05](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4445s) The context holds an entry's key and value, then asks the registry for its readable name. At [01:14:24](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4464s) central metadata avoids duplicating descriptive strings and types in every copied key value. “Globally available” here means available to users of the shared registry, not that descriptions must be global variables.

[01:14:47](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4487s) Names must be supplied when keys are created, and the demonstration prints the newly created context contents to check registration. At [01:14:58](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4498s) a missing name registration is corrected with a call such as `keys.AddName(name, key)`.

[01:15:11](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4511s) Integer keys can remain small identities in memory while the registry supplies their names and type metadata. At [01:15:24](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4524s) `PrintCurrentData` learns what each integer means before reporting the entry. The registry describes keys; the context still stores the execution values.

## String names can become the keys

[01:15:44](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4544s) A simpler variant uses strings themselves as key identities instead of numbers plus separate metadata. **String keys** move readable names into the identity.

[01:15:57](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4557s) The registry can track registered names in a **hash set**, a collection of distinct values. At [01:16:12](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4572s) `HashSet.Add` returns true when the name is newly inserted. At [01:16:22](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4582s) throw if it returns false, reporting that the key is already registered.

The [related string-valued Key and dictionary](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) uses strings for the key's identity but does not contain this registry. The simplified registration change is:

```csharp
public readonly struct Key<T>
{
    public readonly string Value;
    public Key(string value) => Value = value;
}

sealed class StringKeyRegistry
{
    private readonly HashSet<string> names = new();

    public Key<T> NextKey<T>(string name)
    {
        if (!names.Add(name))
            throw new InvalidOperationException("Key already registered");
        return new Key<T>(name);
    }
}
```

[01:16:36](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4596s) The prior integer identity must be replaced by the name string consistently, including the key's field type. A **hash** is the numeric result used to organize key lookup; it does not replace the need to compare keys for equality. At [01:16:50](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4610s) this version drops the separate metadata storage and stores context values under strings. It still retains the generic `T` in each typed key's static contract.

[01:17:07](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4627s) Compared with direct array indexing, dictionary lookup introduces hashing and associated work; strings require computing or obtaining a hash and comparing keys as needed. This is a structural cost explanation, not a recorded benchmark or proof that every string-key workload is slower than every alternative.

[01:17:22](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4642s) Names make ownership easier to express. A library can use a **namespaced identity**, a name with an ownership prefix, such as `my-library.sum`, reducing accidental conflicts without coordinating numbered positions. Namespacing is a convention, not mathematical uniqueness; the registry still detects a repeated registered name.

## Restrict construction to protect the key contract

[01:17:44](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4664s) Bypassing the registry reintroduces conflict risks. At [01:17:50](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4670s) client code can construct its own typed key, and at [01:18:03](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4683s) can give that key an existing identity while choosing a different generic type.

The [related saved forged-key demonstration](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) constructs a `Key<MaliciousThing>` with the same string identity as `Key<Dog>`; the later dog lookup attempts to cast the incompatible value. This minimal reconstruction uses an integer and string:

```csharp
var registeredSum = new Key<int>("sum");
context.Add(registeredSum, 15);

var forgedName = new Key<string>("sum");
var name = context.Get(forgedName); // Runtime cast fails: stored value is int.
```

[01:18:16](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4696s) The compiler trusts the forged key's declared type. It cannot infer from the string identity that another key says the value is an integer. This illustrates the boundary of typed keys: type-safe public calls rely on a valid identity-to-type association.

[01:18:35](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4715s) Make key construction `internal`, preserve the identity in a readonly field, and remove the public constructor. The [related public constructor before this protection](https://github.com/AntonC9018/uniCourse_csharp/blob/9e0565fa096e0e58867255a6cd1dd38d017a2d2c/examples/property_dict/Program.cs) intentionally still permits forgery; the video-based change is:

```csharp
public readonly struct Key<T>
{
    public readonly string Value;
    internal Key(string value) => Value = value;
}
```

[01:18:52](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4732s) The demonstration still compiles because library and application code are in the same project and assembly. `internal` is an **assembly access boundary**: an assembly is the compiled unit containing the library code. The modifier does not impose registry-only access within that unit. At [01:19:36](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4776s) an ordinary consumer in a separate assembly importing the library cannot call the internal constructor.

[01:19:40](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4780s) Deliberately constructing a false key is less likely in normal use and requires knowledge of an existing identity and an incompatible type. At [01:19:53](https://www.youtube.com/watch?v=-YG0SKqdL0U&t=4793s) constructor restriction is presented as minimal, optional protection rather than a requirement of the pattern.

The resulting design keeps traversal ignorant of domain fields, passes execution context from outside, and gives client reads and writes a type-aware contract. Registry-issued identities and restricted construction strengthen that contract; existence, null policy, concurrency, and storage allocation remain separate decisions.
