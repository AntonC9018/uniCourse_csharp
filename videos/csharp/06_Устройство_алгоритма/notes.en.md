# What an algorithm is made of

[00:00:00](https://www.youtube.com/watch?v=C6plSGSYuyc&t=0s) A substantial programming problem usually needs several coordinated actions. This lesson develops a way to discover those actions, describe the data they use, and turn the description into instructions. The main example is finding the average length of the lines in a file. Multiplication supplies a small starting example; summing a list supplies the detailed building block.

The vocabulary below is a preview. Each idea is explained again when it becomes necessary:

- **Task and algorithm:** a task specifies a result to obtain; an algorithm describes how to obtain it from given data. In this lesson, a program that solves a task is described through its inputs, outputs, and implementation.
- **Input and output:** input is the data supplied to a task; output is the result it produces. A **representation** is the concrete form used to carry that data.
- **Interface and implementation:** the interface describes interaction with the algorithm, especially its input and output. The implementation contains the steps that do the work and their temporary storage.
- **Decomposition and sub-algorithm:** decomposition breaks a task into smaller tasks. A sub-algorithm is an algorithm used to perform one of those smaller tasks. A **primitive operation** is an operation already available at the level of detail being used.
- **High level, low level, and abstraction:** a high-level description names existing operations by what they accomplish; a low-level description spells out their smaller steps. Abstraction lets a useful name stand for behavior without exposing its internal steps.
- **File, string, character, line, and newline:** a file stores content; a string represents text as a sequence of characters. A character is an individual text element in the lesson's model. A line is a portion of the content separated from the next portion by a newline transition.
- **Length and average:** length is the number of elements in a sequence, or characters in a string. The average here is the arithmetic mean: the sum of the values divided by their count.
- **Array, element, and index:** an array is modeled as consecutive memory cells containing values, called elements. An index identifies an element by its offset from the beginning; the first index is zero.
- **Traversal and bounds:** traversal visits the elements of a collection. Bounds specify which indices are valid.
- **Variable and working memory:** a variable is a named cell whose value can change. Working memory is the temporary storage an algorithm uses during execution.
- **Loop and running sum:** a loop repeats steps. A running sum, also called an accumulator, stores the total accumulated so far.
- **Associativity, identity, and fold:** associativity permits regrouping additions without changing their mathematical result. Zero is the identity for addition because adding it changes nothing. A left-to-right fold repeatedly combines a running result with the next element.
- **Assignment and control flow:** assignment writes a value to a variable. A compound assignment such as `+=` combines a calculation with writing the result back. Control flow determines which instruction happens next; a jump transfers execution to a named marker, and a for loop packages repeated execution.
- **Function, parameter, and return type:** a function packages instructions under a name. A parameter receives input for a call; the return type describes the kind of result returned. A type describes what kind of value a cell or result holds.
- **Buffer and slice:** a buffer holds a portion of data while it is processed. A slice is a selected portion of a sequence.
- **Optional practice vocabulary:** a contract check verifies a required condition; an assertion checks an expected condition, and an exception reports a failure. These are mentioned only in the follow-up study material.
- **Object, address, and reference:** an object groups related data. An address identifies where it resides in memory; a reference lets the program reach that object through a value passed separately.

## Naming the traversal as a sub-algorithm

[00:16:19](https://www.youtube.com/watch?v=C6plSGSYuyc&t=979s) **Traversal** means visiting the collection's elements. Treat it as its own sub-algorithm so its behavior can be worked out separately from what happens to each value.

[00:16:34](https://www.youtube.com/watch?v=C6plSGSYuyc&t=994s) To visit the values in order, visit their indices in order and read the element at each one. This requires a current index that changes as execution proceeds.

[00:16:40](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1000s) Four rules specify that current index:

1. Interpret the index as the number of element positions skipped from the beginning.
2. Start it at zero.
3. Increase it by one after processing an element.
4. Stop when it exceeds the last valid index.

[00:16:47](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1007s) Starting at zero and advancing by one visits the elements without leaving gaps. [00:17:16](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1036s) Once the index is greater than N minus one, every available index has been visited.

[00:17:32](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1052s) This comparison supplies the stopping rule; there is no need for a separate count of how many iterations have occurred. [00:17:48](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1068s) The index serves two purposes at once: it locates the next value and tells us how far the traversal has progressed.

## Writing the traversal as steps

[00:18:01](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1081s) Now convert those rules into **instructions**, concrete actions the program will execute.

[00:18:17](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1097s) The index must survive from one instruction to the next, even though it changes. A **variable** provides that storage: it is a named memory cell into which a value can be written.

[00:18:28](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1108s) Create the cell and initialize it with zero. This makes the first attempted visit start at the array's beginning. The [recorded traversal construction](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1108s) has the following simplified intermediate form. The running-sum operation is still a placeholder at this point:

```text
create currentIndex
currentIndex = 0
check:
    if currentIndex > length - 1, finish
    value = element at currentIndex
    add value to the current sum       // storage for this comes next
    currentIndex = currentIndex + 1
    go back to check
```

[00:19:03](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1143s) The end check belongs before the first read. An empty array has no valid indices, so it is already finished when the current index is zero.

[00:19:12](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1152s) Terminating at that check prevents a read beyond the bounds. [00:19:26](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1166s) If the index is valid, fetch the element by skipping the number of positions stored in the index cell: zero first, then one, then two, and so on.

[00:19:37](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1177s) After adding the fetched value to the running sum, move to the next element. [00:19:44](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1184s) Incrementing the index—adding one to it—performs that move.

[00:19:55](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1195s) Check the bounds again after the increment. If the index now lies outside the array, stop before another fetch.

[00:20:02](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1202s) A **loop** repeats the same actions until its stopping condition is met. The complete traversal procedure is therefore:

1. Create and initialize the current-index variable.
2. Check whether its index is still valid; finish if it is not.
3. Fetch the element at that index and perform the intended operation on it.
4. Increase the index by one.
5. Return to the check and repeat.

The fetch, add, and increment actions are the repeated work. A single pass through them processes only one value; returning to the check makes them a traversal of the whole array.

## Adding each element to the current sum

[00:20:23](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1223s) The sixth-step discussion returns to the deferred instruction: add each element to the current sum. Traversal now supplies the elements, but the sum itself needs a starting value and storage.

[00:20:41](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1241s) For an empty list, the sum is defined as zero. Initializing a result only after reading the first element would leave that case without an answer.

Associativity explains regrouping; the identity supplies the base value for the empty case.

[00:20:54](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1254s) The lesson's left-to-right combining process is a **fold**: combine a result with the next element, then use that new result in the following combination.

running sum after first element: 0 + first

continue by adding each next element to the preceding result
```

running sums:   0 -> 5 -> 10 -> 19 -> 22 -> 30
```

[00:23:22](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1402s) The sum cell successively holds each of those intermediate results. When the traversal reaches the final node, its value is the complete total.

[00:23:39](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1419s) Combine accumulation with traversal by making each visit add the element's value to this cell.

[00:24:00](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1440s) The change to the earlier pseudocode is small but essential: add a step before the loop that creates the sum cell and writes zero into it. The [recorded accumulator addition](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1444s) yields this simplified complete summing procedure:

```text
create currentSum and write 0 into it
create currentIndex and write 0 into it
check:
    if currentIndex > length - 1, answer with currentSum
    currentSum = currentSum + element at currentIndex
    currentIndex = currentIndex + 1
    go back to check
```

1. Initialize the sum to zero.
2. Initialize the current index to zero.
3. If the index has passed the last valid position, produce the stored sum.
4. Otherwise, add the current element to the sum and store the result.
5. Increase the index and repeat from the bounds check.

[00:24:21](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1461s) The terminating step now identifies the answer explicitly: it is in the current-sum cell. [00:24:45](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1485s) After all elements have contributed once, that cell holds the value of the final node. If there were no elements, it still holds the base sum, zero.

<details>
<summary>Predict the empty-list path. Which steps execute, and where does the answer come from?</summary>

The algorithm initializes the sum and index to zero, then fails the first bounds check because there is no valid index. It reads no element and returns the already initialized sum, zero.
</details>

## From written steps to code

[00:24:54](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1494s) A sufficiently concrete algorithm description has a direct code counterpart. Create a variable for the current sum and assign the base value to it.

[00:25:05](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1505s) Then create the current-index variable and initialize it to zero. [00:25:18](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1518s) Checking whether the index equals the length detects the first position beyond the array. This is equivalent to passing N minus one because this traversal starts at zero and advances one position at a time.

[00:25:33](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1533s) Add the element at the current index to the sum, increment the index, and return to the check. The [recorded translation into code](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1515s) motivates the following simplified C# reconstruction. It is an explanatory example, not an exact screen transcription or a claimed repository snapshot; assume a supplied array named values:

```csharp
int sum = 0;
int i = 0;

CheckIndex:
if (i == values.Length)
    goto Finished;

sum += values[i];
i += 1;
goto CheckIndex;

Finished:
; // Leave sum unchanged; it holds the answer.
```

A **type** describes the kind of value stored: `int` is used here for the small whole-number example. An assignment such as `i = 0` writes a value to the variable. `values.Length` reads the stored number of elements; `values[i]` reads the element identified by the index. The compound assignment `sum += values[i]` means “add this element to the current sum and store the result back.” Likewise, `i += 1` replaces the old index with the next one. A semicolon ends each ordinary instruction. The named markers followed by colons identify jump destinations; `goto` transfers execution to one of them. The `if` instruction performs the end check before any array access. The final standalone semicolon is an empty instruction so the finishing marker has a valid destination.

[00:25:58](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1558s) A **for loop** packages initialization, the continuing condition, and the update in one loop construct. It replaces the manual jump-back while keeping the same traversal. The [recorded loop refinement](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1558s) corresponds to this simplified version:

```csharp
int sum = 0;
for (int i = 0; i < values.Length; i += 1)
{
    sum += values[i];
}
```

Inside the parentheses, the first part initializes the index, the second permits another iteration only while the index is valid, and the third advances it after the body. The semicolons separate those three parts. Braces group the repeated instructions. The continuing condition is expressed positively as “index less than length”; when that condition fails, execution leaves the loop.

[00:26:03](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1563s) This translation works because the prose already specifies the storage, initialization, check, operation, and update. The language syntax supplies a direct way to express each action.

[00:26:08](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1568s) A **function** packages those instructions under a name so another algorithm can call them. Its **parameter** describes the supplied input, and its **return type** describes the result. The [recorded function-interface discussion](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1568s) leads to this simplified complete function:

```csharp
int Sum(int[] values)
{
    int sum = 0;
    for (int i = 0; i < values.Length; i += 1)
    {
        sum += values[i];
    }
    return sum;
}
```

Here `Sum` names the behavior, `int[] values` declares an array of whole numbers as input, and the leading `int` describes the result. `return sum` delivers the value left in the accumulator. Naming the behavior and declaring its input and output give the callable algorithm an **interface**.

[00:26:14](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1574s) The same interface-design step applies to the average sub-algorithm: give it a name, specify the values it receives, and specify the kind of result it returns. Its implementation can use the newly completed summing operation.

[00:26:23](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1583s) The remaining average operation divides the sum by the count. The [recorded average calculation](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1583s) is illustrated mathematically rather than with a choice of C# numeric types:

```text
Average(values):
    total = Sum(values)
    count = length of values
    return total / count
```

[00:26:31](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1591s) The count is already stored with the array. At this level, the remaining primitive actions are reading the sum, reading the length, and dividing. [00:26:38](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1598s) The quotient is the answer, completing the average sub-task.

These samples explain the conversion from steps to code; they are not reported build or execution results. The zero result for an empty sum was reasoned through, not demonstrated by a recorded test run. The recording does not settle an empty-input policy for averaging: the sum being zero does not by itself define division by a zero count.

## The harder sub-algorithm worked out by hand

[00:26:41](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1601s) Extracting lines is the deliberately harder part of the decomposition. The discussion outlines how to do it manually, without completing a file-splitting function.

[00:26:45](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1605s) A **slice** is the portion of a sequence between selected positions. To extract successive lines from the content string:

1. Remember the position where the current line begins.
2. Examine one character at a time until a newline is reached.
3. Take the slice from the remembered position to that boundary as the line.
4. Save the position for the following line.
5. Continue scanning until the next boundary and repeat.

[00:27:01](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1621s) Each action in this outline can itself be decomposed into basic steps, just as traversal and accumulation were. [00:27:17](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1637s) Indexing principles and ordinary reasoning about the required result make that translation possible; no new mystery separates the written procedure from code.

[00:27:37](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1657s) This detailed work is useful when an operation must be built. When a function that already sums the values is available, use it and leave that part of the file algorithm at the higher level. The full scanning code and its boundary policies are not worked out here.

## High level, low level and abstraction

[00:27:55](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1675s) A **high-level** description uses an existing algorithm by the action it performs. A **low-level** description expands that action into its primitive steps. They can describe the same behavior at different degrees of detail.

[00:28:02](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1682s) The detailed sum procedure is low level relative to “sum this list”: it specifies variables, their initial values, element access, accumulation, and index updates.

[00:28:10](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1690s) At the high level, it is enough to know that a summing algorithm exists and what answer it provides. A caller need not reconsider how it allocates temporary cells or visits the list.

[00:28:55](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1735s) **Abstraction** is using such an operation through its name and meaning while leaving its internal construction out of the current description. [00:29:11](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1751s) A useful name describes what will happen at the level where the larger task is being planned.

<details>
<summary>Why can “sum the lengths” be a complete step in one description, even though summing took many steps to construct?</summary>

Once a summing algorithm exists and its interface is known, the larger algorithm can call it as a single sub-task. Its implementation still performs the detailed work. Abstraction changes how much of that work the caller needs to describe.
</details>

## Drawing an algorithm as memory cells

[00:29:15](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1755s) Decomposing an algorithm means specifying its interface as well as its steps.

[00:29:30](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1770s) The **interface** consists of input and output. [00:29:38](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1778s) The **implementation** consists of the concrete instructions and **working memory**: temporary cells such as the changing index and the running sum.

[00:29:47](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1787s) In the memory picture, distinguish three areas: input cells, output cells, and the temporary space used while the algorithm runs. The [recorded memory model](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1803s) is summarized by:

```text
input                  working memory              output
[ a ] [ b ]            [ temporary sum ]            [ answer ]
```

[00:30:14](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1814s) The inputs are supplied from outside. The algorithm does not choose their contents; it works on the data it receives.

[00:30:19](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1819s) For adding two numbers, the input cells hold the values named a and b. A temporary cell can hold their sum, which is then delivered as the answer. The example's result is eleven. This distinguishes the externally supplied values, the intermediate storage, and the output without requiring a physical-memory layout for a particular runtime.

## Passing a list in practice

[00:30:42](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1842s) The cell diagram explains what an algorithm consists of. A practical question remains: how does a whole list reach it?

[00:30:45](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1845s) Normally we do not write every element into separate input positions and then pass an unrelated length alongside them.

[00:30:56](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1856s) Instead, an **object** represents the list and groups its elements with its length. The object resides at an **address**, a position in memory. The passed cell can hold the value that leads to this object—a **reference** in this explanatory model. The [recorded list-passing discussion](https://www.youtube.com/watch?v=C6plSGSYuyc&t=1862s) can be sketched as:

```text
passed input cell                 list object's storage
[ address/reference ] ---------> [ elements ... | length ]

returned data can likewise be treated as separate memory
before the result is written to its destination
```

The elements, the length, and the memory used for returned data remain distinct parts of the conceptual picture. Passing a value that identifies the list lets the function use the collection as one input. This is an explanation of data flow, not a specification of an exact object layout.

**Further practice, not taught in this video:** the [C# implementation lab](../../../labs/1_basic/12_algorithms_code.md) asks for an algorithm function that works only with its parameters and does not print.
