The terms needed for that journey are:

- **Source file, project, compiler, and diagnostic:** a source file contains C# text; a project groups files compiled together; the compiler translates that text and checks its rules; a diagnostic reports an error or warning.
- **Top-level statements and entry point:** top-level statements are executable instructions written outside an explicit method. The entry point is where program execution begins.
- **Type, class, struct, object, instance, and reference:** a type describes values and their operations. A class describes reference-type objects; a struct describes value-type instances. An object is an instance of a type, and a reference identifies a particular object.
- **Field, method, and member:** a field stores data; a method is a function declared in a type; member is the general name used here for either. “Member function” means method.
- **Static class, static member, and instance member:** a static class is a type-level container that cannot be instantiated. A static member belongs to the type; an instance member belongs to, or acts on, a particular instance.
- **Qualification, dot, and `public`:** qualification names the owner of a member; the dot in `Owner.Member` selects that member; `public` allows other code to access it.
- **Parameter, argument, signature, receiver, and `this`:** a parameter declares a function input; an argument supplies it at a call; a signature identifies the method and its declared parameter types. The receiver is the object on which an instance method is invoked; `this` refers to that current object. “Hidden first parameter” is the lesson's model for the receiver, not an extra parameter written in C#.
- **State, stats, global state, mutable, and immutable:** state is the game's current data; stats are health and attack values. Global state is shared beyond a particular game object. Mutable data can change; immutable data does not change after initialization.
- **Factory, initialization, object initializer, and `new`:** a factory creates and returns a ready-to-use object. Initialization supplies starting values; an object initializer supplies field values during construction; `new` creates an instance.
- **Counter, increment, integer, and constant:** a counter records a number of events; increment adds one; `int` stores an integer. A constant is a fixed value, rather than changing game state.
- **Boolean, expression, evaluation, assignment, condition, and return:** `bool` holds `true` or `false`; an expression computes a value; evaluation computes that result; assignment stores it; a condition tests a Boolean; `return` sends a result back and exits the current function. `void` means no result is returned.
- **List and game loop:** `List<Enemy>` is a growable collection of enemy objects; a game loop repeats combat until a stopping condition is reached. These are existing parts of the program, not new collection algorithms taught here.
- **Serialization:** converting state to a representation that can be stored or transmitted and later reconstructed.
- **Extension method:** a static method whose first parameter is marked `this`, allowing an object-style call while keeping its declaration in a separate static class.
- **Scope, local function, capture, and shadowing:** scope is where a name can be used; a local function is declared inside another function; capture lets it use enclosing local data; shadowing is a name collision in which one declaration hides another.
- **Command-line arguments, builder pattern, and encapsulation:** command-line arguments are inputs passed when launching a program; a builder assembles or configures something through successive operations; encapsulation controls how an object's data is accessed. These topics are named to mark later course material.

## Use static methods as factories

[00:09:30](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=570s) A **static method** is attached to a type, so a static utility class is a useful home for functions that operate on inputs without instance behavior. [00:10:16](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=616s) A particularly useful static operation is a **factory**: a function that creates and returns an initialized object. [00:10:28](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=628s) For example, a factory on `Stats` can return a `Stats` object. ```csharp

## Read instance fields through this

[00:18:19](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1099s) Inside an instance method, **`this`** means the object receiving the call. The prefix is often optional when an unqualified field name is unambiguous.

[00:18:32](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1112s) Compare the earlier static-field rule: inside the declaring class, a type qualifier could be omitted. Here the optional qualifier is the **instance** qualifier `this`, not the class name. [00:18:52](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1132s) The field can be addressed directly; writing `Stats.Attack` would incorrectly try to access the instance field through the type.

The shortened equivalent bodies from this video-state explanation are:

```csharp
// With an explicit receiver:
public void ReduceDamage()
{
    this.Attack--;
}

// Alternative spelling, when no local name hides Attack:
public void ReduceDamage()
{
    Attack--;
}
```

Choose one declaration. Both modify the receiving object's field in this example. If a parameter or local variable hides a field name, qualification can distinguish them.

[00:18:59](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1139s) **Instance** means an object of the type, which is why these are called instance methods. The Russian term used in the explanation is “экземпляр,” an instance or object. [00:19:21](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1161s) The recording leaves the non-static version in place: its call supplies the target through the receiver, and its body modifies that target's data.

## Return and store a death decision

[00:19:55](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1195s) Pause for practice: write a function that receives stats and returns whether health is less than or equal to zero. A **Boolean** result is either `true` or `false`. The starting static form of the exercise can be reconstructed as:

```csharp
public static bool IsDead(Stats target)
{
    return target.Health <= 0;
}
```

[00:20:01](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1201s) Store the answer in a `bool` variable and then test the variable. This separates the calculation from its use and gives the result a readable name, rather than nesting the whole call in the condition.

[00:20:09](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1209s) Convert the solution to an instance method: remove `static` and the explicit stats input. [00:20:13](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1213s) Keep the return type `bool`; becoming an instance method does not change what the operation can return.

```csharp
// Inside Stats:
public bool IsDead()
{
    return Health <= 0;
}

// At the call site:
bool playerIsDead = playerStats.IsDead();
if (playerIsDead)
{
    Console.WriteLine("The game is over");
}
```

[00:20:23](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1223s) No stats argument is written inside the parentheses: the receiver supplies the object automatically. [00:20:37](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1237s) The call is just object, dot, and method name. [00:20:50](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1250s) Replace the inline check with assignment to the named Boolean, so the result can also be reused.

[00:21:14](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1274s) An **expression** computes a value. To evaluate the call, execution enters the method, reads the receiver's health, compares it with zero, and returns the Boolean answer. The answer does not appear before the method runs. [00:21:18](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1278s) In the explanatory model, that result replaces the right-hand-side expression, and **assignment** stores it in `playerIsDead`. A **condition** then uses the stored value to choose the following action.

## Move behavior into an extension method

[00:22:01](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1321s) The next demonstration asks whether the operation can live elsewhere, keeping the data type focused on its data. [00:22:05](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1325s) A method's code can be moved into a separate file, but moving it into a different class changes who declares it. An ordinary instance method still has to be declared in its own type; the external form demonstrated next is an **extension method**.

[00:22:15](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1335s) Once `IsDead` is outside `Stats` and inside the utility class, it cannot remain an ordinary instance method of `Stats`. This does not mean object-style calls can never invoke instance methods—the previous examples do exactly that. It means a method declared in a different container is not an instance member of the receiver's type.

Follow the intermediate reconstruction:

1. Remove the demonstrated `IsDead` declaration from `Stats`.
2. [00:22:26](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1346s) Put a static method in `Logic`, accepting the stats object explicitly.
3. [00:22:38](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1358s) Call it as an ordinary static method first.

```csharp
static class Logic
{
    public static bool IsDead(Stats target)
    {
        return target.Health <= 0;
    }
}

// Intermediate call:
bool playerIsDead = Logic.IsDead(playerStats);
```

A static method has no automatic `this`, but it can read instance data through the object supplied as a parameter. The required input here is the stats object, not some “static values” inside that object.

[00:22:38](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1358s) Moving to another class does not by itself make `playerStats.IsDead()` legal. [00:22:50](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1370s) Mark the first parameter with `this` to enable that call shape:

```csharp
static class Logic
{
    public static bool IsDead(this Stats target)
    {
        return target.Health <= 0;
    }
}

// Extension syntax:
bool playerIsDead = playerStats.IsDead();

// Equivalent explicit static call, shown separately:
bool sameAnswer = Logic.IsDead(playerStats);
```

Here **`this` on the first parameter** marks an extension method. The method remains static; object-style invocation supplies the receiver as its first declared argument. The type itself has not gained a new ordinary instance member. Removing the original instance method avoids having that existing member take precedence over the extension.

[00:23:11](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1391s) The method must be inside a static class for the syntax taught here. Moving it into a non-static class produces the recorded diagnostic that extension methods must be defined in a static class. This lesson uses the traditional first-parameter syntax; [Microsoft's extension-method reference](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/extension-methods) confirms that these are static methods invoked with instance-style syntax.

[00:23:41](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1421s) This style appears often in configuration code, including code using the **builder pattern**, which assembles a result through successive configuration operations. [00:23:51](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1431s) The pattern itself is deferred; no builder is implemented here.

[00:23:59](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1439s) Why choose an extension method rather than an instance method? That design question is explicitly postponed until **encapsulation**, control over access to an object's internals, is studied. Understanding the current transformation does not require solving that later design problem.

<summary>Did moving IsDead into Logic make it an instance method of Stats?</summary>

No. It is a static method in Logic. Marking its first parameter with this permits the receiver-style call and passes the Stats object to that parameter.

</details>

## Understand the generated entry point

[00:24:11](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1451s) Return to the special main file. **Top-level statements** are convenient source syntax: the compiler supplies the surrounding program structure and entry point.

[00:24:23](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1463s) The recording sketches a `Program` class with a static `Main` accepting an array of command-line arguments. Its illustrated form is `public static int Main(string[] args)`. Treat that as an explanatory explicit equivalent, not the exact name, access level, or return type guaranteed for compiler-generated code. The generated entry-point shape depends on what the top-level program does.

This shortened video-state model places executable statements and local functions inside a method:

```csharp
// Explicit explanatory equivalent, not exact compiler output:
class Program
{
    public static int Main(string[] args)
    {
        GameState state = new GameState();
        IncrementCounter(state);
        return 0;

        static void IncrementCounter(GameState gameState)
        {
            gameState.AddedEnemies++;
        }
    }
}
```

The **entry point** is the method where execution starts. **Command-line arguments** are launch-time inputs; `string[] args` is the parameter representing an array of strings. [00:24:45](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1485s) Their detailed use is deferred.

[00:24:53](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1493s) Keep source order distinct from this conceptual transformation: in a file using top-level statements, the executable top-level code must precede namespace or type declarations. User-defined types remain type declarations; the compiler does not move every declaration into the entry-point body. Generated structure does not promise a particular textual order “above” or “below” the types. These entry-point and source-order rules are documented in [Microsoft's top-level-statement reference](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/program-structure/top-level-statements).

[00:25:06](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1506s) Types can also be declared inside other types. The recording explicitly expresses uncertainty about whether the compiler uses that arrangement here; it is not evidence that your own types are automatically nested. [00:25:22](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1522s) Other compiler-added details mentioned at the end of the sketch are left for later.

[00:25:28](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1528s) The static functions previously written after the main executable code and before user type declarations are **local functions** in the entry-point body. They are not automatically public utility methods of `Program`. The reconstruction above shows their local placement and explains why moving them to an explicit utility class changes their visibility.

## Keep local function dependencies explicit

[00:25:41](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1541s) A **local function** is declared inside another function. It can be declared even after `return`: the declaration itself is not an executed instruction, so it neither runs at that point nor prevents the return from exiting.

This simplified video-state example shows the call before the declaration and the declaration after the return:

```csharp
static int Main(string[] args)
{
    GameState state = new GameState();
    IncrementCounter(state);
    return 0;

    static void IncrementCounter(GameState gameState)
    {
        gameState.AddedEnemies++;
    }
}
```

[00:25:52](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1552s) Its **scope**, the region in which its name is available, is inside the containing function. [00:26:00](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1560s) Code outside `Main` cannot simply call this local `IncrementCounter`; it is not a class member visible to other methods.

[00:26:13](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1573s) If the local function omits `static`, it can access enclosing locals and parameters. **Capture** is using that enclosing data rather than requiring an explicit input. It does not mean the compiler eagerly captures every local variable whether used or not.

[00:26:31](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1591s) The recording shows a diagnostic involving a name already visible from `Main`. The important danger is changing the source of a name: removing an explicit parameter can make the body refer to the enclosing local instead. **Shadowing** is hiding one name with another; collisions depend on the declarations and scopes involved, so the demonstrated diagnostic is not a rule that every matching name always produces the same error.

The capture problem and the explicit-input alternative can be reconstructed together:

```csharp
// Non-static local function in Main:
GameState state = new GameState();
IncrementCounter();

void IncrementCounter()
{
    state.AddedEnemies++; // uses the enclosing local
}

// Alternative static local function and call:
IncrementCounterExplicit(state);

static void IncrementCounterExplicit(GameState gameState)
{
    gameState.AddedEnemies++; // uses its declared input
}
```

[00:26:51](https://www.youtube.com/watch?v=UVLUbfcCcG0&t=1611s) The course recommendation is to write static local functions when the operation should depend only on explicit inputs. Then an accidental reference to an enclosing local is rejected rather than silently coupling the function to that variable. Static is not mandatory for every local function in C#; it is the safeguard recommended for these helpers. [Microsoft's local-function reference](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/local-functions) explains local scope, declarations after return, and the capture restriction on static local functions.

The lesson ends with these boundaries intact: detailed class-prefix mechanics are deferred, static's meaning is initially postponed and then explained, special uses of static fields remain later material, the Boolean death check is a practice task, extension-method design awaits encapsulation, the builder pattern is only named, and command-line handling and further compiler-generated details remain outside the demonstration.

<details>
<summary>Why does making a helper static help when another game state is introduced?</summary>

The helper cannot silently keep using the enclosing state variable. Its required GameState must be passed explicitly, making the intended game visible at the call site.

</details>
