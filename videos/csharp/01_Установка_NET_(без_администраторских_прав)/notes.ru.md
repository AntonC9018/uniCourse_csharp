# Установка .NET SDK без прав администратора

[00:00:00](https://www.youtube.com/watch?v=QsO1HedgKt8&t=0s) В этом уроке преподаватель устанавливает .NET SDK для разработки на C# без прав администратора, делает команду `dotnet` доступной в новых консолях, собирает крошечный проект и готовит необязательный редактор. **.NET SDK** — это набор средств разработки, содержащий инструменты, нужные для компиляции исходного кода на C#. **Консоль** — это текстовое окно команд; **PowerShell** — консоль Windows, используемая здесь. **Скрипт** — это файл с командами, а `.ps1` — расширение скрипта PowerShell. **Расширение** после последней точки в имени файла сообщает Windows, что это за тип файла.

В ходе разбора используются термины: **путь** — расположение файла или папки; **`cd`** — команда, меняющая текущую папку; **относительный путь** — путь, отсчитываемый от этой папки; **полный путь** — путь, включающий диск и папки; **политика выполнения** — правило PowerShell, управляющее запуском скриптов; **переменная окружения** — именованная настройка, наследуемая программами; **`PATH`** — переменная окружения, в которой ищутся команды; и **`DOTNET_ROOT`** — переменная окружения, указывающая на папку установки .NET. **Проект** — это папка с исходниками и настройками сборки: `Program.cs` — файл исходного кода на C#, а файл `.csproj` — файл настроек проекта в формате XML. **XML** — редактируемый текст с вложенными тегами. **Исполняемый файл** можно запустить; **библиотека** поставляет код для другой программы. **Шаблон** генерирует стартовые файлы. **IDE** — редактор со средствами разработки; VS Code и Rider — два упомянутых здесь редактора.

## Сохранение скрипта установщика

[00:00:30](https://www.youtube.com/watch?v=QsO1HedgKt8&t=30s) Преподаватель сохраняет скачанный установщик PowerShell через Ctrl+S. Первое имя файла может заканчиваться на `.ps1.txt`; `.txt` делает его похожим на текстовый документ вместо скрипта `.ps1`, который должен запускать PowerShell. Удалите только конечное `.txt`. Этот переход имени файла — упрощённый пример [записанного сохранения и переименования](https://www.youtube.com/watch?v=QsO1HedgKt8&t=30s); ни один коммит репозитория не фиксирует скачанный файл:

```text
dotnet-install.ps1.txt  →  dotnet-install.ps1
```

[00:00:47](https://www.youtube.com/watch?v=QsO1HedgKt8&t=47s) Если суффикс скрыт, преподаватель открывает проводник File Explorer и включает **View → Show → File name extensions**. Расширения имён файлов — это видимые суффиксы вроде `.txt` и `.ps1`. Так преподаватель может увидеть и удалить лишний суффикс даже после того, как файл уже скачан.

## Переход к скрипту в PowerShell

[00:01:01](https://www.youtube.com/watch?v=QsO1HedgKt8&t=61s) Преподаватель открывает меню «Пуск» Windows, ищет **PowerShell** и нажимает Enter. PowerShell — это окно команд, которое запустит файл `.ps1`.

[00:01:21](https://www.youtube.com/watch?v=QsO1HedgKt8&t=81s) Перед запуском преподаватель использует `cd` (**change directory**), чтобы перейти в папку со скриптом. **Путь к папке** называет каталог; имя файла скрипта не входит в аргумент `cd`. Эта упрощённая команда иллюстрирует [записанную навигацию](https://www.youtube.com/watch?v=QsO1HedgKt8&t=81s):

```powershell
cd "C:\Users\Student\Downloads"
```

[00:01:37](https://www.youtube.com/watch?v=QsO1HedgKt8&t=97s) **Относительный путь** начинается от текущей папки PowerShell, поэтому `cd Downloads` сработает, если та папка находится прямо внутри текущей. **Полный путь** указывает диск и все папки, как в примере выше; преподаватель говорит, что работают обе формы.

[00:02:00](https://www.youtube.com/watch?v=QsO1HedgKt8&t=120s) Если скрипт находится на диске D, а PowerShell — на диске C, преподаватель вводит `D:`, чтобы сменить диск, а затем переходит в папку. [Записанная смена диска](https://www.youtube.com/watch?v=QsO1HedgKt8&t=120s) проиллюстрирована так:

```powershell
D:
cd "D:\Downloads"
```

[00:02:15](https://www.youtube.com/watch?v=QsO1HedgKt8&t=135s) Когда проводник показывает сокращённый путь, преподаватель использует опцию копирования пути. Скопированный **путь к файлу** включает имя файла, поэтому преподаватель убирает это имя, прежде чем передать оставшийся путь к папке в `cd`. Промежуточное состояние — PowerShell находится рядом с установщиком и готов его вызвать.

<details>
<summary>Прогноз: что произойдёт, если скопированный путь всё ещё заканчивается именем файла скрипта, когда его передают в <code>cd</code>?</summary>

`cd` попытается войти в это имя файла, как будто это папка. Удалите имя файла и оставьте содержащий его каталог.
</details>

## Запуск установщика

[00:02:33](https://www.youtube.com/watch?v=QsO1HedgKt8&t=153s) Сначала преподаватель пробует запустить скрипт напрямую. PowerShell отклоняет его по **политике выполнения** — правилу, управляющему выполнением скриптов, поэтому преподаватель меняет эту политику и пробует снова. Расшифровка не сохранила точную команду политики, показанную на экране. В качестве примера только для текущей сессии [справочник PowerShell по политике выполнения](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/set-executionpolicy) от Microsoft описывает область **Process**, которая действует на текущий процесс PowerShell. Это иллюстративная команда рядом с [записанной неудачей и настройкой](https://www.youtube.com/watch?v=QsO1HedgKt8&t=153s), а не расшифровка переключателя с экрана:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

[00:03:00](https://www.youtube.com/watch?v=QsO1HedgKt8&t=180s) Преподаватель повторяет запуск установщика и добавляет `9.0`, чтобы выбрать .NET 9 SDK. В этой записи установщик иначе выбрал бы версию 8, которая, по словам преподавателя, тоже пригодна. Написание `-Channel` ниже — упрощённый документированный способ выбрать основную линейку SDK, подтверждённый [справочником по скрипту установки](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-install-script); [записанный выбор 9.0](https://www.youtube.com/watch?v=QsO1HedgKt8&t=180s) — источник состояния урока, и точный снимок команды не зафиксирован:

```powershell
.\dotnet-install.ps1 -Channel 9.0
```

[00:03:11](https://www.youtube.com/watch?v=QsO1HedgKt8&t=191s) Когда PowerShell просит подтверждения, преподаватель выбирает **R**, то есть **Run once**, вместо более широкого постоянного разрешения. После этого установщик делает `dotnet` доступным в текущей консоли.

## Делаем dotnet доступным в новых консолях

[00:03:32](https://www.youtube.com/watch?v=QsO1HedgKt8&t=212s) Преподаватель проверяет `dotnet`: он работает в консоли, использованной для установки, но вновь открытая консоль сначала не может его найти. **Команда `dotnet`** запускает установленную программу командной строки .NET; результат показывает, что в новой сессии нет папки установки в пути поиска команд. Этот упрощённый [записанный тест](https://www.youtube.com/watch?v=QsO1HedgKt8&t=212s) противопоставляет две сессии:

```text
installation console: dotnet  → found
new console:          dotnet  → not found yet
```

[00:04:01](https://www.youtube.com/watch?v=QsO1HedgKt8&t=241s) Преподаватель копирует каталог установки, содержащий `dotnet`, открывает редактор переменных окружения Windows, выбирает пользовательский **Path**, нажимает **Edit**, затем **New**, вставляет каталог и подтверждает. **`PATH`** — это список каталогов, в которых ищется команда, введённая без полного пути. Преподаватель использует пользовательскую настройку, потому что установка выполняется без прав администратора. Путь ниже иллюстративный; используйте каталог, в котором действительно находится ваш установленный `dotnet.exe`. Он стоит рядом с [записанным изменением PATH](https://www.youtube.com/watch?v=QsO1HedgKt8&t=241s):

```text
User Path:  C:\Users\Student\.dotnet
```

[00:04:55](https://www.youtube.com/watch?v=QsO1HedgKt8&t=295s) Поскольку этот каталог содержит `dotnet.exe`, ввод `dotnet` в консоли позволяет Windows найти и запустить его. Ключевой результат — обнаружение команды во вновь открытой консоли, а не только в сессии установщика.

<details>
<summary>Почему первая консоль находила <code>dotnet</code>, а новая — нет?</summary>

Сессия установщика имела доступ к своему пути установки. Новой сессии нужен был каталог с `dotnet.exe` в пользовательском `PATH`.
</details>

## Создание минимального проекта

[00:05:05](https://www.youtube.com/watch?v=QsO1HedgKt8&t=305s) Преподаватель создаёт **папку проекта** — место для хранения программы и настроек её сборки; её имя и расположение остаются на усмотрение ученика. [00:05:10](https://www.youtube.com/watch?v=QsO1HedgKt8&t=310s) Первоначальный минимальный проект состоит из двух разных файлов: **`Program.cs`** — исходного текста на C#, который выполняется, и **`<project-name>.csproj`** — настроек проекта, читаемых SDK. [Связанное упражнение курса на ревизии синхронизации](https://github.com/AntonC9018/uniCourse_csharp/blob/a944ae1fd13128aa386007b0681b6019d2b8b97e/labs/1_basic/01_install.md) просит эти файлы, но **не является точным коммитом проекта с экрана преподавателя**. Эти короткие примеры иллюстрируют их роли:

```csharp
// Program.cs — simplified example
Console.WriteLine("Hello, World!");
```

```xml
<!-- Example.csproj — simplified intermediate state -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>
  </PropertyGroup>
</Project>
```

[00:05:50](https://www.youtube.com/watch?v=QsO1HedgKt8&t=350s) Преподаватель описывает файл `.csproj` как редактируемый **XML**, то есть обычный текст, структурированный открывающими и закрывающими тегами. Здесь `Project` охватывает настройки, `PropertyGroup` группирует их, а `TargetFramework` называет версию .NET, на которую нацелен проект. Код выше — поясняющий пример; расшифровка не сохранила точный текст проекта.

[00:06:21](https://www.youtube.com/watch?v=QsO1HedgKt8&t=381s) Преподаватель отмечает, что консоль может сгенерировать минимальные файлы, и оставляет демонстрацию этой команды на потом в уроке. Это граница охвата на данный момент: сначала разобраться в файлах, собранных вручную, затем увидеть генерацию.

[00:07:03](https://www.youtube.com/watch?v=QsO1HedgKt8&t=423s) Собранному вручную проекту всё ещё нужно указать, что это **исполняемый файл** — программа, которую можно запустить, а не **библиотека** — код, предназначенный для использования другой программой. Преподаватель добавляет `OutputType` со значением `Exe` в `.csproj`. Следующее упрощённое изменение стоит рядом с [записанным изменением проекта](https://www.youtube.com/watch?v=QsO1HedgKt8&t=423s); [связанное упражнение курса, привязанное к коммиту](https://github.com/AntonC9018/uniCourse_csharp/blob/a944ae1fd13128aa386007b0681b6019d2b8b97e/labs/1_basic/01_install.md) описывает проект, но не содержит этот точный промежуточный файл:

```xml
<PropertyGroup>
  <OutputType>Exe</OutputType>
  <TargetFramework>net9.0</TargetFramework>
</PropertyGroup>
```

Промежуточный проект имел исходник и целевой фреймворк; изменённый проект теперь объявляет запускаемый тип выходных данных. Урок не показывает отдельного успешного запуска собранного вручную проекта на этом этапе.

## Генерация проекта из шаблона

[00:07:39](https://www.youtube.com/watch?v=QsO1HedgKt8&t=459s) В новой пустой папке преподаватель использует команду `dotnet` с **`new console`**. **Шаблон** — это стартовый образец, встроенный в SDK; шаблон `console` создаёт минимальное консольное приложение. [Связанное упражнение курса на фиксированной ревизии](https://github.com/AntonC9018/uniCourse_csharp/blob/a944ae1fd13128aa386007b0681b6019d2b8b97e/labs/1_basic/01_install.md) также просит эту команду, а [записанный вызов](https://www.youtube.com/watch?v=QsO1HedgKt8&t=459s) показывает это состояние урока:

```powershell
dotnet new console
```

[00:08:11](https://www.youtube.com/watch?v=QsO1HedgKt8&t=491s) Преподаватель осматривает результат: шаблон автоматически создал и файл проекта `.csproj`, и `Program.cs`. [Записанное сгенерированное состояние](https://www.youtube.com/watch?v=QsO1HedgKt8&t=491s) резюмировано ниже; эти имена файлов — наблюдаемый результат, а не утверждение о точном зафиксированном снимке:

```text
new-project/
├── Program.cs
└── new-project.csproj
```

<summary>Самопроверка: в каком файле операторы C#, а какой файл указывает SDK, как их собирать?</summary>

## Настройка необязательного редактора

[00:08:36](https://www.youtube.com/watch?v=QsO1HedgKt8&t=516s) VS Code необязателен: консоли и SDK уже достаточно для работы с проектом. Преподаватель также рекомендует **Rider** — альтернативную **IDE**, то есть программу, сочетающую редактирование и средства разработки. Запись не учит настройке Rider. Для демонстрации преподаватель продолжает с VS Code.

[00:09:15](https://www.youtube.com/watch?v=QsO1HedgKt8&t=555s) В VS Code преподаватель устанавливает **C# Dev Kit** — **расширение**, добавляющее поддержку разработки на C#. Расширение выбирается в представлении Extensions в VS Code; его установка — шаг настройки редактора, а не изменение `Program.cs` или файла проекта.

[00:09:42](https://www.youtube.com/watch?v=QsO1HedgKt8&t=582s) Преподаватель различает две **переменные окружения** — именованные настройки, которые программы читают из своего окружения. **`PATH`** позволяет консоли находить команду `dotnet` по имени; **`DOTNET_ROOT`** указывает редактору или зависящему от .NET инструменту на установленный каталог .NET. Это описывает настройку преподавателя; [руководство Microsoft по установке на Windows](https://learn.microsoft.com/dotnet/core/install/windows) также отмечает, что некоторые инструменты используют `DOTNET_ROOT`.

[00:09:52](https://www.youtube.com/watch?v=QsO1HedgKt8&t=592s) Преподаватель создаёт пользовательскую переменную с именем `DOTNET_ROOT` и присваивает ей тот же каталог SDK, который был добавлен в `PATH`. Это должна быть папка с установленным `dotnet.exe`, а не имя файла исполняемого файла. Это иллюстративное значение стоит рядом с [записанным изменением переменной](https://www.youtube.com/watch?v=QsO1HedgKt8&t=592s):

```text
DOTNET_ROOT = C:\Users\Student\.dotnet
```

[00:10:14](https://www.youtube.com/watch?v=QsO1HedgKt8&t=614s) Наконец, преподаватель закрывает и снова открывает VS Code, чтобы приложение получило новое значение переменной окружения. Урок заканчивается этой ожидаемой настройкой редактора; отдельной успешной сборки или запуска в VS Code после повторного открытия не показано.
